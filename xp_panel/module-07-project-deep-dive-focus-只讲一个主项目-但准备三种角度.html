7. Project Deep Dive Focus：只讲一个主项目，但准备三种角度

主项目固定为 Adobe Context-aware AI Infrastructure。不要一上来轮流介绍三个项目；让面试官先记住一个复杂、完整、由你主导的平台。根据面试官方向选择同一项目的 deep dive：

面试官主动深入第二项目补证据
Yxxxx Rxxtask state、idempotency、failure recovery、data/control plane、scalability用 50B+ discovery 证明 data scale
Yx Gxxmultimodal artifact、dataset reference、edge-cloud、iteration workflow用 cross-modal discovery 证明 multimodal semantics
Bx Txxxshared CPU/GPU pool、execution isolation、scheduling、platform ownership用 100B+/day bidding 证明 production rigor
真实性规则：下文的 architecture state machine、failure protocol 和 scheduling 答法用于帮你把真实项目讲深。只有与你实际系统一致的部分才能说成“我做了”；其余应说成“我会这样设计 / 当时考虑过的 alternative”，不能把推荐设计包装成履历事实。

7.1 30 秒项目定位

“我最想 deep dive 的项目是 Adobe 的 context-aware AI infrastructure。我作为 Tech Lead，要解决的不是单个模型 serving，而是让 media onboarding、retrieval、generation、semantic tagging 和 assistant workflow 共享一套 execution layer。核心难点是：不同 workload 的 schema 和 runtime 不一致，大型 media 不能在服务间反复搬运，长任务要可恢复，而且 CPU preprocessing、tensor inference 和 LLM generation 不能互相抢资源。我的核心设计是统一 intent/artifact contract、execution planning，以及彼此隔离但可组合的执行路径。”

说完停一下，让面试官选择追问。不要在 30 秒内把所有组件念完。

7.2 五分钟完整答案（可直接复述）

1. Problem / Why now

“当时我们面对的不是一个单一 use case，而是一组快速增长的 multimodal 和 LLM workflow，包括 onboarding、retrieval、generation、tagging 和 assistant-style task。如果每个团队直接绑定模型 endpoint，会重复实现 request schema、media transfer、policy、retry、rollout 和 observability。更严重的是，不同 workload 的资源形态完全不同：media preprocessing 偏 CPU/I/O，tensor inference 偏 GPU throughput，LLM generation 又有 KV cache 和长尾 token latency；混在一起会造成 noisy neighbor 和 head-of-line blocking。”

2. My ownership

“我承担的是 architecture 到 production operations 的 Tech Lead ownership。我的重点不是替每个团队写 model code，而是定义跨团队稳定 contract：intent 如何表达、dataset/artifact 如何引用、dependency 如何解析、runtime 如何选择、policy 在哪里执行，以及 rollout 和 failure recovery 如何统一。具体实现边界我会按真实情况说明；我不会把团队所有代码都说成个人完成。”

3. Core design

“入口不是直接指定某个后端，而是提交 versioned intent。Intent 表达目标能力、输入 artifact、quality/latency class 和 policy context。Planner 解析 model/runtime dependency，生成 versioned execution plan。大对象只通过 artifact reference 在 stage 之间传递，metadata 里带 checksum、schema/version 和 provenance，避免在消息队列或 RPC 中反复复制 raw media。执行层分为 orchestration、batch/data processing、tensor inference 和 LLM generation 等独立路径，它们可以各自扩缩、限额和发布，但共享 artifact contract、trace 和 policy。”

4. Reliability

“对 long-running workflow，我把 correctness 建立在 durable state、deterministic task identity 和 checkpoint 上。Task output 先写临时位置，校验后 atomic publish；retry 复用 idempotency key，已经 committed 的 node 不重复执行。错误区分 transient、permanent 和 ambiguous，后两类不能无脑 retry。Control plane 即使短时不可用，已经生成的 plan 和已提交的 artifact 仍可继续运行或恢复，从而减小 blast radius。”

5. Performance / resource

“我没有用一个 autoscaling policy 管所有 worker。CPU/I/O job 看 queue age、bytes 和 processing time；tensor inference 看 batch、GPU utilization 和 latency；LLM generation 看 active tokens、KV cache 和 time-to-first-token。通过独立 pool、quota、priority 和 admission control 防止交互 workload 被 batch job 淹没。Edge-first preprocessing 和 artifact reference 还减少了 heavy media 的跨网络搬运。”

6. Result / learning

“结果是多类 multimodal 和 LLM workflow 可以在共享 execution layer 上生产化，orchestration、batch processing、tensor inference 和 LLM generation 可以独立演进。简历没有给出这个项目的内部吞吐和 SLO，所以我只会使用我能确认的真实 production metric。最大的架构学习是：统一平台不等于统一 runtime；应该统一 contract、policy、lineage 和 observability，把 workload-specific execution 保持可替换。”

7.4 Deep Dive A：Intent Registry 和 Planner

Intent 的最小 contract

IntentRequest
  request_id / idempotency_key
  intent_name + intent_schema_version
  input_artifact_refs[]
  requested_output_schema
  latency_or_batch_class
  policy_context / tenant
  optional quality or cost constraints

Registry 记录：intent schema、compatible model/runtime、input/output type、policy requirement、default resource profile、rollout state。Planner 输出的是 versioned execution plan，而不是立刻执行副作用。

为什么不让 client 直接指定 model endpoint？

  • Client 会与 model name、region、runtime 和 rollout 细节耦合。
  • Model upgrade 要求所有 client migration，难以 canary/rollback。
  • Policy、artifact type 和 compatibility validation 会散落到每个产品。
  • 相同 semantic intent 无法统一观测成本、SLO 和成功率。

如何避免“万能 DSL”失败？

  • Intent 表达稳定业务/AI capability，不暴露所有 backend knob。
  • 扩展字段需有 owner、schema version 和 compatibility rule。
  • 非主流 workload 可走受控 custom execution escape hatch，但仍遵循 artifact/policy/observability contract。
  • 通过 adoption 和 exception rate 判断抽象是否正确；如果大量用户绕开 planner，说明 abstraction boundary 有问题。

Planner 的 availability

  • 尽量 stateless；registry/config versioned 并缓存。
  • Plan 一旦生成即可持久化，由 orchestrator 独立推进。
  • Registry 短时故障用 last-known-good，但需要 freshness bound；security revocation 不能无限使用旧配置。
  • Plan 带 registry/model/runtime version，保证事后可解释和 replay。
  • Planner overload 时 admission control，不让 timeout 触发 retry storm。

7.5 Deep Dive B：Artifact Reference 是平台关键

不要把 artifact 只说成一个 URL。推荐回答：

ArtifactRef
  artifact_id
  immutable version / checksum
  media or tensor schema
  physical locations[]
  size / codec / shape
  producer task + code/model version
  parent artifact IDs
  policy / retention class

它解决五个问题：

  1. Avoid data copy：stage 之间传小 reference，不传 image/video/audio body。
  2. Reproducibility：下游知道读的是哪个 immutable version。
  3. Lineage：能从输出回溯输入、model、transform 和 task。
  4. Locality：planner 可根据 location 决定 edge/cloud/region。
  5. Policy：权限和 retention 跟 artifact 走，而不是只靠 bucket path。

Artifact publish protocol

ALLOCATED → WRITING → VALIDATING → COMMITTED
                 └──────────────→ FAILED / QUARANTINED
  • Writer 使用 deterministic task/output ID 分配 artifact。
  • Payload 先写 staging path，计算 checksum 并校验 schema。
  • Metadata 通过 compare-and-swap/transaction 切为 COMMITTED。
  • Reader 只读 committed artifact。
  • Reconciler 扫描 orphan blob 和卡住的 writing state。
  • Cleanup 必须考虑 active lease/reader 和 retention，不能见到 orphan 就立刻删。

追问：Metadata committed，但 blob 不完整怎么办？

原则上 publish 前先验证 blob；但跨系统无法实现简单原子事务，所以仍需要 checksum-on-read、periodic reconciliation 和 quarantine。把 metadata transaction 说成能 magically 保证 object store 原子性会被追问击穿。

7.6 Deep Dive C：Long-running Workflow 的状态与恢复

Task state 推荐：

PENDING → LEASED → RUNNING → OUTPUT_STAGED → COMMITTED
                     ├──────→ RETRYABLE_FAILED → PENDING
                     └──────→ TERMINAL_FAILED / CANCELLED

必须讲清的 invariant：

  • 同一 task 可以被执行多次，但同一 logical output 只能 publish 一次。
  • Lease 超时后的旧 worker 不能覆盖新 worker，使用 fencing token / attempt number。
  • Checkpoint 是业务状态，不只是“记录进度百分比”；应包含可恢复的 input cursor、已提交 output 和 transform version。
  • Cancellation 需要 cooperative check；已提交 artifact 根据 policy 保留或 GC。
  • DAG 下游只能消费 committed parent，不消费 staging output。

Retry 分类

Error例子处理
Transienttimeout、worker lost、temporary storage errorexponential backoff + jitter + retry budget
ResourceOOM、GPU unavailable调整 resource profile、换 pool；不能原参数无限重试
Datacorrupt media、unsupported codec、schema mismatchquarantine / terminal，不重试
Ambiguous side effecttimeout 但不知写入是否成功先 query/reconcile，用 idempotency key 判断
Code/model bugdeterministic crashstop rollout / rollback，不制造 retry storm

Straggler

先看 bytes、duration、codec、model cost、worker hardware，区分 skew 与机器异常。可做 cost-aware partition、拆分 task、work stealing；speculative execution 只能用于 deterministic/idempotent stage。

7.7 Deep Dive D：共享 CPU/GPU 的隔离与调度

为什么不能只有一个 queue？

一个 30 分钟 video job 会阻塞 100 ms interactive task；GPU model 的显存形态和 batch policy也不同。一个 queue 会让 autoscaler 看不到各 workload 的真实 signal。

推荐的 workload classes

  • interactive: latency SLO，预留容量，严格 admission。
  • async: seconds/minutes，允许 queue 和 batching。
  • batch: throughput/cost 优先，可 preempt/retry。
  • long-running: checkpointable，限制单 task blast radius。

Scheduler 输入

  • CPU/GPU/memory、model/runtime、estimated duration、artifact locality。
  • tenant quota、priority、deadline、preemptibility。
  • GPU type/compute capability、显存、已加载模型和 cache affinity。

Noisy neighbor 防护

  • 独立 pool 或至少 workload class queue。
  • Per-tenant concurrency/quota 与 cluster-wide admission control。
  • Weighted fair sharing；高优先级可以 preempt batch，但必须定义 checkpoint 和 starvation protection。
  • 大 job 用 gang/placement constraint 时防止资源碎片；必要时 queue 而不是占半套资源等待。
  • Cost attribution 给团队可见，避免平台只靠行政限制。

Autoscaling signal

不要只用 GPU utilization：

  • Interactive：queue age、deadline miss risk、p95 latency。
  • Batch：backlog work-seconds，而不只是 item count。
  • Tensor inference：request rate、batch fullness、GPU active time、memory headroom。
  • LLM：queued tokens、active sequences、KV cache pressure、TTFT/TPOT。

7.8 Deep Dive E：Hybrid Edge-Cloud

Placement 决策维度：privacy、payload bytes、edge capability、model availability、latency、network、energy、result reuse、policy。

可以直接说：

“Edge-first 不等于 edge-only。我把能显著减少 bytes、且在弱设备上稳定执行的 deterministic preprocessing 放在 edge；需要全局 index、大模型、共享 GPU 或频繁升级的步骤放 cloud。任何 edge 产物都携带 input checksum、transform/model version 和 quality metadata；如果版本不兼容或 quality gate 失败，cloud 可以 fallback/recompute。”

关键 failure：断网重传、版本漂移、同一 artifact 多 location、partial upload、edge disk pressure。解决：resumable upload、content checksum、version compatibility、store-and-forward、priority/retention policy。

与简历中 10–20x 的区别：该数字来自你的 50B+ discovery 项目，不要自动说成当前 context-aware platform 的指标。

7.9 Deep Dive F：Observability 和 Debugging

每个请求能串起：

request_id → plan_id/version → task_id/attempt → artifact_id
           → model/runtime version → resource pool → outcome/cost

四层指标：

  • API/plan：validation error、plan latency、registry cache age、intent success rate。
  • Orchestration：queue age、task state duration、retry cause、stuck DAG、lease expiration。
  • Execution：CPU/GPU/memory、batch fullness、data wait、model latency、OOM。
  • Artifact：write/read latency、checksum failure、orphan、cache hit、bytes transferred。

Debug 顺序：先确定 failure stage 和版本，再看同一 artifact/model/runtime 是否聚集，再看 resource/system。不要直接翻单个 worker log。对 slow request 用 critical-path trace，不能把所有 task duration 相加。

7.10 Deep Dive G：Rollout 与 Migration

Senior Staff 项目不能停在 design：

  1. 先定义兼容 contract 和 adapter，让旧 workflow 能接入。
  2. 选择一条代表性但 blast radius 小的 workflow 做 pilot。
  3. Shadow execution 或 dual-run 比较 output、latency、cost。
  4. 按 tenant/use case canary，不一次切全量。
  5. 设 success/rollback gate；保留旧路径直到稳定窗口结束。
  6. 用 adoption、exception/escape-hatch、failure 和 onboarding time 反馈抽象。
  7. 发布 deprecation timeline 和 owner，避免永久双系统。

如果被问“如何推动团队采用”：强调减少迁移成本、给出可观测收益和共同定义 contract；不要只回答“通过 design review 说服大家”。

7.11 主项目追问清单：答案要到第二层

Q1：为什么不是 Airflow/Argo 直接编排？ A：通用 orchestrator 可以承载执行，但它不自动提供 domain contract、artifact semantics、model/runtime compatibility、policy 和 edge/cloud placement。我的平台层定义这些语义，底层 orchestrator 是可替换实现。不要贬低成熟 scheduler。

Q2：Planner 会不会增加 latency？ A：对 interactive 请求，registry/cache 本地化、plan template 和预解析降低开销；复杂 plan 可异步。只有当 routing/policy/rollout 的收益超过 planning overhead 才走动态 planner；固定路径可缓存 compiled plan。

Q3：如何保证旧 Intent 兼容？ A：schema version、backward-compatible additive change、adapter、contract test；breaking change 新版本并双轨迁移。Registry 明确 producer/consumer compatibility，不只靠文档。

Q4：怎么处理 task duplicate？ A：at-least-once execution，deterministic task ID，idempotent/atomic output publish，fencing token 和 reconciliation；不轻易承诺物理 exactly-once。

Q5：一个 GPU task OOM 怎么办？ A：记录 input shape/resource/model version；若 workload 可切分则降 batch/拆分，若 model minimum memory 超标则换 GPU class；设置 retry mutation 上限，避免相同参数无限 retry。对持续 OOM 阻断 rollout。

Q6：Artifact store 成为瓶颈怎么办？ A：先分解 metadata、bandwidth、IOPS 和 small-file；reference 不代表没有 I/O。通过 packing/range read、prefetch、locality/cache、multipart、并发限制解决；cache key 带 checksum/transform version。

Q7：多租户 policy 在哪里执行？ A：入口验证 identity/policy，plan 固化 policy decision/version；执行和 artifact access 再做 defense-in-depth。只在入口检查会被绕过，只在数据层检查又缺乏 intent context。

Q8：如果 registry 配错会全平台故障？ A：versioned config、schema/semantic validation、canary intent/tenant、last-known-good、automatic rollback；按 cell/tenant 限制 blast radius。高风险变更需双人 review/audit。

Q9：平台最大的 trade-off？ A：统一抽象提高复用和治理，但会增加 hop、control-plane dependency 和迁移成本。因此只统一稳定 contract，不强制统一所有 runtime；对不成熟场景提供受控 escape hatch。

Q10：如何证明平台成功？ A：adoption 不是唯一指标。看 onboarding lead time、workflow success/SLO、retry/recovery、compute utilization/cost、重复实现减少、model/runtime rollout 时间和 user escape-hatch rate。最终要连接产品/研究迭代速度。

Q11：你最关键的个人 decision？ A：建议选“按 failure/scaling model 拆 execution path，同时统一 artifact/intent contract”。先讲 alternatives、decision criteria、反对意见、验证和结果。具体事实必须按真实经历补充。

Q12：如果重做一次？ A：选择真实反思。一个稳健方向是更早定义 artifact lifecycle、SLO 和 migration telemetry，而不是先增加更多 intent；但只有符合真实经历时才能使用。

7.12 “我做了什么”答法

必须分三层：

I owned:       我定义并负责结果的 architecture / contract / rollout / SLO
I implemented: 我亲自设计或编码的关键模块
We delivered:  团队共同实现、其他团队 owner 的部分

可直接套用：

“我 owned 的是 [真实 architecture/contract/rollout]；我亲自深入实现了 [真实模块]，包括 [关键技术点]；[其他组件] 由合作团队负责，我通过 RFC、interface review、integration test 和 rollout metric 保证端到端结果。这个区分很重要，因为我的 Staff-level contribution 是让多团队交付一个一致系统，而不是声称所有代码由我写。”

7.13 三个必须准备的真实例子

项目设计再完整，也一定会被行为追问。面试前只需给下列三件事各写 3 行：

  1. Architecture disagreement：对方主张什么、你的 evidence、最终谁改变了看法。
  2. Production failure：用户影响、immediate mitigation、root cause、systemic fix。
  3. Migration resistance：用户为什么不愿接入、你减少了什么成本、如何证明收益。

没有真实例子时不要用虚构事故。可以诚实说内部细节不能披露，再讲 decision/failure pattern 和你实际采取的行动。
