2. 核心 System Design：自动驾驶 Foundation Model 数据平台

2.1 先澄清需求

可以问面试官：

  • 输入有哪些：camera、LiDAR、radar、IMU/GPS、CAN bus、HD map、driver action、planner trajectory？
  • 单次训练样本是 frame、clip 还是 episode？典型时间窗口和采样频率？
  • fleet upload 是全量、trigger-based 还是 edge filtering？网络是否间歇连接？
  • 主要场景是 offline training，还是还要求 near-real-time failure mining？
  • 数据规模、每日增量、保留策略、跨地域要求？
  • annotation 是人工、auto-label、simulation，还是混合？
  • 最重要的 SLO 是 data freshness、dataset reproducibility、GPU feeding throughput 还是 cost？

若对方不给数字，明确假设：

“为了推进设计，我假设 PB–EB 级历史数据、每日持续增量、单个 trip 包含多路大对象和高频 telemetry；训练按 clip/episode 读取，offline throughput 优先于单样本 latency。具体数字会影响 partition 和 capacity planning，但不改变核心抽象。”

2.2 总体架构（一口气讲清）

Vehicle / Simulation / Lab
  └─ Edge recorder + trigger + local manifest + checksum
       └─ resumable multipart upload / store-and-forward
            └─ Ingestion gateway + durable event log
                 ├─ Raw immutable object store (source of truth)
                 ├─ Manifest / metadata catalog / lineage graph
                 └─ Validation + quarantine
                       └─ Distributed processing (decode, sync, enrich, auto-label)
                            ├─ Curated scenario/feature tables
                            ├─ Search/index for scenario mining
                            └─ Dataset builder (declarative DatasetSpec)
                                  └─ Versioned immutable snapshot
                                       └─ Sharding / packing / cache
                                            └─ Training loader → GPU training
                                                 └─ Evaluation / failure mining
                                                      └─ New DatasetSpec / labels

横切能力：IAM / policy / PII, schema registry, orchestration, resource scheduler, data quality, observability, cost attribution, retention/deletion。

2.3 数据平面与控制平面

Data plane 传输大对象：sensor blobs、clips、point clouds、shards。走 object storage、multipart upload、range read、local cache；不要让 Kafka 承载视频本体。

Control plane 管理小而关键的描述信息：manifest、event、schema、job state、dataset spec、lineage、ACL。可以通过 durable log + transactional metadata store/catalog 驱动异步状态机。

关键回答：

“大对象和 metadata 分离。blob 用 immutable content-addressed/object key 存储，metadata 用强约束 schema 和事务更新。两者用 artifact_id + checksum + schema_version 关联。这样 retry 不会重复写大对象，catalog 也能做 lineage、search 和 delete propagation。”

2.4 Fleet ingestion：弱网络下仍可靠

车端：

  • Ring buffer 保存最近窗口；由 trigger/event selector 选择上传片段，避免全量回传。
  • 先生成 manifest：vehicle/session、sensor list、time range、calibration version、size、checksum、privacy classification。
  • 大文件分 chunk；resumable multipart、compression、bandwidth throttling、优先级队列。
  • store-and-forward：断网后保留进度；上传成功必须由服务端 checksum ACK 确认。

云端：

  • Gateway 做 auth、rate limit、upload session、region routing。
  • 先落 raw immutable zone，再发布 ObjectCommitted event；不要先发事件后写 blob。
  • 重试以 deterministic artifact_id 或 (vehicle_id, session_id, sensor, chunk_seq) 做 idempotency key。
  • validator 校验 checksum、manifest 完整性、timestamp monotonicity、sensor coverage、schema compatibility；失败进 quarantine，不污染 curated dataset。
  • 定期 reconciler 对比 object store 和 catalog，处理“blob 成功但 metadata 失败”等 orphan state。

Exactly-once 怎么说：

“端到端物理 exactly-once 很昂贵，我不会轻易承诺。我会采用 at-least-once delivery，加 deterministic id、idempotent sink、transactional metadata commit 和 periodic reconciliation，实现业务语义上的 effectively-once。”

2.5 多模态同步与数据模型

推荐层次：

  • DriveSession：vehicle、route、software build、weather、region、start/end。
  • SensorStream：sensor type、intrinsics/extrinsics、frequency、clock domain、codec。
  • Frame/Packet：timestamp、sequence、blob URI、checksum、quality flags。
  • EgoState/Action/Trajectory：pose、velocity、control、planned/executed trajectory。
  • ScenarioClip：time window + participating streams + scenario tags + quality score。
  • Annotation：label schema/version、source（human/auto/sim）、confidence、review state。
  • DatasetVersion：DatasetSpec、resolved members/snapshot、transform code/env、lineage、statistics。

同步策略：

  • 保存 event time 与 ingest time，不要混用。
  • 每个 sensor 保留自己的 timestamp 和 clock source；以 ego/world timeline 建统一索引。
  • 使用 calibration version 和 pose interpolation，将 observation 投影到统一 coordinate frame。
  • 对可容忍误差定义 alignment window；缺失数据不能悄悄填充，写入 missing/modality_mask。
  • 重采样方式必须版本化：nearest neighbor、linear interpolation、aggregation 的语义不同。
  • 训练切片必须防止未来信息泄漏，即 temporal leakage。

2.6 存储组织：PB/EB scale 的回答

分层：

  1. Raw zone：immutable、按 retention 分层，保留原始证据和 replay 能力。
  2. Curated zone：标准化、校准、清洗后的 columnar/table data。
  3. Dataset zone：面向训练的 immutable snapshot 和 packed shards。
  4. Hot cache：训练集本地 NVMe / distributed cache，生命周期短。

格式与索引：

  • 大 binary media 放 object store；结构化 metadata 用 Parquet + Iceberg/Delta 类 table format。
  • Parquet 擅长 column pruning / predicate pushdown；不是视频随机解码格式。
  • 训练时按访问模式生成较大 sequential shards，避免 millions of small files 和随机 GET。
  • 空间/时间/scene tag 建二级索引；向量 embedding 适合语义场景检索，但不能替代权威 metadata catalog。
  • Partition 选择低/中基数且常过滤的字段，如 date/region/source；不要直接按高基数 vehicle_id 产生碎片。

成本策略：hot/warm/cold tier、lifecycle policy、deduplication、derived artifact TTL、cache admission、跨 region egress 控制。删除必须通过 lineage 传播到派生数据，并保留 audit。

2.7 Dataset as Code：版本、血缘、复现

定义声明式 DatasetSpec：

name: urban_night_v3
sources:
  snapshot: curated_frames@2026-07-10
filters:
  region: [urban]
  lighting: [night]
  quality_score_gte: 0.95
sampling:
  strata: [scenario_type, weather, region]
  rare_event_weight: 4.0
transforms:
  code_sha: abc123
  image_decoder: v5
labels:
  schema: trajectory_label_v7
split:
  group_by: drive_session
  seed: 42

一个可复现 dataset version 必须 pin：

  • source table snapshot / manifest；
  • resolved sample IDs，而不只是一个会随时间变化的 SQL query；
  • transform code SHA、container image digest、dependency/environment；
  • annotation schema 和 calibration/map/software version；
  • sampling seed、split policy、statistics 和 validation report。

版本是 immutable。修正数据产生新版本；用 alias（candidate, production）做 promotion，不原地修改。Dataset lineage 记录 raw → validated → transformed → labeled → dataset → model checkpoint → evaluation。

2.8 Dataset quality：不要只回答“label accuracy”

质量分六层：

  1. Integrity：文件可读、checksum、schema、sensor completeness、timestamp continuity。
  2. Label quality：accuracy、inter-annotator agreement、confidence、golden set、review rate。
  3. Coverage：ODD、region、weather、lighting、road type、actor type、maneuver。
  4. Distribution：与 target deployment distribution 的偏差、class imbalance、duplicate rate。
  5. Leakage / split hygiene：同一 trip/route/near-duplicate 不能跨 train/test。
  6. Utility：在固定训练 budget 下，对关键 evaluation slice、closed-loop metric 和 failure rate 的边际提升。

一句高级回答：

“数据质量不是单一静态 score。最终判断是 dataset 对目标模型和关键 safety slice 的 marginal utility；但在训练前仍要用 integrity、coverage、label、distribution 和 leakage guardrail 阻断明显坏数据。”

可用方法：

  • 以 scenario taxonomy 建 coverage cube 和 minimum quota。
  • Perceptual hash / embedding 做 near-duplicate removal。
  • Golden set + spot audit + model disagreement 做 label QA。
  • 比较 dataset 与 fleet/target distribution 的 PSI/KL/Jensen–Shannon（注意解释假设）。
  • 用 slice-based evaluation 看 rare scenarios，不能只看全局平均。
  • 记录 dataset ablation / data attribution 结果，避免“数据越多越好”。

2.9 Data flywheel：模型失败如何回流

Fleet / Simulation
 → trigger & upload
 → scenario mining
 → dedup / diversity sampling
 → human + auto labeling
 → quality gates
 → dataset version
 → train
 → offline + simulation + closed-loop evaluation
 → failure slice / uncertainty / disagreement
 → prioritized recollection or relabeling

优先级不只看 uncertainty：还要综合 severity、frequency、novelty、coverage gap、labeling cost 和 expected information gain。对 safety-critical long-tail，低频不等于低优先级。

防止 feedback loop bias：保留无偏 fleet sample 作为基线；failure mining sample 与自然分布 sample 分开标识；训练时明确 reweighting；evaluation set 独立冻结，避免不断针对 test set 优化。

2.10 Reliability / Observability

四类信号：

  • System metrics：bytes/s、records/s、queue lag、task latency、retry、worker utilization、cache hit、object GET latency。
  • Data metrics：freshness、completeness、schema drift、null/missing modality、duplicate、distribution drift。
  • Training-facing metrics：time-to-first-batch、batch wait、samples/s、GPU data stall、shard skew。
  • Business/model metrics：dataset build lead time、failure slice coverage、model improvement per dataset version。

每个 artifact 和 job 带 trace_id / dataset_version / code_sha。Dashboard 按 stage 分解 throughput 和 latency；告警针对 SLO burn rate，而不是每次短抖动。失败任务保留 structured error、input lineage 和 retry history，支持 replay。
