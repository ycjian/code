8. Project Deep Dive 2：50B+ Multimodal Discovery（规模与数据证明）

只有面试官追问 data ingestion、indexing、retrieval 或 50B scale 时切到这个项目。

8.1 90 秒版本

“在 Adobe Search & Discovery，我设计了统一 image、audio、video、3D 和 document 的 multimodal discovery platform，支持 Photoshop、Lightroom 和 Premiere 等产品。数据侧用事件驱动 pipeline 做 onboarding 和派生 embedding/index；检索侧把 lexical/filter 与 vector ANN 分开，再进行 multi-stage fusion/reranking。平台支持 50B+ assets。通过 client SDK 的 on-device pruning 和 hybrid edge-cloud execution，heavy-media payload transfer 降低 10–20x；后续 multi-objective ranking 和 A/B testing 带来 15% discovery CTR 提升。这个项目最能证明我处理大规模 multimodal data、derived artifact、index evolution 和在线服务的能力。”

8.2 两条数据路径

INGEST / INDEX
Asset event → validate/dedup → extract metadata → generate embedding
            → lexical/filter index + vector index → versioned publish

QUERY
Query/image → encode → metadata/ACL filter → lexical + ANN candidates
            → merge/dedup → feature enrichment → rerank/diversify → result

Kafka/Flink/Milvus/Elasticsearch 是简历已写明的技术，但只有它们确实用于对应 stage 时才按上图说明；不要为了完整而错误归因内部实现。

8.3 50B scale 真正要讲什么

  1. Source of truth 与 projection：asset metadata/artifact 是权威状态；lexical/vector index 是可重建 projection。
  2. Partition/routing：按真实 tenant/region/modality/access pattern 回答；目标是避免 hot shard，并支持独立扩容和 rebalance。
  3. Index build vs serving isolation：backfill/reindex 不能抢占在线查询资源。
  4. Versioned publish：embedding/index version 明确，完成质量检查后 alias/manifest 切换。
  5. Capacity：vector dimension × bytes × replicas × index amplification，加 metadata 和 growth；不要只说 asset count。
  6. Freshness vs cost：增量更新服务 freshness，全量 backfill 用 batch；两者共享 output/version contract。

8.4 Elasticsearch + Milvus 为什么不是重复建设？

“Lexical/filter/ACL 与 ANN 的索引结构和查询能力不同。Elasticsearch 擅长 structured filter、text 和 aggregations；Milvus 承担 dense vector candidate retrieval。查询可以先根据 ACL/metadata 缩小空间，再做 ANN，最后统一 rerank。代价是双索引 consistency，因此它们都不是 source of truth；每条 update 带 asset/version，index 可 replay/rebuild，query 接受短暂 eventual consistency，但不能返回越权结果。”

追问“ACL filter 与 ANN 谁先”：取决于 filter selectivity 和引擎能力。高选择性先 filter；低选择性可 ANN overfetch 再 filter，但必须保证结果数量和 latency，同时 ACL 必须 fail closed。

8.5 Embedding model upgrade

new model validation
 → offline backfill to new embedding/index version
 → shadow queries / recall-quality-latency comparison
 → canary traffic
 → alias switch
 → rollback window
 → old index retirement

不能把新旧 embedding 混进同一 distance space。Backfill 与新数据增量之间要有 cutover boundary：例如 snapshot + change log，backfill 完 snapshot 后 replay delta，再切 alias。

8.6 10–20x payload reduction 怎么讲

只使用简历能确认的表述：on-device pruning 和 hybrid edge-cloud execution 减少了 heavy-media payload transfer。若追问机制，可在真实范围内讲：先在 edge/client 做 lightweight filtering/selection/feature extraction，只上传候选或派生 representation；云端在需要时按 artifact reference 拉取原始数据。

面试官一定可能问：

  • Reduction 的 denominator 是 raw bytes、request payload 还是 network egress？[需要你按真实情况回答]
  • 是否牺牲 recall/quality？用什么 guardrail？[真实指标]
  • Edge version 漂移如何处理？model/version + fallback。
  • 为什么不是压缩？pruning 降低的是无效内容量，compression 降低每个内容的 bytes，两者可叠加。

8.7 15% CTR 的深挖

回答结构：

  1. Baseline：原 ranking 的问题是什么。
  2. Change：multi-stage retrieval/ranking 如何融合 multimodal signal、real-time feature、relevance/diversity。
  3. Experiment：A/B randomization unit、duration、sample、significance [按真实情况]。
  4. Result：CTR +15% 是简历事实。
  5. Guardrail：latency、zero-result、diversity、downstream engagement [只讲真实监控]。
  6. Attribution：哪些 component 做过 ablation，避免把所有提升归给一个模型。
