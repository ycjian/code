12. Leadership / Behavioral Q&A（Senior Staff 标准）

Q：Tell me about a system you owned end-to-end.

用 Context-aware AI Infra。结构：

  1. Context：多个 workload/团队碎片化，heavy media + shared GPU。
  2. Scope：你负责的 architecture、interface、decision 和 rollout；团队边界说清。
  3. Hard decisions：intent abstraction、artifact reference、execution path separation、edge/cloud placement。
  4. Execution：RFC、prototype、stakeholder review、migration、canary、SLO/dashboard、on-call。
  5. Result：真实可量化结果 [请填]；没有数字就说 capability/reliability outcome，不编。
  6. Reflection：初版哪里需要修正，形成什么平台机制。

Q：如何 influence technical direction？

推荐回答：

“我不会先用 title 推方案。我会把分歧转成可验证的 decision criteria，例如 latency、failure isolation、developer onboarding time、GPU utilization 和 migration cost。先写 RFC，把 alternatives 和 reversibility 摆出来；高不确定项做小 prototype 或 shadow traffic。决定后记录 owner、SLO 和 sunset plan，并通过 shared metrics 判断，而不是争论个人偏好。”

补一个你自己的真实例子：谁不同意、为什么、你改变了什么意见、最终结果。

Q：平台和研究团队冲突怎么办？

研究需要速度和自由，平台需要稳定和成本治理。把核心 contract 标准化：artifact、dataset、resource request、observability、security；算法 transform/model code 保持可插拔。提供 golden path 模板，也给受控 escape hatch。用 adoption、time-to-first-run、failure rate 和 compute waste 评估平台，而不是强制所有人用同一框架。

Q：如何制定 roadmap？

来源包括 model/research bottleneck、SLO/incident、capacity/cost、重复建设和未来 model architecture。按 user impact × risk × leverage × urgency 排序。先找跨团队共用 primitive；避免为单个 feature 过度平台化。每项有 outcome metric、owner、migration 和 deprecation plan。

Q：发生重大事故如何处理？

先止损和明确 incident commander；隔离 blast radius、rollback/disable、保护数据正确性；建立 timeline 和 communication cadence。恢复后做 blameless RCA，区分 trigger、root cause 和 latent condition；action item 必须落到自动检测、guardrail、ownership 或 architecture，不只是“加强 review”。

Q：你不懂自动驾驶 domain，风险是什么？

不要防御，答：

“我的 gap 是没有在量产自动驾驶栈里长期负责过 sensor/ODD/safety validation，我不会把 creative media 的假设直接复制过去。我的做法是先和 perception/planning/data 用户共同定义 data semantics 和 safety-critical invariant；我能立即贡献的是 multimodal scale、pipeline correctness、version/lineage、distributed execution 和 platform operations。Domain semantics 由联合 design review 和可执行 validation gate 固化，而不是留在口头知识里。”
