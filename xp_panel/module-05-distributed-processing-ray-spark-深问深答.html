5. Distributed Processing / Ray / Spark 深问深答

Q1：如何处理 billions of samples？

答：先避免把 billion 当作单一任务。按 locality 和 processing cost 做 partition；control plane 生成 immutable work units，worker 通过 lease 获取任务，定期 heartbeat。Output 使用 deterministic path 和 atomic commit；失败可 retry，speculative execution 处理 straggler。对 skewed video/point-cloud 数据，不按 sample count 平均，而按 bytes、duration、estimated decode cost 分区。流水线各 stage 通过 bounded queue 形成 backpressure；批量读写、vectorized transform 和 column pruning 降低 overhead。最后做 compaction，避免 small files。

Q2：Ray vs Spark 怎么选？

维度SparkRay
核心优势成熟的 table/batch/SQL/ETL，optimizer 和 shuffle 能力强Python-native 通用 task/actor，适合 ML pipeline、stateful service、training/serving
执行抽象stage / partition / DataFrametask / actor / object reference / placement group
最适合大规模结构化 transform、join、aggregation、catalog tablePython/ML-heavy preprocessing、heterogeneous CPU/GPU、online/offline 一体工作流
风险非 JVM/Python UDF overhead，ML 控制流不灵活大 shuffle/SQL 生态通常不如 Spark 成熟；object store memory、task granularity 要治理

推荐说法：

“我不会因为团队用了 Ray 就把所有 workload 搬到 Ray。大规模 declarative table transform 可以继续由 Spark 承担；模型耦合的 Python preprocessing、CPU/GPU mixed task、training orchestration 可用 Ray。统一的 artifact contract 和 lineage 比强求单一引擎更重要。”

Q3：Ray 的核心执行模型？

  • Stateless remote task 适合可重试、细粒度并行；Actor 适合需要 state、connection/model reuse 的长生命周期 worker。
  • Object reference 传递依赖；大对象经 shared-memory object store，仍需控制 object spilling 和内存压力。
  • Placement group 支持 gang/colocation 需求；resource label 管 CPU/GPU/custom resource。
  • 任务必须设合理 granularity：太细 scheduler overhead 高，太粗 retry 成本和 straggler 影响大。
  • Fault tolerance 依赖 task lineage/reconstruction、actor restart 和 application checkpoint；外部 side effect 仍需 idempotency。

Q4：如何处理 data skew / straggler？

先区分 input size skew、compute complexity skew、resource heterogeneity 和外部 I/O 抖动。收集 per-partition bytes、records、duration、CPU、I/O。方案包括 pre-scan cost estimation、split hot partition、adaptive repartition、work stealing、salting hot key、local combine、speculative execution。Speculation 只适合 deterministic/idempotent task，否则重复 side effect 会出错。

Q5：Backpressure 如何设计？

每级 bounded queue；consumer 暴露 capacity/lag，producer 按 token/credit 拉取；超载时降低 upstream concurrency、spill to durable storage 或按优先级拒绝。不能靠无限内存 queue 吸收峰值。监控 queue age 而不只是 depth，因为不同 item cost 不同。

Q6：Checkpoint 怎么定频率？

权衡 checkpoint cost 与 expected recomputation。直觉上故障越频繁、重算越贵，checkpoint 越频繁；但写 checkpoint 会阻塞训练，应考虑 asynchronous/sharded checkpoint。先定义 RPO/RTO，再根据 observed MTBF 调整，而不是固定“每 N 分钟”万能答案。

Q7：Ray cluster 里有哪些关键角色？

短答：Ray 用 task、actor、object reference 表达计算。每个 node 有 worker processes、本地 scheduler/raylet 和 shared-memory object store；GCS 管 cluster-level metadata 和资源/actor/placement group 等控制信息。生产排障要区分 user task、node/raylet、object store 和 GCS/control-plane failure。

不要把 Ray object store 当 durable dataset storage。它是执行期的 distributed shared-memory/cache；dataset source of truth 仍应在 durable object/table storage。

Q8：Task 和 Actor 什么时候用？

  • Task：stateless、deterministic、输入输出明确、易 retry 的 transform。
  • Actor：需要复用 model/connection/cache、维护 state、限制 concurrency 或长期占有 GPU 的 worker。

Actor 的风险是 state recovery、hot actor 和 serial bottleneck。Crash 后 constructor 重跑不等于业务 state 恢复；必须从 durable checkpoint 恢复。不要依赖默认 retry/restart 值，生产中明确配置并让 side effect idempotent。

Q9：Ray object 丢了会怎样？

Ray 可以对部分 task-generated object 通过 lineage reconstruction 重算，但前提和限制很重要：producer/owner、task determinism、retry policy 和依赖仍可用。ray.put 创建的任意外部状态不能假设可重建；owner failure 也可能使 object reference 失效。因此关键 artifact 必须 durable publish，不能只存在 Plasma/object store。

面试亮点：

“Ray 的 lineage recovery 是 execution fault tolerance，不是 application correctness。外部 side effect、dataset commit 和 model checkpoint 仍需要自己的 idempotency、transaction/publish protocol。”

Q10：Object store memory 爆了怎么办？

先查：live ObjectRef、closure capture、large task return、block/batch size、fan-out、consumer 是否跟不上、object spilling throughput。Ray 可把 object spill 到外部 storage 并在需要时 restore，但 spilling 会引入磁盘/网络 I/O，不能替代 backpressure 和 bounded in-flight data。

处理顺序：

  1. 限制 in-flight blocks/task，建立 backpressure。
  2. 避免 driver/actor 长期持有无用 ObjectRef。
  3. 调整 block/batch 和 task granularity。
  4. 让 CPU producer 与 GPU consumer 的吞吐匹配。
  5. 最后根据 working set 配 object-store memory 与 spill storage；监控 spill/restore bytes 和 disk saturation。

Q11：Placement Group 解决什么，风险是什么？

Placement Group 用 bundle 原子预留一组资源，支持训练所需的 gang scheduling，以及 PACK/SPREAD locality/failure-domain 选择。风险是大 group 难以放置、造成 fragmentation/head-of-line blocking；PACK 改善通信/locality 但集中故障域，SPREAD 增加容错但可能增加通信成本。要有 queue/admission、最大 group size 和拓扑感知。

Q12：Ray Data 为什么适合 ML preprocessing？

Ray Data 的价值是 Python/ML-native transform、CPU/GPU heterogeneous operator，以及 streaming execution 可在上游未全部结束时推进下游。设计时仍要显式管理 block size、operator concurrency、memory、backpressure、locality 和 sink commit。大规模 SQL/join/shuffle 如果 Spark 更成熟，不应为了统一框架硬迁移。

一个训练数据 pipeline 可以这样表达：

durable dataset snapshot
 → read/partition
 → CPU decode + validate + augment
 → optional GPU model transform / auto-label
 → window/pack/batch
 → training iterator or versioned shard sink

每个 stage 记录 input/output block statistics 和 lineage；写 durable sink 时使用 staging + manifest publish，不能以“Ray job 成功”替代 dataset atomic commit。

Q13：GCS / head failure 怎么想？

GCS 是 cluster control plane，不应把 application source of truth 放在其中。生产上要配置匹配部署方式的 GCS fault tolerance/persistent backing；即使部分已运行 task 暂时存活，actor/placement group/resource 管理等控制操作也可能受影响。Application 仍要能从 durable workflow state 重建，而不是把 Ray cluster lifetime 当 workflow lifetime。

Q14：Bx Txxx 追问 “Ray vs Kubernetes” 怎么答？

它们不是同层替代：Kubernetes 管 pod/node 生命周期、隔离与基础资源；Ray 管 Python task/actor、object dependency 和分布式 application scheduling。KubeRay 把 Ray cluster/job 运行在 Kubernetes 上。必须明确两层 autoscaler/queue 的 ownership，避免 Ray 认为有资源但 pod 未就绪，或 Kubernetes scale-down 杀掉不可恢复 actor。
