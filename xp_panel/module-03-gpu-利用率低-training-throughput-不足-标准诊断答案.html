3. GPU 利用率低 / Training Throughput 不足：标准诊断答案

先定义：

step_time = max(compute_time, input_pipeline_time, communication_time)（存在 overlap 时看 critical path）；最终看 samples/sec、GPU active time 和 end-to-end cost，不只看瞬时 utilization。

3.1 诊断顺序

  1. 建立 baseline：global batch、sequence length、GPU 数、samples/s、step-time p50/p95、GPU active/idle、data wait、NCCL time。
  2. 单机单卡跑 synthetic data：若仍慢，问题在 model kernel/CPU launch；若快，问题在 data 或 distributed communication。
  3. 真数据 + 单 worker；逐步增加 loader workers、nodes、GPUs，找到非线性拐点。
  4. Trace 一次完整 step：read → decode → augment → H2D → forward/backward → all-reduce → optimizer。
  5. 对比 worker/shard：p95 是否由 straggler 或热点 partition 决定。

3.3 不要盲目 cache

先算 working set、reuse distance、cache hit、填充成本和失效语义。训练数据只扫一遍时 cache 可能无收益；多 epoch、共享基础 dataset 或 expensive decode 时收益大。Cache key 应包含 artifact checksum + transform version，避免陈旧派生数据。

3.4 DDP / FSDP / TP / PP：训练并行策略怎么影响 Data Infra

先用一句话区分：

  • DDP (Distributed Data Parallel)：每个 rank 保留完整模型、读取不同 data shard，backward 时做 gradient all-reduce。模型能放进单卡时最直接。
  • FSDP / ZeRO-style sharding：把 parameter、gradient、optimizer state 的部分或全部切到 ranks；用 all-gather / reduce-scatter 换显存，适合单卡放不下或 optimizer state 很大。
  • TP (Tensor Parallelism)：把一个 layer/tensor 的计算拆到多 GPU；通信频繁，通常更依赖高速 intra-node interconnect。
  • PP (Pipeline Parallelism)：按 layer/stage 切模型，用 micro-batch 填 pipeline；要处理 bubble、stage imbalance 和跨 stage activation transfer。
  • 大模型常把它们组合成 3D parallelism；组合越复杂，checkpoint、topology 和 failure recovery 越难。

对数据平台的直接要求

  1. 每个 data-parallel rank 必须读到不重复且完整的 sample shard；global rank / world size / epoch / seed 是 sampler state 的一部分。
  2. Elastic restart 后如果 world size 改变，不能简单从“第 N 个文件”继续；要定义 sample identity、epoch boundary 和重复/遗漏语义。
  3. Variable-length sequence 会造成 rank step-time skew；需要 length-aware bucketing/packing，而不是只按 sample count 分 shard。
  4. Data loader 的 deterministic transform 需要绑定 seed、sample ID 和 transform version，才能复现。
  5. Checkpoint 不只包含 model/optimizer，也要包含 scheduler、RNG、sampler/dataloader cursor、dataset version 和 parallel topology。
  6. FSDP/TP/PP checkpoint 多为 sharded state；保存和恢复要避免所有 rank 同时向同一 object prefix 写小文件或让 rank 0 聚合到 OOM。

Q：DDP 从 8 GPU 扩到 64 GPU 后反而变慢，怎么查？

短答：先看每 step 的 compute、input wait 和 collective；用 strong-scaling efficiency 判断。若单 rank compute 变小而 all-reduce 不变，communication 占比会上升。然后检查 gradient bucket、compute/communication overlap、网络拓扑、straggler、global batch 和数据读取是否按节点放大。

展开：

  • 用 synthetic data 排除 input pipeline；若仍不 scale，集中查 NCCL/collective。
  • 比较每个 rank 的 forward/backward/collective p50/p99；一个慢 rank 会拖住同步 step。
  • 检查是否跨 rack、NIC oversubscription、GPU/NIC affinity 错误。
  • 增加 per-GPU batch 可提高 arithmetic intensity，但会改变 global batch 和优化语义。
  • Gradient accumulation 减少通信频率，但增加 step latency，并可能影响 convergence。
  • Bucket 太小 collective overhead 多；太大会降低 overlap；必须 profile，不背固定值。

Q：什么时候从 DDP 转 FSDP？

不是为了“更先进”。当完整模型 + gradient + optimizer state + activation 不能经济地放入每 GPU，或 replication 限制 scale 时考虑 FSDP。代价是 parameter all-gather/reduce-scatter、wrap/shard policy、checkpoint 和 debugging 更复杂。先确认 memory 是真正 bottleneck，而不是 activation、fragmentation 或 batch 设置问题。

Q：Training checkpoint 怎么设计？

“Checkpoint 是一个 immutable、原子发布的 logical version。各 rank 并行写自己的 shard 到 staging prefix，写 manifest 和 checksum；所有 shard 完成后由 coordinator publish committed manifest。恢复只读取 committed version。Checkpoint metadata 绑定 model code、parallel topology、dataset/sampler cursor 和 RNG；失败的 staging output 由 reconciler/TTL 清理。”

目标先定 RPO/RTO。频率越高重算越少，但会增加 I/O 干扰；可用 asynchronous/sharded checkpoint、带宽限流和独立 storage path。不要只说“每 N steps 保存”。
