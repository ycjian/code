19. Wxxxx-style Interview Experience Deep Dive（Non-Coding）

这一章把公开面经里的随机题，压缩成一套可复用的答题系统。它们与 Xpxxx 的业务相似：都在考 real-world data、simulation/evaluation、ML platform、production inference、safety policy 和 distributed systems，不是要求背某家公司内部架构。

19.0 使用边界：哪些题本章不展开

本章只回答 design、ML、statistics、infra、monitoring 和 behavioral：

  • 不展开 Max Pooling implementation；
  • 不展开 Jump Game / backtracking；
  • 不展开 graph-search coding；
  • 不展开 NumPy / tensor debugging implementation；
  • 不猜未给完整 prompt 的 coding 题。

如果面试官从 design 继续要求 coding，再切到第 10 章的协议：先说 contract、invariant、complexity、edge case 和 test，再写实现。

19.1 Vague System Design：Design a System to Back Up Files

先把 vague prompt 变成明确 contract

开场不要直接画组件：

“我先确认 source/destination 是单机、NAS 还是 object storage；需要 full 还是 incremental backup；是否要求 point-in-time consistent snapshot；文件规模、总 bytes、变更率、RPO/RTO；是否保留 permission、owner、timestamp、symlink 和 empty directory；destination 是否允许 eventual convergence。下面我先假设 source 是多机文件树，destination 是 durable object storage，需要保留相同 logical directory structure，支持增量、恢复、校验和失败重试。”

给定的 filesystem functions 只是 data-plane primitive；系统仍要补 control plane：

Backup Job API
  -> Snapshot / Scan Coordinator
  -> Manifest Builder
  -> Partitioned Task Queue
  -> Directory + File Workers
  -> Destination Blob Store
  -> Metadata / Manifest DB
  -> Verifier + Reconciler

数据模型与 structure preservation

每次 backup 产生 immutable backup_id 与 manifest：

字段作用
backup_id一次 snapshot / job 的唯一 generation
source_rootcanonical root，防止 path traversal
relative_pathdestination 重建相同树的唯一依据
typefile / directory / symlink
size, mtime, modemetadata 与快速 change detection
content_hash完整性、dedupe、idempotency
chunk_ids大文件断点续传与并行 copy
state, attempt, errordurable workflow state

Destination 不应依赖 worker 的执行顺序。Directory 可先显式创建，也可由 manifest 在 restore 时 materialize；关键是 relative_path -> object/chunks + metadata 的映射必须 durable。Empty directory 也必须作为 manifest entry 保存。

Full / incremental / consistent snapshot

  • 第一次 full scan；后续基于 journal/change feed 优先，periodic full reconciliation 防漏事件。
  • 只看 mtime 不够可靠；可先用 size/mtime 快筛，最终以 checksum 或 content-addressed chunk 验证。
  • 正在写的文件不能边读边声称 point-in-time consistent：使用 filesystem snapshot、application quiesce，或记录 changed_during_copy 后重新排队。
  • Manifest 只有在所有 required entries 校验成功后从 BUILDING 原子切到 COMMITTED；restore 只读取 committed generation。

Scale

容量先算：

\[ T_{backup} \ge \max\left(\frac{Bytes}{ReadBW},\frac{Bytes}{NetworkBW},\frac{Bytes}{WriteBW}\right) \]

任务按 (tenant, source_root, path-prefix) 分片；大文件再按 chunk 分片。Metadata scan 与 byte transfer 分开扩容，避免 millions of tiny files 被少量 huge files 拖住。需要 bounded queue、per-tenant quota、bandwidth shaping 和 destination rate limit。

Failure 与 correctness

  • Task ID 由 backup_id + relative_path + chunk_index + source_version 决定，retry 幂等。
  • Chunk 先写 temporary key，checksum 通过后 commit/rename pointer；不能让 partial object 被 restore 看见。
  • Worker crash：lease 超时重派；late worker 用 fencing token 不能覆盖新 attempt。
  • Destination timeout 后结果不明：先 HEAD/checksum，不能直接重复产生另一个 logical copy。
  • Poison file：有限重试后 quarantine，但 job 是否允许 partial success 必须由 policy 决定。
  • Reconciler 比较 source snapshot manifest、task state 与 destination objects，修复 orphan/missing/corrupt entries。

恢复与验证

Backup 没有 restore drill 就不算完成。至少验证：随机 checksum、全量 manifest consistency、permission/path/symlink、空目录、跨版本 restore、RTO、删除/损坏 destination chunk 后的恢复。

19.2 Security Event Platform：Rule Suppression 与 Pluggable Enrichment

HLD：先保留原始事实，再产生可解释 decision

Collectors -> Durable Event Log -> Normalize / Schema Validate
 -> Enrichment Plugins -> Detection / Ranking
 -> Suppression Policy -> Threat Level
 -> Alert Generation -> API / DB / Audit Log

Raw security event 和 detector finding 永不因 suppression 被删除。Suppression 改变的是 downstream action，而不是历史事实：

raw_event -> finding(rule_id, evidence, score)
          -> suppression_decision(policy_id, matched, reason, version)
          -> effective_finding / alert

Rule Suppression 设计

Suppression policy 至少包含：

字段说明
policy_id, tenant_id, version多租户与审计
rule_selectorrule ID / tag / threat family
predicateGeo-IP、entity、CIDR、time window、history 等条件
actionsuppress alert / lower severity / route only / expire
priority, effective_at, expires_atdeterministic evaluation
creator, approver, reasongovernance；公开版本只显示匿名 identity reference

关键语义：

  • 先做 schema/type validation，再编译 predicate；不执行任意用户代码。
  • Match 结果必须带 policy_version 和 reason code，便于重放与审计。
  • Default deny/allow 要按风险定义；安全检测 pipeline 不能因为 suppression service timeout 就静默丢 alert。高风险规则通常 fail open to alert。
  • Policy change 对新事件立即生效；是否 retroactive re-evaluate 历史 finding 是独立 job。
  • Suppression 需要 hit rate、top policies、unexpected drop、expiry 和 shadow mode 指标，防止一条宽规则吞掉所有 alert。

Pluggable Enrichment：Platform Code 不因客户逻辑频繁修改

定义稳定 contract，而不是让插件直接操作内部对象：

PluginManifest
  name / version / input_schema / output_schema
  required_capabilities / timeout / memory / network_policy

EnrichmentResult
  fields / confidence / evidence_refs / status / error_code

Plugin registry 保存签名 artifact、schema、owner、compatibility 和 rollout state。Execution plane 使用 sandboxed process/container/WASM；每个插件有 CPU、memory、timeout、network egress、secret scope 和 retry budget。禁止插件直接写主事件 DB；它只能返回 typed result，由平台统一 commit。

Decorator / Strategy / Pipeline 怎么选

  • Strategy：同一个 enrichment capability 有多个实现，例如 commercial Geo-IP 与 internal Geo-IP。
  • Decorator：在插件调用外统一叠加 timeout、cache、metrics、circuit breaker、redaction 和 authorization。
  • Pipeline / Chain of Responsibility：客户配置执行顺序、条件、短路和并行 fan-out。

客户配置的是 declarative plan：

if event.ip exists:
  geo_ip@v3 -> history@v5
if geo.country in deny_regions:
  raise finding geo-risk
skip expensive reputation plugin when trusted_asset == true

这不是把安全边界交给客户。平台仍控制允许的 plugin、schema、resource、secret、network 和 output namespace。

Versioning / rollout / failure

  • Request pin pipeline_version + plugin_versions + rule_version，同一事件可复现。
  • 新插件先 offline replay，再 shadow，对 output diff、latency、error、alert delta 做 slice check，最后 canary tenant。
  • Non-critical enrichment timeout 可返回 UNKNOWN 并继续；critical evidence 缺失时 policy 决定 quarantine 或保守提升风险。
  • Plugin result cache key 必须含 input fingerprint、plugin version 和 tenant policy，不能跨 tenant 泄漏。

19.3 How to Filter User Requests / Compare Models / Build Datasets

User request filtering：先分清两种含义

如果问的是产品需求筛选：把需求分成 hard constraint / must-have / quality preference / best-effort，先定义 abuse、安全、隐私、权限和 latency/cost boundary，再排功能优先级。

如果问的是 AI request filtering：

Normalize -> AuthN/AuthZ -> Rate/Quota -> Policy Rules
 -> Lightweight Safety Classifier -> Contextual/Risk Classifier
 -> allow / transform / require-confirmation / block / human-review

必须回答：

  • Filter 既看 raw request，也看 retrieved context、tool call 和 final response；只过滤 prompt 不够。
  • Hard policy 用 deterministic rule；ambiguous semantic risk 用 model；高风险 tool action 需要 capability allowlist 与 human confirmation。
  • 保留 redacted reason code、policy/model version、decision latency；不无限保存 raw private prompt。
  • Threshold 不按全局 accuracy 选，而按 risk tier 的 false-negative cost、false-positive friction 和 review capacity 选。
  • Prompt injection 不能只靠 classifier：retrieved text 当 untrusted data，tool schema/permissions 在 runtime enforce。

Model comparison：用 paired、slice-aware、statistically defensible evaluation

先固定 dataset version、preprocessing、prompt、decoding、hardware 和 resource budget。对同一个 example 同时跑 baseline 与 candidate，计算 paired delta：

\[ \Delta_i = metric(candidate_i) - metric(baseline_i) \]

报告 mean/median、bootstrap confidence interval、win/tie/loss、关键 slice 和 worst-case regression。不能只比较两个 global averages。

Decision gate 示例：

  • Primary quality 显著提升或达到 non-inferiority margin；
  • Safety-critical slice 无 regression；
  • p95 latency、memory、cost 在 budget 内；
  • Calibration、abstention、coverage 达标；
  • Shadow/canary online guardrail 通过。

Dataset build：从 decision 与 failure taxonomy 倒推

  1. 定义 unit：request、frame、clip、episode、trip 或 scenario。
  2. 定义 label/rubric、ambiguity 与 adjudication。
  3. 从 production unbiased sample + risk/rare oversample + hard negatives + synthetic coverage 组合数据。
  4. 以 entity/time/geography/scenario group split，避免相邻 frames、同一 trip 或模板泄漏。
  5. 保存 immutable dataset version、lineage、consent/license、feature/preprocess version。
  6. 自动检查 duplicate、missing、alignment、class balance、slice coverage、label disagreement。
  7. Candidate model failure 回流 hard-example pool，但保留固定 unbiased benchmark，防止 benchmark 被追着优化。

19.4 Design a Distributed Transaction Database

开场先问：transaction 是单 region 还是跨 region；read/write QPS、data size、key access、isolation、availability、latency 和 geo requirement。一个可防守的 baseline：sharded SQL/KV，单 shard 用 Raft，跨 shard用 MVCC + 2PC。

SQL/API Gateway -> Transaction Coordinator -> Timestamp/Txn Status
                -> Shard Leaders (Raft groups)
                -> WAL / MVCC storage / CDC

单 shard

  • Leader 将 write intent / WAL replicate 到 quorum 后确认。
  • MVCC 保存 (key, commit_ts, value)；reader 按 snapshot timestamp 读取。
  • Serializable 可用 strict 2PL、SSI 或 serializable timestamp ordering；必须明确选一种及其 abort behavior。

跨 shard transaction

  1. Coordinator 取得 transaction ID / read timestamp。
  2. Participants validate conflict 并持久化 PREPARED intent 到各自 Raft quorum。
  3. Coordinator durable commit/abort decision。
  4. Participants apply commit timestamp，异步清理 intent。

2PC 会 blocking，所以 coordinator decision 不能只在内存；放 replicated transaction-status record。Participant 不确定时查询 status；lease/timeout 不能自行把已 commit transaction 当 abort。

Scale 与 failure

  • Partition by access pattern，避免单 hot account/order；支持 split/merge 与 routing epoch。
  • Request 携带 routing/version；stale router 被 shard redirect。
  • Deadlock 用 wait-die/wound-wait 或 wait-for detection；所有 lock/intent 有 observable age。
  • Cross-region 优先 local transaction；global transaction 的 quorum/clock latency 必须作为显式 trade-off。
  • CDC/outbox 只发布 committed version；consumer 仍幂等。
  • Backup 使用 distributed consistent snapshot + WAL replay；定期 restore drill。

面试官看的是：commit ambiguity、coordinator crash、participant recovery、isolation anomaly、rebalancing 中 transaction correctness，而不是只说 “用 2PC”。

19.5 Design an AI Shopping System

先限定产品：用户可用自然语言表达需求，系统负责检索/比较/解释/推荐；价格、库存、配送、支付必须来自 authoritative services，LLM 不能创造事实或直接绕过确认下单。

User Query -> Intent / Constraint Parser -> Catalog + Inventory Filters
 -> Lexical + Vector Retrieval -> Feature Join -> Rank / Diversify
 -> LLM Grounded Comparison -> Tool Plan -> User Confirmation
 -> Cart / Order APIs

Retrieval 与 ranking

  • Hard constraints：price ceiling、size、availability、delivery date、region、policy，先过滤。
  • Elasticsearch/BM25 处理 exact product terms；vector retrieval 处理语义/风格；query rewrite 只能扩展，不能丢原始约束。
  • Candidate ranker 使用 relevance、quality、price/value、availability、delivery、seller trust、preference；广告必须独立标识。
  • Heavy cross-encoder/LLM 只处理 top N；response 引用 product/version/price timestamp。

Agent / tool safety

  • Tools 最小权限：search/read 可自动；add-to-cart 可确认；purchase/refund/address change 必须强确认和 idempotency key。
  • Prompt injection in product description 视为 untrusted data，不能改变 system/tool policy。
  • Session memory 区分 ephemeral preference 与用户明确保存的 profile；PII 和 payment token 不进入模型日志。

Evaluation

Offline：Recall@K、nDCG、constraint satisfaction、hallucinated attribute、diversity、price freshness。Online：conversion 不是唯一目标，还看 return/cancel、complaint、latency、cost、seller/brand fairness 和 long-term satisfaction。

19.6 Append-only Log Instant Messaging，Search 必须用 grep

要求看似极简，关键是接受 append-only 与无上限日志带来的语义：所有 edit/delete/reaction 都写新 event，不原地改旧行。

Log schema

每个 conversation 一个 logical ordered stream：

seq | event_id | timestamp | actor | type | target_id | payload | checksum

SEND 保存 text；EDIT/RECALL 引用 target message；REPLY 保存 parent ID；MENTION 在 payload 中保存 normalized user IDs。Read model 按 seq fold events，得到当前可见状态。

Ordering 与 durability

  • Conversation 最多 500 人，按 conversation_id 路由到 single logical leader/partition，分配 monotonic seq。
  • Append 先进入 WAL/replicated log，quorum durable 后 ack；client retry 带 idempotency key。
  • Segment file 达到 size/time 后 rollover；旧 segment immutable。单个 conversation “长度无上限”不意味着一个 OS file 永不切分，logical log 可由 ordered segments 组成。
  • Membership change 也是 event；读每条消息必须根据 event-time membership/ACL，而非只看当前 member list。

grep search

既然规定 grep，就明确：search worker 只对用户有权限的 conversation segments 执行 fixed-string/escaped pattern grep，不能把 raw query 拼进 shell。先用 segment time range、conversation ID、optional bloom/trigram side metadata 缩小文件，但最终 match 必须由 grep 完成。

Recall/edit 后搜索不能泄漏被撤回文本：grep 找到 raw SEND 后，必须用 folded visibility/tombstone state 做 final filter。结果按 (segment, byte offset/message_id) 回查 context，并有限制、timeout、cancel 和 resource quota。

Scale / failure / retention

  • Hot conversation 独立 partition；cold segments 压缩并进 object storage，search 时受控 fetch。
  • Replication、checksum、segment manifest、compaction generation 都必须可恢复。
  • Compaction 可产生新的 materialized segment，但旧 append log 按 retention/audit policy 保存；atomic pointer 决定 active search generation。
  • Rate limit mention fan-out；notification 是 derived async effect，可重放且幂等。

19.7 Kubernetes / Docker / Multi-tenancy / Istio 高频

Deployment、ReplicaSet、Pod 的关系

Deployment 是 desired-state rollout controller；它创建/管理 ReplicaSet。ReplicaSet 确保 selector 匹配的 Pod 数量达到 replicas；Pod 是 scheduler 实际放到 node 的最小调度单元。更新 image/template 时 Deployment 创建新 RS，按 rolling-update 的 maxSurge/maxUnavailable 放大新 RS、缩小旧 RS。Controller reconciliation 不是一次命令；Pod 挂了由 RS 补，node 挂了 scheduler 为新 Pod 选 node。

如何减小 Docker image

  • Multi-stage build，只复制 runtime artifact；
  • 选择匹配风险的 minimal/distroless base；
  • .dockerignore 排除源码 cache、test data、git history；
  • 合并并清理 package-manager cache；
  • 固定 dependency，去除 compiler/debug symbols 和不需要的 locale；
  • 不把 secret 写进 layer；用 image scanning/SBOM 验证。

Image size 不是唯一目标：过度精简导致无法 patch/observe 也有成本。看 cold-start、pull bandwidth、CVEs 与 operability。

Requests、limits、QoS 与 scheduler

  • Scheduler 主要根据 requests 做 fit/score，不根据实时 utilization 猜资源。
  • Guaranteed：每个 container CPU/memory request == limit；最不易因 memory pressure 被驱逐。
  • Burstable：至少有 request，但不满足 Guaranteed。
  • BestEffort：无 requests/limits；最先 eviction。
  • CPU 超 limit 通常 throttling；memory 超 limit可能 OOM kill。Request 太小会 overcommit/noisy neighbor，太大浪费并阻塞调度。

GPU 还要 device plugin、node label/taint、topology、MIG/whole-GPU policy；只写 nvidia.com/gpu: 1 不等于解决 memory profile 和 multi-tenant isolation。

Multi-tenancy 与 Istio security

防护是分层的：

  • Identity：独立 service account、短期 workload identity；
  • Namespace/RBAC：tenant/operator 权限最小化；
  • NetworkPolicy：默认拒绝 namespace east-west；
  • Istio mTLS + AuthorizationPolicy：基于 workload identity 做 service-to-service allowlist；
  • Ingress/Egress gateway：限制外部流量和数据外泄；
  • Pod Security、seccomp、read-only rootfs、non-root、capability drop；
  • ResourceQuota、LimitRange、priority/fairness 防 noisy neighbor；
  • Secret/KMS、audit、policy-as-code 与 admission control。

Istio 不是 NetworkPolicy/RBAC 的替代。Mesh policy 配错也会全局放行或中断；先 shadow/audit，按 namespace/service canary，并监控 denied requests、certificate rotation 和 policy drift。

19.8 Design an Evaluation System：Human Eval + LLM Eval

核心对象

EvaluationSpec
  dataset_version / candidate_versions / rubric_version
  evaluator_mix / sampling / slices / aggregation / gates

EvaluationRecord
  example_id / blinded_output / evaluator_id_or_model
  rubric_scores / preference / reason / confidence
  prompt_version / judge_version / timestamp

HLD

Eval API -> Dataset/Output Snapshot -> Task Generator
 -> Human Queue + LLM Judge Pool + Deterministic Checks
 -> Quality Control / Adjudication -> Aggregator
 -> Slice Dashboard / Release Gate / Audit Store

Human eval 使用 blinded randomized A/B，gold questions、duplicate assignment、inter-rater agreement 和 adjudication。敏感数据按 reviewer clearance 路由，UI 默认 redaction。

LLM judge 不是免费 ground truth：固定 prompt/model/version，position swap，定期与 expert-human gold set 校准；监控 self-preference、verbosity bias、order bias、language/slice drift。High-stakes failure 或低置信 disagreement 进入 human review。

Scale 与统计

  • Cheap deterministic checks 全量；LLM judge 大样本；human 用 stratified/risk sampling。
  • 同一个 example paired 比较 candidate，bootstrap confidence interval。
  • 先定义 primary metric 和 release margin，避免看到结果后挑 metric。
  • Dashboard 必须能下钻 dataset version、model/prompt/judge version、slice、error taxonomy 和 raw evidence。

Release gate

不是 “LLM score 高就上线”：quality primary 达标、critical safety slice 零容忍/上限、human/LLM agreement 可接受、latency/cost guardrail、shadow/canary 通过，才能 promotion。Judge 升级本身也要作为 model change 回归。

19.9 Simulation Statistical Experiment：新增“路面坑洞”Feature

Hypothesis 与 experimental unit

H0：candidate 在 pothole scenarios 的 safety/comfort 不优于 baseline，或造成其它场景 regression。H1：在预先定义 margin 下改善 pothole response，且全局关键 guardrail non-inferior。

Unit 不应是每个 frame；通常是 scenario episode / route replay。相邻 frames 强相关，把它们当独立样本会虚增 sample size。

Scenario matrix

按 pothole size/depth、lane position、speed、lighting/weather、road friction、traffic density、map quality、sensor noise、vehicle load、可绕行空间分层。加入 no-pothole control、look-alike（阴影/井盖）和 rare severe cases。

Metrics

层指标
Safetycollision/contact、minimum TTC、lane departure、unsafe swerve、hard-brake rate
Taskdetect recall/precision、avoidance success、route progress、false intervention
Comfortlongitudinal/lateral jerk、peak accel/decel、yaw rate
Policysolid-line/road-boundary violation、priority-rule violation
Systemperception/planning latency、fallback、compute/memory

Experiment

对同一 initial state、map、traffic actors 和 random seed paired 跑 baseline/candidate，减少环境 variance。Pre-register primary metric、guardrail、slice 与 stopping rule。先 deterministic replay，再 randomized actor perturbation / Monte Carlo，最后 shadow/closed-course/on-road staged rollout。

统计报告 paired delta、cluster bootstrap by scenario family、confidence interval；critical safety event 同时报 rate upper bound，不能因零 observed event 就宣称风险为零。Synthetic improvement 还要检查 sim-to-real gap 与 scenario realism。

19.10 给一组 Data：怎样证明 New Model Better

先问 data 是否 paired、unit 是什么、metric 类型、是否重复测量、selection 是否 randomized。标准流程：

  1. Data quality：missing、duplicate、outlier、label leakage、版本与样本选择。
  2. EDA：baseline/candidate distribution、per-slice count、paired scatter、tail。
  3. Primary metric 与 minimum practical effect 预先定义。
  4. 选择 test，并报告 effect size + confidence interval，不只 p-value。
  5. Multiple slices/hypotheses 做 correction 或明确 exploratory。
  6. Safety-critical slice 做 regression gate / non-inferiority。
数据常用方法
Paired continuous metricpaired t-test；非正态/重尾可用 bootstrap 或 Wilcoxon
Binary paired outcomeMcNemar；同时报告 rate difference CI
Independent proportionstwo-proportion test / Fisher exact
Ranking / per-query metricquery-level paired bootstrap / permutation
Repeated trip/intersectioncluster bootstrap 或 mixed-effects model
Rare failureexact/Poisson/binomial interval，关注 upper bound

如果数据不是 randomized，不能把 correlation 当 causal improvement。使用 matching/stratification/propensity weighting 控制 observed confounder，并明确 unobserved confounding 仍存在。最终上线仍需 randomized A/B、shadow 或 staged field experiment。

19.11 ML Design：Passenger 到达目的地下车，如何选停车点

定义问题

输入：destination、HD map/curb、traffic state、乘客偏好/可达性、车辆状态、法规与实时 blockage。输出不是任意坐标，而是少量 feasible pull-over candidates 的排序与 trajectory handoff。

Map / Curb Rules / Real-time Occupancy
 -> Candidate Generator
 -> Hard Safety + Legal Filter
 -> Learned Ranker / Cost Model
 -> Planning Feasibility Check
 -> Selected Stop + Explanation / Fallback

Hard constraints 先于 model score

不可停区域、消防栓/公交站、intersection clearance、crosswalk、自行车道、道路边界、最小 gap、乘客侧开门风险、车辆可达性必须 rule/constraint enforce。模型不能用高 convenience score 覆盖 illegal/unsafe candidate。

Features 与 objective

  • Safety：traffic speed/gap、visibility、door-zone conflict、pedestrian/cyclist、required lane change；
  • Legality：curb type、time restriction、temporary closure；
  • Reachability：planning path、turn/lane constraints、reroute cost；
  • Passenger：walking distance、wheelchair access、lighting、weather、correct side；
  • Operations：dwell time、blocking probability、pickup/drop-off congestion。

Multi-objective 可表示：

\[ Score(c)=w_1 Safety+w_2 Legality+w_3 Reachability+w_4 Convenience-w_5 Disruption \]

但 Safety/Legality 先 hard filter；权重只在 feasible set 内排序。

Model / labels / feedback

Baseline 用规则 + learning-to-rank/GBDT；更复杂时用 scene encoder 预测 occupancy/risk，再由 constrained optimizer 选点。Label 来自 successful safe stops、expert review、passenger feedback 与 intervention；logged policy 有 selection bias，需保留 exploration/shadow 或 counterfactual correction。

Evaluation

Offline：candidate recall、top-k expert preference、constraint violation、calibration。Simulation：door conflict、rear-end risk、traffic disruption、walking distance、comfort。Online staged rollout：override/fallback、complaint/cancel、dwell、near-miss proxy；关键 safety slices 必须独立 gate。

19.12 Aerial Intersection Trajectory：Wxxxx 与其它车辆如何比较

不能直接把不同路口的 global (x,y) 混在一起。先把轨迹投影到 lane/Frenet 或 intersection-relative coordinate，按 maneuver（left/right/straight）、entry/exit lane、signal phase、vehicle type、speed/traffic/weather 对齐，并重采样到统一 time/progress grid。

不要武断假设单一 Gaussian

Trajectory 是多模态 sequence；不同 maneuver/driver style 常是 mixture。先可视化与检验，再选择：

  • functional summary：speed、accel、jerk、curvature、turn radius、lane offset、TTC；
  • pointwise/sequence distance：ADE/FDE、Fréchet/DTW；
  • distribution distance：energy distance、MMD、Wasserstein；
  • conditional model / hierarchical model：控制 traffic 与 intersection effect。

核心 estimand 可以是：在相同 context 下，Wxxxx trajectory 与 human/reference fleet 的 conditional mean/distribution 是否有差异：

\[ y_{ij}=\beta_0+\beta_1 I(Wxxxx)+\beta_2 Traffic+\beta_3 Maneuver+u_{intersection}+\epsilon_{ij} \]

u_intersection 是 intersection random effect；同一路口/同一时间窗口的车辆需 cluster-aware uncertainty。

Traffic volume 不同怎么办

  • 不比较 raw count，比较 per-vehicle/per-turn rate 或 conditional trajectory metric；
  • 对共同 covariate support 做 stratification/matching/weighting；
  • 每个 intersection 先算 effect，再用 hierarchical/meta-analysis 汇总；
  • 报告 volume-weighted 与 equal-intersection-weight 两套结果，避免大路口完全支配结论；
  • Low-volume intersection uncertainty 更大，用 partial pooling，不做过度结论。

还要明确 drone tracking error、occlusion、ID switch、map alignment 和 Wxxxx vehicle selection bias；先做 track-quality filter 与 sensitivity analysis。

19.13 Design a Planning Evaluation System

这类题不是套通用 URL shortener；面试官在看你能否定义 planning quality 与 release decision。

Scenario Registry / Log Replay / Synthetic Generator
 -> Versioned Scenario Dataset
 -> Planner Build + Config Registry
 -> Deterministic Replay + Closed-loop Simulation
 -> Metric Engine + Event Detector
 -> Slice / Regression Analysis
 -> Triage, Human Review, Release Gate

Evaluation ladder

  1. Unit/constraint tests：collision checker、rule、kinematics。
  2. Open-loop log replay：快，但会有 logged-policy bias，不能充分评价 interaction。
  3. Closed-loop simulation：ego action 影响 actor/world；可 Monte Carlo。
  4. Shadow mode：真实 perception/context，不控制车辆。
  5. Closed-course / staged on-road：最高成本，严格 safety process。

Metrics 与 scenario coverage

Safety（collision/TTC/rule violation）、progress、comfort（jerk）、human-likeness、interaction/courtesy、fallback、latency。平均值不能掩盖 rare severe regression；按 ODD、maneuver、vulnerable road user、weather、map、novelty 和 severity 切片。

Scenario registry 保存 source、map/version、initial state、actors、seed、expected invariant、tags 和 provenance。Failure mining 进入 candidate pool，但 fixed benchmark、unbiased sample 与 holdout 不能被反复调参污染。

Release decision

Candidate vs baseline paired replay；关键 safety event zero-tolerance/upper-bound gate，普通 metric 使用 confidence interval 与 practical margin。Regression 自动生成 replay artifact、trace、video、planner diff 和 owner；允许 rollback 到完整 (planner, model, map, config, scenario) generation。

19.14 100M DAU Inference System：Back-of-the-envelope、Latency、OOM

先声明假设，不要直接报 QPS。示例：100M DAU，每用户每天 10 sessions、每 session 2 次 inference，peak/average = 10：

\[ QPS_{avg}=\frac{100M\times 20}{86400}\approx 23K, \qquad QPS_{peak}\approx 230K \]

如果真实 invocation/user 或 regional peak 不同，数字线性变化。再问 request modality、input/output size、model、SLO、region、cacheability 和 personalization。

Architecture

Global DNS/LB -> Regional Gateway/Auth/Quota
 -> Request Classifier / Model Router
 -> CPU Preprocess Pool -> GPU Inference Pool
 -> Postprocess / Safety -> Cache / Response
Registry + rollout + telemetry + capacity controller

Cell architecture 限制 blast radius；按 model/version/hardware/request shape 分 pool。Interactive 与 batch/long-context 分 queue，避免 head-of-line blocking。

Memory estimate

\[ GPU\ Memory \approx Weights+KV/State+Activations+Workspace+Allocator\ Fragmentation+Headroom \]

例如 7B 参数模型仅 weights：FP16 约 14GB，INT8 约 7GB，INT4 约 3.5GB；实际还要 KV cache、activation、CUDA graph/workspace 和 10–20% operational headroom。Vision/video 模型按 input resolution/frame count 形成不同 memory bucket。

Bandwidth / capacity

单副本 throughput 必须来自代表性 batch/shape benchmark：

\[ Replicas \ge \frac{PeakQPS\times ServiceTime}{TargetConcurrency\times UtilizationTarget} \]

再乘 failure/zone headroom。网络还要算 input/output bytes × peak QPS；不要忽略 image/video upload 与 cross-zone feature fetch。

Latency optimization

  • 分解 queue、preprocess、H2D、kernel、collective、postprocess；
  • dynamic batching + bounded max wait；shape bucketing；
  • warm replicas、local model weights、zero-copy/pinned memory；
  • quantization/distillation、cache、early exit；
  • route heavy request 到适合 GPU，small request 可共享/MIG；
  • autoscale 看 queue age、batch fullness、p95、reject/OOM，不只 GPU utilization。

OOM 防护

  • Admission control 用 estimated memory cost，不让任意 shape 进入同一 batch；
  • per-request max tokens/frames/resolution；
  • KV/state paging/eviction，bounded cache；
  • OOM 后缩小具体 bucket batch 或降级 model，不无限 retry；
  • 记录 model/version、shape、batch、free/reserved/allocated、fragmentation 和 worker generation；
  • canary 新 model/preprocess，保留旧 pool rollback。

19.15 QAT、Distillation、eval()、Contrastive Learning

QAT

Quantization-Aware Training 在训练 forward 中模拟 quantize/dequantize 与 scale/zero-point，让模型适应 rounding/clipping error。适合 PTQ quality 不够时；仍需用目标硬件 kernel 验证 latency、memory、accuracy，因为 fake quant improvement 不保证实际 backend 加速。

Distillation

Student 学 teacher 的 soft logits、representation 或 task output。Temperature-softened distribution提供 class similarity；loss 常组合 hard label 与 distillation loss。评估必须同时看质量、tail slice、calibration、latency、memory 和 cost，防止小模型只保留平均能力。

model.eval()

PyTorch eval() 切换 module behavior：Dropout disabled，BatchNorm 使用 running statistics；它不等于关闭 gradient。Inference 通常同时使用 torch.inference_mode() / no_grad()。忘记 eval 会造成 nondeterministic output 或 batch-dependent BN behavior。

Contrastive learning

正样本对靠近、负样本分开；常用 normalized embedding 与 temperature-scaled similarity。关键生产问题是 positive definition、false negatives、hard-negative mining、batch/global-negative size、modality imbalance、embedding version 和 ANN evaluation。不能只报 training loss，要看 Recall@K、retrieval slices、hubness 与 downstream utility。

19.16 Kernel Optimization：Memory Layout、Fusion、Roofline

回答顺序：先 profile，再判断 memory-bound 还是 compute-bound，不要一上来手写 CUDA。

  • Roofline：算 arithmetic intensity = FLOPs / bytes；低 intensity 优先减少 memory traffic，高 intensity 才看 tensor-core utilization。
  • Layout：连续/coalesced access、正确 stride、减少 transpose；根据 operator chain 选 NHWC/NCHW 或 packed layout。
  • Fusion：把 elementwise、bias、activation、normalization 等合并，减少 launch 和 global-memory round trip；但过度 fusion 会增加 register pressure、降低 occupancy、难以复用。
  • Tiling/shared memory：提高 reuse，同时检查 bank conflict、register spill、occupancy。
  • Vectorized load、aligned memory、pinned H2D、async copy/overlap。
  • Mixed precision / tensor cores 需要 shape/alignment 与数值稳定；保留 accumulation precision 和 tolerance test。
  • 验证用 representative shapes、warmup、p50/p95、end-to-end latency；microbenchmark 快不代表 pipeline 快。

19.17 Model Monitoring：Data Quality、Drift、Alert、Time-series Backend

监控分四层：

层指标
Data qualityschema、missing/empty、range、duplicate、freshness、join coverage、label delay
DriftPSI、KS/JS、embedding centroid/MMD、category distribution、slice volume
Modelscore/confidence、calibration、abstention、quality proxy、delayed ground truth
System/businessQPS、p95/p99、error/OOM、queue age、GPU、cost、intervention/complaint

PSI 示例：

\[ PSI=\sum_i (p_i-q_i)\ln\frac{p_i}{q_i} \]

PSI 依赖 binning 和样本量，不能把固定阈值当普适真理。Drift 不等于 performance degradation；还要与 label/outcome、slice 和 upstream change correlation。

Backend

  • Prometheus-compatible TSDB：operational metrics、低延迟 alert；
  • Long-term metrics store / warehouse：高 cardinality、历史分析；
  • Object/lake：raw sampled distributions、embedding sketch、replay artifact；
  • Trace/log：request/model/data generation 与 reason code。

禁止把 user ID、raw prompt、raw frame 当 metric label，避免 PII 与 cardinality explosion。使用 bounded dimensions：model/version/region/slice/error code。

Alert design

Alert 基于 SLO burn rate、sustained window 和 minimum traffic，结合 absolute + relative change；critical safety/data loss fast alert，slow drift走 investigation。每个 alert 必须有 owner、runbook、dashboard、recent deployment/data-version link、silence/expiry。监控 alert precision/recall，避免长期噪声被忽略。

19.18 Behavioral：Policy vs Efficiency / Forest and Trees

面试官在看你能否同时守住原则和交付，不是让你回答电车难题的唯一正确答案。

回答框架：

  1. 明确不可妥协 boundary：safety、privacy、legal、data integrity。
  2. 说明 policy 的原始风险，不把流程当目的。
  3. 用 risk tier 区分高风险严格 gate 与低风险 fast path。
  4. 提出可测量的替代：automation、pre-approved template、shadow、canary、time-bounded exception。
  5. Exception 有 owner、expiry、audit、rollback；不能口头永久绕过。
  6. 用 incident/latency/quality/cost 指标复盘，必要时推动 policy 本身升级。

可直接说：

“我不会为了速度绕过 safety boundary，也不会把所有 workload 都放进最重流程。我先解释 policy 防的具体 failure，然后按 blast radius 分级：高风险 model/data change保留 independent review 与 staged rollout；低风险配置通过 schema validation、automated test 和 pre-approved guardrail self-service。若业务必须临时例外，必须有 owner、expiry、monitoring 和 rollback。这样 policy 保护的是 invariant，而不是制造无差别 friction。”

Forest 是业务结果、风险、组织接口和长期平台方向；trees 是你亲自解决的 bug、contract、metric 和 rollout。Senior Staff 回答必须在两层之间来回：先给 decision，再用一个 implementation/failure example 证明不是空话。

19.19 怎样把你的背景对齐 Simulation / Evaluation / Metrics / Data Infra

如果被问 “为什么你适合 Wxxxx/Xpxxx-like team”，不要声称做过未做过的 planning algorithm。用可迁移 evidence：

“我的直接优势是 large-scale data + evaluation infrastructure，而不是假装自己已经是 planning researcher。我做过 50B+ multimodal data/retrieval、100B+/day real-time production system、batch + streaming pipeline、anomaly/metrics、shared CPU/GPU execution 和 versioned rollout。这些经验可以直接迁移到 scenario registry、simulation replay、evaluation slices、model comparison、failure mining 和 data flywheel。Domain-specific planning metric 我会与 domain expert共同定义，但 dataset/version/lineage、paired experiment、failure recovery、capacity 和 release gate 是我能立即负责的部分。”

团队优先级可以明确表达：Simulation / Evaluation / Metrics / Data Infra 最匹配；In-vehicle experience / trip platform 也可从 low-latency inference、event platform、monitoring、privacy 和 rollout 切入。
