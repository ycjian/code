9. Project Deep Dive 3：100B+/day Bidding（只作 Reliability 备选）

不要主动展开，除非被问超高吞吐、实时系统、graceful degradation 或早期经历。

9.1 60 秒版本

“在 Amazon Sizmek，我设计并部署实时 AI bidding system，每日处理 100B+ opportunities。系统把 streaming feature、model inference 和 bid decision 放在严格 latency budget 下。我负责 end-to-end ML pipeline，包括 feature engineering、training、serving 和 online inference；通过实际的 pipeline/serving 优化，把 prediction latency 降低约 30%，throughput 提升约 30%。这段经历训练了我在 peak load、backpressure、feature freshness、fallback、online/offline consistency 和 production observability 上的判断。”

9.2 被追问时按这一棵树回答

  • Latency：先分 network、feature fetch、serialization、inference、decision；讲真实最大项和优化。
  • Throughput：batch/vectorization、cache、async I/O、horizontal scale 中哪些是真实措施。
  • Freshness：event time、late event、online/offline feature parity。
  • Failure：model timeout、feature miss、dependency fail 的真实 fallback。
  • Correctness：budget/state 更新是否需要强一致，如何避免 duplicate spend [按真实架构]。
  • Rollout：shadow/canary/A-B/rollback 中实际使用的机制。

9.3 必须防守的数字

  • 100B+ 是 daily opportunities，不要不经计算直接说成系统 QPS。
  • 平均约为 100B / 86400 ≈ 1.16M events/s，但这只是数学平均，不是实际 peak QPS，也不代表每条都由同一 service 处理。
  • 30% latency 和 30% throughput 必须能解释 measurement baseline、具体 change 和验证方法；答不出时数字会反噬 credibility。
