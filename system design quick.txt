# System Design Quick Notes

这份笔记的目标不是背概念，而是把系统设计面试里最容易被追问的点整理成可以直接说出口的答案。中文解释为主，保留常用 English keywords，方便你在面试中快速切换。

---

## 0. 面试沟通原则

优秀的系统设计候选人不只是知道很多概念，而是能快速抓住问题核心，用简洁语言说明取舍。

### 不要过度解释

如果是入门级概念，除非面试官主动问，否则不要花太多时间展开。例如负载均衡器是什么、HTTP 是什么、Redis 是什么，这些可以点到为止。

### 要做决定，不要只列选项

面试官想看到你如何做 trade-off，而不是只听你列出 3 个方案。

好的表达：

> 我这里选择 Postgres，因为需要 transaction、durability 和跨表一致性。当前规模下它不会成为瓶颈；如果写入规模继续增长，可以再讨论 sharding 或 async pipeline。

坏的表达：

> 可以用 Postgres，也可以用 DynamoDB，也可以用 Cassandra，也可以用 Kafka。

### 推荐回答结构

1. 先明确 core requirement。
2. 给出一个默认方案。
3. 说明为什么选它。
4. 主动标记 trade-off。
5. 如果有风险，再说后续如何扩展。

## 1. 全球聊天系统：类似 WhatsApp

### 核心问题

全球用户分布在多个 data centers。系统既要低延迟投递消息，又要保证同一个 chat 内的 message ordering。

### 高层架构

```
Client
  -> Global Load Balancer
  -> nearest Data Center
  -> Message Server
  -> Message DB / Chat Primary Shard
  -> Cross-DC Forwarding / Pub-Sub
  -> recipient Message Server
```

### 关键设计

- Global Load Balancer 把用户路由到最近的 DC。
- 每个 DC 内有多个 Message Server。
- 用 `user_id -> message_server` registry 或 consistent hashing，把用户连接固定到某个 server。
- Message Server 维护该 user/device 的 WebSocket connection。
- 每个 chat 按 `chat_id` sharding，落到某个 primary shard。
- 新消息先写入 chat 的 primary shard，再推送给其他 participant 所在的 Message Server。

### 两条 flow 要分清楚

1. DB replication flow：message 从 primary DB 同步到 replica。
2. Delivery flow：message 直接 forward 到 recipient 所在的 Message Server。

这两条 flow 是独立的。为了低延迟，不能等 DB 跨 DC replication 完成后才投递。

### 为什么需要 single writer / primary shard

如果同一个 chat 可以在多个 DC 同时写，很难保证 message ordering。更稳妥的设计是让每个 chat 有一个 primary shard，所有写入都经过它。

### 面试回答模板

> For global chat, I would separate persistence from delivery. Each chat has a primary shard to preserve ordering. The sender's Message Server writes the message to the primary shard, then forwards it to recipients' Message Servers through a global user-location registry. DB replication is for durability and recovery, while cross-DC forwarding is for low-latency delivery.

## 2. Job Scheduler / Delayed Job

### 标准方案

使用 `DynamoDB + SQS Delay Queue` 的 two-phase architecture。

### 数据模型

```
task_id
execute_at
status: PENDING / RUNNING / DONE / FAILED
retry_count
next_execute_at
payload
lease_until
```

### 两阶段执行

1. Persistent storage
   - 所有 task 先写入 DynamoDB。
   - 远期任务只存在 DynamoDB，不直接进入队列。

2. Scheduler / Watcher
   - Scheduler 每隔一小段时间扫描下一时间窗口，例如未来 2 分钟内到期的任务。
   - 把即将到期的任务投递到 SQS，并设置 Delivery Delay。

3. Near-term direct enqueue
   - 如果任务本来就在未来 2 分钟内执行，可以写 DynamoDB 的同时直接放入 SQS。

### 为什么不用 Kafka 做精确定时

Kafka 是 append-only log，只能追加在 tail，不能高效“插队”。如果 task creation time 和 schedule time 不一致，Kafka 不适合直接按任意 execute_at 做精确定时。

### SQS 的价值

- SQS Delay Queue 可以让消息在指定 delay 后才可见。
- SQS visibility timeout 可以防止多个 worker 同时处理同一条消息。
- 如果 worker crash，没有 delete message，visibility timeout 后消息会重新可见。
- SQS 通常是 at-least-once，所以 worker 必须幂等。

### Worker flow

```
Worker receives message
SQS hides message for visibility timeout
Worker processes task
If success: DeleteMessage
If crash: message becomes visible again
Another worker retries
```

### DynamoDB conditional write 抢任务

多个 worker 抢同一个 task 时，不需要显式 distributed lock，可以用 conditional write：

```sql
UPDATE task
SET status = 'RUNNING', lease_until = now + 30s
WHERE task_id = ?
  AND status = 'PENDING'
```

只有一个 worker 能成功把 `PENDING -> RUNNING`。如果 worker 超时没完成，其他 worker 可以在 `lease_until < now` 后重新抢。

### 面试回答模板

> I would store every scheduled job durably in DynamoDB, then use a watcher to enqueue near-term jobs into SQS Delay Queue. Workers process SQS messages with visibility timeout. To avoid duplicate execution, workers claim jobs using DynamoDB conditional writes, moving status from PENDING to RUNNING with a lease. Since SQS is at-least-once, job execution must be idempotent.

## 3. DynamoDB 适合什么场景

### 一句话判断

如果 access pattern 固定、主要按 key 查询或更新、QPS 高、不需要复杂 join，DynamoDB 是自然选择。

### 适合的场景

- Scheduler / Delayed Job
- Notification Job Table
- Retry Task Table
- Idempotency Key Store
- Rate Limiter Counter
- Short URL Metadata
- User Session Store
- Shopping Cart
- Order / Payment 状态表
- Workflow State Table
- Feature Flag / Config Store
- IoT Device Latest State

### 为什么适合 Scheduler

- 数据是大量小记录。
- 查询模式固定：找出 `execute_at <= now` 的任务。
- 支持 conditional write，适合 worker 抢任务。
- Managed service，高可用、自动扩容，不容易打爆主业务 DB。

### 避免全表扫描

不要让 worker 扫全表。常见设计：

```
partition_key = shard_id or time_bucket
sort_key = execute_at
```

worker 只扫描自己负责 shard / time bucket 中已经到期的任务。

## 4. Lock / Mutex / Conditional Write

### 区别

| 类型 | 控制范围 | 保护什么 |
|---|---|---|
| Mutex | 单进程 / 单机器 | 内存变量 |
| DB Lock | 多 server 共享 | 数据库记录 |
| Redis / ZooKeeper Distributed Lock | 多 server 共享 | 跨机器资源 |
| Conditional Write | 多 server 共享 | 状态转换 |

### Mutex

Mutex is an in-process lock. It protects shared memory within one process. 多台 server 不共享同一个 mutex，所以分布式系统里通常需要 DB lock、conditional write 或 distributed lock。

### Conditional write 更适合任务抢占

在 Scheduler 里，任务本身就有状态机：

```
PENDING -> RUNNING -> DONE
PENDING -> RUNNING -> FAILED -> PENDING
```

用 conditional update 抢任务通常比显式 distributed lock 更简单。

### Distributed Lock 的使用场景

适合多个服务短时间独占同一个稀缺资源：

- 抢票 seat hold
- 库存 reservation
- ride-sharing driver matching
- distributed cron
- auction bid

### Distributed Lock 注意点

- 必须有 TTL，防止 holder crash 后锁永远不释放。
- lock granularity 要小，能锁一张票就不要锁整个 event。
- 要处理 retry、deadlock、lock expiry。
- Redis Redlock 可以提，但不要说它绝对安全。

## 5. Replica Lag / Replication

如果 replica lag 太大，副本恢复后不能立刻接读流量，也不能立刻 promoted to primary。它必须先 catch up。

### 常见做法

- Primary 给每次写入一个递增的 log offset 或 sequence number。
- Replica 记录自己同步到哪里。
- Replica 恢复后从 primary 或 durable replication log 拉取 missed writes。
- 追平后才能重新加入 read traffic 或被提升为 primary。
- 如果落后太多，replication log 已经过期，就先做 snapshot restore，再继续增量追平。

### 面试回答模板

> We use async replication for low write latency, but replicas must track log offsets. After recovery, a replica first replays missed writes from the replication log. Only after it catches up should it serve reads or be promoted. If the lag is beyond log retention, we restore from snapshot and then apply incremental logs.

## 6. Index / Search / Range Query

### Index 是什么

Index 是存储系统里的目录。它把某个字段或 key 映射到数据位置，让查询不用 full table scan。

### 常见索引

- Postgres / MySQL: B+Tree index
- DynamoDB: primary key / GSI
- Elasticsearch: inverted index
- RocksDB / LevelDB: sparse index, Bloom filter
- PostGIS: geospatial index

### Trade-off

- 读更快。
- 写更慢。
- 占更多空间。
- 维护更复杂。

一句话：index 是用空间和写入成本换查询速度。

### SQL range query

例如查询 200 到 500 美元的票、某城市的演唱会、某日期范围内的酒店。Postgres 是 source of truth，可以通过 B+Tree / composite index 支持常见 range query：

```sql
CREATE INDEX idx_event_city_date_price
ON events(city, event_date, price);
```

### Elasticsearch 什么时候用

如果需要全文搜索、多字段搜索、复杂过滤、相关性排序，可以把 Postgres 的变更同步到 Elasticsearch。

推荐同步方式：

```
Postgres WAL / binlog
  -> Debezium / Canal
  -> Kafka
  -> Elasticsearch
```

注意：Elasticsearch 是 derived index，允许 eventual consistency。Postgres 仍然是 source of truth。

## 7. Sharding / Consistent Hashing

### Sharding key 怎么选

好的 shard key 应该：

- 高基数 high cardinality。
- 分布均匀，避免 hot shard。
- 符合主要查询路径。
- 方便未来扩容。

常见选择：`user_id`、`tenant_id`、`chat_id`、`order_id`。

### Hash-based sharding

```
shard = hash(key) % N
```

优点是分布均匀。缺点是节点数 N 变化时，大量 key 需要重新映射。

### Range-based sharding

适合自然按范围查询的场景，例如时间范围、tenant range。风险是热点明显，比如最新时间段可能写入特别多。

### Consistent Hashing

Consistent Hashing 用 hash ring 把 key 分配到节点。节点增删时，只需要迁移一部分 key。

关键点：

- key 和 server 都 hash 到同一个环上。
- key 顺时针找到第一个 server。
- 新增节点只接管部分 key。
- 删除节点时，它负责的 key 迁移到下一个节点。
- 使用 virtual nodes 让分布更均匀。

### 面试提醒

不要过早 sharding。先估算容量。一个调优好的单库加 read replicas 能撑过很多场景。只有数据量或写入量证明需要分片时再引入。

## 8. High Availability / Scaling

### High Availability 的核心

不要让 single point of failure 打挂整个系统。

常见手段：

1. Service / DB / cache 多副本。
2. Multi-AZ / multi-region deployment。
3. Load balancer + health check。
4. Primary-replica failover。
5. Timeout / retry with exponential backoff / circuit breaker。
6. Queue / Kafka 做缓冲。
7. Graceful degradation，让非核心功能失败时核心功能还能用。

### Read-heavy 系统怎么优化

1. Cache：Redis / Memcached 缓存热点数据。
2. Read replica：读走 replica，写走 primary。
3. CDN：静态资源、图片、视频、公开内容走边缘节点。
4. Index：避免 full table scan。
5. Pre-computation：提前计算排行榜、推荐、聚合结果。
6. Sharding：数据量太大时分散到多个节点。
7. Pagination / cursor / throttling：避免一次读取过多数据。
8. Batch read：业务允许时减少 I/O round trips。

### Write-heavy 系统怎么优化

1. 减少同步索引，index 太多会拖慢写入。
2. 用 Kafka / Pulsar / queue 先接住写流量。
3. Batch insert，减少 round trip 和 I/O。
4. 顺序写 / append-only log。
5. 按 `user_id` / `tenant_id` / `entity_id` sharding。
6. Search index、analytics、notification 异步处理。
7. 能接受 eventual consistency 的路径不要强同步。

一句话：

> Write-heavy 优化就是缩短 synchronous write path，把非核心工作异步化，用 log / queue / batch / sharding 分散和缓冲写压力。

### High connection 怎么优化

使用 connection proxy / connection pool，把大量 client connection 聚合成较少的 DB connection。

例子：

- Client 连接 proxy。
- Proxy 维护少量到 DB 的 connection。
- Non-blocking Redis commands 可以共享 connection。
- Blocking commands 如 `BLPOP` 单独使用 connection。

### Capacity Estimation 怎么做

系统设计面试里不要一上来画组件。先用粗略数字判断瓶颈在哪里。

常见估算顺序：

1. DAU / MAU。
2. QPS：平均 QPS 和 peak QPS。
3. Read/write ratio。
4. Payload size。
5. Storage growth per day。
6. Bandwidth。
7. Hot key / hot partition 风险。
8. Latency SLA。

示例：

```
10M DAU
每人每天 20 requests
daily requests = 200M
avg QPS = 200M / 86400 ~= 2300 QPS
peak QPS ~= avg * 5 to 10 = 12k ~ 23k QPS
```

面试里你不需要算得特别精确，重点是通过估算指导设计：

- 如果 peak QPS 只有几千，先别急着 sharding。
- 如果 payload 很大，bandwidth / object storage / CDN 可能更关键。
- 如果 write QPS 很高，queue、batch、partition key 更关键。
- 如果 read QPS 很高，cache、CDN、read replica 更关键。

### API Gateway / Rate Limiter

API Gateway 常见职责：

- Authentication / authorization。
- Rate limiting。
- Request validation。
- Routing。
- TLS termination。
- Logging / tracing。
- Canary / version routing。

Rate limiter 常见算法：

| 算法 | 思路 | 适合 |
|---|---|---|
| Fixed window | 每个时间窗口计数 | 简单，但边界会突刺 |
| Sliding window log | 记录每次请求时间 | 精准，但存储成本高 |
| Sliding window counter | 当前窗口 + 上一窗口加权 | 准确度和成本折中 |
| Token bucket | 按速率补 token，允许短突发 | API 限流最常见 |
| Leaky bucket | 固定速率流出 | 平滑流量 |

Token bucket 解释：

```
bucket capacity = burst size
refill rate = allowed requests per second
each request consumes 1 token
if no token -> reject or queue
```

分布式 rate limiter：

- 单机 limiter 只能保护单台 server。
- 多 API server 需要共享计数，常用 Redis。
- Redis key 可以是 `rate:{user_id}:{window}`。
- 高 QPS 下可以做 local pre-limit + global Redis limit，减少 Redis 压力。

面试回答模板：

> I would use token bucket because it supports both steady-state rate control and limited burst. For distributed API servers, I would store counters in Redis with TTL. For very high QPS, I would add a local limiter first and use Redis only for global enforcement.

### Load Shedding / Backpressure

高并发系统不能让所有请求都进入核心链路。系统快崩时，必须主动拒绝或降级。

常见信号：

- Queue length 持续增长。
- P99 latency 超 SLA。
- CPU / memory / connection pool 接近上限。
- DB connection exhausted。
- Kafka consumer lag 增长。
- GPU KV cache / memory pool 接近上限。

常见动作：

- Reject low-priority requests。
- Return `429 Too Many Requests` 或 `503 Retry-After`。
- 限制 expensive query。
- 降级非核心功能。
- 暂停 batch / offline traffic。
- 缩短 timeout，避免线程被慢依赖占满。

面试回答模板：

> I would rather shed load than let the whole system collapse. When queue length, latency, or resource utilization crosses thresholds, I would reject or degrade low-priority traffic and return retry-after. This protects core traffic and prevents cascading failure.

## 9. Kafka / Queue / Stream

### Kafka 是什么

Kafka 不是纯内存队列，而是基于磁盘的分布式 append-only commit log。

```
Producer
  -> Kafka Broker
  -> append to disk log
  -> Consumer reads by offset
```

Kafka 快的原因：

- 顺序写磁盘 append-only。
- OS page cache 缓存热数据。
- zero-copy 减少数据拷贝。
- batch 写入和 batch 读取。

### Kafka 用来解决什么

- 解耦：上游不用直接调用所有下游。
- 削峰填谷：突发流量先进 Kafka。
- 可靠事件日志：consumer 失败后从 offset 继续。
- 异步处理：notification、search indexing、analytics。
- CDC：DB change log 同步到 cache、ES、warehouse。

### Kafka 和 Queue 的区别

Queue 更像任务队列，消息被消费后通常删除或不可见。Kafka 是 event log，消息保留一段时间，consumer 通过 offset 记录消费位置，可以 replay。

### Kafka 核心概念

```
Producer -> Topic -> Partition -> Broker -> Consumer Group -> Consumer
```

- Partition 是扩展吞吐的核心。
- Kafka 只保证同一个 partition 内有序，不保证整个 topic 全局有序。
- 如果 order events 需要有序，partition key 应该用 `order_id`。
- 同一个 consumer group 内，一个 partition 同一时间只能被一个 consumer 消费。
- Consumer 数量的有效上限是 partition 数。

### Consumer 处理顺序

如果 Kafka 用来发 notification：

1. Consume Kafka message。
2. Call provider。
3. 把结果写 DB：`DELIVERED / FAILED / RETRYING`。
4. Commit Kafka offset。

不要先 commit offset 再写 DB。否则 provider 成功但 worker crash 后，系统不知道发送结果。

### 如何保证消息不丢

- Producer 开启 ack / retry。
- Kafka replication。
- Consumer 先持久化处理结果，再 commit offset。
- 对 DB -> Kafka 的可靠发布，用 outbox pattern。

### 如何处理重复消息

Kafka 常见语义是 at-least-once，所以重复消息很正常。

解决：

- 每条消息带 `event_id`。
- Consumer 处理前检查是否已处理。
- DB 加 unique constraint：`event_id` 或 `order_id + event_type`。
- 业务逻辑必须 idempotent。

### 如何处理消费慢

- 增加 partition 数。
- 增加 consumer 数。
- 优化单条消息处理逻辑。
- Batch consume / batch write。
- 下游 DB 压力大时加限流、缓冲、降级。
- 监控 consumer lag。

核心指标：

```
consumer lag = latest offset - committed offset
```

如果 lag 持续增长，说明消费速度跟不上生产速度。

### Stream vs Queue

Stream 是事件日志，能保留、重放、多 consumer group，适合 realtime analytics、event sourcing、pub/sub。Queue 更像任务分发，适合每个 task 被一个 worker 消费。

### Backpressure 怎么设计

Backpressure 的意思是：下游处理不过来时，上游必须感知并放慢速度，否则队列、内存、连接都会被打爆。

常见做法：

1. Bounded queue
   - 队列必须有上限。
   - 超过上限后 reject、drop low-priority、或者返回 retry-after。

2. Consumer lag based throttling
   - 如果 Kafka consumer lag 持续增长，说明下游处理不过来。
   - 上游 producer 降速，或者暂停非核心事件。

3. Per-tenant quota
   - 防止一个 tenant 把 shared queue 塞满。

4. Priority queue
   - 支付、订单、告警优先。
   - analytics、email digest、batch job 可以延后。

5. Circuit breaker
   - 下游不健康时，不继续同步调用。
   - 请求进入 queue 或直接 fail fast。

面试回答模板：

> I would make queues bounded and use consumer lag as a feedback signal. If lag grows beyond a threshold, the producer should throttle or shed low-priority traffic. Without backpressure, the system only moves the failure from one service to the queue or database.

### Retry / DLQ / Poison Message

Retry 不是无限重试。无限重试会放大故障。

标准策略：

- Retry with exponential backoff。
- 加 jitter，避免所有请求同时重试。
- 最大重试次数。
- 超过次数进入 DLQ。
- DLQ 需要 dashboard、alert、replay tool。

Poison message 是指某条消息永远处理失败，例如 payload 格式坏了或业务状态非法。必须识别并移到 DLQ，否则会卡住 consumer。

面试回答模板：

> I would use bounded retries with exponential backoff and jitter. After max retries, the message goes to DLQ with enough metadata for debugging and replay. This prevents poison messages from blocking the whole consumer group.

## 10. Transactional Outbox / Dual Write

### 问题

如果系统先写 DB，再 publish Kafka，中间 crash，会出现：

```
DB 已经写入成功
Kafka 没有消息
下游永远不知道这次变更
```

### Outbox pattern

在同一个 DB transaction 中同时写业务数据和 outbox event：

```sql
BEGIN;

UPDATE booking
SET status = 'CANCELLED'
WHERE booking_id = 123;

INSERT INTO outbox(event_type, payload, status)
VALUES ('CancellationAvailableEvent', '{"booking_id":123}', 'PENDING');

COMMIT;
```

之后由 relay / CDC publisher 读取 outbox，发布到 Kafka，成功后标记 sent。

### CDC 发布方式

```
DB WAL / binlog
  -> Debezium / Canal
  -> Kafka
  -> Consumers
```

优点：延迟低，不需要业务服务轮询 DB。缺点：引入额外基础设施。

### Dual write 迁移原则

不要裸 dual write。更安全的方式是：

- Single source of truth + outbox/event log。
- 下游写入必须 idempotent。
- 失败进入 retry / DLQ。
- 定期 reconciliation。
- 新系统先 shadow write / shadow read compare。
- 用 percentage / user_id / region 灰度切流量。
- 保留 kill switch。
- Schema 要 backward-compatible。

### Saga Pattern

Saga 用来处理跨多个服务的 long-running transaction。它不用一个大 distributed transaction 锁住所有资源，而是把流程拆成多个本地 transaction，每一步都有 compensating action。

例子：下单流程

```
Create Order
  -> Reserve Inventory
  -> Authorize Payment
  -> Create Shipment
  -> Confirm Order
```

如果 `Authorize Payment` 失败，就执行补偿：

```
Release Inventory
Cancel Order
```

两种 Saga：

1. Orchestration
   - 有一个 central orchestrator。
   - 它决定下一步调用哪个 service。
   - 好处是流程清晰、易 debug。
   - 缺点是 orchestrator 变成复杂中心。

2. Choreography
   - 每个 service 通过 events 驱动下一步。
   - 好处是解耦。
   - 缺点是流程分散，debug 更难。

面试回答模板：

> For cross-service workflows, I would avoid distributed transactions unless absolutely required. I would use Saga: each service commits a local transaction and emits an event. If a later step fails, we trigger compensating actions. For complex payment or booking flows, I prefer orchestration because it is easier to reason about and debug.

### Reconciliation / 对账

只靠 online transaction 不够。支付、库存、订单系统都需要 reconciliation。

为什么：

- Webhook 可能延迟或重复。
- Provider 状态和本地状态可能不一致。
- Kafka / worker 可能失败后进入 DLQ。
- 人工退款、chargeback、取消订单可能绕过主流程。

常见设计：

```
Internal transaction log
External provider report
Immutable audit log in S3
Reconciliation job
Mismatch table
Auto repair or manual review
```

面试回答模板：

> For financial correctness, I would not rely only on the online request path. I would keep an immutable event/audit log and run reconciliation jobs against the payment provider. Any mismatch goes to an exception table for auto-retry or manual review.

## 11. Stateless Server / Multi-region

### Stateless server

API server 不依赖本机内存状态处理请求。用户第一次请求到 Server 1，第二次到 Server 3，也应该都能处理。

```
Client
  -> Load Balancer
  -> API Server 1 / 2 / 3
  -> Shared DB / Cache / Session Store
```

### 为什么重要

- 可以随意水平扩容。
- Load Balancer 不需要 sticky session。
- 单台 server 挂了不会丢用户状态。

### Multi-region 用户数据

常见方案：每个 user 有 home region。写入落在 home region，其他 region 有 async replica，用于就近读、灾备或 failover。

### 全球共享资源

如果是只读内容，可以每个 DC 都有 replica，并使用 CDN。

如果是全球用户都要写同一个有限资源，比如 inventory / ticket / booking，需要更谨慎：

1. Single writer region：所有写入集中到一个 DC，强一致但远端 latency 高。
2. Regional allocation：提前把库存分配到不同 region。
3. Kafka single partition：同一个 resource 的请求进同一个 partition，天然有序。
4. Global transaction DB：Spanner / CockroachDB，强一致但 latency 和成本高。

## 12. Atomicity / Concurrency Control

### Atomic 是什么

Atomic = 原子性。一个操作要么完整成功，要么完全不发生，中间不会被别人打断，也不会只执行一半。

### 扣库存示例

不要先读再写：

```python
if stock > 0:
    stock = stock - 1
```

更好的方式是让 DB 原子完成：

```sql
UPDATE inventory
SET stock = stock - 1
WHERE product_id = 123
  AND stock > 0;
```

如果 update 1 row，说明扣减成功。如果 update 0 row，说明库存没了。

### Optimistic concurrency

适合读多写少、冲突不频繁的场景。每条记录带 version：

```sql
UPDATE jobs
SET cron = 'every 10 min', version = version + 1
WHERE job_id = 123
  AND version = 7;
```

如果 version 已经变了，更新失败，返回 `409 Conflict`。

### 写多冲突多怎么办

1. Pessimistic locking

```sql
SELECT *
FROM inventory
WHERE product_id = 123
FOR UPDATE;
```

适合库存、账户余额、订单状态流转。缺点是吞吐下降。

2. Atomic update

用一条 SQL 完成条件检查和更新。

3. Single writer / queue

```
requests
  -> Kafka partition by product_id
  -> single consumer
  -> update stock
```

4. Reduce contention

把热点拆成多个 bucket。例如库存 10,000 个，不要所有请求更新同一行，可以拆成多个 inventory bucket。

5. Serializable transaction

金融账本、结算等严格正确场景可以使用 transaction + serializable isolation，但成本更高。

## 13. Cache / TTL / Dirty Cache / Stampede

### TTL 如何实现

常见两种机制：

1. Lazy delete：读取时检查 `expire_at`，如果已过期就删除。
2. Periodic cleanup：后台线程定期扫描并删除过期数据。

### Cache Aside

读路径：

```
read cache
if hit: return
if miss: read DB -> set cache with TTL -> return
```

写路径推荐：

```
update DB
delete cache
```

不要直接 update cache，因为并发写容易乱序导致 dirty cache：

```
T1: DB = A
T2: DB = B
T2: cache = B
T1: cache = A
```

最后 DB 是 B，但 cache 是 A。

### Cache stampede / invalidation storm

热门抢票系统中，如果每次 seat 状态变化都 invalidate cache，缓存和 DB 会被打爆。

更好的设计：

1. Static data 和 dynamic data 分离。
   - Static：演唱会名字、时间、海报，长 TTL。
   - Dynamic：座位状态、剩余票数，单独处理。

2. 放弃逐条实时 invalidation。
   - Booking service 把 seat change 写 MQ。
   - Background aggregator 每 1 到 3 秒批量更新 Redis。

3. 接受读路径 eventual consistency。
   - 用户可能看到旧座位状态。
   - 但写路径用 Redis `SET NX` 或 DB atomic update 保证不会超卖。

## 14. Exactly-once Effect / Idempotency

### 不要轻易说 exactly-once delivery

分布式系统中，network timeout、retry、crash、ack 丢失都会导致重复。

更准确的目标是 exactly-once effect：

> 请求或消息可以重复，但业务结果只能生效一次。

### API 幂等

客户端带 idempotency key：

```http
POST /payments
Idempotency-Key: abc123
```

服务端保存：

```
idempotency_key -> request_hash, status, response
```

同一个 key 再来时直接返回上次结果。如果 key 相同但 request body 不同，应该 reject。

### DB 幂等

使用 unique constraint：

```sql
UNIQUE(idempotency_key)
UNIQUE(order_id, operation_type)
```

### 消息幂等

每条消息带 `event_id`。Consumer 处理前把 `event_id` 插入 `processed_events` 表，表上有 unique index。业务更新和 processed event 写入要在同一个 transaction。

### 状态机条件更新

例如订单只能：

```
PENDING -> PAID
```

用 conditional update：

```sql
UPDATE orders
SET status = 'PAID'
WHERE order_id = ?
  AND status = 'PENDING';
```

第二次执行时不会重复扣款。

## 15. CAP / Consistency

CAP 说的是：在分布式系统遇到 network partition 时，Consistency、Availability、Partition tolerance 不能同时完全满足。

### 三个概念

- Consistency：所有节点读到的数据像来自同一个最新副本。
- Availability：每个请求都能收到非错误响应，即使结果可能不是最新。
- Partition tolerance：节点之间网络断开或消息丢失时，系统仍能运行。

现实中 P 基本必须接受，所以真正取舍是 partition 发生时选 CP 还是 AP。

### CP

优先 consistency。网络分区时可能拒绝部分请求。

适合：

- 金融转账
- 库存扣减
- 预订有限资源

### AP

优先 availability。网络分区时继续服务，但可能返回旧数据。

适合：

- 社交 feed
- 点赞数
- 浏览量
- 缓存

### 面试回答模板

> For money, inventory, and booking limited resources, I would favor consistency even if it reduces availability. For feeds, likes, and cached views, eventual consistency is usually acceptable because user experience benefits more from availability and low latency.

## 16. Realtime Communication

### Long Polling / SSE / WebSocket

| 方式 | 通信方向 | 怎么工作 | 适合场景 |
|---|---|---|---|
| Long Polling | server -> client | Client 发请求，server 等到有消息才返回，返回后 client 再发下一个请求 | 低频通知、老系统兼容 |
| SSE | server -> client 单向 | Client 建一个 HTTP 连接，server 持续推送 | 通知、状态更新、AI streaming |
| WebSocket | 双向 | 建立长连接，双方都能随时发消息 | 聊天、游戏、协同编辑 |

### 面试回答模板

> If the server only needs to push updates, I would use SSE. If both client and server need bidirectional realtime communication, I would use WebSocket. Long polling is mostly a fallback for compatibility.

## 17. Ticketmaster / Seat Reservation

### 查询 API

```http
GET /events/{eventId}
```

返回 event、venue、artist、seat map / ticket info。

```http
GET /events/search?keyword={keyword}&start={start_date}&end={end_date}&pageSize={page_size}&page={page}
```

返回 event list。

### 订票 API

```http
POST /bookings/{eventId}
```

Request:

```json
{
  "ticketIds": ["seat-1", "seat-2"]
}
```

Response:

```json
{
  "bookingId": "booking_123",
  "paymentIntent": "pi_123"
}
```

后端先创建 payment intent，前端再用 payment provider SDK / hosted fields 完成支付。不要自己保存原始卡号。

### Seat hold

使用 Redis `SET NX EX` 做短时间 reservation：

```redis
SET seat:123 user_123 EX 600 NX
```

- `NX` 保证只有第一个人能 hold 成功。
- `EX 600` 表示 10 分钟后自动释放。
- 支付成功后，真正写入 Postgres order / booking。

### 多座位原子 hold

如果用户一次买多个座位，不能用普通 for-loop，因为可能部分成功、部分失败。

使用 Redis Lua script：

1. 预检所有 `seat_id` 是否已存在。
2. 如果任意一个已存在，返回失败。
3. 如果全部可用，一次性为所有 seat 写入 hold key。

Redis 执行 Lua script 时是原子的，脚本执行期间不会插入其他命令。

### 搜索与座位状态

- Search listing 可以 eventual consistency，用 Elasticsearch / cache。
- Booking / reservation 必须强一致，使用 unique key、Redis atomic operation 或 DB transaction。

## 18. Airbnb Reservation

### 最简单的数据模型

一个 listing 的一天一行：

```
ReservationNight(listing_id, date, reservation_id, state)
UNIQUE(listing_id, date)
```

这样同一个 listing 同一天只能被一个 reservation 占用。

### Booking flow

1. Search 走 eventually consistent index。
2. Reserve / hold 使用 transaction 或 unique constraint。
3. Payment 使用 `reservation_id` 或 `idempotency_key` 保证幂等。
4. Confirm reservation 后写 outbox event。

### Reservation confirmed 的 outbox

```sql
BEGIN;

UPDATE reservation
SET status = 'CONFIRMED'
WHERE reservation_id = ?;

UPDATE reservation_night
SET state = 'BOOKED'
WHERE reservation_id = ?;

INSERT INTO outbox(event_type, aggregate_id, payload, status)
VALUES ('ReservationConfirmed', ?, ?, 'PENDING');

COMMIT;
```

如果 service crash，outbox event 仍然存在，后续 worker 可以继续发布 notification、email、analytics、search index update。

### Cancellation -> Waitlist

不要在 Booking Service cancel 成功后直接同步 call Waitlist Service。更可靠的做法：

```
Booking Service updates booking / inventory transactionally
Booking Service writes CancellationAvailableEvent to outbox
Outbox publishes to Kafka
Waitlist Matcher consumes event
```

关键点：cancellation event 不能丢。

## 19. Payment System

### Non-functional requirements

- Security。
- Transaction safety and financial integrity。
- Strong durability，不能丢交易。
- No double charge。
- High consistency。
- 可扩展到高 TPS，例如 10k TPS。
- Auditability / reconciliation。

### Payment API

Create payment intent:

```http
POST /payment-intents
```

```json
{
  "amountInCents": 2499,
  "currency": "usd",
  "description": "Order #1234"
}
```

Process payment:

```http
POST /payment-intents/{paymentIntentId}/transactions
```

实际生产中，前端通常使用 provider SDK / hosted fields 收集卡信息。Merchant backend 不保存原始卡号，只保存 token / paymentMethodId。

Check status:

```http
GET /payment-intents/{paymentIntentId}
```

也可以通过 webhook 接收 provider 的异步状态更新。

### Card security

更安全的表达：

> The browser uses the payment provider's official SDK or hosted fields. Card details are encrypted or tokenized by the provider before reaching our backend. Our backend stores only tokenized payment method IDs, not raw card numbers. Provider-side private keys are protected by HSM.

### Merchant request signing

为了确认是真实 merchant 在请求付款，使用 `API key + request signing`。

Merchant 拿到：

- Public API key：标识 merchant。
- Secret key：生成 HMAC signature，不能泄露。

每次请求签名：

```
signature = HMAC(secret, method + path + body + timestamp + nonce)
```

服务端校验：

1. 根据 API key 找到 merchant。
2. 用保存的 secret key 重新计算 HMAC。
3. 比较 signature。
4. 检查 timestamp 是否在允许窗口内。
5. 检查 nonce 是否用过，防 replay attack。

不需要 unhash。HMAC 的验证方式是服务端用同样输入再算一遍，然后比较结果。

### Payment audit

交易状态会不断更新，只看主 DB 可能只看到最新值。为了 audit：

```
DB transaction log / WAL
  -> Kafka
  -> S3 / data lake immutable log
  -> reconciliation with external provider
```

Kafka partition key 建议用 `payment_id`，避免用 `merchant_id` 或 `customer_id` 造成 hot partition。

## 20. Webhook

### Webhook 是什么

Webhook 是事件驱动的 HTTP callback。别人系统发生事件后，主动 call 你的 API 通知你。

传统 API polling：

> 你一直问：好了没？

Webhook：

> 你告诉对方：好了就 call 这个 URL。

### 支付为什么需要 webhook

支付是异步过程。Provider 可能需要银行清算、风控、3D Secure。你的 server 不应该一直等待，也不应该每秒轮询。

标准流程：

1. 用户在前端发起支付。
2. Provider 处理支付。
3. Provider 主动 POST 到你的 webhook endpoint。
4. 你的系统验证签名。
5. 幂等更新订单状态。

### Webhook 三个高频追问

#### 1. 如何防止假通知

使用 signature verification。Provider 在 header 中带签名，你用 webhook secret 重新计算并比较。

#### 2. 通知丢了或重复怎么办

- Provider 没收到 `200 OK` 会 retry。
- 你的 webhook handler 必须 idempotent。
- 处理前检查 `event_id` 或 `payment_id` 是否处理过。
- 如果已处理，直接返回 200。

#### 3. 乱序到达怎么办

使用 state machine control、timestamp、version 或 conditional update，防止旧事件覆盖新状态。

例如：

```sql
UPDATE payment
SET status = 'SUCCEEDED'
WHERE payment_id = ?
  AND status = 'PENDING';
```

## 21. Dependency Failure / Provider Isolation

### 下游 dependency 有问题怎么办

1. Timeout。
2. Exponential backoff retry。
3. Failover to backup service。
4. Circuit breaker：下游明显不健康时停止调用。
5. Queue buffering：消息留在队列中，等下游恢复。
6. Monitoring / alerting。
7. DLQ：超过最大重试次数后进入 Dead Letter Queue。

### Provider-specific concurrency isolation

例如 notification system 同时接 Twilio、SendGrid、Firebase。Twilio 变慢时，不能耗尽所有 worker。

做法：

- 为每个 provider 建 dedicated worker pool / semaphore。
- Twilio 最多占用自己的并发额度。
- SendGrid / Firebase 不受影响。
- 这个限制要应用到所有 Twilio traffic，包括 critical alerts 和 marketing messages。
- 达到并发限制时 fail fast，放回 retry queue 或 DLQ，不要阻塞 worker。

### Notification System

高频题：设计 push / email / SMS notification system。

核心 requirements：

- 支持多 channel：push、email、SMS。
- 支持 priority：critical alert、transactional、marketing。
- 可靠投递，不能丢关键通知。
- 幂等，不能重复发。
- Provider failure isolation。
- 用户 preference / unsubscribe。
- Rate limit，防止 spam。

高层架构：

```
Producer services
  -> Notification API
  -> Notification DB(status=PENDING)
  -> Outbox / Kafka
  -> Channel workers
  -> Provider adapters
  -> Delivery status table
  -> Webhook from providers
```

关键设计：

- API 层先写 notification record 和 outbox event。
- Kafka 按 `notification_id` 或 `user_id` partition。
- Worker 发送前检查 sent-state idempotency key。
- Provider 返回成功后写 `DELIVERED`。
- 失败后 retry with backoff，超过次数进 DLQ。
- Twilio / SendGrid / Firebase 各自独立 worker pool。
- Provider webhook 更新最终状态。

面试回答模板：

> I would make notification delivery asynchronous. The request path only writes a durable notification record and an outbox event. Workers consume Kafka, send through provider-specific adapters, persist delivery status before committing offset, and use idempotency keys to avoid duplicate sends. Each provider has an isolated worker pool so a slow SMS provider cannot block email or push.

### News Feed / Timeline

高频题：设计 Twitter / Instagram feed。

核心问题：

- Fanout on write 还是 fanout on read。
- Celebrity user 热点。
- Feed freshness。
- Ranking。
- Cache。

Fanout on write：

```
User posts
  -> write post
  -> fanout to followers' feed inbox
```

优点：

- 读 feed 很快。
- 适合普通用户。

缺点：

- celebrity 有几千万 followers，写入爆炸。

Fanout on read：

```
User opens feed
  -> fetch recent posts from followed users
  -> merge/rank
```

优点：

- 发帖轻。
- 适合 celebrity。

缺点：

- 读 feed 慢，merge 成本高。

混合方案：

- 普通用户 fanout on write。
- Celebrity 不 fanout，读 feed 时单独拉取并 merge。
- Feed inbox 存 post_id，不存完整 post。
- Ranking service 根据 recency、engagement、relationship score 排序。

面试回答模板：

> I would use a hybrid fanout model. For normal users, fanout-on-write gives fast feed reads. For celebrities, I would avoid pushing to every follower and instead merge their recent posts at read time. The feed inbox stores post IDs, and the read path hydrates post details from cache or post service.

### Search / Autocomplete

搜索系统常见 requirements：

- Full-text search。
- Prefix autocomplete。
- Typo tolerance。
- Filtering / sorting。
- Near real-time index update。
- 高 QPS、低 latency。

高层架构：

```
Write path:
  DB source of truth
  -> CDC / outbox
  -> Kafka
  -> Indexer
  -> Elasticsearch / OpenSearch

Read path:
  API
  -> Search service
  -> Search index
  -> hydrate details from DB/cache if needed
```

Autocomplete 设计：

- Trie 适合内存小规模 prefix。
- Elasticsearch completion suggester / edge n-gram 适合生产搜索。
- 热门 query 可以 cache。
- 搜索结果允许 eventual consistency。

注意：

- Search index 不是 source of truth。
- DB update 到 search index 会有 lag。
- 删除和权限变化要小心，避免搜索泄漏。

面试回答模板：

> I would keep the primary database as source of truth and build Elasticsearch as a derived index through CDC or outbox. Search reads from the index for low latency, then hydrates details from cache or DB. I would accept slight index lag for search, but handle deletes and permission changes carefully.

### File Upload / Media Processing

高频题：设计图片 / 视频上传系统。

核心要求：

- 大文件上传。
- 断点续传。
- 病毒扫描 / 内容审核。
- 转码 / thumbnail。
- CDN 分发。
- 元数据管理。

推荐流程：

```
Client asks API for upload URL
API returns pre-signed URL
Client uploads directly to object storage
Storage event -> Kafka / queue
Media worker processes file
  -> validate
  -> transcode
  -> thumbnail
  -> metadata update
  -> CDN available
```

为什么 client 直接传 object storage：

- 避免大文件经过 API server。
- API server 不被 bandwidth 打爆。
- Object storage 更适合大文件和 multipart upload。

状态机：

```
INITIATED -> UPLOADING -> UPLOADED -> PROCESSING -> READY
                                  -> FAILED
```

面试回答模板：

> I would not proxy large files through the application server. The API returns a pre-signed upload URL, and the client uploads directly to object storage. A storage event triggers an async media pipeline for validation, transcoding, thumbnails, and metadata update. The final artifact is served through CDN.

## 22. Classic System Design Question Bank

这一节来自 `sd_pages` 里的 noisy system design pages。不要背原文；面试里要按固定结构讲：需求、核心难点、架构、数据模型、扩展性、failure mode、trade-off。

每道题都用这个模板：

1. Clarify requirements。
2. Estimate scale。
3. Define APIs。
4. Pick storage / cache / queue。
5. Explain critical path。
6. Call out bottleneck and trade-off。
7. Give one senior-level deep dive。

### 1. Design a URL Shortener Like Bit.ly

#### Question

设计一个 URL shortener，用户提交 long URL，系统返回 short URL。访问 short URL 时重定向到 long URL。需要高可用、低延迟、支持 analytics。

#### Approach

这题核心不是“生成一个短码”，而是：

- 如何生成 unique short code。
- Redirect path 如何做到极低 latency。
- Custom alias 怎么处理冲突。
- Analytics 是否同步写入。
- Abuse / malicious URL 怎么防。

#### API

```http
POST /urls
{
  "longUrl": "https://example.com/a/b/c",
  "customAlias": "optional"
}
-> { "shortUrl": "https://sho.rt/abc123" }

GET /{code}
-> 301/302 redirect
```

#### Data model

```
UrlMapping(
  code,
  long_url,
  user_id,
  created_at,
  expire_at,
  status
)

ClickEvent(
  code,
  timestamp,
  ip_hash,
  user_agent,
  referrer
)
```

#### Code generation

常见方案：

1. Auto-increment id + Base62
   - 简单、短、唯一。
   - 但容易暴露增长趋势。

2. Random Base62
   - 不暴露顺序。
   - 需要 collision check。

3. Snowflake id + Base62
   - 分布式生成，不依赖单 DB sequence。

面试里推荐：

> For simplicity and scale, I would generate a unique numeric id using a distributed ID generator, then encode it using Base62. Custom aliases go through a uniqueness check.

#### Read path

Redirect 是核心高 QPS path：

```
Client -> CDN/Edge optional -> Redirect Service -> Redis cache -> DB fallback -> 301/302
```

- Hot code 放 Redis。
- DB 是 source of truth。
- Analytics event 异步写 Kafka，不阻塞 redirect。

#### 301 vs 302

- `301 permanent redirect`：浏览器/CDN 可能缓存，性能好，但后续修改 long URL 不方便。
- `302 temporary redirect`：每次都回源，更灵活，analytics 更完整。

面试里可以说：默认用 302 支持 analytics 和可变 mapping；对永久短链可以用 301。

#### Bottlenecks

- Hot URL 被大量访问：cache + CDN。
- DB read pressure：Redis read-through。
- Analytics 写入量大：Kafka async event pipeline。
- Abuse：URL scanning, domain blacklist, rate limiting。

#### Interview answer

> I would keep redirect latency extremely low. The redirect service first checks Redis for code-to-URL mapping and falls back to DB. Click analytics is emitted asynchronously to Kafka so it does not block redirect. For code generation, I would use a distributed id and Base62 encoding; custom aliases require uniqueness checks and abuse scanning.

### 2. Design a Distributed Rate Limiter

#### Question

设计一个 rate limiter，限制 user / IP / API key 的请求速率，支持多 API server 分布式部署。

#### Approach

重点不是算法名，而是限流精度、低延迟、分布式一致性、hot key 和 failure behavior。

#### Requirements

- 支持 per-user / per-IP / per-API-key。
- 支持 burst。
- 多 API server 共享限制。
- 低延迟，不能每次都打慢 DB。
- Redis 故障时要 fail-open 还是 fail-closed。

#### Algorithm

推荐 token bucket：

```
capacity = burst size
refill_rate = tokens per second
request consumes one token
if token available -> allow
else -> reject
```

#### Distributed design

```
API Gateway / Service
  -> local pre-limiter
  -> Redis token bucket Lua script
  -> allow / reject
```

为什么用 Lua：

- refill、check、decrement 必须原子。
- 避免 race condition。

Redis key：

```
rl:{tenant}:{api_key}:{route}
```

value:

```
tokens
last_refill_timestamp
```

#### Hot key 问题

如果一个 global API key 流量极大，单 Redis key 会热。

缓解：

- Local token bucket 先挡一部分。
- Shard by key hash。
- 对超大 tenant 分配 dedicated limiter。
- 使用 approximate local counters + periodic sync。

#### Failure behavior

- 登录、防刷、支付：Redis 故障时 fail-closed 或 strict fallback。
- 普通 read API：Redis 故障时 fail-open，保护可用性。

#### Interview answer

> I would use token bucket implemented with Redis Lua script so refill and consume are atomic. Each API server calls the limiter using a key such as tenant plus route. To reduce Redis hot-key pressure, I would add local pre-limiting and shard large tenants. Failure mode depends on business risk: security-sensitive APIs fail closed, normal reads may fail open.

### 3. Design a Web Crawler

#### Question

设计一个 web crawler，持续抓取网页，去重，遵守 robots.txt，支持大规模并发和增量更新。

#### Approach

核心难点：

- URL frontier 如何调度。
- URL dedup。
- Politeness：不能打爆同一个 domain。
- 内容去重。
- 失败重试。
- 页面更新频率。

#### Architecture

```
Seed URLs
  -> URL Frontier
  -> Per-domain scheduler
  -> Fetcher workers
  -> Parser
  -> Content store
  -> Link extractor
  -> Dedup filter
  -> URL Frontier
```

#### URL Frontier

不要一个 global FIFO。应该按 domain 分 queue：

```
frontier:{domain}
```

并维护 next_allowed_fetch_time，保证同一 domain 的抓取间隔。

#### Dedup

两层去重：

1. URL dedup
   - Canonicalize URL：lowercase host、remove fragment、normalize query。
   - Bloom filter 快速判断 seen。
   - DB/Key-value store 做最终记录。

2. Content dedup
   - Hash normalized content。
   - SimHash / MinHash 判断近似重复。

#### Storage

- Raw HTML：object storage。
- Metadata：DB / KV。
- Index：search index。
- Crawl state：URL status, last crawled, next crawl time。

#### Retry

- 5xx retry with backoff。
- 404 降低优先级或停止。
- robots.txt 禁止则不抓。

#### Interview answer

> I would design the crawler around a URL frontier, not just a worker pool. The frontier is partitioned by domain to enforce politeness. Fetchers download pages, parsers extract links, and a dedup layer canonicalizes URLs and uses Bloom filters plus persistent state. Raw pages go to object storage, metadata to DB, and searchable content to an index.

### 4. Design Dropbox / File Sync

#### Question

设计一个 Dropbox-like file storage and sync service，支持上传、下载、跨设备同步、大文件、版本历史。

#### Approach

核心难点：

- 大文件不能经过 app server。
- Chunking / dedup。
- Metadata 和 blob 分离。
- Sync conflict。
- 多设备变更通知。

#### Architecture

```
Client
  -> Metadata Service
  -> pre-signed upload URL
  -> Object Storage for chunks
  -> Sync Service
  -> Notification / Change Log
```

#### Data model

```
FileMetadata(
  file_id,
  owner_id,
  path,
  current_version,
  size,
  updated_at
)

FileVersion(
  file_id,
  version,
  chunk_hashes[],
  created_at
)

Chunk(
  chunk_hash,
  storage_url,
  size,

)
```

#### Upload flow

1. Client splits file into chunks。
2. Compute content hash for each chunk。

#### Conflict handling

- Server 不做 magical merge。
- 生成 conflict copy。
- 对支持 merge 的文档类型可用 CRDT/OT。

#### Interview answer

> I would separate metadata from blob storage. Files are split into content-addressed chunks so uploads can deduplicate unchanged chunks. Clients upload chunks directly to object storage using pre-signed URLs, then commit a metadata version. Sync is driven by a per-user change log so devices can ask for changes since last sync token.

### 5. Design Collaborative Document Editor Like Google Docs

#### Question

设计协同文档编辑系统，多个用户同时编辑，同步看到变化，支持离线、冲突处理、历史版本。

#### Approach

核心不是 WebSocket 本身，而是并发编辑算法：

- Operational Transform (OT)
- CRDT

#### Architecture

```
Client editor
  -> WebSocket gateway
  -> Collaboration session service
  -> OT/CRDT engine
  -> Document store
  -> Snapshot + operation log
```

#### Operation log

不要每次保存整个 document。保存 operations：

```
op_id
doc_id
base_version
user_id
operation: insert/delete/format
timestamp
```

定期 compact 成 snapshot：

```
snapshot_version
document_content
```

#### OT vs CRDT

- OT：server 协调 transform，Google Docs 经典路线。中心化更强，理解和控制容易。
- CRDT：每个 client 可独立合并，离线更强，但 metadata 更复杂。

面试里可选 OT：

> For interview simplicity, I would use OT with a central collaboration service. Clients send operations with base version; server transforms against concurrent operations, appends to log, then broadcasts canonical operations.

#### Failure handling

- WebSocket 断开后 client reconnect。
- Client 带 last_seen_version。
- Server replay missing ops。
- 定期 snapshot 减少 replay 成本。

#### Interview answer

> I would model edits as operations rather than full document writes. A collaboration service maintains document version, transforms concurrent operations using OT, appends them to an operation log, and broadcasts canonical operations over WebSocket. Periodic snapshots make recovery and loading efficient.

设计直播评论系统，用户发评论，其他观看者实时看到。需要低延迟、高 fanout、防 spam。

核心难点：

- Ordering。
- Moderation。
- Hot live room。
- Slow consumers。

## 23. More Product System Design Interview Bank

这一节补充更常见的 product system design 题。面试官通常会先问功能需求，然后迅速转向：数据模型、读写路径、fanout、ranking、consistency、hot key、failure handling、cost。答题时不要只画组件，要把每个设计的核心矛盾讲出来。

建议固定回答顺序：

1. Clarify requirements：核心功能、规模、SLA、读写比例。
2. Identify core entities：user、object、edge、event、state。
3. Design APIs：写路径和读路径分开。
4. Data model：source of truth、index、cache、derived view。
5. Scale strategy：partition key、fanout、queue、cache、search index。
6. Correctness：idempotency、dedup、ordering、consistency。
7. Failure mode：重试、降级、backpressure、recovery。
8. Metrics：latency、QPS、lag、error、cost。

### 1. News Feed / Twitter / Reddit Feed

#### Question

设计一个 News Feed。用户关注其他用户，发帖后粉丝能在 home timeline 看到内容。系统要支持发帖、关注、取 feed、ranking、热门用户、删除/隐藏内容。

#### 核心矛盾

Feed 最大的问题不是存帖子，而是 fanout：

- Fanout on write：发帖时把 post id 推给粉丝 timeline。
- Fanout on read：读 feed 时动态拉取关注者最近帖子。
- Hybrid：普通用户 fanout on write， celebrity / 大 V fanout on read。

#### Architecture

```
Post Service
  -> Post DB
  -> Kafka post_created
  -> Feed Fanout Workers
  -> Timeline Store
  -> Feed API
  -> Ranking Service
  -> Cache
```

#### Data model

```
post(post_id, author_id, text, media_ids, created_at, visibility, status)
follow(follower_id, followee_id, created_at)
timeline(user_id, score, post_id, author_id, created_at)
```

Timeline store 可以用 Redis sorted set、Cassandra、DynamoDB wide partition，核心是按 `user_id` 查询最近 N 条。

#### Write path

1. User creates post。
2. Post Service 写 Post DB。
3. 发布 `post_created` event 到 Kafka。
4. Fanout worker 查 follower list。
5. 把 post id 写入粉丝 timeline。
6. 对热门作者只写 celebrity source，不全量 fanout。

#### Read path

1. Feed API 读取用户 timeline candidate。
2. 补充 celebrity / promoted / fresh candidates。
3. Ranking Service 打分。
4. Hydrate post metadata。
5. 返回分页结果。

#### Hot celebrity

如果一个用户有 1 亿粉丝，不要同步 fanout：

- celebrity posts 进入单独表。
- 用户读 feed 时 merge celebrity recent posts。
- 对活跃粉丝可以异步预计算。
- 设置 fanout upper bound。

#### Consistency

Feed 可以 eventual consistency。用户发帖后自己的 profile timeline 必须立即可见，但粉丝 home feed 延迟几秒可以接受。删除或屏蔽内容要优先在 read path filter，后台再清 timeline。

#### Interview answer

> I would use a hybrid fanout model. Normal users use fanout-on-write so home feed reads are fast. Celebrity users use fanout-on-read to avoid writing to millions of timelines per post. The source of truth is the post table and follow graph; timelines are derived views that can be rebuilt. Ranking happens on candidates from timeline, celebrity sources, and freshness signals.

### 3. Coding Platform / LeetCode

#### Question

设计在线刷题平台。用户提交代码，系统编译运行测试，返回结果。需要支持多语言、排队、sandbox、实时结果、比赛高峰。

Online judge 的难点是安全和隔离：

- 用户代码不可信。
- 需要限制 CPU、memory、network、file system。

```
Submission API
  -> Submission DB
```

- Read-only root filesystem。
- CPU/memory/time limits。
- 容器或 microVM 隔离。
- 清理临时文件。

#### Interview answer

> I would make submission asynchronous. The API stores the submission and enqueues a judge job. Workers run untrusted code inside a sandbox with CPU, memory, time, filesystem, and network limits. Results are persisted and streamed back to the client. The platform scales by language-specific queues, worker pools, test-case caching, and per-user throttling.

### 4. Online Auction / eBay

#### Question

设计在线拍卖。用户可以出价，最高价赢，拍卖结束后生成订单。支持实时价格更新、anti-sniping、并发出价、支付。

#### 核心不变量

- 每个 auction 同一时刻只有一个最高有效出价。
- Bid amount 必须大于当前价格加 increment。
- Auction ended 后不能接受新 bid。
- 生成订单必须 exactly-once effect。

#### Data model

```
auction(auction_id, seller_id, item_id, start_at, end_at, status, current_price, highest_bid_id, version)
bid(bid_id, auction_id, bidder_id, amount, created_at, status)
order(order_id, auction_id, buyer_id, amount, status)
```

#### Bid write path

1. Validate auction is active。
2. Validate bid amount。
3. Conditional update auction row：

```sql
UPDATE auction
SET current_price = ?,
    highest_bid_id = ?,
    version = version + 1
WHERE auction_id = ?
  AND status = 'ACTIVE'
  AND current_price < ?
  AND version = ?
```

4. 写 bid record。
5. 通过 WebSocket / pubsub 推送 price update。

#### Anti-sniping

如果结束前最后 N 秒有新 bid，可以延长 end time。例如最后 2 分钟出价延长 2 分钟。这样防止最后一秒抢拍。

#### Partitioning

用 `auction_id` 做 partition key，让同一 auction 的 bid 进入同一 shard 或单线程 actor。这样高并发 auction 可以按 auction 隔离，避免全局锁。

#### Interview answer

> I would treat each auction as a consistency boundary. Bids are accepted with conditional updates or a per-auction single-writer actor so only one highest bid wins. Price updates are pushed through pubsub/WebSocket, but the auction table is the source of truth. At auction close, a scheduled worker transitions the auction to ended and creates the order idempotently.

### 5. Price Tracking / CamelCamelCamel

#### Question

设计价格追踪服务。用户关注商品，当价格低于阈值时收到通知。系统要定期抓取价格、存历史、去重、触发 alert。

#### Architecture

```
Product Catalog
  -> Crawl Scheduler
  -> Fetch Workers
  -> Parser
  -> Price Time Series Store
  -> Alert Evaluator
  -> Notification Service
```

#### Data model

```
product(product_id, url, merchant, crawl_frequency, last_crawled_at)
price_point(product_id, timestamp, price, availability)
watch(user_id, product_id, threshold, channel, status)
alert(alert_id, user_id, product_id, price, sent_at, dedup_key)
```

#### Scheduling

热门商品高频抓，冷门商品低频抓。不要所有商品固定频率：

- high-interest products：minutes。
- normal products：hours。
- inactive products：days。

Scheduler 只产生 crawl jobs，worker 执行 fetch。失败要 exponential backoff。

#### Alert correctness

通知必须幂等。使用：

```
dedup_key = user_id + product_id + threshold + price_bucket + day
```

避免同一次降价重复轰炸用户。

#### Interview answer

> I would separate crawling from alerting. A scheduler creates crawl jobs based on product popularity and freshness requirements. Fetch workers parse prices and append immutable price points. Alert evaluators compare new prices against active watches and send idempotent notifications with dedup keys. Historical prices are stored in a time-series optimized table.

### 6. Dating App / Tinder

#### Question

设计 dating app。用户设置 profile 和偏好，系统推荐候选人，用户 swipe left/right，双方 like 后 match，可以聊天。

#### Candidate generation

候选人不是全量扫描：

- Geo index：附近的人。
- Preference filter：年龄、距离、性别、兴趣。
- Exclusion set：已经 swipe 过、blocked、reported。
- Ranking：活跃度、quality score、mutual interests。

#### Data model

```
profile(user_id, geo_cell, age, gender, preferences, status)
swipe(user_id, target_user_id, direction, created_at)
match(match_id, user_a, user_b, created_at, status)
```

#### Match flow

当 A right swipe B：

1. 写 swipe(A, B, RIGHT)，幂等。
2. 查是否存在 swipe(B, A, RIGHT)。
3. 如果存在，创建 match，使用唯一约束：

```sql
UNIQUE(min(user_a, user_b), max(user_a, user_b))
```

#### Privacy

- Block/report 后 read path 必须立即过滤。
- Location 只存粗粒度 geo cell。
- 不暴露精确在线状态。

#### Interview answer

> I would split candidate generation from match creation. Candidate generation uses geo indexing, preference filters, exclusion sets, and ranking. Swipes are immutable user actions. A match is created idempotently when both users have right-swiped, protected by a unique pair constraint. Privacy filters such as block and report must be enforced at read time.

### 7. Local Delivery / GoPuff

#### Question

设计本地即时配送服务。用户下单，系统从本地仓库扣库存，分配 picker/driver，实时跟踪配送状态。

#### Core states

```
Order:
CREATED -> RESERVED -> PAID -> PICKING -> READY -> ASSIGNED -> PICKED_UP -> DELIVERED
       -> CANCELLED / FAILED

Inventory:
AVAILABLE -> RESERVED -> SOLD / RELEASED
```

#### Architecture

```
Order Service
  -> Inventory Reservation
  -> Payment
  -> Picking Queue
  -> Dispatch Service
  -> Driver Location Stream
  -> ETA Service
  -> Notification
```

#### Inventory reservation

下单时不要直接扣最终库存。先 reserve：

```sql
UPDATE inventory
SET available = available - ?,
    reserved = reserved + ?
WHERE warehouse_id = ?
  AND sku_id = ?
  AND available >= ?
```

支付成功后 commit，支付失败或超时 release。

#### Dispatch

分配 driver 时考虑：

- driver location。
- order ready time。
- capacity。
- route distance。
- promised SLA。

可以先用 greedy nearest-driver，再升级到 batching/route optimization。

#### Interview answer

> I would model delivery as a workflow with explicit order and inventory states. Checkout creates inventory reservations with TTL, payment commits them, and failures release them. Picking and delivery are asynchronous steps. Driver dispatch uses location and ETA signals, while clients receive order state through realtime updates.

### 8. Like Button / Social Reactions

#### Question

设计 Like button。用户可以 like/unlike post，页面显示总数，并把行为用于推荐和通知。

#### 核心矛盾

Like 写入 QPS 很高，但 count 不一定要强一致。用户自己的 like 状态必须准确，计数可以 eventual consistency。

#### Data model

```
reaction(user_id, object_id, reaction_type, created_at)
reaction_count(object_id, reaction_type, count, updated_at)
```

`reaction` 使用唯一键 `(user_id, object_id)`，保证重复点击幂等。

#### Write path

1. Toggle like 写 source of truth。
2. 发布 reaction event。
3. Counter worker 异步更新 count。
4. Notification / ranking consumer 使用同一 event。

#### Hot object

热门 post 的 count 会变 hot key：

- Local aggregation 后批量 flush。
- Sharded counters。
- Approximate counter for display。
- Periodic reconciliation from source table。

#### Interview answer

> I would make the user-object reaction table the source of truth and keep counters as derived data. Like and unlike operations are idempotent through a unique user-object key. Counts are updated asynchronously through events, with sharded counters or local aggregation for hot posts. The UI can tolerate slightly stale counts, but the user's own like state must be correct.

### 9. Search / Facebook Post Search

#### Question

设计帖子搜索。用户搜索关键词，结果要按 relevance、recency、privacy 排序。帖子更新和删除要尽快反映。

#### Architecture

```
Post DB
  -> CDC / Kafka
  -> Indexer
  -> Search Index
  -> Search API
  -> Privacy Filter
  -> Ranking
```

#### Index document

```
post_id
author_id
text
tokens
created_at
engagement_signals
visibility
allowed_groups
```

#### Query flow

1. Search API 解析 query。

> I would not query the primary post database for search. Posts are indexed asynchronously through CDC or Kafka into a search engine. Deletes and privacy updates are high-priority index events.

## 24. Low Level Design Interview Bank

这一节来自 `sd_pages` 里的 Low Level Design pages。LLD 面试和 system design 不一样：面试官更看重 class modeling、state transition、API boundaries、extensibility、edge cases、testability。

LLD 每题建议用这个顺序：

1. Clarify entities and use cases。
2. Define core classes / interfaces。
3. Define state machine。
4. Explain main operations。
5. Handle concurrency / consistency。
6. Show extensibility。

### 1. Amazon Locker Low Level Design

#### Question

设计 Amazon Locker。用户下单后包裹被投递到 locker，用户收到 pickup code，在有效时间内取件。系统要支持不同 locker size、过期释放、通知、运营人员补货/取回。

#### Core objects

```java
class Locker {
  String lockerId;
  LockerSize size;
  LockerStatus status;
  String locationId;
}

class Package {
  String packageId;
  LockerSize requiredSize;
  PackageStatus status;
}

class Reservation {
  String reservationId;
  String packageId;
  String lockerId;
  String pickupCodeHash;
  Instant expireAt;
  ReservationStatus status;
}
```

#### State machines

Locker:

```
AVAILABLE -> RESERVED -> OCCUPIED -> AVAILABLE
AVAILABLE -> OUT_OF_SERVICE
```

Reservation:

```
CREATED -> DELIVERED -> PICKED_UP
CREATED -> EXPIRED
DELIVERED -> EXPIRED
```

#### Main operations

1. `reserveLocker(packageId, size, location)`
   - Find smallest available locker >= required size。
   - Mark locker as RESERVED。
   - Create reservation with expiry。

2. `deliverPackage(reservationId)`
   - Courier opens locker。
   - Put package。
   - Locker becomes OCCUPIED。
   - Send pickup code to user。

3. `pickupPackage(code)`
   - Verify code hash。
   - Check not expired。
   - Open locker。
   - Mark reservation PICKED_UP。
   - Mark locker AVAILABLE。

4. `expireReservation()`
   - Background job scans expired reservations。
   - Release locker or create return task。

#### Concurrency

多个订单可能同时抢同一个 locker。核心是 atomic reservation：

```sql
UPDATE locker
SET status = 'RESERVED'
WHERE locker_id = ?
  AND status = 'AVAILABLE'
```

只有 update 成功的 request 拿到 locker。

#### Extensibility

- 新 locker size：enum / config。
- 新通知方式：NotificationChannel interface。
- 不同分配策略：LockerAssignmentStrategy。

#### Interview answer

> I would model locker assignment as a state transition problem. The critical operation is reserving a locker atomically so two packages cannot get the same locker. I would separate Locker, Package, Reservation, and Notification. Locker assignment uses the smallest available locker that fits the package, and reservation expiry is handled by a background job.

### 2. Parking Lot Low Level Design

#### Question

设计停车场，支持不同 vehicle type、spot type、入场取票、出场计费、找车位、支付。

#### Core objects

```java
class ParkingLot {
  List<ParkingFloor> floors;
  ParkingSpotAssignmentStrategy strategy;
}

class ParkingSpot {
  String spotId;
  SpotType type;
  SpotStatus status;
}

class Ticket {
  String ticketId;
  String vehicleNumber;
  String spotId;
  Instant entryTime;
  TicketStatus status;
}

class PricingPolicy {
  Money calculate(Instant entry, Instant exit, VehicleType type);
}
```

#### Main operations

1. `park(vehicle)`
   - Choose compatible spot。
   - Mark spot occupied。
   - Create ticket。

2. `unpark(ticketId)`
   - Calculate fee。
   - Process payment。
   - Mark ticket paid。
   - Free spot。

#### Spot assignment

不要把策略写死在 ParkingLot 里。使用 strategy pattern：

```java
interface ParkingSpotAssignmentStrategy {
  ParkingSpot findSpot(Vehicle vehicle, List<ParkingFloor> floors);
}
```

可扩展策略：

- nearest entrance。
- nearest elevator。
- compact-first。
- EV charging priority。

#### Concurrency

多个入口同时分配车位，要保证 spot 状态更新原子：

```sql
UPDATE spot
SET status = 'OCCUPIED'
WHERE spot_id = ?
  AND status = 'AVAILABLE'
```

#### Interview answer

> I would separate domain entities from policies. ParkingLot owns floors and spots, Ticket tracks a parking session, PricingPolicy calculates fees, and SpotAssignmentStrategy chooses a spot. The critical concurrency point is spot assignment, which must atomically move a spot from AVAILABLE to OCCUPIED.

### 3. Elevator Low Level Design

#### Question

设计电梯系统，多个 elevator 服务多个 floor。用户在楼层按 up/down，在电梯内选择目标楼层。系统要调度电梯、处理方向、停靠、开关门。

#### Core objects

```java
class Elevator {
  String elevatorId;
  int currentFloor;
  Direction direction;
  ElevatorState state;
  SortedSet<Integer> upStops;
  SortedSet<Integer> downStops;
}

class Request {
  int sourceFloor;
  Integer destinationFloor;
  Direction direction;
  RequestType type;
}

interface SchedulingStrategy {
  Elevator assign(Request request, List<Elevator> elevators);
}
```

#### State machine

```
IDLE -> MOVING_UP -> DOOR_OPEN -> MOVING_UP
IDLE -> MOVING_DOWN -> DOOR_OPEN -> MOVING_DOWN
MOVING_* -> IDLE when no stops
```

#### Scheduling

简单策略：

- 同方向且会经过 source floor 的 elevator 优先。
- 否则选最近 IDLE elevator。
- 否则选择 estimated cost 最低的 elevator。

Cost function:

```
cost = distance + direction_penalty + current_queue_size
```

#### Stop handling

- Up direction 使用 min-heap / sorted set。
- Down direction 使用 max-heap / reverse sorted set。
- 当前方向 stops 清空后再考虑反方向。

#### Interview answer

> I would model each elevator as a state machine with current floor, direction, and ordered stop sets. The scheduler assigns hall requests based on estimated cost, preferring elevators moving in the same direction. The design should keep scheduling strategy pluggable so we can replace nearest-elevator with cost-based or destination-dispatch later.

### 4. Inventory Management Low Level Design

#### Question

设计库存系统，支持 stock add/remove、reservation、purchase、release、multi-warehouse。重点是防止 oversell。

#### Core objects

```java
class SKU {
  String skuId;
  String name;
}

class InventoryItem {
  String skuId;
  String warehouseId;
  int available;
  int reserved;
  long version;
}

class Reservation {
  String reservationId;
  String skuId;
  int quantity;
  Instant expireAt;
  ReservationStatus status;
}
```

#### Main operations

1. `reserve(skuId, quantity)`
   - Check available。
   - Decrease available。
   - Increase reserved。
   - Create reservation with TTL。

2. `commit(reservationId)`
   - Decrease reserved。
   - Mark reservation committed。

3. `release(reservationId)`
   - Increase available。
   - Decrease reserved。
   - Mark released。

#### Prevent oversell

Atomic update:

```sql
UPDATE inventory
SET available = available - ?,
    reserved = reserved + ?
WHERE sku_id = ?

```

如果 affected rows = 0，说明库存不足。

#### Reservation expiry

后台 job 扫描 expired reservation：

```
RESERVED -> EXPIRED
return quantity to available
```

#### Interview answer

> I would model inventory as available plus reserved, not just one stock number. Checkout first creates a reservation with TTL using an atomic conditional update. Payment success commits the reservation; timeout releases it. This prevents oversell while avoiding long database locks during payment.

### 6. Spreadsheet With Formulas

#### Question

设计一个 spreadsheet，支持 set cell、get cell、formula，例如 `C1 = A1 + B1`，当依赖变化时结果更新。

#### Core objects

```java
class Cell {
  String id;
  CellValue rawValue;
  Formula formula;
  CellValue computedValue;
}

class Spreadsheet {
  Map<String, Cell> cells;
  DependencyGraph graph;
}
```

#### Dependency graph

如果 `C1 = A1 + B1`：

```
C1 depends on A1, B1
A1 has dependent C1
B1 has dependent C1
```

更新 A1 时，需要 recompute C1。

#### Operations

1. `setValue(cellId, value)`
   - Remove old dependencies。
   - Set raw value。
   - Recompute dependents。

2. `setFormula(cellId, formula)`

   - Compute value。

3. `getValue(cellId)`

如果：

```
B1 = A1 + 1
```

必须 reject。使用 DFS 检查新 edge 是否造成 cycle。

#### Interview answer

> I would model formulas as a dependency graph. Each formula cell depends on referenced cells, and each cell tracks its dependents. When a cell changes, we recompute affected cells in topological order. Formula updates must run cycle detection before committing graph changes.

### 7. Connect Four Low Level Design

#### Question

### 8. LLD Delivery Framework

#### What interviewers expect

LLD 不是背 class diagram，而是展示你能把需求转成可维护代码结构。

#### Recommended flow

1. Clarify use cases
   - Who uses it?
   - What operations are required?
   - What is out of scope?

2. Identify nouns and verbs
   - Nouns become candidate classes。
   - Verbs become methods / services。

3. Define relationships
   - one-to-many。
   - composition vs aggregation。
   - ownership and lifecycle。

4. Define state machines
   - Booking, order, ticket, elevator, locker 都有 states。
   - 状态转换比 class 数量更重要。

5. Apply patterns only when useful
   - Strategy for pluggable algorithms。
   - Factory for object creation。
   - Observer for notification。
   - State pattern for complex state transitions。

6. Discuss concurrency
   - atomic update。
   - lock。
   - optimistic concurrency。
   - idempotency。

7. Mention tests
   - unit tests for policies。
   - state transition tests。
   - concurrency tests。
   - edge cases。

#### Common mistakes

- 一上来画 20 个 classes，但没有 main flow。
- 忘记 state transition。
- 把 policy 写死，无法扩展。
- 不讲 concurrency。
- 不讲 invalid input。
- 不讲 tests。

#### Interview answer

> In LLD, I start from use cases and state transitions, then define entities and interfaces. I keep policies pluggable through strategy interfaces, keep persistence separate from domain logic, and explicitly handle invalid states and concurrency. I also call out unit tests for state transitions and edge cases.

## 25. Advanced Infra Patterns Interview Bank

这一节补充 system design 面试里经常被追问的基础设施 pattern。很多候选人会做单题，但一被问到 read scaling、write contention、large blob、workflow、streaming、search、gateway 就断掉。面试时可以把这些 pattern 当作工具箱，主动嵌入到具体题目里。

### 1. API Gateway Deep Dive

#### 它解决什么

API Gateway 是 client 和 backend services 之间的入口层。不要只说“转发请求”，要说明它承担 cross-cutting concerns：

- Auth / token validation。
- Rate limit / quota。
- Request routing。
- TLS termination。
- API versioning。
- Request/response transformation。
- Timeout / retry / circuit breaker。
- Observability：request id、metrics、logs、tracing。

#### Architecture

```
Client
  -> Edge Load Balancer
  -> API Gateway
       - auth filter
       - rate limit filter
       - routing filter
       - timeout/retry policy
       - request logging
  -> Backend Services
```

#### 关键设计

1. Gateway 不应该放太多业务逻辑。
   - 好：身份校验、限流、路由、统一超时。
   - 坏：把 order/payment/feed 业务规则写在 gateway。

2. Retry 要谨慎。
   - GET 可以重试。
   - POST 必须依赖 idempotency key。
   - 不要在下游已经过载时无限 retry。

3. Timeout 必须端到端分配。

```
client timeout = 1500 ms
gateway budget = 1300 ms
service A = 500 ms
service B = 500 ms
buffer = 300 ms
```

4. Rate limit 分层。
   - per IP。
   - per user。
   - per API key。
   - per tenant。
   - per route。

#### Interview answer

> I would use the API gateway for cross-cutting concerns such as auth, rate limiting, routing, timeouts, and observability, but I would keep business logic in backend services. Retries are only safe for idempotent operations or requests with idempotency keys. The gateway also propagates request ids and enforces a latency budget so slow downstreams do not exhaust client or server resources.

### 2. Distributed Cache / Redis Deep Dive

#### Redis 常见用途

- Cache-aside。
- Session store。
- Rate limiter counters。
- Sorted set leaderboard / timeline。
- Pub/sub for lightweight realtime。
- Distributed lock, but only when carefully bounded。

#### Cache-aside flow

```
read:
  get cache
  if miss:
    read DB
    set cache with TTL

write:
  update DB
  delete cache
```

为什么 delete cache 而不是 update cache：避免并发写导致 dirty cache。DB 是 source of truth，cache 是 derived data。

#### Hot key

热门 key 会压垮单个 Redis shard。解决：

- local in-process cache。
- key replication。
- request coalescing / singleflight。
- sharded counters。
- 加随机 TTL jitter，避免同时过期。

#### Cache stampede

大量请求同时 miss 同一个 key：

- singleflight：只有一个请求回源。
- stale-while-revalidate：先返回旧值，后台刷新。
- mutex lock with timeout。
- negative cache：缓存空结果，防止穿透。

#### Redis Cluster

Redis Cluster 通过 hash slot 分片。多 key 操作要注意 key 是否在同一个 slot。面试里可以说：

> If we need atomic multi-key operations, I would either keep related keys in the same hash slot using hash tags, or avoid cross-key Redis transactions and move the atomicity to the database.

#### Interview answer

> I would treat Redis as a fast derived-data layer, not the source of truth for critical state. For cache-aside, reads populate cache on miss, and writes update the database first then delete cache. For hot keys, I would use local cache, request coalescing, sharded counters, or replicated keys. TTL jitter and stale-while-revalidate help prevent stampedes.

### 3. Elasticsearch / Search Infra

#### 什么时候用 search index

当需求是 keyword search、text relevance、filter + sort、autocomplete、log search，不应该用 primary DB 的 `LIKE '%keyword%'` 硬查。

#### Write path

```
Primary DB
  -> CDC / Outbox / Kafka
  -> Indexer
  -> Elasticsearch
```

DB 是 source of truth，Elasticsearch 是 derived index。Indexer 必须处理：

- duplicate events。
- out-of-order updates。
- delete tombstone。
- reindex。
- backfill。

#### Index design

```
document_id
text fields
keyword fields
timestamp
tenant_id
visibility
ranking signals
version
```

#### Refresh interval

Elasticsearch 不是每次写入都立即可搜。refresh interval 影响 freshness 和 throughput：

- refresh 太频繁：写入成本高。
- refresh 太慢：搜索结果不新。

面试回答：根据业务 SLA 设置。例如商品搜索可以秒级，安全删除需要 read-time filter 兜底。

#### Reindex strategy

改 mapping 或 ranking 时不要直接改线上 index：

1. 创建 new index。
2. Backfill data。
3. Dual write / replay events。
4. Shadow query compare。
5. Alias switch。
6. 保留 rollback path。

#### Interview answer

> I would keep the database as the source of truth and build Elasticsearch as a derived index through CDC or Kafka. The indexer must be idempotent and version-aware to handle duplicate or out-of-order events. For schema or ranking changes, I would build a new index, backfill, replay recent events, compare shadow queries, then switch an alias for low-risk rollout.

### 4. Flink / Stream Processing

#### 什么时候需要 stream processing

当系统要处理持续事件流，并且需要 window、aggregation、join、late event、stateful computation，就会用 Flink / streaming engine。

例子：

- Ad click aggregation。
- Fraud detection。
- Realtime dashboard。
- Notification trigger。
- Feature computation。

#### Core concepts

- Event time：事件发生时间。
- Processing time：系统处理时间。
- Watermark：系统认为更早事件基本到齐的进度。
- Window：按时间聚合。
- State：每个 key 的中间状态。
- Checkpoint：故障恢复状态快照。

#### Architecture

```
Kafka topic
  -> Flink job
       - parse
       - keyBy
       - window
       - aggregate
       - dedup
  -> Redis / OLAP / Warehouse
```

#### Late events

迟到事件不能简单丢：

- 允许 allowed lateness。
- 使用 watermark 关闭 window。
- 太晚的事件进 side output。
- 对 billing/reporting 使用 batch correction。

#### Exactly-once effect

不要随便说 exactly-once。更准确：

- Flink state 可以通过 checkpoint 实现 exactly-once state update。
- Sink 是否 exactly-once 取决于外部系统是否支持事务或幂等写。
- 业务最终目标是 exactly-once effect。

#### Interview answer

> I would use event time and watermarks rather than processing time for correctness. The stream job keys events by business id, maintains state for deduplication or aggregation, and checkpoints state for recovery. For late events, I would allow bounded lateness and send very late events to a correction path. For exactly-once, I would focus on idempotent or transactional sinks to achieve exactly-once business effect.

### 5. Scaling Reads

#### 常用手段

读扩展不是只有“加 cache”。要按瓶颈分层：

| Bottleneck | Solution |
|---|---|
| DB read QPS 高 | cache, read replica |
| Query 太慢 | index, denormalized table |
| Join 太重 | materialized view, CQRS read model |
| Global latency 高 | CDN, geo replica |
| Hot object | local cache, replicated cache, request coalescing |

#### Read replica

优点：分担 read QPS。缺点：replica lag。适合：

- profile view。
- feed hydrate。
- analytics read。

不适合：

- 刚写完必须立即读到的 money/inventory。
- 强一致状态检查。

#### Materialized view

当 read query 很复杂，可以预计算：

```
source tables -> events -> view builder -> read optimized table
```

代价是 eventual consistency 和 rebuild 成本。

#### Interview answer

> I would first identify whether read pressure comes from QPS, query complexity, or geographic latency. Cache helps hot reads, replicas help read QPS, indexes help selective queries, and materialized views help expensive joins. For derived views I would explicitly call out eventual consistency and rebuild strategy.

### 6. Scaling Writes / Contention

#### 写扩展常见问题

- 单行热点：counter、inventory、auction current price。
- 单 partition 热点：celebrity feed、hot room messages。
- 全局顺序要求：payment ledger、matching engine。
- 写放大：fanout、secondary index、multi-region replication。

#### 解法工具箱

1. Shard by business key。
   - 按 `user_id`、`auction_id`、`tenant_id`、`room_id` 分片。

2. Single-writer per key。
   - 同一 auction / inventory item 的写进入同一 queue 或 actor。

3. Conditional update。
   - 用 version 或 condition 防止 lost update。

4. Batch writes。
   - Counter 先局部聚合，再 flush。

5. Move work async。
   - 写 source of truth 后，把 fanout / index / notification 放到 queue。

#### Counter example

不要所有 like 都更新一行：

```
counter_shard(object_id, shard_id, count)
```

读取时 sum shards，或周期性 rollup。

#### Interview answer

> For write scaling, I would look for the contention key first. If many writes hit the same entity, adding more servers does not solve the hotspot. I would use conditional updates for correctness, single-writer or queue-based serialization for highly contended entities, and sharded counters or batching for high-volume approximate counts.

### 7. Large Blobs Pattern

#### 不要把大文件塞进 DB

图片、视频、PDF、model artifact、log archive 都应该放 object storage。DB 存 metadata 和 object key。

#### Upload architecture

```
Client
  -> API: create upload session
  -> Object Storage: multipart upload
  -> API: complete upload
  -> Metadata DB
  -> Processing Queue
  -> CDN
```

#### 为什么 client direct upload

- API server 不扛大流量。
- 支持断点续传 / multipart。
- 更便宜。
- 更容易走 CDN / regional object storage。

#### Metadata

```
blob_id
owner_id
object_key
content_type
size
checksum
status
created_at
```

#### Consistency

常见失败：

- object 上传成功，metadata 写失败。
- metadata 创建成功，object 上传失败。
- processing 失败。

处理：

- upload session state machine。
- background cleanup orphan objects。
- checksum verification。
- processing retry。

#### Interview answer

> I would store large bytes in object storage and keep only metadata in the database. The client uploads directly using pre-signed multipart URLs. After upload completion, the system verifies checksum, updates metadata, and triggers asynchronous processing. Cleanup jobs remove abandoned upload sessions and orphaned objects.

### 8. Long-running Tasks

#### 例子

- Video transcoding。
- Report generation。
- ML inference batch job。
- Data export。
- Web crawling。

这些任务不能同步 HTTP 等待完成。

#### Architecture

```
API
  -> Job DB
  -> Queue
  -> Worker
  -> Progress Store
  -> Status API / WebSocket
```

#### Job state machine

```
QUEUED -> RUNNING -> SUCCEEDED
       -> FAILED
       -> CANCELLED
       -> RETRYING
```

#### Worker lease

Worker 领取 job 时写 lease：

```
job_id
worker_id
lease_until
attempt
```

如果 worker crash，lease expire 后 job 可以被重新领取。

#### Idempotency

重试可能重复执行，所以 output 要幂等：

- deterministic output key。
- write temp then atomic rename。
- DB state conditional update。
- external calls use idempotency key。

#### Interview answer

> I would turn long-running work into asynchronous jobs. The API creates a job record and returns job_id. Workers claim jobs with leases, update progress, and write outputs idempotently. Clients poll a status API or subscribe to realtime updates. If a worker dies, the lease expires and another worker retries the job safely.

### 9. Multi-step Process / Saga

#### 例子

- Order checkout：reserve inventory -> charge payment -> create shipment。
- Travel booking：flight -> hotel -> car。
- Account onboarding：KYC -> risk -> account creation。

#### 为什么不用大分布式事务

跨服务 ACID transaction 很重，耦合高，失败处理复杂。实际系统常用 Saga / workflow：

- 每一步本地事务。
- 状态持久化。
- 失败时 retry 或 compensation。

#### Orchestration vs Choreography

Orchestration：

```
Workflow Engine controls steps
```

优点：状态清晰，容易 debug。缺点：中心化。

Choreography：

```
Services react to events
```

优点：服务松耦合。缺点：流程分散，debug 难。

#### Compensation

不是所有操作都能真正 undo：

- reserve inventory 可以 release。
- payment capture 可以 refund，但不是瞬时。
- email sent 不能撤回，只能补偿通知。

#### Interview answer

> I would model the process as a Saga with explicit state. Each step commits a local transaction and emits an event. On failure, the workflow retries transient errors and runs compensation for completed steps when necessary. I prefer orchestration for complex business-critical flows because it makes state, retries, and debugging clearer.

### 10. Real-time Updates Pattern

#### 选型

| Mechanism | Best for |
|---|---|
| Polling | 简单状态查询，低频 |
| Long polling | 中低频更新 |
| SSE | server-to-client stream |
| WebSocket | 双向实时通信 |

#### Architecture

```
Client
  -> WebSocket Gateway
  -> Connection Registry
  -> Pub/Sub
  -> Backend event producers
```

#### Connection registry

需要知道 user 在哪些 gateway 上：

```
user_id -> connection_ids -> gateway_id
```

但这个 registry 可能是 eventually consistent。发送失败要允许连接已经断开。

#### Backpressure

实时系统最怕慢 client：

- per-connection send buffer limit。
- 丢弃低优先级 update。
- 合并状态 update。
- 断开长期慢连接。

#### Interview answer

> I would terminate WebSocket connections at gateway nodes and use pub/sub to deliver backend events to the right gateway. A connection registry maps users to active connections, but delivery should tolerate stale entries. For slow clients, I would enforce send-buffer limits, coalesce updates, and drop low-priority messages rather than letting one connection consume unbounded memory.

### 11. Time-series Database

#### 适用场景

- Metrics。
- IoT sensor data。
- Price history。
- Ad events aggregation。
- System logs with timestamp。

#### Data model

```
measurement
tags: host, region, service, tenant
fields: cpu, memory, latency
timestamp
```

#### 核心设计

- Append-heavy write。
- Time-based partition。
- Retention policy。
- Downsampling / rollup。
- Compression。
- High-cardinality tag control。

#### Retention

```
raw 1-second data: keep 7 days
1-minute rollup: keep 30 days
1-hour rollup: keep 1 year
```

#### High cardinality

如果把 `user_id`、`request_id` 放 tag，series 数量会爆炸。高 cardinality 字段要谨慎，可能放 log/search 系统而不是 metrics DB。

#### Interview answer

> I would use a time-series store for append-heavy timestamped data with retention and rollup. Data is partitioned by time and commonly queried tags. Raw high-resolution data is kept briefly, then downsampled for long-term storage. I would avoid high-cardinality tags such as request_id because they can explode the number of series.

### 12. Staff-level System Design Answer Anatomy

#### 普通答案 vs 高分答案

普通答案：

- 画 API、DB、cache、queue。
- 说可以 scale。
- 说加 Kafka。

高分答案：

- 明确 business invariant。
- 说清楚 source of truth 和 derived data。
- 分开 write path / read path / async path。
- 找到 bottleneck 和 contention key。
- 说明 consistency tradeoff。
- 给出 failure handling。
- 用 metrics 证明系统可运营。

#### 白板结构

```
1. Requirements and scale
2. Core entities and APIs
3. High-level architecture
4. Write path
5. Read path
6. Async processing
7. Data partitioning
8. Correctness and consistency
9. Failure modes
10. Metrics and operations
```

#### 主动讲的 tradeoff

- Cache freshness vs DB load。
- Fanout-on-write vs fanout-on-read。
- Strong consistency vs availability。
- Low latency vs cost。
- Exact counter vs approximate counter。
- Sync user experience vs async reliability。

#### 面试收尾模板

> The core invariant I would protect is [business invariant]. The source of truth is [primary store], while [cache/index/timeline] is derived and rebuildable. The main bottleneck is [read/write/fanout/contention], so I would scale it with [specific strategy]. For failures, I would use idempotency, retries with backoff, dead-letter queues, and operational metrics such as latency, error rate, queue lag, and saturation.

## 26. Data Modeling & Storage Design Interview Bank

这一节补齐 `sd.html` 里 Data Modeling、Data Model: Cloud Storage / NewsFeed / Ride Sharing / Streaming Video、Cassandra Deep Dive、Kafka Deep Dive、Big Data Structures 等内容。面试里很多人会画服务图，但数据模型一问就虚。高分答案要讲清楚：source of truth、query pattern、partition key、index、derived view、rebuild path、consistency。

### 1. Data Modeling Interview Framework

#### Question

系统设计面试里，如何从需求推导 data model？什么时候用 normalized relational model，什么时候 denormalize，什么时候用 wide-column / document / search / graph / object storage？

#### Approach

先不要直接选数据库。先写 access patterns：

```
Write:
  - 谁写？
  - 写入频率？
  - 是否需要 transaction？

Read:
  - 按什么 key 查？
  - 是否需要排序 / range scan？
  - 是否需要 join / aggregation？
  - P50/P99 latency 要求？

Lifecycle:
  - 数据是否 immutable？
  - 是否有 TTL / retention？
  - 是否需要审计 / replay？
```

#### Entity vs access pattern

Entity-first 只能帮你找到 nouns：

```
User, Post, Comment, Like
```

但真正决定存储设计的是 access pattern：

```
get posts by user
get feed by user
get comments by post sorted by time
get like count by post
```

#### Source of truth vs derived view

高分回答一定要区分：

- Source of truth：不可随便丢，强一致要求更高。
- Derived view：为了读快而建，可以异步更新，可以 rebuild。

例子：

```
post table = source of truth
timeline table = derived view
search index = derived view
counter cache = derived view
```

#### Normalization vs denormalization

| Choice | When to use |
|---|---|
| Normalized SQL | transaction, constraints, ad-hoc queries |
| Denormalized read model | read latency critical, query pattern stable |
| Wide-column | high write/read by partition key, large scale |
| Document | flexible schema, object-like access |
| Search index | keyword/relevance query |
| Graph | relationship traversal |
| Object storage | large blob / immutable bytes |

#### Interview answer

> I would start with access patterns, not database names. For each entity, I identify the write path, read path, consistency requirement, and query keys. The primary store should protect the source of truth, while indexes, feeds, counters, and search documents are derived views that can be rebuilt. Denormalization is acceptable when the read pattern is stable and we have a clear async update and repair path.

### 2. Cloud Storage App Data Model / Dropbox

#### Question

设计 Dropbox / Google Drive 的 data model。用户有 folders/files，文件有 versions，支持 sharing、sync、delete/restore、large file upload。

#### Core entities

```
user(user_id, email, plan, quota_bytes)
namespace(namespace_id, owner_id, type)
node(node_id, namespace_id, parent_id, name, type, status)
file_version(version_id, node_id, blob_id, size, checksum, created_at)
blob(blob_id, object_key, size, checksum, ref_count)
share(share_id, node_id, principal_id, permission)
sync_cursor(user_id, namespace_id, last_change_seq)
change_log(namespace_id, seq, node_id, operation, created_at)
```

#### Key design

不要把 folder tree 和 file bytes 混在一起：

- `node` 表示 logical filesystem tree。
- `file_version` 表示文件版本。
- `blob` 表示 object storage 里的 bytes。
- 多个 file version 可以引用同一个 blob，用 checksum 去重。

#### Folder listing

Access pattern：

```
list children by (namespace_id, parent_id)
```

Index：

```
(namespace_id, parent_id, name)
```

这样列目录不需要递归扫描。

#### Sync model

客户端同步不应该每次全量 scan。使用 change log：

```
client sends cursor seq
server returns changes after seq
client applies changes
client updates cursor
```

#### Sharing

Sharing 可以是：

- file/folder direct share。
- shared namespace。
- inherited permission。

面试里可以先做 folder share，并说明 permission inheritance 需要 read path resolve 或 precomputed ACL。

#### Interview answer

> I would separate metadata from file bytes. The metadata database stores a namespace tree, file versions, sharing permissions, and a change log. Actual bytes are stored in object storage by blob id and checksum. Folder listing uses an index on namespace and parent id. Sync uses an append-only change log and cursor so clients only fetch incremental changes.

### 3. NewsFeed Data Model

#### Question

设计 Instagram/Facebook/Twitter NewsFeed 的 data model。用户发帖、关注、点赞、评论，首页 feed 快速展示。

#### Source tables

```
user(user_id, profile, status)
post(post_id, author_id, content_ref, created_at, visibility, status)
follow(follower_id, followee_id, created_at)
reaction(user_id, post_id, type, created_at)
comment(comment_id, post_id, user_id, body, created_at)
```

#### Derived tables

```
home_timeline(user_id, score, post_id, author_id, created_at)
author_timeline(author_id, created_at, post_id)
post_counter(post_id, like_count, comment_count, share_count)
search_document(post_id, text, author_id, visibility)
```

#### Partition keys

- `post`: by `post_id` or `author_id + created_at` depending access pattern。
- `follow`: query followers by followee, followees by follower，通常需要双向表。
- `home_timeline`: by `user_id`。
- `author_timeline`: by `author_id`。

#### Fanout data model

普通用户：

```
post_created -> fanout worker -> insert into followers' home_timeline
```

Celebrity：

```
do not fanout to all followers
read-time merge celebrity posts
```

#### Delete and privacy

Timeline 是 derived view，可能 stale。所以 read path 必须检查：

- post status。
- author block。
- visibility。
- user mute/hide。

后台再异步清理 timeline entries。

#### Interview answer

> I would keep posts, follows, reactions, and comments as source-of-truth tables. Home timelines, author timelines, counters, and search documents are derived read models. The timeline table is partitioned by user id for fast feed reads. For celebrity users, I would avoid full fanout and instead merge their posts at read time. Privacy and delete checks must still happen on the read path because derived timelines can be stale.

### 4. Ride-sharing Data Model / Uber-Lyft

#### Question

设计 Uber/Lyft 的 data model。要支持 rider request、driver location、matching、trip lifecycle、pricing、payment、history。

#### Core entities

```
rider(rider_id, profile, payment_method_id)
driver(driver_id, profile, vehicle_id, status)
vehicle(vehicle_id, type, plate, capacity)
trip(trip_id, rider_id, driver_id, pickup, dropoff, status, created_at)
trip_event(trip_id, event_seq, event_type, payload, timestamp)
driver_location(driver_id, lat, lon, cell_id, updated_at)
fare(trip_id, base, distance_fee, time_fee, surge, total)
payment(trip_id, amount, status, provider_ref)
```

#### Trip state machine

```
REQUESTED -> MATCHING -> DRIVER_ASSIGNED -> DRIVER_ARRIVING
-> IN_PROGRESS -> COMPLETED -> PAID
-> CANCELLED / FAILED
```

Trip state changes are critical. Use `trip_event` as append-only audit log and `trip` as current snapshot.

#### Driver location

Driver location is ephemeral and high-write:

- Keep latest location in in-memory geo index / Redis。
- TTL old locations。
- Persist sampled location history only if needed for audit/debug。

Do not write every 2-second driver ping into the main relational DB.

#### Matching and consistency

The critical invariant:

```
one driver cannot be assigned to two active trips
```

Use conditional update:

```sql
UPDATE driver
SET status = 'ASSIGNED'
WHERE driver_id = ?
  AND status = 'AVAILABLE'
```

Only one matching attempt wins.

#### Interview answer

> I would model trips as a state machine with an append-only trip_event log for audit and a trip snapshot for fast reads. Driver location is a separate ephemeral geo index with TTL because it has high write frequency. Matching uses conditional updates to ensure a driver is assigned to only one active trip. Payment and fare are separate records so financial state is auditable.

### 5. Streaming Video Platform Data Model / Netflix

#### Question

设计 Netflix/Disney+ 的 data model。用户浏览 catalog、播放视频、继续观看、推荐、订阅、profile、多设备。

#### Core entities

```
account(account_id, plan, billing_status)
profile(profile_id, account_id, name, maturity_level)
title(title_id, type, metadata, maturity_rating, status)
asset(asset_id, title_id, codec, resolution, drm_key_id, manifest_url)
watch_progress(profile_id, title_id, position_sec, updated_at)
playback_event(event_id, profile_id, title_id, event_type, timestamp)
entitlement(account_id, title_id or region, valid_from, valid_to)
```

#### Catalog vs playback

Catalog data is mostly read-heavy and cacheable：

- title metadata。
- artwork。
- genres。
- availability by region。

Playback path is latency-sensitive and security-sensitive：

- manifest URL。
- DRM license。
- CDN selection。
- entitlement check。

#### Watch progress

Access pattern：

```
get continue watching by profile_id
update progress frequently
```

Write optimization：

- client batches progress updates。
- update every N seconds or percentage change。
- last-write-wins by timestamp。

#### Event pipeline

Playback events feed：

- recommendation。
- quality monitoring。
- billing analytics。
- content popularity。

Use event log, not OLTP tables, for high-volume playback telemetry.

#### Interview answer

> I would separate catalog metadata, playback assets, user profile state, and telemetry. Catalog is read-heavy and CDN/cache friendly. Playback requires entitlement and DRM checks before returning manifests. Watch progress is keyed by profile and title and updated with last-write-wins. High-volume playback events go to Kafka or an event lake for recommendations and analytics rather than the transactional database.

### 6. Cassandra Deep Dive for Interviews

#### Question

什么时候用 Cassandra？如何设计 Cassandra table？为什么不能像 SQL 一样随便 query？

#### When Cassandra fits

Cassandra 适合：

- high write throughput。
- large scale。
- predictable query by partition key。
- multi-region / high availability。
- append-heavy data。

不适合：

- complex joins。
- ad-hoc queries。
- multi-row transactions。
- arbitrary secondary index query。

#### Table design principle

Cassandra 是 query-first design。每个 table 服务一个 query。

Example: user timeline

```sql
CREATE TABLE user_timeline (
  user_id text,
  created_at timestamp,
  post_id text,
  author_id text,
  PRIMARY KEY (user_id, created_at, post_id)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

Partition key:

```
user_id
```

Clustering key:

```
created_at, post_id
```

#### Hot partition

如果某个 partition 太大或太热，比如 celebrity timeline / global feed：

- add bucket key。
- split by time。
- write to multiple shards。

Example：

```
PRIMARY KEY ((user_id, bucket_day), created_at, post_id)
```

#### Consistency levels

可以按读写要求选择：

- `ONE`: low latency, weaker consistency。
- `QUORUM`: stronger consistency。
- `LOCAL_QUORUM`: multi-region 常用。

不要泛泛说 Cassandra 最终一致。要说 read/write consistency level 是可调的。

#### Interview answer

> I would use Cassandra when the query patterns are predictable and the system needs high write throughput and horizontal scalability. Cassandra table design is query-first: each table is built around a partition key and clustering order for one access pattern. I would avoid joins and ad-hoc queries. To prevent hot partitions, I would bucket large partitions by time or shard id, and choose consistency levels based on the correctness requirement.

### 7. Kafka Deep Dive for Interviews

#### Question

Kafka 在系统设计中到底解决什么？如何设计 topic、partition、consumer group、ordering、replay、retention？

#### Kafka mental model

Kafka 是 durable event log，不只是 queue。

```
Producer -> Topic partitions -> Consumer groups
```

同一个 topic 可以被多个 consumer group 独立消费：

- feed fanout。
- search indexing。
- notification。
- analytics。
- fraud detection。

#### Partition key

Partition key 决定 ordering 和 parallelism。

```
payment events -> key = payment_id
order events -> key = order_id
chat messages -> key = room_id
user activity -> key = user_id
```

同一个 key 的 events 在同一 partition 内有序。

#### Consumer lag

Consumer lag 增长说明下游处理不过来：

- 增加 consumers，但不能超过 partition 数。
- 增加 partitions。
- 优化 processing。
- batch writes。
- 降低 downstream dependency latency。

#### Replay

Kafka 的高分点是 replay：

- rebuild search index。
- recompute materialized views。
- recover failed consumer。
- backfill new pipeline。

这要求 events schema 稳定，consumer 幂等。

#### Retention and compaction

- Retention topic：保留一段时间的 event log。
- Compacted topic：按 key 保留最新状态，比如 user profile / config。

#### Interview answer

> I would use Kafka as a durable event log to decouple services and allow independent consumers to process the same event stream. Partition key is important because it controls ordering and parallelism. Consumers must be idempotent because delivery is at-least-once. Kafka also gives us replay, which is valuable for rebuilding derived views such as search indexes, timelines, counters, and analytics tables.

### 8. Big Data Structures in System Design

#### Question

系统设计面试里哪些 data structures 可以主动提？Bloom filter、Count-Min Sketch、HyperLogLog、LSM tree、consistent hashing、heap/top-k 分别什么时候用？

#### Bloom Filter

用途：快速判断“可能存在 / 一定不存在”。

适合：

- web crawler seen URL。
- cache penetration 防护。
- DB read before expensive lookup。

Tradeoff：

- false positive possible。
- false negative no, if implemented correctly。

#### Count-Min Sketch

用途：近似计数。

适合：

- ad click counts。
- trending item。
- hot key detection。

Tradeoff：

- over-estimates count。
- memory 小，速度快。

#### HyperLogLog

用途：估算 distinct count。

适合：

- daily active users。
- unique viewers。
- unique IPs。

Tradeoff：

- approximate，不适合 billing truth。

#### Heap / Top-K

用途：维护 top K。

适合：

- top videos。
- top search queries。
- leaderboard candidate merge。

For distributed top K：

```
local top K per shard -> global merge top K
```

#### LSM Tree

用途：解释高写入数据库如 Cassandra/RocksDB/LevelDB。

思路：

- writes 先到 memtable / WAL。
- flush to SSTable。
- background compaction。
- Bloom filter 减少无效 disk lookup。

#### Interview answer

> I would bring up specialized data structures when they match the bottleneck. Bloom filters reduce expensive negative lookups, Count-Min Sketch estimates high-volume counters, HyperLogLog estimates unique counts, heaps support Top-K, and LSM trees explain write-optimized storage. I would also call out approximation error and whether the result is safe for user-facing display or financial truth.

### 9. Storage Choice Interview Cheat Sheet

#### Quick mapping

| Need | Good choice |
|---|---|
| Transaction / constraints | Postgres / MySQL |
| High-scale key-value | DynamoDB / Cassandra |
| Append event log | Kafka |
| Text search | Elasticsearch / OpenSearch |
| Large files | Object storage |
| Cache / counters / sorted sets | Redis |
| Analytics / OLAP | BigQuery / Snowflake / ClickHouse |
| Graph traversal | Graph DB or graph projection |
| Time-series metrics | Timescale / Influx / Prometheus style TSDB |

#### How to say it in interview

不要说“我会用 X because scalable”。要说：

> The access pattern is [key/range/search/transaction/blob/analytics]. The correctness requirement is [strong/eventual]. The expected scale is [QPS/storage/latency]. Therefore I would choose [store] for the source of truth and use [derived store] for the read-optimized view.

#### Example

For search:

```
Postgres = source of truth
Kafka CDC = change stream
Elasticsearch = derived search index
```

For feed:

```
Post table = source of truth
Timeline table = read model
Redis = hot cache
Kafka = fanout event bus
```

#### Interview answer

> I would choose storage based on access pattern and correctness. The primary database should protect the source of truth. Caches, search indexes, counters, timelines, and OLAP tables are derived stores optimized for specific reads. Every derived store needs an update path, idempotency, monitoring, and a rebuild strategy.

### 1. Architecting a Robust Payment System

#### Question

在已有 Payment System 基础上，如何把它讲到 production-grade？面试官会追问：幂等、状态机、外部 provider 超时、重复扣款、退款、对账、审计、合规。

#### Approach

支付系统的核心不是调用 Stripe/银行 API，而是保护 financial invariant：

```
same business request should create at most one financial effect
every money movement must be auditable
external uncertainty must be reconciled
```

#### Architecture

```
Payment API
  -> Idempotency Store
  -> Payment Intent Service
  -> Payment Orchestrator
  -> Provider Adapter
  -> Ledger / Transaction Store
  -> Webhook Processor
  -> Reconciliation Job
```

#### State machine

```
CREATED -> REQUIRES_CONFIRMATION -> PROCESSING
-> SUCCEEDED / FAILED / CANCELLED
-> REFUND_PENDING -> REFUNDED
-> DISPUTED
```

#### Idempotency

Client sends:

```
Idempotency-Key: uuid
payload_hash
merchant_id
```

Server behavior:

- key missing：reject non-idempotent POST。
- key exists with same payload and final response：return cached response。
- key exists with different payload：return 400。
- key in progress：return 409/202 or wait briefly。

#### External timeout

最难的 case：

```
we sent charge request to provider
client timed out
provider may or may not have charged
```

处理：

- 不要立即重试创建新 charge。
- 查询 provider by provider_request_id。
- webhook eventual update。
- reconciliation job 修正 unknown state。

#### Ledger

Ledger 应该 append-only：

```
ledger_entry(entry_id, account_id, amount, currency, direction, payment_id, created_at)
```

不要 update money history。错误用 reversal/refund entry。

#### Interview answer

> I would model payment as a state machine around PaymentIntent and protect every non-idempotent API with an idempotency key and payload hash. External provider calls are uncertain, so timeouts move the payment into an unknown/processing state rather than creating a second charge. Webhooks and reconciliation jobs eventually resolve the state. Financial records should be append-only ledger entries for auditability.

### 2. Price Tracking at Scale

#### Question

设计大规模 price tracking / insight tracking system。系统跟踪商品价格变化、历史趋势、阈值提醒、价格洞察。

#### Architecture

```
Product Catalog
  -> Crawl Scheduler
  -> Fetch Workers
  -> Parser / Normalizer
  -> Price Event Log
  -> Time-series Store
  -> Alert Evaluator
  -> Insight / Analytics Jobs
```

#### Scheduling strategy

不要所有商品固定频率 crawl：

- hot products：高频。
- watched products：中频。
- cold products：低频。
- failed sources：backoff。
- merchant rate limits：per-domain token bucket。

#### Data model

```
product(product_id, merchant, url, canonical_key, status)
price_point(product_id, timestamp, price, currency, availability)
watch(user_id, product_id, threshold, channel, status)
price_alert(alert_id, user_id, product_id, price, dedup_key, sent_at)
```

#### Detect change

Price point 是 append-only。Current price 可以是 materialized view：

```
current_price(product_id, price, timestamp)
```

这样历史和最新读取都高效。

#### Alert dedup

不要每次 crawl 到低价都发通知：

```
dedup_key = user_id + product_id + threshold + price_bucket + day
```

#### Interview answer

> I would separate crawling, price history, and alerting. A scheduler prioritizes products by popularity, active watches, and source limits. Crawlers emit immutable price events, and a time-series store keeps historical price points. Alert evaluators compare new prices to user thresholds with dedup keys so users do not receive repeated alerts for the same drop.

### 3. Notification Fanout

#### Question

设计 notification fanout。一个事件可能通知一个用户、几千个粉丝、或者几百万订阅者。支持 push、email、in-app inbox，且不能重复轰炸。

#### Architecture

```
Event Producer
  -> Notification Service
  -> Fanout Planner
  -> Recipient Resolver
  -> Preference / Policy Filter
  -> Channel Queues
  -> Push/Email/In-app Workers
  -> Delivery Log
```

#### Fanout modes

- Small fanout：同步 resolve recipients + enqueue。
- Large fanout：create fanout job，分片处理。
- Celebrity fanout：延迟/批量，或者只写 inbox/feed，不 push 每个人。

#### Data model

```
notification_event(event_id, type, actor_id, object_id, created_at)
notification_job(job_id, event_id, shard, status)
delivery(user_id, event_id, channel, status, dedup_key)
preference(user_id, channel, topic, enabled)
```

#### Dedup and aggregation

用户不想收到：

```
A liked your post
B liked your post
C liked your post
...
```

可以聚合：

```
A and 23 others liked your post
```

Dedup key：

```
user_id + event_type + object_id + time_bucket
```

#### Interview answer

> I would separate event creation from delivery. Notification events are durable, fanout jobs resolve recipients and apply preferences, and channel-specific workers handle push, email, and in-app delivery. For large fanout, I would shard recipient processing and use dedup/aggregation so users are not spammed by repeated notifications.

### 4. Optimize Real-time Feeds

#### Question

Feed 已经能工作，但 latency 高、fanout 慢、hot users 压力大。如何优化 real-time feed？

#### Bottlenecks

- celebrity fanout 太大。
- timeline write amplification。
- feed read hydrate 太慢。
- ranking service 太重。
- cache invalidation storm。

#### Optimization playbook

1. Hybrid fanout
   - normal users fanout-on-write。
   - celebrities fanout-on-read。

2. Candidate caching
   - cache timeline post ids。
   - hydrate metadata in batch。

3. Feed item snapshot
   - timeline entry 存 author_id、preview、score。
   - 减少 read path fanout to many services。

4. Priority queue
   - active users timeline first。
   - inactive users lazy build。

5. Backpressure
   - fanout queue lag 高时降级 ranking/freshness。

#### Freshness vs latency

Feed 可以不是绝对实时。可以给用户自己的 post 强一致，别人 feed eventual consistency。

#### Interview answer

> I would optimize feed by separating source-of-truth posts from derived timelines. Hybrid fanout prevents celebrity write amplification, active-user prioritization reduces wasted work, and candidate caches plus batch hydration improve read latency. If fanout lags, the system can still serve older timeline candidates and merge recent celebrity posts at read time.

```
tweet_id
```

#### Query types

- keyword。
- hashtag。
- from:user。

### 6. Indexing Performance Playbook

#### Question

数据库查询慢，怎么系统化优化？什么时候加 index，什么时候改数据模型？

#### Steps

1. Inspect query pattern。
2. Check cardinality / selectivity。
3. Use explain plan。
4. Add composite index in query order。
5. Avoid unbounded scans。
6. Consider denormalized read model。

#### Composite index rule

Index should match：

```
WHERE equality fields first
then range field
then ORDER BY field if possible
```

Example：

```sql
WHERE user_id = ?
  AND status = ?
  AND created_at > ?
ORDER BY created_at DESC
```

Index：

```
(user_id, status, created_at DESC)
```

#### When index is not enough

- Query joins huge tables repeatedly。
- Low-selectivity field。
- Hot partition。
- Need aggregation over massive data。

Then consider：

- materialized view。
- precomputed counter。
- search index。
- OLAP store。
- partitioning。

#### Interview answer

> I would not blindly add indexes. I would inspect the query pattern and explain plan, then add a composite index that matches equality filters, range filters, and sort order. If the query is fundamentally an aggregation or join over large data, I would build a read model, materialized view, or OLAP pipeline instead of forcing the OLTP database to do it repeatedly.

### 7. Networking Architecture Playbook

#### Question

系统设计里怎么讲 load balancer、gateway、service discovery、timeouts、retries、circuit breaker、regional routing？

#### Request path

```
Client
  -> DNS / Global Load Balancer
  -> CDN / Edge
  -> API Gateway
  -> Service Load Balancer
  -> Backend Service
  -> Database / Cache / Queue
```

#### Timeouts

每一层都要有 timeout budget：

```
client: 2000 ms
gateway: 1500 ms
service A: 500 ms
service B: 500 ms
buffer: 500 ms
```

没有 timeout 的 retry 会放大故障。

#### Retry rules

- Retry only idempotent calls。
- Use exponential backoff + jitter。
- Respect Retry-After。
- Set max attempts。
- Do not retry overload blindly。

#### Circuit breaker

当下游错误率/timeout 过高：

- open circuit。
- fail fast。
- fallback。
- half-open probe。

#### Interview answer

> I would design the network path with explicit timeout budgets, idempotent retries, circuit breakers, and observability. Global load balancing routes users to healthy regions; API gateway handles auth/rate limits; service discovery and load balancing route internal calls. Retries must use backoff and only be used when the operation is idempotent or protected by an idempotency key.

### 8. Job Scheduling Scale and Reliability

#### Question

Job scheduler 已经有 delayed jobs，但如何支持大规模、可靠、可恢复、可观测？

#### Architecture

```
Job API
  -> Job Store
  -> Scheduler Shards
  -> Ready Queue
  -> Worker Pool
  -> Lease / Heartbeat
  -> Retry / DLQ
```

#### Sharding

Scheduler 可以按 `job_id` 或 `tenant_id` shard：

```
shard = hash(job_id) % N
```

每个 scheduler shard 扫描自己负责的 due jobs，避免全局锁。

#### Lease

Worker 领取 job：

```sql
UPDATE job
SET status = 'RUNNING',
    lease_until = now() + interval '60 seconds',
    worker_id = ?
WHERE job_id = ?
  AND status = 'READY'
```

Worker crash 后 lease 到期，job 回到 READY。

#### Retry

- exponential backoff。
- max attempts。
- dead-letter queue。
- poison job detection。
- idempotent handler。

#### Interview answer

> I would scale the scheduler by sharding the due-job scan and separating scheduling from execution. Workers claim jobs with leases so crashes do not lose work. Retries use exponential backoff and eventually move poison jobs to a dead-letter queue. Job handlers must be idempotent because a job can run more than once after lease expiry.

### 9. Scaling Reads Playbook

#### Question

读流量上来后，除了“加 cache”，还有哪些系统化手段？

#### Layers

```
Browser / client cache
CDN
API cache
Redis / Memcached
Read replica
Search index
Materialized view
OLAP store
```

#### Decision

- Static or media：CDN。
- Hot object：cache + request coalescing。
- Read-heavy relational：read replicas。
- Query by keyword：search index。
- Expensive join：materialized view。
- Aggregation dashboard：OLAP。

#### Cache correctness

Cache aside:

```
read cache
miss -> read DB -> set cache
write DB -> delete cache
```

Add:

- TTL jitter。
- stale-while-revalidate。
- negative caching。
- singleflight。

#### Interview answer

> I would first classify the read bottleneck: hot object, expensive query, geographic latency, or aggregation. Then I would choose the right layer: CDN for static content, Redis for hot objects, replicas for read QPS, search index for keyword queries, materialized views for joins, and OLAP for analytics. Cache correctness needs invalidation, TTL jitter, and stampede protection.

### 10. AI-driven Realtime Recommendations

#### Question

如何把 recommendation 做成 realtime personalization？用户刚点击/观看/购买后，推荐马上变。

#### Architecture

```
User Event
  -> Kafka
  -> Realtime Feature Processor
  -> Online Feature Store
  -> Candidate Refresh
  -> Ranking Service
  -> Recommendation API
```

#### Feature design

Long-term:

- category affinity。

Short-term:

- current session clicks。

- negative feedback。

> I would combine batch user profiles with realtime session features. ### 1. Messaging App / WhatsApp

#### Question

设计 WhatsApp / Messenger 类 messaging app。支持 1:1 chat、group chat、online/offline delivery、read receipt、push notification、multi-device、message ordering。

#### Approach

Messaging 的核心不是简单 WebSocket，而是：

- connection management。
- durable message store。
- per-conversation ordering。
- offline delivery。
- multi-device sync。

#### Architecture

```
Client
  -> WebSocket Gateway
  -> Message Service
  -> Conversation Service
  -> Message Store
  -> Delivery Queue
  -> Push Notification Service
  -> Presence Service
```

#### Data model

```
conversation(conversation_id, type, created_at)
conversation_member(conversation_id, user_id, role, joined_at)
message(conversation_id, message_seq, message_id, sender_id, body_ref, created_at)
delivery_state(message_id, user_id, device_id, delivered_at, read_at)
```

Use `conversation_id + message_seq` for ordering inside a conversation. Global ordering across all chats is unnecessary.

#### Send flow

1. Client sends message with client_msg_id。
2. Gateway forwards to Message Service。
3. Message Service assigns sequence number。
4. Persist message。
5. Enqueue delivery to recipients/devices。
6. Online devices receive via WebSocket。
7. Offline users receive push notification and later sync missed messages。

#### Delivery semantics

Exactly-once delivery is unrealistic. Aim for exactly-once effect:

- client_msg_id for dedup。
- server message_id。
- idempotent delivery ack。
- client can ignore duplicate message_id。

#### Interview answer

> I would design messaging around durable per-conversation message logs and realtime delivery gateways. WebSocket handles online delivery, but the source of truth is the message store ordered by conversation sequence. Offline users sync missed messages from the store and may receive push notifications. Duplicate sends are handled with client message ids and idempotent writes.

### 2. Pastebin / Paste Service

#### Question

设计 Pastebin。用户提交一段文本，系统返回短链接。支持 public/private paste、TTL、large paste、abuse detection、read-heavy traffic。

#### Difference from URL shortener

URL shortener maps short key -> long URL。Pastebin stores content itself：

```
short_key -> paste metadata -> blob/text content
```

核心瓶颈从 redirect latency 变成 content storage、read caching、abuse scanning。

#### Architecture

```
Create Paste API
  -> Key Generator
  -> Metadata DB
  -> Text/Object Store
  -> Abuse Scanner
  -> CDN / Cache
  -> Read API
```

#### Data model

```
paste(paste_id, short_key, owner_id, visibility, expires_at, content_ref, status)
paste_content(content_ref, storage_type, size, checksum)
```

Small paste 可以直接存在 DB text column；large paste 放 object storage。

#### Read path

1. Lookup short_key。
2. Check status / visibility / expiration。
3. Fetch content。
4. Cache hot paste。

#### TTL and deletion

Expired paste：

- read path rejects after `expires_at`。
- background cleanup deletes metadata/content later。
- object storage lifecycle policy can clean large blobs。

#### Interview answer

> Pastebin is similar to URL shortener in key generation but different in storage because the system owns the content. I would store paste metadata in a database and large content in object storage. Reads are cacheable by short key, while expiration is enforced on the read path and cleaned asynchronously. Abuse scanning can run synchronously for obvious cases and asynchronously for deeper checks.

### 3. CAP Theorem Interview Framing

#### Question

面试官问 CAP theorem，应该怎么回答而不是背定义？

#### Correct framing

CAP 不是说系统只能从 C/A/P 三选二。更准确：

> When a network partition happens, a distributed system must choose between consistency and availability for the affected operation.

Partition tolerance 不是可选项。真实分布式系统必须假设网络会失败。

#### CP vs AP examples

CP：

- payment。
- inventory reservation。
- seat booking。
- leader election。

Partition 时宁愿 reject / timeout，也不要产生错误状态。

AP：

- likes count。
- feed freshness。
- analytics。
- presence。

Partition 时可以返回 stale/partial data，之后修复。

#### PACELC extension

CAP 只看 partition。PACELC 更贴近日常：

```
if Partition: choose Availability or Consistency
Else: choose Latency or Consistency
```

很多系统平时就在 latency vs consistency 之间 tradeoff。

#### Interview answer

> I would not treat CAP as a database-labeling exercise. For each operation, I identify the business invariant. If the operation protects money, inventory, or reservations, I choose consistency and may reject requests during a partition. For feeds, counters, and analytics, I can choose availability and serve stale data. The important part is explaining the tradeoff per operation, not calling the whole system CP or AP.

### 4. ML System Design Blueprint

#### Question

ML system design 面试的 blueprint 是什么？怎么避免一上来就讲模型？

#### Blueprint

```
  -> Data collection
  -> Label definition
  -> Feature pipeline
  -> Training
  -> Offline evaluation
  -> Online serving
  -> A/B test
  -> Monitoring
  -> Feedback loop
```

#### Key idea

模型不是系统的起点，目标和 label 才是。比如 recommendation：

- Product objective：increase long-term engagement。
- Prediction target：probability of meaningful watch / click / conversion。
- Label：watch time, completion, hide/report, conversion。

#### Serving split

常见 two-stage：

```
candidate generation -> ranking -> re-ranking
```

Candidate generation 追求 recall，ranking 追求 precision，re-ranking 加 diversity/safety/business constraints。

#### Interview answer

> I would start ML system design from the product objective and prediction target, then work backward to labels, data, features, training, serving, evaluation, and monitoring. The online serving path must meet latency and reliability requirements, while the offline path builds datasets and retrains models. I would validate with both offline metrics and online A/B tests because model metrics alone can be misleading.

### 6. Manager Interview / Sustainable Change

#### Question

如果面试官问“你如何推动一个跨团队 infra 改造？”应该怎么回答？

#### Approach

大型系统改造不只是技术方案，还包括 adoption：

1. Define the pain with data。
2. Find a small high-impact slice。
3. Build migration path。
4. Add observability。
5. Create rollback plan。
6. Document and teach。
7. Measure adoption。

#### Example

迁移 payment webhook processing：

- Problem：duplicates and missed retries caused manual repair。
- First slice：one provider + one event type。
- Change：idempotency table + outbox + retry queue。

- Result：reduced duplicate effects and manual tickets。

#### Interview answer

> For sustainable change, I would avoid a big-bang rewrite. I would quantify the problem, choose a narrow slice, build a migration path with observability and rollback, and prove impact before expanding. Cross-team adoption requires clear contracts, documentation, and dashboards so other teams trust the new path.

   - moderation for malicious edits。

5. Data correction
   - duplicate business merge。
   - moved/closed business。

#### Interview answer

> I would push Yelp beyond a simple geo-search problem. The source of truth includes business profiles, reviews, photos, and user actions, but ranking depends on distance, relevance, rating, freshness, trust, and personalization. Reviews need spam detection and reputation signals, while business metadata updates require moderation and freshness guarantees.

## 29. ML System Design Interview Bank

这一节面向 MLE / AI infra 面试。ML system design 和普通 backend system design 的区别是：你不仅要讲 service、DB、queue、cache，还要讲 data、label、feature、training、evaluation、online serving、feedback loop、monitoring。高分答案要能同时覆盖 model quality 和 production reliability。

### ML System Design 通用回答框架

#### 白板顺序

```
1. Product goal
2. Prediction task
3. Data and labels
4. Feature pipeline
5. Model choice
6. Training pipeline
7. Online serving path
8. Evaluation
9. Monitoring and feedback
10. Failure modes
```

#### 一句话原则

> I would first define the product metric and prediction target, then design the data pipeline, feature pipeline, model training, online serving, evaluation, and monitoring around that target.

#### 不能漏的 tradeoff

- Offline metric vs online business metric。
- Precision vs recall。
- Latency vs model complexity。
- Freshness vs stability。
- Personalization vs privacy。
- Exploration vs exploitation。
- Batch features vs realtime features。
- Model quality vs serving cost。

### 1. Recommendation System Design

#### Question

设计推荐系统，比如首页推荐商品、文章、视频或帖子。用户打开 app 后系统返回 personalized ranked items。

#### 核心结构

推荐系统通常分两阶段：

```
Candidate Generation -> Ranking -> Re-ranking -> Response
```

Candidate generation 负责从海量 item 中快速找几百到几千个候选。Ranking 负责用更复杂模型精排。Re-ranking 处理多样性、业务规则、安全过滤。

#### Architecture

```
User events
  -> Kafka / Event Log
  -> Feature Pipeline
  -> Offline Feature Store
  -> Training Pipeline
  -> Model Registry

Online Request
  -> Candidate Service
  -> Feature Fetcher
  -> Ranking Service
  -> Re-ranker / Filters
  -> Response
```

#### Candidate sources

- Collaborative filtering：相似用户喜欢的 item。
- Content-based：和用户历史内容相似。
- Trending：全站热门。
- Follow graph：关注的人发的内容。
- Fresh content：新内容探索。
- Sponsored / business candidates。

#### Features

User features:

- 用户长期兴趣 embedding。
- 最近点击/观看/购买序列。
- 地域、设备、语言。
- 活跃度、付费状态。

Item features:

- item category、creator、price、freshness。
- text/image/video embedding。
- historical CTR / CVR / watch time。

Context features:

- time of day。
- session intent。
- network type。
- request surface。

#### Label

推荐系统的 label 不能只看 click：

- click：容易被标题党污染。
- dwell time / watch time：更接近满意度。
- purchase / conversion：价值高但稀疏。
- hide / report / skip：负反馈。

可以做 multi-task model：

```
score = w1 * P(click)
      + w2 * E(watch_time)
      + w3 * P(conversion)
      - w4 * P(hide/report)
```

#### Online serving latency

推荐服务通常有严格 latency budget：

```
candidate generation: 20-50 ms
feature fetch: 10-30 ms
ranking: 20-80 ms
re-ranking/filter: 5-20 ms
```

优化：

- 预计算 user embedding / item embedding。
- cache 热门 candidate。
- ranking batch inference。
- 模型蒸馏 / quantization。
- fallback to trending when feature/model unavailable。

#### Interview answer

> I would design the recommender as a multi-stage system. Candidate generation retrieves a few thousand items from collaborative filtering, content similarity, trending, and freshness sources. Ranking uses user, item, and context features to predict business-aligned objectives such as watch time or conversion. Re-ranking applies diversity, safety, freshness, and business constraints. I would monitor both offline metrics and online A/B metrics because offline AUC alone may not predict product impact.

### 2. Video Recommendation System

#### Question

设计短视频推荐系统。用户滑动视频流，系统要持续推荐可能观看、点赞、分享的视频。

#### 为什么比普通推荐更难

Video recommendation 的目标不是简单 click，而是 engagement quality：

- watch time。
- completion rate。
- replay。
- like/share/comment。
- not interested / report。
- creator diversity。

而且 feedback 是 sequence-based：用户连续刷视频，当前推荐会影响后续行为。

#### Architecture

```
Playback Events
  -> Realtime Event Pipeline
  -> User Session Features
  -> Candidate Retrieval
  -> Ranking Model
  -> Diversity / Safety Re-ranker
  -> Feed Response
```

#### Candidate generation

- User embedding ANN search。
- Item-to-item similarity from recent watches。
- Trending in geo/language/category。
- Creator follow graph。
- New creator exploration。
- Safety-approved candidate pool。

#### Ranking features

- user long-term interests。
- session short-term interests。
- video embedding。
- creator quality。
- video freshness。
- predicted watch time。
- negative feedback probability。

#### Re-ranking

视频流不能只按分数排序，还要处理：

- diversity：避免连续同类视频。
- freshness：插入新内容。
- creator cap：避免一个 creator 占满 feed。
- safety：敏感内容过滤。
- fatigue：用户刚看过类似内容就降权。

#### Cold start

New user:

- 使用 geo/language/device/default trending。
- 快速收集 onboarding signals。
- 增加 exploration。

New video:

- 小流量 exploration bucket。
- 根据早期 watch/completion 估计质量。
- 表现好再扩大曝光。

#### Interview answer

> For video recommendation, I would optimize for watch quality rather than clicks only. The system uses multi-source candidate generation, then a ranking model predicts watch time, completion, engagement, and negative feedback. A re-ranker enforces diversity, safety, freshness, and creator caps. For cold start, I would use controlled exploration and gradually expand exposure based on early engagement signals.

### 3. Bot Detection ML System

#### Question

设计 bot detection system。系统要识别虚假账号、自动化行为、刷量、垃圾注册，同时尽量不误伤正常用户。

#### Prediction task

这是 risk scoring 问题：

```
input: user/account/session/activity features
output: risk score or class: human / suspicious / bot
```

#### Signals

Account features:

- account age。
- email/phone verification。
- device count。
- IP / ASN / geo。

Behavior features:

- click interval。
- request rate。
- repeated action pattern。
- session duration。
- mouse/touch dynamics, if available。

Graph features:

- shared device / IP clusters。
- referral graph。
- payment instrument reuse。
- follow/like network anomalies。

Content features:

- repeated text。
- spam URL。
- template similarity。

#### Architecture

```
Events
  -> Feature Aggregation
  -> Online Feature Store
  -> Risk Scoring Service
  -> Policy Engine
       - allow
       - challenge
       - rate limit
       - shadow ban
       - block
  -> Analyst Review / Feedback
```

#### Precision vs recall

Bot detection 不能只追求 recall。误封正常用户代价很高。通常分层处理：

| Risk score | Action |
|---|---|
| low | allow |
| medium | rate limit / captcha / phone verification |
| high | block / manual review |

#### Adversarial nature

Bot 会适应模型，所以要：

- monitor feature drift。
- rotate rules/features。
- keep some signals private。
- add graph-based features。
- use human review feedback。

#### Interview answer

> I would frame bot detection as a risk scoring system, not a binary classifier that immediately bans users. The model combines account, behavior, graph, and content signals. The policy engine maps risk score to graduated actions such as allow, challenge, rate limit, review, or block. Because attackers adapt, I would monitor drift, keep feedback loops from manual review, and avoid exposing exact thresholds.

### 4. Harmful Content Detection

#### Question

设计 harmful content detection system，识别暴力、仇恨、色情、垃圾内容、诈骗或 policy violation。需要支持文字、图片、视频，多语言，低延迟和高准确率。

#### Pipeline

```
Content Upload
  -> Lightweight synchronous checks
  -> Async ML moderation pipeline
       - text classifier
       - image classifier
       - video frame sampler
       - audio transcription
       - policy model
  -> Decision Service
  -> Human Review Queue
  -> Enforcement
```

#### Synchronous vs asynchronous

同步检查：

- hash match known bad content。
- URL blocklist。
- lightweight text rules。
- small model quick score。

异步检查：

- heavy vision/video model。
- multi-frame analysis。
- human review。

#### Decision design

不要只有 delete/allow：

- allow。
- downrank。
- age gate。
- blur / warning。
- send to review。
- remove。
- account strike。

#### Video 特殊处理

Video 很贵，不能每帧跑大模型：

- sample key frames。
- scene change detection。
- audio ASR。
- OCR for embedded text。
- escalate only suspicious videos to heavy model。

#### Evaluation

核心指标：

- precision：被拦截的是否真的违规。
- recall：违规内容是否漏掉。
- false positive rate by user/content group。
- review queue latency。
- appeal overturn rate。

#### Interview answer

> I would use a tiered moderation pipeline. Cheap synchronous checks catch known bad content and obvious violations before publication. Heavier multimodal models and human review run asynchronously. The decision service supports graduated enforcement such as allow, downrank, warning, review, remove, and account strike. I would monitor precision, recall, appeal overturn rate, and review latency because false positives can seriously harm user trust.

### 5. ML Evaluation and Experimentation

#### Offline evaluation

Offline metrics depend on task：

| Task | Metrics |
|---|---|
| Binary classifier | AUC, precision, recall, F1, calibration |
| Ranking | NDCG, MAP, MRR, recall@K |
| Recommendation | hit rate, watch time proxy, diversity |
| Generation | human eval, safety, latency, quality score |
| Fraud/risk | precision at high recall, false positive rate |

#### Online evaluation

最终要看 A/B test：

- CTR。
- conversion。
- watch time。
- retention。
- revenue。
- complaint/report rate。
- latency/cost。

#### Why offline can lie

- Training data bias。
- Position bias。
- Delayed feedback。
- Label leakage。
- Distribution shift。
- Metric mismatch。

#### Experiment guardrails

上线新模型不能只看主指标：

- error rate。
- P95/P99 latency。
- cost per request。
- bad content/report rate。
- fairness / false positive by segment。
- business guardrails。

#### Interview answer

> I would use offline evaluation to filter bad models, but I would not rely on it as the final decision. Offline metrics can suffer from bias, leakage, and metric mismatch. The final validation is an online experiment with product metrics and guardrails such as latency, error rate, cost, and safety metrics. I would also slice metrics by important user segments to catch regressions hidden in averages.

### 6. Feature Store / Training-Serving Consistency

#### Problem

训练时用一套 feature，线上 serving 用另一套计算逻辑，很容易产生 training-serving skew。

#### Feature store 结构

```
Raw events
  -> Batch feature pipeline
  -> Offline feature store
  -> Training datasets

Raw/realtime events
  -> Streaming feature pipeline
  -> Online feature store
  -> Model serving
```

#### Feature types

- Batch features：过去 7 天点击数、历史购买次数。
- Realtime features：最近 5 分钟行为、当前 session。
- Embedding features：user/item vector。
- Context features：device、time、geo。

#### Point-in-time correctness

训练数据不能使用未来信息。构建 training set 时要 point-in-time join：

```
label time = T
feature value must be computed using data <= T
```

#### Consistency strategy

- 共享 feature definition。
- 离线和在线同源逻辑。
- feature versioning。
- backfill support。
- monitor missing/default feature rate。

#### Interview answer

> I would design the feature store to keep offline training features and online serving features consistent. Training data must use point-in-time joins to avoid leakage. Feature definitions should be versioned and shared across batch and realtime pipelines. Online serving monitors missing feature rate, default value rate, and feature distribution drift.

### 7. Model Serving and Rollout

#### Generic serving architecture

```
Model Registry
  -> Deployment Controller
  -> Online Inference Service
  -> Feature Fetcher
  -> Prediction Logger
  -> Monitoring
```

#### Rollout strategy

1. Offline evaluation。
2. Shadow traffic。
3. Canary 1%。
4. A/B test。
5. Gradual ramp。
6. Rollback if guardrails regress。

#### Prediction logging

线上要记录：

- model version。
- feature snapshot or feature references。
- prediction score。
- decision。
- request context。
- later label, when available。

这些用于 debugging、retraining、bias analysis。

#### Fallback

模型服务失败时不能让产品完全不可用：

- cached recommendations。
- rule-based baseline。
- popular/trending fallback。
- previous stable model。
- degrade heavy model to smaller model。

#### Interview answer

> I would put every model version in a registry with artifact, config, features, and evaluation results. New models first receive shadow traffic, then canary or A/B traffic. The serving path logs predictions with model version and feature references so we can join future labels. If the model or feature store fails, the product falls back to cached, rule-based, or previous-model results.

### 8. Drift, Monitoring, and Feedback Loop

#### What to monitor

System metrics:

- QPS。
- latency。
- error rate。
- timeout。
- CPU/GPU utilization。
- cost per request。

ML metrics:

- feature distribution drift。
- prediction score drift。
- calibration。
- missing feature rate。
- label distribution。
- delayed outcome metrics。

Business metrics:

- CTR / conversion。
- retention。
- complaint/report。
- revenue。
- moderation appeals。

#### Drift types

- Data drift：input distribution changes。
- Concept drift：relationship between feature and label changes。
- Label drift：label distribution changes。

#### Feedback loop risk

推荐系统会影响自己看到的数据。例如模型推荐什么，用户就只能点击什么。这会造成 exposure bias。解决：

- exploration bucket。
- randomized logging for evaluation。
- counterfactual / debiasing methods。
- holdout traffic。

#### Interview answer

> I would monitor both production health and model health. Production metrics tell me whether serving is reliable; model metrics tell me whether the predictions still match reality. I would track feature drift, prediction drift, missing features, delayed labels, and business metrics. For recommenders, I would keep some exploration traffic because the model's own decisions affect future training data.

### 9. Generalization and Data Quality

#### 常见问题

- 模型只在训练集/老用户上表现好。
- 新用户、新地区、新设备效果差。
- Label noisy。
- Data leakage。
- Long-tail case 没覆盖。

#### Data quality checks

- schema validation。
- null/default rate。
- duplicate events。
- timestamp sanity。
- label delay。
- feature range。
- train/serving distribution comparison。

#### Slicing

不要只看整体 metric。要按 segment 看：

- country / language。
- device type。
- new vs existing user。
- traffic source。
- content category。
- model version。

#### Interview answer

> I would not trust aggregate model metrics alone. I would slice evaluation by important user, content, and traffic segments to catch regressions. I would also build data quality checks for missing values, duplicate events, timestamp issues, and label leakage. Generalization problems are often data problems before they are model architecture problems.

### 10. ML System Design 面试高分模板

#### 开场模板

> I would start by clarifying the product objective and the prediction target. Then I would design the data collection, labeling strategy, feature pipeline, model training, online serving, evaluation, and monitoring around that target.

#### 讲 architecture 模板

> The offline path builds training data and trains models. The online path fetches features and serves predictions within the latency budget. Events from online traffic are logged back into the data lake, joined with delayed labels, and used for retraining and evaluation.

#### 讲 tradeoff 模板

> The main tradeoff is model quality versus latency and cost. A larger model may improve offline metrics, but if it increases P99 latency or reduces system reliability, it may hurt the product. I would use a multi-stage design where cheap retrieval narrows candidates and a heavier ranker only scores a small set.

#### 讲 monitoring 模板

> I would monitor serving health, feature health, model score distribution, delayed labels, and business metrics. I would alert on latency, errors, missing feature rate, drift, and guardrail regressions. Every prediction should include model version and feature references for debugging and retraining.

## 30. Specialized System Design & LLD Extras

这一节继续消化 `sd_pages` 里还没有完整覆盖的 specialized questions。它们有些原文只有图片或导航噪声，所以这里按题目意图重写成面试可直接讲的版本：先定义 question，再给 approach、数据模型、关键 tradeoff、follow-up 答法。

### 1. Fitness Tracking App / Strava

#### Question

设计 Strava 类 fitness tracking app。用户可以记录跑步/骑行活动，上传 GPS trace，查看距离、速度、路线、历史活动、朋友动态、leaderboard，并可选择实时分享活动位置。

#### Approach

核心不是“每秒上传 GPS”，而是区分两条路径：

- Activity recording path：移动端本地记录 GPS points，活动结束后批量上传。
- Social/realtime path：只有开启 live sharing 时才定期上传位置。

这样可以省电、省流量，也减少后端写入压力。

#### Architecture

```
Mobile App
  -> Activity API
  -> Activity Service
  -> GPS Trace Store / Object Storage
  -> Activity Metadata DB
  -> Async Stats Processor
  -> Feed / Social Service
  -> Leaderboard Service
```

#### Data model

```
activity(activity_id, user_id, type, start_at, end_at, distance, duration, status)
activity_point(activity_id, seq, lat, lon, elevation, timestamp)
segment_effort(segment_id, activity_id, user_id, duration, speed)
leaderboard(scope, activity_type, period, user_id, score)
```

GPS points 可以压缩后放 object storage，metadata 放 DB。读 activity detail 时再拉 trace。

#### Leaderboard

不要每次查询都 scan activities。可以用：

- Daily batch aggregation：适合周/月榜。
- Redis sorted set：适合实时榜。
- Scope key：`leaderboard:run:US:2026-07-08`。

活动完成后异步更新 leaderboard。允许 eventual consistency。

#### Live sharing follow-up

如果朋友要看实时位置：

- athlete device 每 2-5 秒上传 location update。
- viewer 可以 polling / SSE / WebSocket。
- 位置展示可以故意 buffer 5-10 秒，让动画更平滑。
- 不必为了秒级精度过度设计。

#### Interview answer

> I would keep normal activity recording mostly client-side and upload the full trace after completion. The server stores metadata separately from compressed GPS traces. Derived stats, social feed items, segment efforts, and leaderboards are updated asynchronously. For live sharing, I would upload periodic location updates and choose polling, SSE, or WebSocket based on fanout and freshness requirements.

### 2. News Aggregator / Google News

#### Question

设计 Google News 类 news aggregator。系统要抓取多来源新闻，去重相似文章，按 topic 聚类，排序展示，并支持搜索、个性化和 breaking news。

#### Approach

新闻系统的核心是 ingestion + dedup + ranking：

```
Source Crawlers
  -> Article Parser
  -> Canonical Article Store
  -> Dedup / Clustering
  -> Search Index
  -> Ranking / Personalization
  -> News API
```

#### Data model

```
source(source_id, domain, crawl_policy, trust_score)
article(article_id, source_id, url, title, body_ref, published_at, language)
cluster(cluster_id, topic, canonical_article_id, article_ids, updated_at)
user_interest(user_id, topic, score)
```

#### Dedup and clustering

同一新闻会被多个媒体报道。不能只按 URL 去重，要用：

- canonical URL。
- title normalized hash。
- content fingerprint / simhash。
- embedding similarity。
- published time window。

Cluster 是 derived data，可以重建。

#### Ranking

排序信号：

- freshness。
- source authority。
- local relevance。
- topic popularity。
- user interest。
- diversity，避免同一 source 占满首页。

Breaking news 可以给 freshness boost，但要有可信来源阈值，避免谣言。

#### Failure modes

- crawler 抓取失败：retry + backoff。
- source 内容变更：re-parse。
- duplicate cluster 错误：manual/editorial correction。
- 个性化模型失败：fallback to regional top stories。

#### Interview answer

> I would design a news aggregator as an ingestion and ranking pipeline. Crawlers fetch articles, parsers normalize content, dedup/clustering groups similar stories, and search/ranking indexes serve user requests. The article store is the source of truth, while clusters and personalized feeds are derived. Ranking balances freshness, authority, relevance, diversity, and safety.

### 3. YouTube Top K Videos

#### Question

设计 YouTube Top K videos feature。按时间窗口返回最热视频，比如全站 top videos、某国家 top videos、某 category top videos。

#### Core challenge

Top K 看似简单，难点是 event volume 极大，窗口多，维度多，不能每次 query 都 scan。

#### Architecture

```
View / Like / Watch Events
  -> Kafka
  -> Stream Processor
  -> Windowed Counters
  -> Top-K Aggregator
  -> Redis / OLAP Store
  -> Top-K API
```

#### Event schema

```
event_id
video_id
user_id_hash
event_type: view/like/watch_time
watch_seconds
country
category
timestamp
```

#### Algorithm

可以两层聚合：

1. Per-shard local top K。
   - 每个 stream task 维护 local heavy hitters。
   - 定期输出 top candidates。

2. Global merge。
   - 合并各 shard candidates。
   - 计算全局 top K。

对于巨大流量，可以用 approximate algorithm：

- Count-Min Sketch for approximate counts。
- Space-Saving / Heavy Hitters for candidate top K。
- Exact correction for final candidates。

#### Time windows

```
top:global:1h
top:global:24h
top:US:sports:1h
top:JP:music:24h
```

Window 使用 event time + watermark，迟到事件可以小幅修正。

#### Interview answer

> I would not compute Top K from raw events at query time. View and engagement events go into Kafka, stream processors maintain windowed counters, and each shard emits local top candidates. A global aggregator merges candidates into final Top K per region/category/window. For very high volume, I would use approximate heavy-hitter algorithms and then correct exact counts for the final candidates.

### 4. Uber Location Index

#### Question

设计 Uber driver location index。乘客请求附近司机，司机每几秒更新位置，系统需要快速查询某个 pickup 点附近可用司机。

#### Core challenge

位置是高频更新数据。普通 DB secondary index 不适合频繁写入和半径查询。要用空间索引，把经纬度映射成 cell。

#### Architecture

```
Driver App
  -> Location Ingest Service
  -> Location Index Service
       - geohash / S2 / H3 cell index
       - TTL / heartbeat
  -> Matching Service
  -> Trip Service
```

#### Data model

```
driver_location(driver_id, lat, lon, heading, speed, updated_at, status)
cell_index(cell_id, driver_id, updated_at)
```

实际系统通常用内存 store / Redis / custom service，而不是每次写 DB。

#### Query flow

1. Pickup lat/lon -> cell id。
2. 查询当前 cell。
3. 如果不足，查询 neighbor cells。
4. 对 candidates 计算真实距离和 ETA。
5. 过滤 busy/offline/stale drivers。
6. 传给 matching/ranking。

#### Update flow

司机每 2-5 秒发送位置：

- 如果 cell 没变，只更新 location payload。
- 如果 cell 变了，从旧 cell remove，加入新 cell。
- 每条 location 有 TTL，过期视为 offline。

#### Tradeoffs

- Cell 太大：candidate 多，精排成本高。
- Cell 太小：neighbor 查询多，司机频繁跨 cell。
- 位置新鲜度越高，写入压力越大。
- matching 需要 ETA，不只是直线距离。

#### Interview answer

> I would build an in-memory geospatial index using geohash, S2, or H3 cells. Driver updates refresh their current cell with TTL. A rider query looks up the pickup cell and neighboring cells, filters stale or unavailable drivers, then ranks candidates by ETA. The source of truth for trips is the Trip Service; the location index is ephemeral and optimized for fast nearby lookup.

### 7. Design SQL / In-memory Relational Table

#### Question

设计一个简化 SQL engine / in-memory table，支持 create table、insert row、select with condition、delete/update，可能扩展到 index 和 transaction。

#### LLD approach

先不要写 parser。先定义 domain model：

```java
class Database {
  Map<String, Table> tables;
}

class Table {
  String name;
  Schema schema;
  List<Row> rows;
  Map<String, Index> indexes;
}

class Row {
  long rowId;
  Map<String, Value> values;
}
```

#### Operations

1. `createTable(name, schema)`
   - validate duplicate table。
   - store column definitions。

2. `insert(table, row)`
   - validate schema。
   - assign row id。
   - append row。
   - update indexes。

3. `select(table, predicate)`
   - if indexed column, use index。
   - else scan rows。

4. `delete/update`
   - update base rows and index entries consistently。

#### Index design

```java
interface Index {
  void add(Value key, long rowId);
  void remove(Value key, long rowId);
  Set<Long> lookup(Value key);
}
```

Hash index supports equality. Tree index supports range.

#### Follow-up: transaction

先讲 single-threaded correctness，再扩展：

- table-level lock for simple version。
- row-level lock for concurrency。
- WAL for durability。
- MVCC for read/write concurrency。

#### Interview answer

> I would separate SQL parsing from execution. The core model has Database, Table, Schema, Row, and Index. Inserts validate schema, append rows, and update indexes. Select uses an index when possible and falls back to scan. For transactions, I would start with table-level locking and WAL, then discuss row locks or MVCC as the system matures.

### 10. Real-time Systems Two-hop Framework

#### Question

面试里遇到实时系统，比如 live comments、presence、collaborative editing、driver tracking、chat typing indicator，该如何快速判断用 polling、SSE、WebSocket，还是 pub/sub?

#### Two-hop mental model

实时系统可以拆成两跳：

```
Hop 1: producer -> backend
Hop 2: backend -> consumers
```

先问每一跳的方向、频率、fanout、latency，再选技术。

#### Decision table

| Pattern | Producer to backend | Backend to consumer | Best choice |
|---|---|---|---|
| Order status | rare updates | one user | polling / SSE |
| Live location | predictable every few sec | small friends group | polling / SSE |
| Chat | bidirectional | participants | WebSocket |
| Live comments | many producers | many viewers | WebSocket gateway + pub/sub |
| Notification | backend event | user devices | push + inbox |

#### Architecture

```
Producer
  -> Write API
  -> Event Bus / PubSub
  -> Fanout Service
  -> Connection Gateway
  -> Consumer
```

#### Backpressure

实时连接必须有内存保护：

- per-connection buffer limit。
- drop/coalesce low-value events。
- disconnect slow clients。
- replay from durable log only when required。

#### Interview answer

> I would break realtime design into producer-to-backend and backend-to-consumer hops. If updates are predictable and low fanout, polling or SSE may be enough. If communication is bidirectional or high fanout, I would use WebSocket gateways backed by pub/sub. The important production detail is backpressure: slow clients need buffer limits, event coalescing, or disconnect policies.

### 11. OOP Concepts / Design Principles Follow-up

#### Question

LLD 面试里常追问 OOP principles、design patterns、SOLID。怎么讲才不是背概念？

#### Useful framing

把原则绑定到变化点：

- Strategy：算法会变，比如 pricing、parking spot assignment、rate limit algorithm。
- Observer：事件通知，比如 locker pickup notification、order status update。
- Factory：对象创建复杂，比如 payment method、vehicle、notification channel。
- State：状态转换复杂，比如 order、auction、elevator。
- Repository：隔离 persistence，方便测试。

#### SOLID 用法

- Single Responsibility：class 只负责一个变化原因。
- Open/Closed：新增策略不改核心流程。
- Liskov：子类不破坏父类契约。
- Interface Segregation：不要让 client 依赖用不到的方法。
- Dependency Inversion：业务逻辑依赖 interface，不依赖具体 DB/Redis。

#### Example

Parking lot 不要这样：

```java
class ParkingLot {
  Money calculateFee(Ticket t) { ... }
  Spot findSpot(Vehicle v) { ... }
  void chargeCard(...) { ... }
}
```

更好：

```java
class ParkingLot {
  SpotAssignmentStrategy assignment;
  PricingPolicy pricing;
  PaymentService payment;
}
```

#### Interview answer

> I would explain design principles through change points. If pricing can change, I use a PricingPolicy strategy. If notifications can have multiple channels, I use an interface and dependency injection. If an entity has complex transitions, I make the state machine explicit. The goal is not to add patterns everywhere, but to keep the core flow readable and make expected changes cheap.

## 31. Multi-GPU LLM Inference Serving

### 题目背景

白板设计一个高吞吐的 Multi-GPU 大模型推理服务。面试官通常不是想听“把模型部署到 GPU 上”，而是想看你是否理解 LLM serving 的核心瓶颈：

- GPU memory 被 model weights、KV Cache、activation workspace 同时争抢。
- Prefill 和 decode 的计算形态完全不同。
- Continuous batching 提高吞吐，但会让 KV Cache 生命周期更复杂。
- Multi-GPU tensor parallelism 会引入 All-Reduce / All-Gather 通信延迟。
- 极长 prompt 或突发长输出会把 KV memory pool 打爆，必须能 graceful degradation。

### 高层架构

```
Client
  -> API Gateway / Auth / Rate Limit
  -> Request Router
  -> Admission Controller
  -> Scheduler / Continuous Batcher
  -> GPU Worker Node
       - Model Executor
       - KV Cache Manager
       - Token Scheduler
       - NCCL Communication
       - Metrics / OOM Guard
  -> Streaming Response
```

### 核心组件

1. API Gateway
   - 做 auth、rate limit、request size limit、tenant quota。
   - 尽早拒绝明显过长或不合法请求，避免进入 GPU 队列后浪费资源。

2. Router
   - 根据 model name、tenant、SLA、当前 GPU load、KV cache free blocks，把请求路由到合适的 replica。
   - 可以区分 latency-sensitive traffic 和 throughput-oriented batch traffic。

3. Admission Controller
   - 根据 prompt length、max_new_tokens、当前 KV cache free blocks 估算 worst-case memory。
   - 如果资源不足，选择 reject、queue、降级 max tokens、swap、preempt。

4. Scheduler / Continuous Batcher
   - 不是固定 batch size，而是 iteration-level scheduling。
   - 每个 decode step 动态把还活着的 requests 合成一个 batch。
   - 已完成的 request 释放 KV blocks，新 request 可以插入 batch。

5. KV Cache Manager
   - 管理每个 sequence 的 K/V tensor blocks。
   - 处理 block allocation、free、sharing、eviction、swap、preemption。

6. Model Executor
   - 执行 prefill 和 decode。
   - 支持 Tensor Parallelism、Pipeline Parallelism、CUDA Graph、fused kernels、quantization。

### Request lifecycle

```
1. Receive request
2. Tokenize prompt
3. Estimate KV cache requirement
4. Admission control
5. Prefill: process prompt tokens, build initial KV cache
6. Decode loop:
   - scheduler forms active batch
   - allocate one new KV slot per active sequence
   - run model forward for next token
   - stream token back
   - stop when EOS / max_new_tokens / timeout
7. Free KV blocks
```

### Prefill vs Decode

| 阶段 | 输入形态 | 主要瓶颈 | 优化重点 |
|---|---|---|---|
| Prefill | 一次处理完整 prompt | compute-heavy, attention over prompt | 大 batch、FlashAttention、chunked prefill |
| Decode | 每轮每个 request 生成 1 个 token | memory bandwidth + KV cache read | continuous batching、KV cache paging、CUDA Graph |

重要判断：

- Prefill 吃计算，长 prompt 会占用大量 compute。
- Decode 吃显存带宽和 KV cache，batch 越大，吞吐越高，但 latency 也可能上升。
- Scheduler 要平衡 prefill 和 decode，避免长 prompt 把 decode traffic 饿死。

### KV Cache 是显存刺客

LLM 推理时，KV Cache 会随着 sequence length 线性增长。每个 request 不只占 prompt memory，还会为未来生成 tokens 持续申请 KV space。

粗略公式：

```
KV memory ~= num_layers
           * sequence_length
           * hidden_size
           * 2(K and V)
           * bytes_per_element
           * batch_size
```

如果是 Tensor Parallelism，KV cache 也可能按 heads / hidden dimension 切到不同 GPU 上，但总量仍然巨大。

### 为什么普通 continuous batching 还不够

Continuous batching 解决的是 GPU utilization：每轮 decode 动态组成 batch，让 GPU 不空转。

但它没有自动解决 memory fragmentation：

- 每个 request 长度不同。
- 有的 request 早结束，有的继续生成。
- 如果为每个 request 预分配连续大块显存，会产生大量 unused holes。
- 长 prompt 进来时，可能总 free memory 足够，但找不到连续空间。

所以高分答案必须讲 KV Cache 的 block-based memory management。

### PagedAttention / Block-based KV Cache

核心思想：像操作系统虚拟内存一样管理 KV Cache。

不要为每个 sequence 分配一整段连续 KV memory，而是把 KV Cache 切成固定大小 blocks。

```
Logical sequence tokens:
  token 0 ... token 15 | token 16 ... token 31 | token 32 ...

Logical KV blocks:
  logical block 0 -> physical block 17
  logical block 1 -> physical block 3
  logical block 2 -> physical block 91
```

### KV block table

每个 request 维护一个 block table：

```
request_id
logical_block_id -> physical_block_id
```

Attention kernel 读取 KV 时，通过 block table 找到实际物理 block。物理 blocks 可以不连续。

### 这样解决什么问题

1. 减少 external fragmentation
   - 不需要连续大块显存。
   - 只要有足够 free blocks，就可以服务 request。

2. 减少 internal fragmentation
   - 只在最后一个 block 可能有浪费。
   - block size 越小，浪费越少，但 kernel overhead 和 metadata overhead 变高。

3. 支持 dynamic growth
   - 每生成新 token，只在当前 block 满了后再申请新 block。

4. 支持 sharing
   - 多个 request 共享相同 prefix 时，可以共享 prefix KV blocks。
   - Beam search / parallel sampling / agent branching 特别受益。

### KV Cache Manager 需要哪些数据结构

```
GlobalBlockPool:
  free_block_list
  used_block_map
  ref_count
  block_location: GPU / CPU / evicted

SequenceState:
  request_id
  logical_block_table
  current_length
  max_tokens
  priority
  status: RUNNING / WAITING / SWAPPED / PREEMPTED / FINISHED
```

### KV block lifecycle

```
Request admitted
  -> allocate blocks for prefill
  -> decode needs more tokens
  -> allocate next block when current block full
  -> request finishes
  -> decrement ref_count
  -> free blocks back to pool
```

如果 prefix sharing：

```
shared prefix block ref_count += 1
child request writes new tokens to private blocks
```

### Memory pool 图可以这样画

```
GPU KV Block Pool

[free][used A][used A][free][used B][shared][used C][free]
   |      |       |            |       |        |
free list |       |            |       |        |
          request A table      request B        request C

Request A logical blocks:
  0 -> physical 1
  1 -> physical 2

Request B logical blocks:
  0 -> physical 4
  1 -> physical 5(shared)

Request C logical blocks:
  0 -> physical 5(shared)
  1 -> physical 6
```

这张图的表达重点是：sequence 逻辑上连续，物理显存可以不连续。

### Admission control：不要等 OOM 才处理

收到请求时先估算：

```
required_blocks =
  ceil((prompt_tokens + max_new_tokens) / block_size)
```

更保守的系统会区分：

- guaranteed blocks：prompt prefill 必须马上有。
- speculative blocks：未来 decode 可能需要，可以边生成边申请。
- tenant quota blocks：每个用户或业务线最多占多少 KV blocks。

Admission Controller 的输出：

1. Accept now。
2. Queue。
3. Accept with reduced `max_new_tokens`。
4. Ask client to shorten prompt。
5. Route to another replica。
6. Reject with clear error。

### 极长 prompt 打进来，KV pool 见底怎么办

这是高频 follow-up。正确答案不是“让它 OOM”，而是分层 graceful degradation。

#### 1. Hard admission limit

在进 GPU 前限制：

- max prompt tokens。
- max total tokens = prompt + output。
- per-tenant KV block quota。
- per-request max blocks。

如果请求超过 hard limit，直接拒绝或要求 truncation。

#### 2. Chunked prefill

长 prompt 不一次性 prefill，而是切成 chunks：

```
long prompt
  -> chunk 1 prefill
  -> yield to decode batch
  -> chunk 2 prefill
  -> yield again
```

这样避免一个长 prompt 长时间霸占 GPU，也减少 tail latency。

#### 3. Preemption

如果新请求优先级更高，或者系统需要释放显存，可以暂停低优先级 sequence：

```
RUNNING -> PREEMPTED
free or swap its KV blocks
later resume
```

Preemption 的关键是要有 sequence state 和 block table，知道哪些 KV blocks 属于哪个 request。

#### 4. Swap KV Cache to CPU memory

把低优先级或暂时不活跃 request 的 KV blocks 从 GPU 显存 swap 到 CPU pinned memory。

优点：

- 不需要重新计算 prompt。
- 可以保留长上下文。

缺点：

- PCIe / NVLink copy latency 高。
- Resume 时要把 KV blocks 拷回 GPU。
- 对 latency-sensitive request 不友好。

适合：

- 长上下文 batch job。
- 用户可以接受较高 latency。
- 比 recomputation 更便宜的场景。

#### 5. Recomputation

释放某些 KV blocks，之后需要时重新跑 prefill 计算恢复 KV cache。

优点：

- 节省 GPU memory。
- 不占 CPU memory / PCIe bandwidth。

缺点：

- 需要额外 compute。
- 长 prompt recomputation 很贵。

适合：

- GPU memory 极度紧张。
- Prompt 不太长。
- Compute 比 memory 更富余。

#### 6. Degrade generation policy

对低优先级请求降低资源需求：

- 降低 `max_new_tokens`。
- 禁用 parallel sampling / beam search。
- 降低 best-of。
- 降低并发。
- 切到小模型或量化模型。
- 返回 partial result / retry-after。

### Follow-up 答案模板

> I would not let a long prompt enter the GPU blindly. First, the admission controller estimates KV blocks based on prompt length and max output tokens. If the request exceeds hard limits, I reject or ask the client to truncate. If it is acceptable but the pool is tight, I use chunked prefill, queueing, or route it to another replica. Under pressure, I can preempt lower-priority sequences and either swap their KV blocks to CPU memory or recompute them later. The trade-off is latency versus memory: swapping preserves compute but pays PCIe/NVLink copy cost, while recomputation saves memory but burns GPU cycles.

### Multi-GPU parallelism

大模型单卡放不下，或者单卡吞吐不够时，需要多 GPU。

常见 parallelism：

| 方式 | 怎么切 | 优点 | 缺点 |
|---|---|---|---|
| Tensor Parallelism | 单层矩阵按 hidden/head 切到多卡 | 单层模型可跨卡，decode 常用 | 每层需要 All-Reduce / All-Gather |
| Pipeline Parallelism | 不同 layers 放不同 GPU | 减少单层通信 | pipeline bubble，batch 小时利用率差 |
| Data Parallelism | 每张卡一份完整模型 | 简单、吞吐好 | 模型必须单卡放得下 |
| Expert Parallelism | MoE experts 分布到不同 GPU | MoE 模型扩展好 | routing 和 token dispatch 复杂 |

### Tensor Parallelism 的通信瓶颈

Tensor Parallelism 把一层的矩阵乘拆到多张 GPU。每张 GPU 算部分结果，然后需要 collective communication 合并。

常见通信：

- All-Reduce：把各卡 partial result 求和并广播给所有卡。
- All-Gather：收集各卡 partial tensor。
- Reduce-Scatter：reduce 后切分结果给各卡。

Decode 阶段每 token 都要过所有 layers，所以 All-Reduce latency 会被放大。

### 为什么 All-Reduce 会成为 latency bottleneck

- Decode 每次只生成一个 token，单步 compute 不一定足够大。
- 单步计算粒度小，communication overhead 更明显。
- 跨 PCIe 的通信比 NVLink / NVSwitch 慢很多。
- TP degree 越高，每步 collective 越频繁。

### 如何优化 multi-GPU 通信

#### 1. Overlap computation and communication

把通信和后续计算重叠：

```
GPU computes partial GEMM
start async All-Reduce on stream A
meanwhile compute next independent part on stream B
wait only when result is needed
```

目标不是消灭通信，而是隐藏通信。

#### 2. Fused kernels

把多个小 kernel 合并，减少 kernel launch overhead 和中间 memory traffic。

例如：

- fused attention
- fused RMSNorm
- fused bias + activation
- fused communication + computation when possible

#### 3. Topology-aware placement

模型切分要考虑硬件拓扑：

- 同一个 TP group 尽量放在 NVLink / NVSwitch 内。
- 避免频繁跨 PCIe root complex。
- 跨节点通信比单节点更贵，除非有高速 InfiniBand。

#### 4. 合理选择 TP degree

TP degree 不是越大越好。

- TP 太小：单卡 memory 不够或 compute 不够。
- TP 太大：communication overhead 太高。

面试里可以说会根据 model size、GPU memory、interconnect bandwidth、batch size 做 profiling。

#### 5. Prefill / Decode 分离

Prefill 和 decode 的资源形态不同，可以拆成不同 worker pool：

- Prefill workers：适合大 batch、compute-heavy。
- Decode workers：适合低 latency、持续 token generation。

这种 disaggregated serving 可以减少长 prompt 对 decode latency 的影响，但系统复杂度更高，需要 KV transfer 或 prefix handoff。

### Scheduler 高分点

一个好的 LLM scheduler 不只是 batch requests，还要同时考虑：

- token budget：每轮最多处理多少 tokens。
- KV block budget：每轮最多占多少 blocks。
- prefill/decode fairness：避免长 prompt 饿死 decode。
- priority：高优先级用户或 interactive request 优先。
- deadline：有 SLA 的请求优先。
- fragmentation：优先调度能复用 blocks 或短请求。
- starvation prevention：低优先级也不能永远不跑。

### Metrics / Observability

LLM serving 必须监控：

- Time to first token (TTFT)。
- Inter-token latency (ITL)。
- End-to-end latency。
- Tokens/sec per GPU。
- GPU utilization。
- HBM memory usage。
- KV cache free blocks / used blocks。
- KV cache fragmentation / block waste。
- Preemption count。
- Swap in/out bytes。
- OOM prevention count。
- Queue length。
- Request reject / degrade rate。
- NCCL All-Reduce latency。
- Consumer / scheduler lag。

### 白板画法

你可以画三层：

```
Control Plane:
  Gateway -> Router -> Admission Controller -> Scheduler

GPU Worker:
  Continuous Batcher -> Model Executor -> NCCL TP Group
                  \-> KV Cache Manager -> GPU Block Pool

Degradation:
  Queue / Preempt / Swap to CPU / Recompute / Reject
```

然后重点展开 KV Cache Manager：

```
Sequence A block table: [7, 9, 12]
Sequence B block table: [7(shared), 15]
Free list: [2, 3, 4, 20, 21]
CPU swapped blocks: [30, 31]
```

### Vision / Video Generation Inference 重点

如果岗位是基础大模型 Vision / Video generation 的 MLE，面试重点会比普通 LLM serving 更贴近底层 infra。对方想确认你不是只会调 API，而是真的理解 GPU pipeline、memory layout、multi-GPU communication 和端到端吞吐瓶颈。

### 这类岗位日常在优化什么

1. Multi-GPU inference acceleration
   - 模型太大或视频生成计算太重，需要跨多 GPU 执行。
   - 重点是 Tensor Parallelism、Pipeline Parallelism、sequence / frame parallelism、NCCL communication。

2. Frame loading / preprocessing
   - 视频模型经常不是 GPU compute 一项瓶颈。
   - frame decode、resize、crop、normalize、batch packing、host-to-device copy 都可能拖慢 pipeline。

3. GPU memory efficiency
   - Video generation 会同时吃 activation、attention memory、latent tensors、KV cache 或 feature cache。
   - 分辨率、帧数、batch size、sampling steps 都会线性或更糟地推高 memory。

4. End-to-end latency / throughput
   - 不是只看 model forward。
   - 要看 request queueing、CPU preprocessing、GPU compute、GPU communication、postprocessing、streaming / storage output。

### Video generation 为什么更难

文本 LLM 的 token sequence 已经很长，但 video generation 还有几个额外维度：

```
batch_size
num_frames
height
width
channels / latent_channels
num_sampling_steps
attention_heads
```

所以 memory 和 compute 通常跟这些因素一起放大。比如扩散模型或 video transformer 里，帧数翻倍不只是输出大一倍，还会增加 attention / temporal module / latent buffer 的压力。

### Frame Loading Pipeline

高吞吐视频推理常见 pipeline：

```
Storage / Object Store
  -> video read
  -> decode frames
  -> resize / crop / normalize
  -> pack tensor batch
  -> pinned CPU memory
  -> async H2D copy
  -> GPU inference
  -> postprocess / encode / upload
```

### Frame loading 的常见瓶颈

- Video decode 在 CPU 上太慢。
- 小文件 / remote storage 读取 latency 高。
- Resize / crop / normalize 没有 batch 化。
- CPU memory 到 GPU memory copy 没有用 pinned memory。
- H2D copy 和 GPU compute 没有 overlap。
- Data loader worker 数不够，GPU 等数据。
- Batch 内视频长短不一致，padding 太多。

### Frame loading 优化话术

> I would profile the input pipeline separately from model forward. For video generation, GPU underutilization often comes from CPU decode, preprocessing, or H2D transfer. I would use parallel dataloader workers, pinned memory, async copy, prefetching, and batch-level preprocessing. If decode is the bottleneck, I would consider GPU-accelerated decode or caching decoded frames / latent features depending on storage cost and reuse pattern.

### Multi-GPU 通信瓶颈怎么深挖

面试官问 multi-GPU bottleneck，不要只说“用 NCCL”。要讲清楚是哪种 parallelism 引入哪种通信。

| 场景 | 通信类型 | 瓶颈 |
|---|---|---|
| Tensor Parallelism | All-Reduce / All-Gather / Reduce-Scatter | 每层都通信，decode step latency 敏感 |
| Pipeline Parallelism | activation send/recv | micro-batch 太小时 pipeline bubble 大 |
| Data Parallel replicas | request routing 较简单 | 模型必须单卡放得下 |
| Frame / sequence parallel | exchange partial attention states | attention pattern 和 frame dependency 决定通信量 |
| Distributed output storage | upload generated frames/video | postprocess 可能拖慢 end-to-end latency |

### Multi-GPU 优化回答

1. 先 profile
   - 分开测 compute time、NCCL time、H2D/D2H copy、CPU preprocessing。
   - 用 Nsight Systems / PyTorch profiler / NCCL logs 看 kernel timeline。

2. 减少通信
   - 合理选择 TP degree，不是越多越好。
   - 能在单 NVLink island 内完成就不要跨慢链路。
   - 使用 fused kernels，减少中间 tensor materialization。

3. 隐藏通信
   - async collectives。
   - overlap computation and communication。
   - 多 CUDA streams。

4. 拓扑感知
   - TP group 放在 NVLink / NVSwitch 连接更紧密的 GPU 上。
   - 避免跨 PCIe root complex。
   - 跨节点时考虑 InfiniBand / RDMA 成本。

5. 调 batch / micro-batch
   - batch 太小，communication overhead 占比高。
   - batch 太大，显存爆或 latency 太高。
   - 找 throughput 和 latency 的 sweet spot。

### 显存分配策略

Vision / Video inference 里，显存通常被这些东西吃掉：

- Model weights。
- Activations / intermediate tensors。
- Attention workspace。
- KV cache / feature cache。
- Latent tensors。
- CUDA graph memory pool。
- Temporary buffers from cuDNN / custom kernels。
- Fragmentation。

### OOM 排查顺序

遇到 OOM，不要只说“减 batch size”。更 senior 的排查顺序：

1. 复现 OOM
   - 固定 model、resolution、num_frames、batch、sampling steps、precision。
   - 区分是 deterministic OOM 还是偶发 OOM。

2. 看 memory curve
   - 记录 peak allocated、reserved、fragmentation。
   - 看 OOM 出现在 prefill、attention、decode、postprocess 还是 copy 阶段。

3. 区分 memory 类型
   - weights 固定占用。
   - activations 随 batch / resolution / frames 增长。
   - KV / feature cache 随 sequence / frames / output length 增长。
   - temporary workspace 可能由某些 kernel 突然申请。

4. 看 fragmentation
   - 总 free memory 看似足够，但没有连续 block。
   - 需要 memory pool、block allocator、预分配、固定 shape bucket。

5. 看是否有 leak
   - request 完成后 cache / tensor reference 没释放。
   - Python object 持有 GPU tensor。
   - stream / callback / logging 保存了 tensor。

### OOM 解决手段

按优先级可以这样答：

1. Admission control
   - 在进入 GPU 前按 resolution、frames、batch、max tokens / steps 估算 memory。
   - 超过 budget 就 reject、queue 或降级。

2. Shape bucketing
   - 把请求按 resolution、frame count、sequence length 分 bucket。
   - 减少动态 shape 导致的 workspace 波动和 fragmentation。

3. Mixed precision / quantization
   - FP16 / BF16 / FP8 / INT8。
   - 注意质量回归和 kernel 支持。

4. Memory-efficient attention
   - FlashAttention / xFormers / tiled attention。
   - 降低 attention intermediate memory。

5. Chunking / tiling
   - 长视频按 frame chunks 处理。
   - 高分辨率按 spatial tiles 处理。
   - 代价是边界一致性和额外 stitching。

6. Offloading / swapping
   - 不活跃 cache offload 到 CPU memory。
   - 代价是 PCIe / NVLink copy latency。

7. Recomputation
   - 用 compute 换 memory。
   - 适合 memory 紧但 compute 还有余量的场景。

8. Graceful degradation
   - 降低 resolution。
   - 降低 num_frames。
   - 降低 sampling steps。
   - 降低 batch size。
   - 切小模型。
   - 返回 retry-after 或 async job id。

### OOM Follow-up 答案模板

> I would first prevent OOM through admission control rather than reacting after CUDA OOM. For video generation, I estimate memory from resolution, frame count, batch size, sampling steps, and model precision. If the request exceeds budget, I either queue it, route to a larger GPU, reduce generation parameters, or reject it. If OOM happens only under fragmentation, I would use shape bucketing and a preallocated memory pool. If it is true peak memory, I would use mixed precision, memory-efficient attention, chunked frame processing, offloading, or recomputation depending on the latency and quality requirements.

### 性能优化要怎么讲

不要只说“提高 GPU utilization”。要把端到端链路拆开：

```
T_total =
  T_queue
  + T_load
  + T_decode_frames
  + T_preprocess
  + T_H2D
  + T_model_compute
  + T_NCCL_comm
  + T_postprocess
  + T_upload
```

然后说你会 profile 哪一段最大，再针对最大段优化。

### 好的高分表达

> In this kind of inference pipeline, I would not assume the model forward is the only bottleneck. I would break down latency into frame loading, decode, preprocessing, H2D transfer, GPU compute, NCCL communication, and postprocessing. For Multi-GPU models, I would pay special attention to All-Reduce latency and topology placement. For memory, I would track not only allocated memory but also reserved memory, fragmentation, cache growth, and temporary workspace spikes. The goal is to maximize GPU occupancy without letting long or high-resolution requests destabilize the node.

### 面试官真正想确认什么

- 你是否知道 GPU memory 是硬约束，不是普通服务多加机器就能解决。
- 你是否理解 pre-processing / loading 也可能让 GPU 空转。
- 你是否知道 multi-GPU 通信可能吞掉模型切分带来的收益。
- 你是否会用 profiler 定位问题，而不是凭感觉调参数。
- 你是否能在 OOM 时做系统性排查：peak memory、fragmentation、leak、workspace、input shape。
- 你是否能给出 engineering trade-off：latency、throughput、quality、cost、stability。

### 更完整的白板架构：Video Generation Serving

如果题目偏 Vision / Video generation，可以把架构画得比普通文本 LLM 更具体：

```
Client
  -> API Gateway
  -> Request Validator
       - resolution / frames / steps / model / LoRA / seed
  -> Cost Estimator
       - memory estimate
       - runtime estimate
       - quota check
  -> Router
       - choose model replica / GPU pool / priority queue
  -> Scheduler
       - shape bucket
       - micro-batch builder
       - prefetch planner
  -> Worker Node
       - Input Loader
       - Text/Image/Video Encoder
       - Denoising / Transformer Core
       - VAE Decoder / Postprocess
       - Output Encoder / Upload
  -> Stream progress / return artifact URL
```

### 为什么要有 Cost Estimator

Video generation 的成本差异太大。同一个模型下，下面这些参数都会显著改变 memory 和 latency：

- `num_frames`
- `height / width`
- `num_sampling_steps`
- `guidance_scale` / classifier-free guidance
- batch size
- reference image / control video / mask
- LoRA adapter 数量
- output format and encoding

Cost Estimator 要在 request 进入 GPU 前给出估算：

```
estimated_gpu_memory
estimated_runtime_ms
estimated_output_size
priority_class
can_run_now / queue / degrade / reject
```

这一步是防止 OOM、控制多租户公平性、保证 SLA 的核心。

### Video generation memory 粗略模型

不要只说“显存不够就减 batch size”。可以这样拆：

```
GPU memory =
  model_weights
  + text_encoder / image_encoder weights
  + activations
  + attention workspace
  + latent video tensor
  + KV / feature cache
  + communication buffers
  + CUDA graph / allocator reserved memory
  + temporary postprocess buffers
```

其中 latent video tensor 大概跟下面因素成正比：

```
batch_size
* latent_channels
* num_frames
* latent_height
* latent_width
* bytes_per_element
```

如果 attention 在时空维度上做全局 attention，attention cost 可能接近：

```
O((frames * height * width)^2)
```

实际模型通常会用 window attention、factorized temporal/spatial attention、sparse attention 或 latent-space attention 来控制成本。

### Diffusion / DiT 推理链路

很多 image/video generation 模型不是一次 forward 就结束，而是多步 denoising：

```
prompt / condition
  -> text encoder
  -> initial noise / latent
  -> for timestep in sampling_steps:
       denoiser / DiT / U-Net forward
       scheduler update latent
  -> VAE decode
  -> video encode / upload
```

所以 latency 大概是：

```
T_total ~= T_condition_encoder
          + sampling_steps * T_denoiser_step
          + T_vae_decode
          + T_encode_upload
```

这就是为什么 `sampling_steps` 是非常关键的 admission control 参数。

### Classifier-Free Guidance 的隐藏成本

如果使用 classifier-free guidance，常见做法是同时跑 conditional 和 unconditional 分支：

```
pred = uncond + guidance_scale * (cond - uncond)
```

这可能让 denoiser forward 的 effective batch 近似翻倍。面试里可以主动提：

> Guidance quality is not free. It can double the denoising compute or memory depending on implementation, so I would include guidance mode in the cost estimator and batching policy.

### Shape Bucketing 为什么重要

Video requests 的 shape 很多：

```
480p / 720p / 1080p
16 / 32 / 64 frames
20 / 30 / 50 sampling steps
different aspect ratios
```

如果每个 request 都是动态 shape，会导致：

- kernel selection 不稳定。
- CUDA Graph 难复用。
- memory workspace 波动。
- batch packing 困难。
- fragmentation 更严重。

解决：

- 把请求归到固定 buckets，比如 `(resolution, frames, steps, model_variant)`。
- 对接近的 shape 做 padding 到 bucket。
- 每个 bucket 预热 engine / CUDA graph / memory pool。
- Queue 可以按 bucket 组织，提升 batch efficiency。

Trade-off：

- bucket 太少：padding 浪费多。
- bucket 太多：每个 bucket 流量不足，batch 很难凑满。

### Scheduler Policy：不要只按 FIFO

高分回答可以说 scheduler 有多个队列：

```
interactive_queue
batch_queue
premium_tenant_queue
long_video_queue
retry_queue
```

每轮调度考虑：

- GPU memory budget。
- 当前 bucket 是否能凑 batch。
- 请求 deadline / SLA。
- tenant quota。
- estimated runtime。
- 是否会造成 head-of-line blocking。
- 是否需要 prefetch input frames。

### Head-of-line blocking

如果 FIFO 里第一个请求是 1080p 128 frames，后面很多 480p 16 frames 都会被堵住。解决：

- 按 shape bucket 分队列。
- 长任务进入 async / batch queue。
- interactive 小任务优先。
- 对长任务做 chunking。
- 设置 max queue wait time，超过就降级或转异步。

### Micro-batching

Video generation 的 micro-batching 要比文本更小心：

- batch 大：吞吐好，但 peak memory 高，单请求 latency 变差。
- batch 小：latency 好，但 GPU utilization 差。
- 不同 frame count / resolution 混 batch，会造成 padding waste。

好的说法：

> I would use shape-aware micro-batching. Requests with the same model, resolution bucket, frame bucket, and step count are batched together. For interactive traffic, I cap max batch wait time. For offline traffic, I allow longer wait to improve throughput.

### Preprocessing 和 GPU Compute 的流水线

不要让 GPU 等 CPU。Worker 内可以分 stage：

```
Stage 1: async read / download
Stage 2: decode / resize / normalize
Stage 3: H2D copy into staging buffer
Stage 4: GPU inference
Stage 5: D2H / encode / upload
```

使用 double buffering：

```
GPU runs batch N
CPU prepares batch N+1
H2D copies batch N+1 on another stream
```

目标是 overlap：

- CPU decode with GPU compute。
- H2D copy with previous GPU compute。
- output upload with next request compute。

### CPU/GPU 分工

可以按成本选择：

| 工作 | CPU 做 | GPU 做 |
|---|---|---|
| Video decode | 简单部署，便宜 | 高吞吐，减少 CPU bottleneck |
| Resize / crop | 灵活 | 大 batch 时更快 |
| Normalize / layout transform | CPU 可做 | GPU 上可 fuse 到 input kernel |
| VAE decode | 通常 GPU | CPU 太慢 |
| Video encode | CPU 常见 | GPU encode 可降低 latency |

面试里不要绝对化。更好的回答是 profile 后决定，把最慢 stage 移到更合适的硬件。

### Memory Pool / Allocator 设计

Video inference 中 frequent alloc/free 会导致 fragmentation 和 allocator overhead。可以设计：

- per-bucket preallocated memory pool。
- fixed-size block allocator。
- separate pools for activations / KV cache / temporary workspace。
- warmup 后稳定最大 workspace。
- request finish 后明确 release references。

为什么 separate pools：

- KV cache 生命周期长。
- activation / workspace 生命周期短。
- output buffer 可能很大但只在尾部使用。
- 混在一起更容易碎片化。

### CUDA Graph 什么时候有用

CUDA Graph 可以减少 kernel launch overhead，但它偏好固定 shape。

适合：

- 固定 bucket shape。
- 稳定 batch size 或有限 batch size set。
- decode / repeated denoising step。

不适合：

- request shape 完全动态。
- control flow 很复杂。
- 每轮 tensor shape 都变化。

所以 CUDA Graph 和 shape bucketing 是一对组合拳。

### Quantization 怎么讲

Quantization 可以减少 weight memory 和提高吞吐，但要分清对象：

- Weight-only INT8 / INT4：主要减少 weights memory。
- FP8：可能提高 GEMM throughput 并减少 activation / weight memory。
- KV cache quantization：减少 cache memory，但要关注质量和 kernel support。
- VAE / decoder 量化：可能影响视觉质量，需要 A/B eval。

回答不要只说“用 INT8”。要说：

> I would quantize the parts that are memory or compute bottlenecks, then validate visual quality metrics and human evaluation. For generation models, small numerical changes can create visible artifacts, so quantization needs per-module validation.

### LoRA / 多模型 Serving

如果线上有多个 LoRA adapter 或 model variants：

- base model weights 常驻 GPU。
- adapter weights 可按热度缓存。
- request 带 adapter_id。
- scheduler 尽量把同 adapter 的请求 batch 在一起。
- 冷 adapter 需要 load，会增加 latency。

风险：

- adapter 频繁切换导致 cache miss。
- 多租户 adapter 占显存。
- 不同 adapter 可能不能高效 batch。

### Multi-GPU 切分策略怎么选

可以这样说：

1. 模型单卡放得下，优先 data parallel replicas。
   - 简单，通信少，吞吐随 replicas 扩展。

2. 模型单卡放不下，用 tensor parallel / pipeline parallel。
   - TP 降低单卡 weight memory，但每层引入 collective communication。
   - PP 降低每卡层数，但 batch 小时有 pipeline bubble。

3. Video 很长或 attention 很重时，考虑 sequence / frame parallel。
   - 但要看 attention dependency，可能需要跨卡 exchange states。

4. 结合硬件拓扑。
   - 单节点 NVLink / NVSwitch 内做 TP。
   - 跨节点尽量减少 latency-sensitive collective。

### 8-GPU Node 白板例子

```
Node: 8 x H100

Option A: 8 data-parallel replicas
  - each GPU has full model
  - best if model fits one GPU
  - minimal communication

Option B: 2 replicas x 4-way TP
  - each request uses 4 GPUs
  - model weights sharded
  - good for larger model
  - NCCL All-Reduce per layer

Option C: 1 replica x 8-way TP
  - largest model / highest per-request throughput
  - strongest communication pressure
  - lower concurrency

Option D: PP + TP hybrid
  - layers split into pipeline stages
  - each stage internally tensor-parallel
  - useful for very large models
```

面试里可以说你会 benchmark A/B/C/D，而不是凭感觉选。

### Profiling Playbook

第一步不要改代码，先把时间分解出来：

```
nsight / profiler timeline:
  CPU data loading
  CPU preprocessing
  H2D copy
  GPU kernels
  NCCL collectives
  D2H copy
  video encode / upload
```

看几个问题：

- GPU 有没有空洞？如果有，谁让它等？
- NCCL kernel 是否和 compute overlap？
- All-Reduce 占每步多少比例？
- H2D copy 是否阻塞 default stream？
- 是否有大量小 kernel launch？
- 是否有某个 dynamic shape 触发超大 workspace？
- batch 内 padding waste 多不多？

### Nsight / PyTorch Profiler 里重点看什么

- SM utilization。
- Memory bandwidth utilization。
- Tensor Core utilization。
- Kernel launch gaps。
- CUDA memcpy H2D / D2H。
- NCCL AllReduce / AllGather 时间。
- CPU thread 是否在 data loader / decode 上打满。
- GPU memory allocated vs reserved。
- Peak memory by stage。

### OOM Case Studies

#### Case 1: 偶发 OOM，只在某些请求出现

可能原因：

- 某些 request resolution / frames 特别大。
- dynamic shape 触发更大的 cuDNN / attention workspace。
- 某个 bucket 没有被 warmup。

解决：

- admission control 加 shape limit。
- shape bucketing。
- warmup 每个 bucket。
- 记录 OOM request 的 shape 和 stage。

#### Case 2: 跑一段时间后 OOM

可能原因：

- tensor reference leak。
- cache 没释放。
- output buffer / logging 保存了 GPU tensor。
- allocator reserved memory 持续增长。

解决：

- request 完成后检查 live tensor。
- 监控 per-request allocated delta。
- 确保 cache ref_count 归零。
- 避免把 GPU tensor 放入 Python list / closure / metrics。

#### Case 3: 总显存够，但仍然 OOM

可能原因：

- fragmentation。
- 需要连续大 block。
- temporary workspace 瞬时过大。

解决：

- memory pool。
- block allocator。
- shape bucket。
- 降低最大 workspace。
- 使用 memory-efficient attention。

#### Case 4: Multi-GPU 后 latency 反而变差

可能原因：

- TP degree 太高。
- All-Reduce 通信超过节省的 compute。
- GPU 拓扑不合理。
- batch 太小，通信无法摊薄。

解决：

- 降低 TP degree。
- 同 TP group 放 NVLink 内。
- overlap comm/compute。
- 增大 micro-batch 或改为 data parallel replicas。

### Graceful Degradation Policy

可以把降级策略按用户体验分层：

| 压力等级 | 系统动作 |
|---|---|
| 轻微压力 | 增加 queue wait，优先 batch 同 bucket 请求 |
| 中等压力 | 降低 offline traffic batch priority，限制 max frames / steps |
| 高压力 | preempt low-priority jobs，切小模型或低分辨率 |
| 极端压力 | reject 新长任务，返回 retry-after，保护 GPU node 不 OOM |

关键原则：

> Protect the node first. A failed request is better than crashing the entire GPU worker and losing all in-flight requests.

### 面试中可以主动说的 Production Guardrails

- Per-request max resolution / frames / steps。
- Per-tenant GPU memory quota。
- Queue timeout。
- OOM circuit breaker。
- GPU worker health check。
- Automatic draining of unhealthy worker。
- Canary new model / new kernel。
- Rollback path。
- Load shedding。
- Artifact cleanup job。

### Model Serving Reliability

AI inference 面试里，面试官经常会问：模型服务怎么上线、回滚、监控？

核心设计：

```
Model Registry
  -> model artifact + version + config + eval metrics
Deployment Controller
  -> canary / blue-green / shadow
Inference Gateway
  -> route by model version / tenant / experiment
Metrics
  -> latency / error / quality / cost
Rollback
  -> fast switch to previous stable version
```

上线策略：

1. Shadow traffic
   - 新模型接收复制流量，但不影响用户结果。
   - 比较 latency、error rate、output quality。

2. Canary
   - 先放 1% 流量。
   - 监控 P50/P95/P99 latency、OOM、error、quality metrics。
   - 逐步扩大到 5%、25%、50%、100%。

3. Blue-green
   - 新旧环境并存。
   - 通过 routing switch 切换。
   - 回滚快，但成本更高。

必须监控：

- Request QPS。
- TTFT / inter-token latency / end-to-end latency。
- GPU utilization。
- GPU memory / KV cache free blocks。
- OOM / preemption / swap count。
- Error rate。
- Output quality proxy metrics。
- Cost per request。

面试回答模板：

> I would treat model rollout like a production deployment, not a notebook update. Every model version is registered with artifact, config, and evaluation metrics. New versions first receive shadow traffic, then canary traffic. The gateway can route by model version, tenant, or experiment. If latency, OOM, error rate, or quality metrics regress, we roll back quickly to the previous stable version.

### Model Cache / Cold Start

大模型 serving 的 cold start 很贵：

- Load weights from storage。
- Initialize CUDA kernels。
- Warm up memory pool。
- Build CUDA Graph。
- Load LoRA adapters。

优化：

- Hot models 常驻 GPU。
- Warm pool：提前启动 workers。
- Lazy load 冷门 model，但返回 async job 或较长 SLA。
- Adapter cache 按 LRU / LFU 管理。
- 预热常见 input shape buckets。

面试回答模板：

> I would keep hot models resident on GPU and maintain a warm worker pool. For cold models or rare LoRA adapters, I would either lazy-load with a longer SLA or route to an async queue. I would also warm up common shape buckets so the first real user request does not pay kernel and memory initialization cost.

### 一段强回答

> For a video generation inference pipeline, I would treat performance as an end-to-end systems problem, not only a model-forward problem. I would first build a cost estimator based on resolution, frame count, sampling steps, precision, and guidance mode. Then I would route requests into shape-aware queues and use micro-batching per bucket. On the worker, I would pipeline frame loading, preprocessing, H2D copy, GPU inference, and output encoding so the GPU is not waiting for CPU or storage. For multi-GPU execution, I would profile NCCL collectives and choose data parallel, tensor parallel, or pipeline parallel based on model size and hardware topology. For memory, I would use admission control, memory pools, bucketed shapes, and graceful degradation so a single long or high-resolution request cannot OOM the node.

### 面试回答模板

> I would design the service around two scarce resources: GPU compute and KV cache memory. Continuous batching keeps GPU compute busy, but the real memory challenge is KV cache fragmentation. So I would use a paged KV cache manager: split KV cache into fixed-size blocks, maintain a per-sequence block table, and allow physical blocks to be non-contiguous, similar to virtual memory. This lets us admit dynamic-length requests without requiring large contiguous memory.

> For multi-GPU execution, if the model is tensor-parallel, each layer requires collective communication such as All-Reduce or All-Gather. Decode is especially sensitive because this happens every generated token. I would optimize by keeping TP groups within fast interconnect topology, overlapping communication with computation using async streams, using fused kernels, and tuning TP degree based on profiling.

> For a sudden long prompt, I would handle it before OOM through admission control. If accepted, I would use chunked prefill. Under memory pressure, I would preempt lower-priority sequences and choose between CPU swap and recomputation based on latency tolerance. For interactive requests I prefer rejecting or reducing max tokens over swapping; for batch jobs swapping may be acceptable.

## 32. Quick Capacity / Scaling Reference

| Component | 常见指标 | Scale trigger |
|---|---|---|
| Cache | ~1 ms latency, 100k+ ops/sec, memory-bound | hit rate < 80%, latency 上升, memory > 80% |
| Database | 高 TPS, sub-ms 到数 ms read latency, 大容量存储 | write throughput 太高, read latency 上升, storage/region 需求 |
| App Server | 大量 concurrent connections, CPU/RAM bound | CPU > 70%, latency 超 SLA, connection 接近上限 |
| Message Queue / Kafka | 高吞吐, partition-based scaling | consumer lag 增长, partition/broker 接近上限 |

这些数字不要死背，重点是知道什么指标触发扩容：latency、throughput、CPU、memory、connection、consumer lag、cache hit rate。

## 33. 面试中最常用的句子

### 数据库选择

> I would choose Postgres here because the core requirement is transactional correctness. We need ACID semantics and constraints more than unbounded horizontal write scaling.

> I would choose DynamoDB here because the access pattern is key-value like, QPS is high, and we do not need joins or complex ad-hoc queries.

### 一致性选择

> For money, inventory, and reservations, I would prioritize consistency. For feeds, counts, and search indexes, eventual consistency is acceptable.

### Kafka

> Kafka is not just a queue; it is a durable event log. I would use it to decouple services, buffer write spikes, and let multiple downstream consumers process the same event stream independently.

### Outbox

> To avoid the DB-write-success but Kafka-publish-fail gap, I would use the transactional outbox pattern. The business update and outbox event are committed in the same DB transaction.

### Idempotency

> I would not rely on exactly-once delivery. I would design for at-least-once delivery with idempotent processing, so duplicate requests or messages do not create duplicate business effects.

### Cache

> The DB is the source of truth; cache is derived data. For cache-aside, I would update the DB first, then delete the cache, and let the next read repopulate it.

### Multi-region

> For user-owned data, I would use home region writes with async replicas. For globally shared scarce resources, I would avoid multi-writer unless using a global transaction system, because correctness matters more than local write latency.

### Rate limiter

> I would use token bucket for API rate limiting because it supports steady rate control while allowing a bounded burst. In a distributed setup, I would store counters in Redis with TTL, and add a local limiter before Redis to reduce hot-key pressure.

### Backpressure

> I would make queues bounded and use lag, latency, and resource utilization as backpressure signals. When downstream systems fall behind, producers should throttle, shed low-priority traffic, or return retry-after instead of allowing unbounded queue growth.

### Saga

> For cross-service workflows, I would use Saga rather than a global distributed transaction. Each service commits a local transaction and emits an event; if a later step fails, we run compensating actions. For payment or booking flows, orchestration is easier to debug than pure choreography.

### Notification

> I would make notification delivery asynchronous. The request path writes a durable notification record and outbox event; workers send through provider-specific pools, persist delivery status before committing offsets, and use idempotency keys to avoid duplicate sends.

### Feed

> I would use hybrid fanout. Normal users use fanout-on-write for fast feed reads, while celebrities are merged at read time to avoid massive write amplification. Feed inboxes store post IDs, and the read path hydrates details from cache or post service.

### Search

> I would keep the primary database as source of truth and build Elasticsearch as a derived index through CDC or outbox. Search can tolerate slight lag, but deletes and permission changes need careful handling to avoid leaking stale results.

### File upload

> I would not proxy large files through app servers. The API returns a pre-signed object-store URL; the client uploads directly; storage events trigger async validation, transcoding, thumbnail generation, metadata update, and CDN distribution.

### Model rollout

> I would treat model rollout as a production deployment. New model versions go through shadow traffic, then canary traffic, with monitoring for latency, OOM, error rate, cost, and quality. The gateway must support quick rollback to the previous stable version.
