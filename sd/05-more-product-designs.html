23. More Product System Design Interview Bank

这一节补充更常见的 product system design 题。面试官通常会先问功能需求，然后迅速转向：数据模型、读写路径、fanout、ranking、consistency、hot key、failure handling、cost。答题时不要只画组件，要把每个设计的核心矛盾讲出来。

建议固定回答顺序：

  1. Clarify requirements：核心功能、规模、SLA、读写比例。
  2. Identify core entities：user、object、edge、event、state。
  3. Design APIs：写路径和读路径分开。
  4. Data model：source of truth、index、cache、derived view。
  5. Scale strategy：partition key、fanout、queue、cache、search index。
  6. Correctness：idempotency、dedup、ordering、consistency。
  7. Failure mode：重试、降级、backpressure、recovery。
  8. Metrics：latency、QPS、lag、error、cost。

1. News Feed / Twitter / Reddit Feed

Question

设计一个 News Feed。用户关注其他用户，发帖后粉丝能在 home timeline 看到内容。系统要支持发帖、关注、取 feed、ranking、热门用户、删除/隐藏内容。

核心矛盾

Feed 最大的问题不是存帖子，而是 fanout：

  • Fanout on write：发帖时把 post id 推给粉丝 timeline。
  • Fanout on read：读 feed 时动态拉取关注者最近帖子。
  • Hybrid：普通用户 fanout on write， celebrity / 大 V fanout on read。

Architecture

Post Service
  -> Post DB
  -> Kafka post_created
  -> Feed Fanout Workers
  -> Timeline Store
  -> Feed API
  -> Ranking Service
  -> Cache

Data model

post(post_id, author_id, text, media_ids, created_at, visibility, status)
follow(follower_id, followee_id, created_at)
timeline(user_id, score, post_id, author_id, created_at)

Timeline store 可以用 Redis sorted set、Cassandra、DynamoDB wide partition，核心是按 user_id 查询最近 N 条。

Write path

  1. User creates post。
  2. Post Service 写 Post DB。
  3. 发布 post_created event 到 Kafka。
  4. Fanout worker 查 follower list。
  5. 把 post id 写入粉丝 timeline。
  6. 对热门作者只写 celebrity source，不全量 fanout。

Read path

  1. Feed API 读取用户 timeline candidate。
  2. 补充 celebrity / promoted / fresh candidates。
  3. Ranking Service 打分。
  4. Hydrate post metadata。
  5. 返回分页结果。

Hot celebrity

如果一个用户有 1 亿粉丝，不要同步 fanout：

  • celebrity posts 进入单独表。
  • 用户读 feed 时 merge celebrity recent posts。
  • 对活跃粉丝可以异步预计算。
  • 设置 fanout upper bound。

Consistency

Feed 可以 eventual consistency。用户发帖后自己的 profile timeline 必须立即可见，但粉丝 home feed 延迟几秒可以接受。删除或屏蔽内容要优先在 read path filter，后台再清 timeline。

Interview answer

I would use a hybrid fanout model. Normal users use fanout-on-write so home feed reads are fast. Celebrity users use fanout-on-read to avoid writing to millions of timelines per post. The source of truth is the post table and follow graph; timelines are derived views that can be rebuilt. Ranking happens on candidates from timeline, celebrity sources, and freshness signals.

2. Photo Sharing / Instagram

Question

设计 Instagram。用户上传图片/视频，关注者能看到 feed，可以 like、comment、查看 profile grid。重点是 media storage、feed、image processing、CDN、privacy。

Architecture

Client
  -> Upload API
  -> Object Storage
  -> Metadata DB
  -> Media Processing Queue
  -> Thumbnail / Transcode Workers
  -> CDN
  -> Feed Fanout
  -> Feed API

Upload flow

  1. Client 请求 upload URL。
  2. Client 直接上传到 object storage，避免 API server 扛大文件。
  3. Upload complete 后写 media metadata。
  4. 异步生成 thumbnail、不同分辨率、video transcode。
  5. Post publish 后触发 feed fanout。

Data model

media(media_id, owner_id, object_key, type, width, height, duration, status)
post(post_id, user_id, caption, media_ids, visibility, created_at)
like(user_id, post_id, created_at)
comment(comment_id, post_id, user_id, text, created_at)

CDN strategy

  • 原图/视频放 object storage。
  • 常用尺寸放 CDN。
  • Signed URL 处理 private media。
  • 对 profile grid 预生成小图，降低移动端加载成本。

Feed

Instagram feed 类似 News Feed，但 media hydrate 成本更高。read path 要返回 CDN URLs、尺寸、blurhash / placeholder、like count、comment preview。不能每次都查多个服务，可以用 feed item snapshot 加缓存。

Failure handling

  • Upload complete 但 processing fail：post 标记 processing_failed 或只展示原图。
  • CDN miss：回源 object storage。
  • Fanout lag：profile page 仍从 post table 可见。

Interview answer

I would split media bytes from metadata. Large files go directly to object storage using pre-signed URLs, while metadata is stored in a database. Processing workers generate thumbnails and optimized versions asynchronously. Feed is a derived view triggered by post events, and CDN serves media efficiently. Privacy is enforced by signed URLs and read-time authorization.

3. Coding Platform / LeetCode

Question

设计在线刷题平台。用户提交代码，系统编译运行测试，返回结果。需要支持多语言、排队、sandbox、实时结果、比赛高峰。

核心矛盾

Online judge 的难点是安全和隔离：

  • 用户代码不可信。
  • 需要限制 CPU、memory、network、file system。
  • 测试任务可能很慢，不能同步卡住 API。

Architecture

Submission API
  -> Submission DB
  -> Judge Queue
  -> Judge Worker Pool
       - language runtime
       - sandbox/container
       - resource limits
  -> Result Store
  -> WebSocket/SSE result stream

Data model

problem(problem_id, title, statement, difficulty)
test_case(test_case_id, problem_id, input_ref, expected_ref, hidden)
submission(submission_id, user_id, problem_id, language, code_ref, status)
judge_result(submission_id, verdict, runtime_ms, memory_mb, failed_case)

Judge flow

  1. API 保存 submission，status = QUEUED。
  2. 发布 job 到 queue。
  3. Worker 拉取 job，创建 sandbox。
  4. 编译代码。
  5. 逐个运行 sample 和 hidden tests。
  6. 写 verdict：Accepted / Wrong Answer / TLE / MLE / Runtime Error / Compile Error。
  7. 通知 client。

Scaling

  • 按 language 分队列，因为 runtime 和资源不同。
  • 比赛期间预热 worker pool。
  • 对热门题测试数据缓存到 worker local disk。
  • 使用 priority queue：contest submission > normal practice。
  • 限制每个用户 pending submissions。

Security

  • 禁止 outbound network。
  • Read-only root filesystem。
  • CPU/memory/time limits。
  • 容器或 microVM 隔离。
  • 清理临时文件。

Interview answer

I would make submission asynchronous. The API stores the submission and enqueues a judge job. Workers run untrusted code inside a sandbox with CPU, memory, time, filesystem, and network limits. Results are persisted and streamed back to the client. The platform scales by language-specific queues, worker pools, test-case caching, and per-user throttling.

4. Online Auction / eBay

Question

设计在线拍卖。用户可以出价，最高价赢，拍卖结束后生成订单。支持实时价格更新、anti-sniping、并发出价、支付。

核心不变量

  • 每个 auction 同一时刻只有一个最高有效出价。
  • Bid amount 必须大于当前价格加 increment。
  • Auction ended 后不能接受新 bid。
  • 生成订单必须 exactly-once effect。

Data model

auction(auction_id, seller_id, item_id, start_at, end_at, status, current_price, highest_bid_id, version)
bid(bid_id, auction_id, bidder_id, amount, created_at, status)
order(order_id, auction_id, buyer_id, amount, status)

Bid write path

  1. Validate auction is active。
  2. Validate bid amount。
  3. Conditional update auction row：
UPDATE auction
SET current_price = ?,
    highest_bid_id = ?,
    version = version + 1
WHERE auction_id = ?
  AND status = 'ACTIVE'
  AND current_price < ?
  AND version = ?
  1. 写 bid record。
  2. 通过 WebSocket / pubsub 推送 price update。

Anti-sniping

如果结束前最后 N 秒有新 bid，可以延长 end time。例如最后 2 分钟出价延长 2 分钟。这样防止最后一秒抢拍。

Partitioning

用 auction_id 做 partition key，让同一 auction 的 bid 进入同一 shard 或单线程 actor。这样高并发 auction 可以按 auction 隔离，避免全局锁。

Interview answer

I would treat each auction as a consistency boundary. Bids are accepted with conditional updates or a per-auction single-writer actor so only one highest bid wins. Price updates are pushed through pubsub/WebSocket, but the auction table is the source of truth. At auction close, a scheduled worker transitions the auction to ended and creates the order idempotently.

5. Price Tracking / CamelCamelCamel

Question

设计价格追踪服务。用户关注商品，当价格低于阈值时收到通知。系统要定期抓取价格、存历史、去重、触发 alert。

Architecture

Product Catalog
  -> Crawl Scheduler
  -> Fetch Workers
  -> Parser
  -> Price Time Series Store
  -> Alert Evaluator
  -> Notification Service

Data model

product(product_id, url, merchant, crawl_frequency, last_crawled_at)
price_point(product_id, timestamp, price, availability)
watch(user_id, product_id, threshold, channel, status)
alert(alert_id, user_id, product_id, price, sent_at, dedup_key)

Scheduling

热门商品高频抓，冷门商品低频抓。不要所有商品固定频率：

  • high-interest products：minutes。
  • normal products：hours。
  • inactive products：days。

Scheduler 只产生 crawl jobs，worker 执行 fetch。失败要 exponential backoff。

Alert correctness

通知必须幂等。使用：

dedup_key = user_id + product_id + threshold + price_bucket + day

避免同一次降价重复轰炸用户。

Interview answer

I would separate crawling from alerting. A scheduler creates crawl jobs based on product popularity and freshness requirements. Fetch workers parse prices and append immutable price points. Alert evaluators compare new prices against active watches and send idempotent notifications with dedup keys. Historical prices are stored in a time-series optimized table.

6. Dating App / Tinder

Question

设计 dating app。用户设置 profile 和偏好，系统推荐候选人，用户 swipe left/right，双方 like 后 match，可以聊天。

Candidate generation

候选人不是全量扫描：

  • Geo index：附近的人。
  • Preference filter：年龄、距离、性别、兴趣。
  • Exclusion set：已经 swipe 过、blocked、reported。
  • Ranking：活跃度、quality score、mutual interests。

Data model

profile(user_id, geo_cell, age, gender, preferences, status)
swipe(user_id, target_user_id, direction, created_at)
match(match_id, user_a, user_b, created_at, status)

Match flow

当 A right swipe B：

  1. 写 swipe(A, B, RIGHT)，幂等。
  2. 查是否存在 swipe(B, A, RIGHT)。
  3. 如果存在，创建 match，使用唯一约束：
UNIQUE(min(user_a, user_b), max(user_a, user_b))

Privacy

  • Block/report 后 read path 必须立即过滤。
  • Location 只存粗粒度 geo cell。
  • 不暴露精确在线状态。

Interview answer

I would split candidate generation from match creation. Candidate generation uses geo indexing, preference filters, exclusion sets, and ranking. Swipes are immutable user actions. A match is created idempotently when both users have right-swiped, protected by a unique pair constraint. Privacy filters such as block and report must be enforced at read time.

7. Local Delivery / GoPuff

Question

设计本地即时配送服务。用户下单，系统从本地仓库扣库存，分配 picker/driver，实时跟踪配送状态。

Core states

Order:
CREATED -> RESERVED -> PAID -> PICKING -> READY -> ASSIGNED -> PICKED_UP -> DELIVERED
       -> CANCELLED / FAILED

Inventory:
AVAILABLE -> RESERVED -> SOLD / RELEASED

Architecture

Order Service
  -> Inventory Reservation
  -> Payment
  -> Picking Queue
  -> Dispatch Service
  -> Driver Location Stream
  -> ETA Service
  -> Notification

Inventory reservation

下单时不要直接扣最终库存。先 reserve：

UPDATE inventory
SET available = available - ?,
    reserved = reserved + ?
WHERE warehouse_id = ?
  AND sku_id = ?
  AND available >= ?

支付成功后 commit，支付失败或超时 release。

Dispatch

分配 driver 时考虑：

  • driver location。
  • order ready time。
  • capacity。
  • route distance。
  • promised SLA。

可以先用 greedy nearest-driver，再升级到 batching/route optimization。

Interview answer

I would model delivery as a workflow with explicit order and inventory states. Checkout creates inventory reservations with TTL, payment commits them, and failures release them. Picking and delivery are asynchronous steps. Driver dispatch uses location and ETA signals, while clients receive order state through realtime updates.

8. Like Button / Social Reactions

Question

设计 Like button。用户可以 like/unlike post，页面显示总数，并把行为用于推荐和通知。

核心矛盾

Like 写入 QPS 很高，但 count 不一定要强一致。用户自己的 like 状态必须准确，计数可以 eventual consistency。

Data model

reaction(user_id, object_id, reaction_type, created_at)
reaction_count(object_id, reaction_type, count, updated_at)

reaction 使用唯一键 (user_id, object_id)，保证重复点击幂等。

Write path

  1. Toggle like 写 source of truth。
  2. 发布 reaction event。
  3. Counter worker 异步更新 count。
  4. Notification / ranking consumer 使用同一 event。

Hot object

热门 post 的 count 会变 hot key：

  • Local aggregation 后批量 flush。
  • Sharded counters。
  • Approximate counter for display。
  • Periodic reconciliation from source table。

Interview answer

I would make the user-object reaction table the source of truth and keep counters as derived data. Like and unlike operations are idempotent through a unique user-object key. Counts are updated asynchronously through events, with sharded counters or local aggregation for hot posts. The UI can tolerate slightly stale counts, but the user's own like state must be correct.

9. Search / Facebook Post Search

Question

设计帖子搜索。用户搜索关键词，结果要按 relevance、recency、privacy 排序。帖子更新和删除要尽快反映。

Architecture

Post DB
  -> CDC / Kafka
  -> Indexer
  -> Search Index
  -> Search API
  -> Privacy Filter
  -> Ranking

Index document

post_id
author_id
text
tokens
created_at
engagement_signals
visibility
allowed_groups

Query flow

  1. Search API 解析 query。
  2. Search index 返回 candidate post ids。
  3. Privacy filter 移除不可见内容。
  4. Ranking 结合 text relevance、recency、engagement。
  5. Hydrate metadata。

Freshness vs consistency

搜索可以接受秒级延迟，但删除/隐私变更不能长期不生效。做法：

  • delete event 高优先级进入 indexer。
  • read-time privacy filter 兜底。
  • 对敏感内容使用 tombstone。

Interview answer

I would not query the primary post database for search. Posts are indexed asynchronously through CDC or Kafka into a search engine. The index optimizes keyword matching and candidate generation, while privacy is enforced again at read time. Ranking combines relevance, recency, and engagement signals. Deletes and privacy updates are high-priority index events.
