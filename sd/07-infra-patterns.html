25. Advanced Infra Patterns Interview Bank

这一节补充 system design 面试里经常被追问的基础设施 pattern。很多候选人会做单题，但一被问到 read scaling、write contention、large blob、workflow、streaming、search、gateway 就断掉。面试时可以把这些 pattern 当作工具箱，主动嵌入到具体题目里。

1. API Gateway Deep Dive

它解决什么

API Gateway 是 client 和 backend services 之间的入口层。不要只说“转发请求”，要说明它承担 cross-cutting concerns：

  • Auth / token validation。
  • Rate limit / quota。
  • Request routing。
  • TLS termination。
  • API versioning。
  • Request/response transformation。
  • Timeout / retry / circuit breaker。
  • Observability：request id、metrics、logs、tracing。

Architecture

Client
  -> Edge Load Balancer
  -> API Gateway
       - auth filter
       - rate limit filter
       - routing filter
       - timeout/retry policy
       - request logging
  -> Backend Services

关键设计

  1. Gateway 不应该放太多业务逻辑。
  • 好：身份校验、限流、路由、统一超时。
  • 坏：把 order/payment/feed 业务规则写在 gateway。
  1. Retry 要谨慎。
  • GET 可以重试。
  • POST 必须依赖 idempotency key。
  • 不要在下游已经过载时无限 retry。
  1. Timeout 必须端到端分配。
client timeout = 1500 ms
gateway budget = 1300 ms
service A = 500 ms
service B = 500 ms
buffer = 300 ms
  1. Rate limit 分层。
  • per IP。
  • per user。
  • per API key。
  • per tenant。
  • per route。

Interview answer

I would use the API gateway for cross-cutting concerns such as auth, rate limiting, routing, timeouts, and observability, but I would keep business logic in backend services. Retries are only safe for idempotent operations or requests with idempotency keys. The gateway also propagates request ids and enforces a latency budget so slow downstreams do not exhaust client or server resources.

2. Distributed Cache / Redis Deep Dive

Redis 常见用途

  • Cache-aside。
  • Session store。
  • Rate limiter counters。
  • Sorted set leaderboard / timeline。
  • Pub/sub for lightweight realtime。
  • Distributed lock, but only when carefully bounded。

Cache-aside flow

read:
  get cache
  if miss:
    read DB
    set cache with TTL

write:
  update DB
  delete cache

为什么 delete cache 而不是 update cache：避免并发写导致 dirty cache。DB 是 source of truth，cache 是 derived data。

Hot key

热门 key 会压垮单个 Redis shard。解决：

  • local in-process cache。
  • key replication。
  • request coalescing / singleflight。
  • sharded counters。
  • 加随机 TTL jitter，避免同时过期。

Cache stampede

大量请求同时 miss 同一个 key：

  • singleflight：只有一个请求回源。
  • stale-while-revalidate：先返回旧值，后台刷新。
  • mutex lock with timeout。
  • negative cache：缓存空结果，防止穿透。

Redis Cluster

Redis Cluster 通过 hash slot 分片。多 key 操作要注意 key 是否在同一个 slot。面试里可以说：

If we need atomic multi-key operations, I would either keep related keys in the same hash slot using hash tags, or avoid cross-key Redis transactions and move the atomicity to the database.

Interview answer

I would treat Redis as a fast derived-data layer, not the source of truth for critical state. For cache-aside, reads populate cache on miss, and writes update the database first then delete cache. For hot keys, I would use local cache, request coalescing, sharded counters, or replicated keys. TTL jitter and stale-while-revalidate help prevent stampedes.

3. Elasticsearch / Search Infra

什么时候用 search index

当需求是 keyword search、text relevance、filter + sort、autocomplete、log search，不应该用 primary DB 的 LIKE '%keyword%' 硬查。

Write path

Primary DB
  -> CDC / Outbox / Kafka
  -> Indexer
  -> Elasticsearch

DB 是 source of truth，Elasticsearch 是 derived index。Indexer 必须处理：

  • duplicate events。
  • out-of-order updates。
  • delete tombstone。
  • reindex。
  • backfill。

Index design

document_id
text fields
keyword fields
timestamp
tenant_id
visibility
ranking signals
version

Refresh interval

Elasticsearch 不是每次写入都立即可搜。refresh interval 影响 freshness 和 throughput：

  • refresh 太频繁：写入成本高。
  • refresh 太慢：搜索结果不新。

面试回答：根据业务 SLA 设置。例如商品搜索可以秒级，安全删除需要 read-time filter 兜底。

Reindex strategy

改 mapping 或 ranking 时不要直接改线上 index：

  1. 创建 new index。
  2. Backfill data。
  3. Dual write / replay events。
  4. Shadow query compare。
  5. Alias switch。
  6. 保留 rollback path。

Interview answer

I would keep the database as the source of truth and build Elasticsearch as a derived index through CDC or Kafka. The indexer must be idempotent and version-aware to handle duplicate or out-of-order events. For schema or ranking changes, I would build a new index, backfill, replay recent events, compare shadow queries, then switch an alias for low-risk rollout.

4. Flink / Stream Processing

什么时候需要 stream processing

当系统要处理持续事件流，并且需要 window、aggregation、join、late event、stateful computation，就会用 Flink / streaming engine。

例子：

  • Ad click aggregation。
  • Fraud detection。
  • Realtime dashboard。
  • Notification trigger。
  • Feature computation。

Core concepts

  • Event time：事件发生时间。
  • Processing time：系统处理时间。
  • Watermark：系统认为更早事件基本到齐的进度。
  • Window：按时间聚合。
  • State：每个 key 的中间状态。
  • Checkpoint：故障恢复状态快照。

Architecture

Kafka topic
  -> Flink job
       - parse
       - keyBy
       - window
       - aggregate
       - dedup
  -> Redis / OLAP / Warehouse

Late events

迟到事件不能简单丢：

  • 允许 allowed lateness。
  • 使用 watermark 关闭 window。
  • 太晚的事件进 side output。
  • 对 billing/reporting 使用 batch correction。

Exactly-once effect

不要随便说 exactly-once。更准确：

  • Flink state 可以通过 checkpoint 实现 exactly-once state update。
  • Sink 是否 exactly-once 取决于外部系统是否支持事务或幂等写。
  • 业务最终目标是 exactly-once effect。

Interview answer

I would use event time and watermarks rather than processing time for correctness. The stream job keys events by business id, maintains state for deduplication or aggregation, and checkpoints state for recovery. For late events, I would allow bounded lateness and send very late events to a correction path. For exactly-once, I would focus on idempotent or transactional sinks to achieve exactly-once business effect.

5. Scaling Reads

常用手段

读扩展不是只有“加 cache”。要按瓶颈分层：

BottleneckSolution
DB read QPS 高cache, read replica
Query 太慢index, denormalized table
Join 太重materialized view, CQRS read model
Global latency 高CDN, geo replica
Hot objectlocal cache, replicated cache, request coalescing

Read replica

优点：分担 read QPS。缺点：replica lag。适合：

  • profile view。
  • feed hydrate。
  • analytics read。

不适合：

  • 刚写完必须立即读到的 money/inventory。
  • 强一致状态检查。

Materialized view

当 read query 很复杂，可以预计算：

source tables -> events -> view builder -> read optimized table

代价是 eventual consistency 和 rebuild 成本。

Interview answer

I would first identify whether read pressure comes from QPS, query complexity, or geographic latency. Cache helps hot reads, replicas help read QPS, indexes help selective queries, and materialized views help expensive joins. For derived views I would explicitly call out eventual consistency and rebuild strategy.

6. Scaling Writes / Contention

写扩展常见问题

  • 单行热点：counter、inventory、auction current price。
  • 单 partition 热点：celebrity feed、hot room messages。
  • 全局顺序要求：payment ledger、matching engine。
  • 写放大：fanout、secondary index、multi-region replication。

解法工具箱

  1. Shard by business key。
  • 按 user_id、auction_id、tenant_id、room_id 分片。
  1. Single-writer per key。
  • 同一 auction / inventory item 的写进入同一 queue 或 actor。
  1. Conditional update。
  • 用 version 或 condition 防止 lost update。
  1. Batch writes。
  • Counter 先局部聚合，再 flush。
  1. Move work async。
  • 写 source of truth 后，把 fanout / index / notification 放到 queue。

Counter example

不要所有 like 都更新一行：

counter_shard(object_id, shard_id, count)

读取时 sum shards，或周期性 rollup。

Interview answer

For write scaling, I would look for the contention key first. If many writes hit the same entity, adding more servers does not solve the hotspot. I would use conditional updates for correctness, single-writer or queue-based serialization for highly contended entities, and sharded counters or batching for high-volume approximate counts.

7. Large Blobs Pattern

不要把大文件塞进 DB

图片、视频、PDF、model artifact、log archive 都应该放 object storage。DB 存 metadata 和 object key。

Upload architecture

Client
  -> API: create upload session
  -> Object Storage: multipart upload
  -> API: complete upload
  -> Metadata DB
  -> Processing Queue
  -> CDN

为什么 client direct upload

  • API server 不扛大流量。
  • 支持断点续传 / multipart。
  • 更便宜。
  • 更容易走 CDN / regional object storage。

Metadata

blob_id
owner_id
object_key
content_type
size
checksum
status
created_at

Consistency

常见失败：

  • object 上传成功，metadata 写失败。
  • metadata 创建成功，object 上传失败。
  • processing 失败。

处理：

  • upload session state machine。
  • background cleanup orphan objects。
  • checksum verification。
  • processing retry。

Interview answer

I would store large bytes in object storage and keep only metadata in the database. The client uploads directly using pre-signed multipart URLs. After upload completion, the system verifies checksum, updates metadata, and triggers asynchronous processing. Cleanup jobs remove abandoned upload sessions and orphaned objects.

8. Long-running Tasks

例子

  • Video transcoding。
  • Report generation。
  • ML inference batch job。
  • Data export。
  • Web crawling。

这些任务不能同步 HTTP 等待完成。

Architecture

API
  -> Job DB
  -> Queue
  -> Worker
  -> Progress Store
  -> Status API / WebSocket

Job state machine

QUEUED -> RUNNING -> SUCCEEDED
       -> FAILED
       -> CANCELLED
       -> RETRYING

Worker lease

Worker 领取 job 时写 lease：

job_id
worker_id
lease_until
attempt

如果 worker crash，lease expire 后 job 可以被重新领取。

Idempotency

重试可能重复执行，所以 output 要幂等：

  • deterministic output key。
  • write temp then atomic rename。
  • DB state conditional update。
  • external calls use idempotency key。

Interview answer

I would turn long-running work into asynchronous jobs. The API creates a job record and returns job_id. Workers claim jobs with leases, update progress, and write outputs idempotently. Clients poll a status API or subscribe to realtime updates. If a worker dies, the lease expires and another worker retries the job safely.

9. Multi-step Process / Saga

例子

  • Order checkout：reserve inventory -> charge payment -> create shipment。
  • Travel booking：flight -> hotel -> car。
  • Account onboarding：KYC -> risk -> account creation。

为什么不用大分布式事务

跨服务 ACID transaction 很重，耦合高，失败处理复杂。实际系统常用 Saga / workflow：

  • 每一步本地事务。
  • 状态持久化。
  • 失败时 retry 或 compensation。

Orchestration vs Choreography

Orchestration：

Workflow Engine controls steps

优点：状态清晰，容易 debug。缺点：中心化。

Choreography：

Services react to events

优点：服务松耦合。缺点：流程分散，debug 难。

Compensation

不是所有操作都能真正 undo：

  • reserve inventory 可以 release。
  • payment capture 可以 refund，但不是瞬时。
  • email sent 不能撤回，只能补偿通知。

Interview answer

I would model the process as a Saga with explicit state. Each step commits a local transaction and emits an event. On failure, the workflow retries transient errors and runs compensation for completed steps when necessary. I prefer orchestration for complex business-critical flows because it makes state, retries, and debugging clearer.

10. Real-time Updates Pattern

选型

MechanismBest for
Polling简单状态查询，低频
Long polling中低频更新
SSEserver-to-client stream
WebSocket双向实时通信

Architecture

Client
  -> WebSocket Gateway
  -> Connection Registry
  -> Pub/Sub
  -> Backend event producers

Connection registry

需要知道 user 在哪些 gateway 上：

user_id -> connection_ids -> gateway_id

但这个 registry 可能是 eventually consistent。发送失败要允许连接已经断开。

Backpressure

实时系统最怕慢 client：

  • per-connection send buffer limit。
  • 丢弃低优先级 update。
  • 合并状态 update。
  • 断开长期慢连接。

Interview answer

I would terminate WebSocket connections at gateway nodes and use pub/sub to deliver backend events to the right gateway. A connection registry maps users to active connections, but delivery should tolerate stale entries. For slow clients, I would enforce send-buffer limits, coalesce updates, and drop low-priority messages rather than letting one connection consume unbounded memory.

11. Time-series Database

适用场景

  • Metrics。
  • IoT sensor data。
  • Price history。
  • Ad events aggregation。
  • System logs with timestamp。

Data model

measurement
tags: host, region, service, tenant
fields: cpu, memory, latency
timestamp

核心设计

  • Append-heavy write。
  • Time-based partition。
  • Retention policy。
  • Downsampling / rollup。
  • Compression。
  • High-cardinality tag control。

Retention

raw 1-second data: keep 7 days
1-minute rollup: keep 30 days
1-hour rollup: keep 1 year

High cardinality

如果把 user_id、request_id 放 tag，series 数量会爆炸。高 cardinality 字段要谨慎，可能放 log/search 系统而不是 metrics DB。

Interview answer

I would use a time-series store for append-heavy timestamped data with retention and rollup. Data is partitioned by time and commonly queried tags. Raw high-resolution data is kept briefly, then downsampled for long-term storage. I would avoid high-cardinality tags such as request_id because they can explode the number of series.

12. Staff-level System Design Answer Anatomy

普通答案 vs 高分答案

普通答案：

  • 画 API、DB、cache、queue。
  • 说可以 scale。
  • 说加 Kafka。

高分答案：

  • 明确 business invariant。
  • 说清楚 source of truth 和 derived data。
  • 分开 write path / read path / async path。
  • 找到 bottleneck 和 contention key。
  • 说明 consistency tradeoff。
  • 给出 failure handling。
  • 用 metrics 证明系统可运营。

白板结构

1. Requirements and scale
2. Core entities and APIs
3. High-level architecture
4. Write path
5. Read path
6. Async processing
7. Data partitioning
8. Correctness and consistency
9. Failure modes
10. Metrics and operations

主动讲的 tradeoff

  • Cache freshness vs DB load。
  • Fanout-on-write vs fanout-on-read。
  • Strong consistency vs availability。
  • Low latency vs cost。
  • Exact counter vs approximate counter。
  • Sync user experience vs async reliability。

面试收尾模板

The core invariant I would protect is [business invariant]. The source of truth is [primary store], while [cache/index/timeline] is derived and rebuildable. The main bottleneck is [read/write/fanout/contention], so I would scale it with [specific strategy]. For failures, I would use idempotency, retries with backoff, dead-letter queues, and operational metrics such as latency, error rate, queue lag, and saturation.
