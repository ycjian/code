22. Classic System Design Question Bank

这一节来自 sd_pages 里的 noisy system design pages。不要背原文；面试里要按固定结构讲：需求、核心难点、架构、数据模型、扩展性、failure mode、trade-off。

每道题都用这个模板：

  1. Clarify requirements。
  2. Estimate scale。
  3. Define APIs。
  4. Pick storage / cache / queue。
  5. Explain critical path。
  6. Call out bottleneck and trade-off。
  7. Give one senior-level deep dive。

1. Design a URL Shortener Like Bit.ly

Question

设计一个 URL shortener，用户提交 long URL，系统返回 short URL。访问 short URL 时重定向到 long URL。需要高可用、低延迟、支持 analytics。

Approach

这题核心不是“生成一个短码”，而是：

  • 如何生成 unique short code。
  • Redirect path 如何做到极低 latency。
  • Custom alias 怎么处理冲突。
  • Analytics 是否同步写入。
  • Abuse / malicious URL 怎么防。

API

POST /urls
{
  "longUrl": "https://example.com/a/b/c",
  "customAlias": "optional"
}
-> { "shortUrl": "https://sho.rt/abc123" }

GET /{code}
-> 301/302 redirect

Data model

UrlMapping(
  code,
  long_url,
  user_id,
  created_at,
  expire_at,
  status
)

ClickEvent(
  code,
  timestamp,
  ip_hash,
  user_agent,
  referrer
)

Code generation

常见方案：

  1. Auto-increment id + Base62
  • 简单、短、唯一。
  • 但容易暴露增长趋势。
  1. Random Base62
  • 不暴露顺序。
  • 需要 collision check。
  1. Snowflake id + Base62
  • 分布式生成，不依赖单 DB sequence。

面试里推荐：

For simplicity and scale, I would generate a unique numeric id using a distributed ID generator, then encode it using Base62. Custom aliases go through a uniqueness check.

Read path

Redirect 是核心高 QPS path：

Client -> CDN/Edge optional -> Redirect Service -> Redis cache -> DB fallback -> 301/302
  • Hot code 放 Redis。
  • DB 是 source of truth。
  • Analytics event 异步写 Kafka，不阻塞 redirect。

301 vs 302

  • 301 permanent redirect：浏览器/CDN 可能缓存，性能好，但后续修改 long URL 不方便。
  • 302 temporary redirect：每次都回源，更灵活，analytics 更完整。

面试里可以说：默认用 302 支持 analytics 和可变 mapping；对永久短链可以用 301。

Bottlenecks

  • Hot URL 被大量访问：cache + CDN。
  • DB read pressure：Redis read-through。
  • Analytics 写入量大：Kafka async event pipeline。
  • Abuse：URL scanning, domain blacklist, rate limiting。

Interview answer

I would keep redirect latency extremely low. The redirect service first checks Redis for code-to-URL mapping and falls back to DB. Click analytics is emitted asynchronously to Kafka so it does not block redirect. For code generation, I would use a distributed id and Base62 encoding; custom aliases require uniqueness checks and abuse scanning.

2. Design a Distributed Rate Limiter

Question

设计一个 rate limiter，限制 user / IP / API key 的请求速率，支持多 API server 分布式部署。

Approach

重点不是算法名，而是限流精度、低延迟、分布式一致性、hot key 和 failure behavior。

Requirements

  • 支持 per-user / per-IP / per-API-key。
  • 支持 burst。
  • 多 API server 共享限制。
  • 低延迟，不能每次都打慢 DB。
  • Redis 故障时要 fail-open 还是 fail-closed。

Algorithm

推荐 token bucket：

capacity = burst size
refill_rate = tokens per second
request consumes one token
if token available -> allow
else -> reject

Distributed design

API Gateway / Service
  -> local pre-limiter
  -> Redis token bucket Lua script
  -> allow / reject

为什么用 Lua：

  • refill、check、decrement 必须原子。
  • 避免 race condition。

Redis key：

rl:{tenant}:{api_key}:{route}

value:

tokens
last_refill_timestamp

Hot key 问题

如果一个 global API key 流量极大，单 Redis key 会热。

缓解：

  • Local token bucket 先挡一部分。
  • Shard by key hash。
  • 对超大 tenant 分配 dedicated limiter。
  • 使用 approximate local counters + periodic sync。

Failure behavior

  • 登录、防刷、支付：Redis 故障时 fail-closed 或 strict fallback。
  • 普通 read API：Redis 故障时 fail-open，保护可用性。

Interview answer

I would use token bucket implemented with Redis Lua script so refill and consume are atomic. Each API server calls the limiter using a key such as tenant plus route. To reduce Redis hot-key pressure, I would add local pre-limiting and shard large tenants. Failure mode depends on business risk: security-sensitive APIs fail closed, normal reads may fail open.

3. Design a Web Crawler

Question

设计一个 web crawler，持续抓取网页，去重，遵守 robots.txt，支持大规模并发和增量更新。

Approach

核心难点：

  • URL frontier 如何调度。
  • URL dedup。
  • Politeness：不能打爆同一个 domain。
  • 内容去重。
  • 失败重试。
  • 页面更新频率。

Architecture

Seed URLs
  -> URL Frontier
  -> Per-domain scheduler
  -> Fetcher workers
  -> Parser
  -> Content store
  -> Link extractor
  -> Dedup filter
  -> URL Frontier

URL Frontier

不要一个 global FIFO。应该按 domain 分 queue：

frontier:{domain}

并维护 next_allowed_fetch_time，保证同一 domain 的抓取间隔。

Dedup

两层去重：

  1. URL dedup
  • Canonicalize URL：lowercase host、remove fragment、normalize query。
  • Bloom filter 快速判断 seen。
  • DB/Key-value store 做最终记录。
  1. Content dedup
  • Hash normalized content。
  • SimHash / MinHash 判断近似重复。

Storage

  • Raw HTML：object storage。
  • Metadata：DB / KV。
  • Index：search index。
  • Crawl state：URL status, last crawled, next crawl time。

Retry

  • 5xx retry with backoff。
  • 404 降低优先级或停止。
  • robots.txt 禁止则不抓。

Interview answer

I would design the crawler around a URL frontier, not just a worker pool. The frontier is partitioned by domain to enforce politeness. Fetchers download pages, parsers extract links, and a dedup layer canonicalizes URLs and uses Bloom filters plus persistent state. Raw pages go to object storage, metadata to DB, and searchable content to an index.

4. Design Dropbox / File Sync

Question

设计一个 Dropbox-like file storage and sync service，支持上传、下载、跨设备同步、大文件、版本历史。

Approach

核心难点：

  • 大文件不能经过 app server。
  • Chunking / dedup。
  • Metadata 和 blob 分离。
  • Sync conflict。
  • 多设备变更通知。

Architecture

Client
  -> Metadata Service
  -> pre-signed upload URL
  -> Object Storage for chunks
  -> Sync Service
  -> Notification / Change Log

Data model

FileMetadata(
  file_id,
  owner_id,
  path,
  current_version,
  size,
  updated_at
)

FileVersion(
  file_id,
  version,
  chunk_hashes[],
  created_at
)

Chunk(
  chunk_hash,
  storage_url,
  size,
  ref_count
)

Upload flow

  1. Client splits file into chunks。
  2. Compute content hash for each chunk。
  3. Ask server which chunks already exist。
  4. Upload missing chunks directly to object storage。
  5. Commit metadata transaction。
  6. Emit change event to sync devices。

Conflict handling

如果两个设备离线编辑同一个 file：

  • Server 不做 magical merge。
  • 生成 conflict copy。
  • 对支持 merge 的文档类型可用 CRDT/OT。

Interview answer

I would separate metadata from blob storage. Files are split into content-addressed chunks so uploads can deduplicate unchanged chunks. Clients upload chunks directly to object storage using pre-signed URLs, then commit a metadata version. Sync is driven by a per-user change log so devices can ask for changes since last sync token.

5. Design Collaborative Document Editor Like Google Docs

Question

设计协同文档编辑系统，多个用户同时编辑，同步看到变化，支持离线、冲突处理、历史版本。

Approach

核心不是 WebSocket 本身，而是并发编辑算法：

  • Operational Transform (OT)
  • CRDT

Architecture

Client editor
  -> WebSocket gateway
  -> Collaboration session service
  -> OT/CRDT engine
  -> Document store
  -> Snapshot + operation log

Operation log

不要每次保存整个 document。保存 operations：

op_id
doc_id
base_version
user_id
operation: insert/delete/format
timestamp

定期 compact 成 snapshot：

snapshot_version
document_content

OT vs CRDT

  • OT：server 协调 transform，Google Docs 经典路线。中心化更强，理解和控制容易。
  • CRDT：每个 client 可独立合并，离线更强，但 metadata 更复杂。

面试里可选 OT：

For interview simplicity, I would use OT with a central collaboration service. Clients send operations with base version; server transforms against concurrent operations, appends to log, then broadcasts canonical operations.

Failure handling

  • WebSocket 断开后 client reconnect。
  • Client 带 last_seen_version。
  • Server replay missing ops。
  • 定期 snapshot 减少 replay 成本。

Interview answer

I would model edits as operations rather than full document writes. A collaboration service maintains document version, transforms concurrent operations using OT, appends them to an operation log, and broadcasts canonical operations over WebSocket. Periodic snapshots make recovery and loading efficient.

6. Design Yelp / Local Business Review Search

Question

设计 Yelp-like local business review site，支持附近商家搜索、评分、评论、排序。

Approach

核心难点：

  • Geo search。
  • Review write/read model。
  • Ranking。
  • Search index consistency。
  • Abuse / fake reviews。

Architecture

Business Service
Review Service
Search / Geo Index
Ranking Service
Photo / Media Service
Moderation Pipeline

Geo index

常见选择：

  • Geohash：把经纬度编码成 prefix，适合 nearby search。
  • S2 / H3：更均匀的地理网格。
  • Elasticsearch geo index / PostGIS。

Read path：

query location + radius + filters
  -> geo index returns candidate business ids
  -> ranking service scores
  -> hydrate business details and reviews

Ranking signals：

  • distance。
  • rating。
  • review count。
  • freshness。
  • open now。
  • personalization。
  • sponsored / ads policy。

Review consistency

  • Review 写入 DB。
  • Outbox/CDC 更新 search index 和 aggregate rating。
  • Rating aggregate 可以 async，但用户自己的 review 要 read-your-write。

Interview answer

I would keep business and review data in the primary DB, then build a derived geo/search index for low-latency nearby queries. The search path finds candidates by geohash or geo index, then ranks by distance, rating, freshness, and business signals. Review writes update the primary DB first and asynchronously update aggregates and search index.

7. Design Uber / Ride Sharing

Question

设计 ride-sharing 系统，乘客请求附近司机，司机实时上报位置，系统匹配、派单、计费。

Approach

核心难点：

  • 实时位置更新。
  • Nearby driver search。
  • Matching。
  • Driver state consistency。
  • Surge pricing。
  • Trip lifecycle。

Architecture

Rider App / Driver App
  -> Location Ingestion
  -> Geo Index
  -> Matching Service
  -> Trip Service
  -> Pricing Service
  -> Notification Service

Driver location

司机每几秒上报 location：

driver_id
lat/lng
heading
timestamp
availability

存储：

  • Redis / in-memory geo index for active drivers。
  • Kafka for location stream。
  • Long-term storage for analytics。

Matching flow

  1. Rider requests trip。
  2. Find nearby available drivers by geo cell。
  3. Score by ETA、distance、driver status、acceptance rate。
  4. Offer to best driver。
  5. Use state transition to reserve driver。

Driver 状态机：

AVAILABLE -> OFFERED -> ACCEPTED -> ON_TRIP -> AVAILABLE

状态更新必须 conditional，避免一个 driver 被派给两个 riders。

Interview answer

I would keep active driver locations in a low-latency geo index partitioned by geohash/S2 cells. The matching service queries nearby cells, ranks drivers by ETA and status, then uses a conditional state transition to reserve a driver. Location events also go to Kafka for analytics and pricing, but matching reads from the hot geo index.

8. Design Live Comments System

Question

设计直播评论系统，用户发评论，其他观看者实时看到。需要低延迟、高 fanout、防 spam。

Approach

核心难点：

  • Fanout to many viewers。
  • Ordering。
  • Moderation。
  • Hot live room。
  • Slow consumers。

Architecture

Client
  -> WebSocket Gateway
  -> Comment Service
  -> Moderation / Spam filter
  -> Kafka topic per stream or partition
  -> Fanout workers
  -> WebSocket rooms

Write path

  1. Client sends comment over WebSocket/HTTP。
  2. Comment service validates and assigns sequence id。
  3. Moderation fast path。
  4. Persist comment。
  5. Publish to Kafka。
  6. Fanout to connected viewers。

Ordering

对于一个 live stream，使用 stream_id as partition key，保证同一 stream 内顺序。超大直播可以分 shard，但需要接受局部顺序或在 client 端按 sequence merge。

Slow consumers

  • 每个 connection 有 bounded send buffer。
  • 慢 client 丢弃旧评论或降级为 sampled comments。
  • 不能让一个慢连接阻塞整个 room。

Interview answer

I would use WebSocket for realtime delivery, but the core is fanout control. Comments are validated, assigned sequence numbers, persisted, and published to Kafka by stream_id. Fanout workers broadcast to WebSocket gateways. Each client connection has a bounded buffer so slow consumers do not block the room.

9. Design a Stock Trading Platform

Question

设计 Robinhood-like trading platform，支持下单、订单状态、账户余额、行情展示。

Approach

这题金融属性强，必须优先 correctness、audit、idempotency。

核心组件：

API Gateway
Account Service
Order Service
Risk / Buying Power Service
Execution Gateway
Ledger Service
Market Data Service
Notification Service
Audit Log

Order flow

Client places order
  -> idempotency check
  -> validate account / buying power
  -> create order PENDING
  -> send to broker/exchange
  -> receive execution report
  -> update order status
  -> update ledger
  -> notify user

Data correctness

  • Order state machine must be explicit。
  • Ledger 用 append-only entries，不只存 balance。
  • 外部 execution reports 要幂等处理。
  • 所有状态变化写 audit log。
  • Reconciliation with broker/exchange。

Order states:

NEW -> ACCEPTED -> PARTIALLY_FILLED -> FILLED
NEW -> CANCELLED
NEW -> REJECTED

Market data

Market data 是 read-heavy stream：

  • WebSocket/SSE 推送报价。
  • Cache latest quote。
  • 不要把 market data 和 order transaction 混在一个服务里。

Interview answer

I would separate trading correctness from market-data display. Orders go through an idempotent order service, risk check, execution gateway, and append-only ledger. Execution reports from broker/exchange are processed idempotently and reconciled later. Market data is a separate streaming path optimized for fanout and low latency.

10. Design an Ad Click Aggregator

Question

设计广告点击聚合系统，收集 click/impression events，实时统计，支持报表和 billing。

Approach

核心难点：

  • Very high write volume。
  • Dedup。
  • Late / out-of-order events。
  • Realtime vs accurate reporting。
  • Billing correctness。

Architecture

Click endpoint
  -> edge collector
  -> Kafka
  -> realtime stream processor
  -> Redis / OLAP realtime counters
  -> raw event lake
  -> batch validation
  -> final reporting warehouse

Event schema

event_id
ad_id
campaign_id
user_id_hash
timestamp
event_type: impression/click/conversion
request_id
device/context

Dedup

event_id 可以由：

request_id + ad_id + event_type

Consumer 侧用 state store / Redis / warehouse merge 去重。

Realtime vs final truth

  • Realtime dashboard 可以 approximate。
  • Billing/reporting 必须走 validated batch / warehouse。
  • Late events 使用 watermark 处理。

Interview answer

I would split the pipeline into realtime feedback and financial truth. Edge collectors write events to Kafka. Stream processors produce fast approximate counters for dashboards and pacing. Raw events are also stored immutably, then batch jobs deduplicate, validate, handle late events, and produce final billing/reporting tables.
