24. Low Level Design Interview Bank

这一节来自 sd_pages 里的 Low Level Design pages。LLD 面试和 system design 不一样：面试官更看重 class modeling、state transition、API boundaries、extensibility、edge cases、testability。

LLD 每题建议用这个顺序：

  1. Clarify entities and use cases。
  2. Define core classes / interfaces。
  3. Define state machine。
  4. Explain main operations。
  5. Handle concurrency / consistency。
  6. Show extensibility。
  7. Mention tests。

1. Amazon Locker Low Level Design

Question

设计 Amazon Locker。用户下单后包裹被投递到 locker，用户收到 pickup code，在有效时间内取件。系统要支持不同 locker size、过期释放、通知、运营人员补货/取回。

Core objects

class Locker {
  String lockerId;
  LockerSize size;
  LockerStatus status;
  String locationId;
}

class Package {
  String packageId;
  LockerSize requiredSize;
  PackageStatus status;
}

class Reservation {
  String reservationId;
  String packageId;
  String lockerId;
  String pickupCodeHash;
  Instant expireAt;
  ReservationStatus status;
}

State machines

Locker:

AVAILABLE -> RESERVED -> OCCUPIED -> AVAILABLE
AVAILABLE -> OUT_OF_SERVICE

Reservation:

CREATED -> DELIVERED -> PICKED_UP
CREATED -> EXPIRED
DELIVERED -> EXPIRED

Main operations

  1. reserveLocker(packageId, size, location)
  • Find smallest available locker >= required size。
  • Mark locker as RESERVED。
  • Create reservation with expiry。
  1. deliverPackage(reservationId)
  • Courier opens locker。
  • Put package。
  • Locker becomes OCCUPIED。
  • Send pickup code to user。
  1. pickupPackage(code)
  • Verify code hash。
  • Check not expired。
  • Open locker。
  • Mark reservation PICKED_UP。
  • Mark locker AVAILABLE。
  1. expireReservation()
  • Background job scans expired reservations。
  • Release locker or create return task。

Concurrency

多个订单可能同时抢同一个 locker。核心是 atomic reservation：

UPDATE locker
SET status = 'RESERVED'
WHERE locker_id = ?
  AND status = 'AVAILABLE'

只有 update 成功的 request 拿到 locker。

Extensibility

  • 新 locker size：enum / config。
  • 新通知方式：NotificationChannel interface。
  • 不同分配策略：LockerAssignmentStrategy。

Interview answer

I would model locker assignment as a state transition problem. The critical operation is reserving a locker atomically so two packages cannot get the same locker. I would separate Locker, Package, Reservation, and Notification. Locker assignment uses the smallest available locker that fits the package, and reservation expiry is handled by a background job.

2. Parking Lot Low Level Design

Question

设计停车场，支持不同 vehicle type、spot type、入场取票、出场计费、找车位、支付。

Core objects

class ParkingLot {
  List<ParkingFloor> floors;
  ParkingSpotAssignmentStrategy strategy;
}

class ParkingSpot {
  String spotId;
  SpotType type;
  SpotStatus status;
}

class Ticket {
  String ticketId;
  String vehicleNumber;
  String spotId;
  Instant entryTime;
  TicketStatus status;
}

class PricingPolicy {
  Money calculate(Instant entry, Instant exit, VehicleType type);
}

Main operations

  1. park(vehicle)
  • Choose compatible spot。
  • Mark spot occupied。
  • Create ticket。
  1. unpark(ticketId)
  • Calculate fee。
  • Process payment。
  • Mark ticket paid。
  • Free spot。

Spot assignment

不要把策略写死在 ParkingLot 里。使用 strategy pattern：

interface ParkingSpotAssignmentStrategy {
  ParkingSpot findSpot(Vehicle vehicle, List<ParkingFloor> floors);
}

可扩展策略：

  • nearest entrance。
  • nearest elevator。
  • compact-first。
  • EV charging priority。

Concurrency

多个入口同时分配车位，要保证 spot 状态更新原子：

UPDATE spot
SET status = 'OCCUPIED'
WHERE spot_id = ?
  AND status = 'AVAILABLE'

Interview answer

I would separate domain entities from policies. ParkingLot owns floors and spots, Ticket tracks a parking session, PricingPolicy calculates fees, and SpotAssignmentStrategy chooses a spot. The critical concurrency point is spot assignment, which must atomically move a spot from AVAILABLE to OCCUPIED.

3. Elevator Low Level Design

Question

设计电梯系统，多个 elevator 服务多个 floor。用户在楼层按 up/down，在电梯内选择目标楼层。系统要调度电梯、处理方向、停靠、开关门。

Core objects

class Elevator {
  String elevatorId;
  int currentFloor;
  Direction direction;
  ElevatorState state;
  SortedSet<Integer> upStops;
  SortedSet<Integer> downStops;
}

class Request {
  int sourceFloor;
  Integer destinationFloor;
  Direction direction;
  RequestType type;
}

interface SchedulingStrategy {
  Elevator assign(Request request, List<Elevator> elevators);
}

State machine

IDLE -> MOVING_UP -> DOOR_OPEN -> MOVING_UP
IDLE -> MOVING_DOWN -> DOOR_OPEN -> MOVING_DOWN
MOVING_* -> IDLE when no stops

Scheduling

简单策略：

  • 同方向且会经过 source floor 的 elevator 优先。
  • 否则选最近 IDLE elevator。
  • 否则选择 estimated cost 最低的 elevator。

Cost function:

cost = distance + direction_penalty + current_queue_size

Stop handling

  • Up direction 使用 min-heap / sorted set。
  • Down direction 使用 max-heap / reverse sorted set。
  • 当前方向 stops 清空后再考虑反方向。

Interview answer

I would model each elevator as a state machine with current floor, direction, and ordered stop sets. The scheduler assigns hall requests based on estimated cost, preferring elevators moving in the same direction. The design should keep scheduling strategy pluggable so we can replace nearest-elevator with cost-based or destination-dispatch later.

4. Inventory Management Low Level Design

Question

设计库存系统，支持 stock add/remove、reservation、purchase、release、multi-warehouse。重点是防止 oversell。

Core objects

class SKU {
  String skuId;
  String name;
}

class InventoryItem {
  String skuId;
  String warehouseId;
  int available;
  int reserved;
  long version;
}

class Reservation {
  String reservationId;
  String skuId;
  int quantity;
  Instant expireAt;
  ReservationStatus status;
}

Main operations

  1. reserve(skuId, quantity)
  • Check available。
  • Decrease available。
  • Increase reserved。
  • Create reservation with TTL。
  1. commit(reservationId)
  • Decrease reserved。
  • Mark reservation committed。
  1. release(reservationId)
  • Increase available。
  • Decrease reserved。
  • Mark released。

Prevent oversell

Atomic update:

UPDATE inventory
SET available = available - ?,
    reserved = reserved + ?
WHERE sku_id = ?
  AND available >= ?

如果 affected rows = 0，说明库存不足。

Reservation expiry

后台 job 扫描 expired reservation：

RESERVED -> EXPIRED
return quantity to available

Interview answer

I would model inventory as available plus reserved, not just one stock number. Checkout first creates a reservation with TTL using an atomic conditional update. Payment success commits the reservation; timeout releases it. This prevents oversell while avoiding long database locks during payment.

5. Rate Limiter Low Level Design

Question

设计一个 rate limiter class/library，支持不同算法和 rule，例如 per-user、per-IP、per-route。

Core interfaces

interface RateLimiter {
  boolean allow(RequestContext ctx);
}

interface RateLimitRule {
  String key(RequestContext ctx);
  int limit();
  Duration window();
}

interface RateLimitStore {
  CounterState get(String key);
  void save(String key, CounterState state);
}

Strategy pattern

class TokenBucketLimiter implements RateLimiter { }
class SlidingWindowLimiter implements RateLimiter { }
class FixedWindowLimiter implements RateLimiter { }

这样新增算法不会改调用方。

RequestContext

user_id
ip
api_key
route
timestamp
tenant_id

Store choices

  • InMemoryStore：单机测试。
  • RedisStore：分布式生产。
  • MockStore：unit tests。

Interview answer

I would design the limiter around interfaces: RateLimiter for the algorithm, RateLimitRule for policy, and RateLimitStore for state. This separates algorithm from storage. Token bucket can support burst; sliding window gives smoother accuracy. In production the store is Redis, but tests can use in-memory store.

6. Spreadsheet With Formulas

Question

设计一个 spreadsheet，支持 set cell、get cell、formula，例如 C1 = A1 + B1，当依赖变化时结果更新。

Core objects

class Cell {
  String id;
  CellValue rawValue;
  Formula formula;
  CellValue computedValue;
}

class Spreadsheet {
  Map<String, Cell> cells;
  DependencyGraph graph;
}

Dependency graph

如果 C1 = A1 + B1：

C1 depends on A1, B1
A1 has dependent C1
B1 has dependent C1

更新 A1 时，需要 recompute C1。

Operations

  1. setValue(cellId, value)
  • Remove old dependencies。
  • Set raw value。
  • Recompute dependents。
  1. setFormula(cellId, formula)
  • Parse referenced cells。
  • Detect cycle。
  • Update dependency graph。
  • Compute value。
  • Recompute dependents。
  1. getValue(cellId)
  • Return computed value。

Cycle detection

如果：

A1 = B1 + 1
B1 = A1 + 1

必须 reject。使用 DFS 检查新 edge 是否造成 cycle。

Interview answer

I would model formulas as a dependency graph. Each formula cell depends on referenced cells, and each cell tracks its dependents. When a cell changes, we recompute affected cells in topological order. Formula updates must run cycle detection before committing graph changes.

7. Connect Four Low Level Design

Question

设计 Connect Four 游戏。两个玩家轮流往列里放棋子，先连成 4 个获胜。

Core objects

class Game {
  Board board;
  Player currentPlayer;
  GameStatus status;
}

class Board {
  int rows = 6;
  int cols = 7;
  Piece[][] grid;
  int[] nextEmptyRowByCol;
}

class Move {
  Player player;
  int col;
  int row;
}

Main operation

MoveResult makeMove(int col)

Steps:

  1. Check game is active。
  2. Check col in range。
  3. Check column not full。
  4. Place piece at nextEmptyRowByCol[col]。
  5. Check winner。
  6. Switch player。

Winner detection

只需要从新落子的 cell 检查四个方向：

  • horizontal。
  • vertical。
  • diagonal down-right。
  • diagonal up-right。

每个方向向两边扩展计数，>= 4 则 win。

Extensibility

  • Board size configurable。
  • Win length configurable。
  • AI player 实现 Player interface。
  • Undo 支持 move history。

Interview answer

I would keep the board state simple and optimize winner detection around the last move. After placing a piece, check four directions from that cell rather than scanning the whole board. The design has Game for turn/state, Board for grid operations, and configurable win length for extensibility.

8. LLD Delivery Framework

What interviewers expect

LLD 不是背 class diagram，而是展示你能把需求转成可维护代码结构。

Recommended flow

  1. Clarify use cases
  • Who uses it?
  • What operations are required?
  • What is out of scope?
  1. Identify nouns and verbs
  • Nouns become candidate classes。
  • Verbs become methods / services。
  1. Define relationships
  • one-to-many。
  • composition vs aggregation。
  • ownership and lifecycle。
  1. Define state machines
  • Booking, order, ticket, elevator, locker 都有 states。
  • 状态转换比 class 数量更重要。
  1. Apply patterns only when useful
  • Strategy for pluggable algorithms。
  • Factory for object creation。
  • Observer for notification。
  • State pattern for complex state transitions。
  1. Discuss concurrency
  • atomic update。
  • lock。
  • optimistic concurrency。
  • idempotency。
  1. Mention tests
  • unit tests for policies。
  • state transition tests。
  • concurrency tests。
  • edge cases。

Common mistakes

  • 一上来画 20 个 classes，但没有 main flow。
  • 忘记 state transition。
  • 把 policy 写死，无法扩展。
  • 不讲 concurrency。
  • 不讲 invalid input。
  • 不讲 tests。

Interview answer

In LLD, I start from use cases and state transitions, then define entities and interfaces. I keep policies pluggable through strategy interfaces, keep persistence separate from domain logic, and explicitly handle invalid states and concurrency. I also call out unit tests for state transitions and edge cases.
