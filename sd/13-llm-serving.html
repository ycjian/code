31. Multi-GPU LLM Inference Serving

题目背景

白板设计一个高吞吐的 Multi-GPU 大模型推理服务。面试官通常不是想听“把模型部署到 GPU 上”，而是想看你是否理解 LLM serving 的核心瓶颈：

  • GPU memory 被 model weights、KV Cache、activation workspace 同时争抢。
  • Prefill 和 decode 的计算形态完全不同。
  • Continuous batching 提高吞吐，但会让 KV Cache 生命周期更复杂。
  • Multi-GPU tensor parallelism 会引入 All-Reduce / All-Gather 通信延迟。
  • 极长 prompt 或突发长输出会把 KV memory pool 打爆，必须能 graceful degradation。

高层架构

Client
  -> API Gateway / Auth / Rate Limit
  -> Request Router
  -> Admission Controller
  -> Scheduler / Continuous Batcher
  -> GPU Worker Node
       - Model Executor
       - KV Cache Manager
       - Token Scheduler
       - NCCL Communication
       - Metrics / OOM Guard
  -> Streaming Response

核心组件

  1. API Gateway
  • 做 auth、rate limit、request size limit、tenant quota。
  • 尽早拒绝明显过长或不合法请求，避免进入 GPU 队列后浪费资源。
  1. Router
  • 根据 model name、tenant、SLA、当前 GPU load、KV cache free blocks，把请求路由到合适的 replica。
  • 可以区分 latency-sensitive traffic 和 throughput-oriented batch traffic。
  1. Admission Controller
  • 根据 prompt length、max_new_tokens、当前 KV cache free blocks 估算 worst-case memory。
  • 如果资源不足，选择 reject、queue、降级 max tokens、swap、preempt。
  1. Scheduler / Continuous Batcher
  • 不是固定 batch size，而是 iteration-level scheduling。
  • 每个 decode step 动态把还活着的 requests 合成一个 batch。
  • 已完成的 request 释放 KV blocks，新 request 可以插入 batch。
  1. KV Cache Manager
  • 管理每个 sequence 的 K/V tensor blocks。
  • 处理 block allocation、free、sharing、eviction、swap、preemption。
  1. Model Executor
  • 执行 prefill 和 decode。
  • 支持 Tensor Parallelism、Pipeline Parallelism、CUDA Graph、fused kernels、quantization。

Request lifecycle

1. Receive request
2. Tokenize prompt
3. Estimate KV cache requirement
4. Admission control
5. Prefill: process prompt tokens, build initial KV cache
6. Decode loop:
   - scheduler forms active batch
   - allocate one new KV slot per active sequence
   - run model forward for next token
   - stream token back
   - stop when EOS / max_new_tokens / timeout
7. Free KV blocks

Prefill vs Decode

阶段输入形态主要瓶颈优化重点
Prefill一次处理完整 promptcompute-heavy, attention over prompt大 batch、FlashAttention、chunked prefill
Decode每轮每个 request 生成 1 个 tokenmemory bandwidth + KV cache readcontinuous batching、KV cache paging、CUDA Graph

重要判断：

  • Prefill 吃计算，长 prompt 会占用大量 compute。
  • Decode 吃显存带宽和 KV cache，batch 越大，吞吐越高，但 latency 也可能上升。
  • Scheduler 要平衡 prefill 和 decode，避免长 prompt 把 decode traffic 饿死。

KV Cache 是显存刺客

LLM 推理时，KV Cache 会随着 sequence length 线性增长。每个 request 不只占 prompt memory，还会为未来生成 tokens 持续申请 KV space。

粗略公式：

KV memory ~= num_layers
           * sequence_length
           * hidden_size
           * 2(K and V)
           * bytes_per_element
           * batch_size

如果是 Tensor Parallelism，KV cache 也可能按 heads / hidden dimension 切到不同 GPU 上，但总量仍然巨大。

为什么普通 continuous batching 还不够

Continuous batching 解决的是 GPU utilization：每轮 decode 动态组成 batch，让 GPU 不空转。

但它没有自动解决 memory fragmentation：

  • 每个 request 长度不同。
  • 有的 request 早结束，有的继续生成。
  • 如果为每个 request 预分配连续大块显存，会产生大量 unused holes。
  • 长 prompt 进来时，可能总 free memory 足够，但找不到连续空间。

所以高分答案必须讲 KV Cache 的 block-based memory management。

PagedAttention / Block-based KV Cache

核心思想：像操作系统虚拟内存一样管理 KV Cache。

不要为每个 sequence 分配一整段连续 KV memory，而是把 KV Cache 切成固定大小 blocks。

Logical sequence tokens:
  token 0 ... token 15 | token 16 ... token 31 | token 32 ...

Logical KV blocks:
  logical block 0 -> physical block 17
  logical block 1 -> physical block 3
  logical block 2 -> physical block 91

KV block table

每个 request 维护一个 block table：

request_id
logical_block_id -> physical_block_id

Attention kernel 读取 KV 时，通过 block table 找到实际物理 block。物理 blocks 可以不连续。

这样解决什么问题

  1. 减少 external fragmentation
  • 不需要连续大块显存。
  • 只要有足够 free blocks，就可以服务 request。
  1. 减少 internal fragmentation
  • 只在最后一个 block 可能有浪费。
  • block size 越小，浪费越少，但 kernel overhead 和 metadata overhead 变高。
  1. 支持 dynamic growth
  • 每生成新 token，只在当前 block 满了后再申请新 block。
  1. 支持 sharing
  • 多个 request 共享相同 prefix 时，可以共享 prefix KV blocks。
  • Beam search / parallel sampling / agent branching 特别受益。

KV Cache Manager 需要哪些数据结构

GlobalBlockPool:
  free_block_list
  used_block_map
  ref_count
  block_location: GPU / CPU / evicted

SequenceState:
  request_id
  logical_block_table
  current_length
  max_tokens
  priority
  status: RUNNING / WAITING / SWAPPED / PREEMPTED / FINISHED

KV block lifecycle

Request admitted
  -> allocate blocks for prefill
  -> decode needs more tokens
  -> allocate next block when current block full
  -> request finishes
  -> decrement ref_count
  -> free blocks back to pool

如果 prefix sharing：

shared prefix block ref_count += 1
child request writes new tokens to private blocks

Admission control：不要等 OOM 才处理

收到请求时先估算：

required_blocks =
  ceil((prompt_tokens + max_new_tokens) / block_size)

更保守的系统会区分：

  • guaranteed blocks：prompt prefill 必须马上有。
  • speculative blocks：未来 decode 可能需要，可以边生成边申请。
  • tenant quota blocks：每个用户或业务线最多占多少 KV blocks。

Admission Controller 的输出：

  1. Accept now。
  2. Queue。
  3. Accept with reduced max_new_tokens。
  4. Ask client to shorten prompt。
  5. Route to another replica。
  6. Reject with clear error。

极长 prompt 打进来，KV pool 见底怎么办

这是高频 follow-up。正确答案不是“让它 OOM”，而是分层 graceful degradation。

1. Hard admission limit

在进 GPU 前限制：

  • max prompt tokens。
  • max total tokens = prompt + output。
  • per-tenant KV block quota。
  • per-request max blocks。

如果请求超过 hard limit，直接拒绝或要求 truncation。

2. Chunked prefill

长 prompt 不一次性 prefill，而是切成 chunks：

long prompt
  -> chunk 1 prefill
  -> yield to decode batch
  -> chunk 2 prefill
  -> yield again

这样避免一个长 prompt 长时间霸占 GPU，也减少 tail latency。

3. Preemption

如果新请求优先级更高，或者系统需要释放显存，可以暂停低优先级 sequence：

RUNNING -> PREEMPTED
free or swap its KV blocks
later resume

Preemption 的关键是要有 sequence state 和 block table，知道哪些 KV blocks 属于哪个 request。

4. Swap KV Cache to CPU memory

把低优先级或暂时不活跃 request 的 KV blocks 从 GPU 显存 swap 到 CPU pinned memory。

优点：

  • 不需要重新计算 prompt。
  • 可以保留长上下文。

缺点：

  • PCIe / NVLink copy latency 高。
  • Resume 时要把 KV blocks 拷回 GPU。
  • 对 latency-sensitive request 不友好。

适合：

  • 长上下文 batch job。
  • 用户可以接受较高 latency。
  • 比 recomputation 更便宜的场景。

5. Recomputation

释放某些 KV blocks，之后需要时重新跑 prefill 计算恢复 KV cache。

优点：

  • 节省 GPU memory。
  • 不占 CPU memory / PCIe bandwidth。

缺点：

  • 需要额外 compute。
  • 长 prompt recomputation 很贵。

适合：

  • GPU memory 极度紧张。
  • Prompt 不太长。
  • Compute 比 memory 更富余。

6. Degrade generation policy

对低优先级请求降低资源需求：

  • 降低 max_new_tokens。
  • 禁用 parallel sampling / beam search。
  • 降低 best-of。
  • 降低并发。
  • 切到小模型或量化模型。
  • 返回 partial result / retry-after。

Follow-up 答案模板

I would not let a long prompt enter the GPU blindly. First, the admission controller estimates KV blocks based on prompt length and max output tokens. If the request exceeds hard limits, I reject or ask the client to truncate. If it is acceptable but the pool is tight, I use chunked prefill, queueing, or route it to another replica. Under pressure, I can preempt lower-priority sequences and either swap their KV blocks to CPU memory or recompute them later. The trade-off is latency versus memory: swapping preserves compute but pays PCIe/NVLink copy cost, while recomputation saves memory but burns GPU cycles.

Multi-GPU parallelism

大模型单卡放不下，或者单卡吞吐不够时，需要多 GPU。

常见 parallelism：

方式怎么切优点缺点
Tensor Parallelism单层矩阵按 hidden/head 切到多卡单层模型可跨卡，decode 常用每层需要 All-Reduce / All-Gather
Pipeline Parallelism不同 layers 放不同 GPU减少单层通信pipeline bubble，batch 小时利用率差
Data Parallelism每张卡一份完整模型简单、吞吐好模型必须单卡放得下
Expert ParallelismMoE experts 分布到不同 GPUMoE 模型扩展好routing 和 token dispatch 复杂

Tensor Parallelism 的通信瓶颈

Tensor Parallelism 把一层的矩阵乘拆到多张 GPU。每张 GPU 算部分结果，然后需要 collective communication 合并。

常见通信：

  • All-Reduce：把各卡 partial result 求和并广播给所有卡。
  • All-Gather：收集各卡 partial tensor。
  • Reduce-Scatter：reduce 后切分结果给各卡。

Decode 阶段每 token 都要过所有 layers，所以 All-Reduce latency 会被放大。

为什么 All-Reduce 会成为 latency bottleneck

  • Decode 每次只生成一个 token，单步 compute 不一定足够大。
  • 单步计算粒度小，communication overhead 更明显。
  • 跨 PCIe 的通信比 NVLink / NVSwitch 慢很多。
  • TP degree 越高，每步 collective 越频繁。

如何优化 multi-GPU 通信

1. Overlap computation and communication

把通信和后续计算重叠：

GPU computes partial GEMM
start async All-Reduce on stream A
meanwhile compute next independent part on stream B
wait only when result is needed

目标不是消灭通信，而是隐藏通信。

2. Fused kernels

把多个小 kernel 合并，减少 kernel launch overhead 和中间 memory traffic。

例如：

  • fused attention
  • fused RMSNorm
  • fused bias + activation
  • fused communication + computation when possible

3. Topology-aware placement

模型切分要考虑硬件拓扑：

  • 同一个 TP group 尽量放在 NVLink / NVSwitch 内。
  • 避免频繁跨 PCIe root complex。
  • 跨节点通信比单节点更贵，除非有高速 InfiniBand。

4. 合理选择 TP degree

TP degree 不是越大越好。

  • TP 太小：单卡 memory 不够或 compute 不够。
  • TP 太大：communication overhead 太高。

面试里可以说会根据 model size、GPU memory、interconnect bandwidth、batch size 做 profiling。

5. Prefill / Decode 分离

Prefill 和 decode 的资源形态不同，可以拆成不同 worker pool：

  • Prefill workers：适合大 batch、compute-heavy。
  • Decode workers：适合低 latency、持续 token generation。

这种 disaggregated serving 可以减少长 prompt 对 decode latency 的影响，但系统复杂度更高，需要 KV transfer 或 prefix handoff。

Scheduler 高分点

一个好的 LLM scheduler 不只是 batch requests，还要同时考虑：

  • token budget：每轮最多处理多少 tokens。
  • KV block budget：每轮最多占多少 blocks。
  • prefill/decode fairness：避免长 prompt 饿死 decode。
  • priority：高优先级用户或 interactive request 优先。
  • deadline：有 SLA 的请求优先。
  • fragmentation：优先调度能复用 blocks 或短请求。
  • starvation prevention：低优先级也不能永远不跑。

Metrics / Observability

LLM serving 必须监控：

  • Time to first token (TTFT)。
  • Inter-token latency (ITL)。
  • End-to-end latency。
  • Tokens/sec per GPU。
  • GPU utilization。
  • HBM memory usage。
  • KV cache free blocks / used blocks。
  • KV cache fragmentation / block waste。
  • Preemption count。
  • Swap in/out bytes。
  • OOM prevention count。
  • Queue length。
  • Request reject / degrade rate。
  • NCCL All-Reduce latency。
  • Consumer / scheduler lag。
