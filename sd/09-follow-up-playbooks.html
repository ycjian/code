1. Architecting a Robust Payment System

Question

在已有 Payment System 基础上，如何把它讲到 production-grade？面试官会追问：幂等、状态机、外部 provider 超时、重复扣款、退款、对账、审计、合规。

Approach

支付系统的核心不是调用 Stripe/银行 API，而是保护 financial invariant：

same business request should create at most one financial effect
every money movement must be auditable
external uncertainty must be reconciled

Architecture

Payment API
  -> Idempotency Store
  -> Payment Intent Service
  -> Payment Orchestrator
  -> Provider Adapter
  -> Ledger / Transaction Store
  -> Webhook Processor
  -> Reconciliation Job

State machine

CREATED -> REQUIRES_CONFIRMATION -> PROCESSING
-> SUCCEEDED / FAILED / CANCELLED
-> REFUND_PENDING -> REFUNDED
-> DISPUTED

Idempotency

Client sends:

Idempotency-Key: uuid
payload_hash
merchant_id

Server behavior:

  • key missing：reject non-idempotent POST。
  • key exists with same payload and final response：return cached response。
  • key exists with different payload：return 400。
  • key in progress：return 409/202 or wait briefly。

External timeout

最难的 case：

we sent charge request to provider
client timed out
provider may or may not have charged

处理：

  • 不要立即重试创建新 charge。
  • 查询 provider by provider_request_id。
  • webhook eventual update。
  • reconciliation job 修正 unknown state。

Ledger

Ledger 应该 append-only：

ledger_entry(entry_id, account_id, amount, currency, direction, payment_id, created_at)

不要 update money history。错误用 reversal/refund entry。

Interview answer

I would model payment as a state machine around PaymentIntent and protect every non-idempotent API with an idempotency key and payload hash. External provider calls are uncertain, so timeouts move the payment into an unknown/processing state rather than creating a second charge. Webhooks and reconciliation jobs eventually resolve the state. Financial records should be append-only ledger entries for auditability.

2. Price Tracking at Scale

Question

设计大规模 price tracking / insight tracking system。系统跟踪商品价格变化、历史趋势、阈值提醒、价格洞察。

Architecture

Product Catalog
  -> Crawl Scheduler
  -> Fetch Workers
  -> Parser / Normalizer
  -> Price Event Log
  -> Time-series Store
  -> Alert Evaluator
  -> Insight / Analytics Jobs

Scheduling strategy

不要所有商品固定频率 crawl：

  • hot products：高频。
  • watched products：中频。
  • cold products：低频。
  • failed sources：backoff。
  • merchant rate limits：per-domain token bucket。

Data model

product(product_id, merchant, url, canonical_key, status)
price_point(product_id, timestamp, price, currency, availability)
watch(user_id, product_id, threshold, channel, status)
price_alert(alert_id, user_id, product_id, price, dedup_key, sent_at)

Detect change

Price point 是 append-only。Current price 可以是 materialized view：

current_price(product_id, price, timestamp)

这样历史和最新读取都高效。

Alert dedup

不要每次 crawl 到低价都发通知：

dedup_key = user_id + product_id + threshold + price_bucket + day

Interview answer

I would separate crawling, price history, and alerting. A scheduler prioritizes products by popularity, active watches, and source limits. Crawlers emit immutable price events, and a time-series store keeps historical price points. Alert evaluators compare new prices to user thresholds with dedup keys so users do not receive repeated alerts for the same drop.

3. Notification Fanout

Question

设计 notification fanout。一个事件可能通知一个用户、几千个粉丝、或者几百万订阅者。支持 push、email、in-app inbox，且不能重复轰炸。

Architecture

Event Producer
  -> Notification Service
  -> Fanout Planner
  -> Recipient Resolver
  -> Preference / Policy Filter
  -> Channel Queues
  -> Push/Email/In-app Workers
  -> Delivery Log

Fanout modes

  • Small fanout：同步 resolve recipients + enqueue。
  • Large fanout：create fanout job，分片处理。
  • Celebrity fanout：延迟/批量，或者只写 inbox/feed，不 push 每个人。

Data model

notification_event(event_id, type, actor_id, object_id, created_at)
notification_job(job_id, event_id, shard, status)
delivery(user_id, event_id, channel, status, dedup_key)
preference(user_id, channel, topic, enabled)

Dedup and aggregation

用户不想收到：

A liked your post
B liked your post
C liked your post
...

可以聚合：

A and 23 others liked your post

Dedup key：

user_id + event_type + object_id + time_bucket

Interview answer

I would separate event creation from delivery. Notification events are durable, fanout jobs resolve recipients and apply preferences, and channel-specific workers handle push, email, and in-app delivery. For large fanout, I would shard recipient processing and use dedup/aggregation so users are not spammed by repeated notifications.

4. Optimize Real-time Feeds

Question

Feed 已经能工作，但 latency 高、fanout 慢、hot users 压力大。如何优化 real-time feed？

Bottlenecks

  • celebrity fanout 太大。
  • timeline write amplification。
  • feed read hydrate 太慢。
  • ranking service 太重。
  • cache invalidation storm。

Optimization playbook

  1. Hybrid fanout
  • normal users fanout-on-write。
  • celebrities fanout-on-read。
  1. Candidate caching
  • cache timeline post ids。
  • hydrate metadata in batch。
  1. Feed item snapshot
  • timeline entry 存 author_id、preview、score。
  • 减少 read path fanout to many services。
  1. Priority queue
  • active users timeline first。
  • inactive users lazy build。
  1. Backpressure
  • fanout queue lag 高时降级 ranking/freshness。

Freshness vs latency

Feed 可以不是绝对实时。可以给用户自己的 post 强一致，别人 feed eventual consistency。

Interview answer

I would optimize feed by separating source-of-truth posts from derived timelines. Hybrid fanout prevents celebrity write amplification, active-user prioritization reduces wasted work, and candidate caches plus batch hydration improve read latency. If fanout lags, the system can still serve older timeline candidates and merge recent celebrity posts at read time.

5. Search Twitter / Social Conversations

Question

设计 Twitter/X social search。用户搜索关键词、hashtag、用户、实时讨论。要求新内容快速可搜，删除/隐私要生效。

Architecture

Tweet Service
  -> Kafka / CDC
  -> Indexer
  -> Search Index
  -> Query Service
  -> Ranking
  -> Privacy Filter

Index fields

tweet_id
author_id
text
hashtags
mentions
language
created_at
engagement signals
visibility

Query types

  • keyword。
  • hashtag。
  • from:user。
  • since/until。
  • trending/realtime。

Freshness

Realtime search wants seconds-level freshness：

  • streaming indexer。
  • small refresh interval for hot index。
  • time-partitioned indexes。
  • hot recent index + cold historical index。

Delete/privacy

Search index can be stale, so read path still checks：

  • tweet deleted。
  • account blocked。
  • private account。
  • viewer permission。

Interview answer

I would build social search as a derived search index from the tweet event stream. Recent tweets go into a hot index optimized for freshness, while older tweets live in time-partitioned historical indexes. Ranking uses text relevance, recency, engagement, and social context. Delete and privacy checks must be enforced at read time because indexes can lag.

6. Indexing Performance Playbook

Question

数据库查询慢，怎么系统化优化？什么时候加 index，什么时候改数据模型？

Steps

  1. Inspect query pattern。
  2. Check cardinality / selectivity。
  3. Use explain plan。
  4. Add composite index in query order。
  5. Avoid unbounded scans。
  6. Consider denormalized read model。

Composite index rule

Index should match：

WHERE equality fields first
then range field
then ORDER BY field if possible

Example：

WHERE user_id = ?
  AND status = ?
  AND created_at > ?
ORDER BY created_at DESC

Index：

(user_id, status, created_at DESC)

When index is not enough

  • Query joins huge tables repeatedly。
  • Low-selectivity field。
  • Hot partition。
  • Need aggregation over massive data。

Then consider：

  • materialized view。
  • precomputed counter。
  • search index。
  • OLAP store。
  • partitioning。

Interview answer

I would not blindly add indexes. I would inspect the query pattern and explain plan, then add a composite index that matches equality filters, range filters, and sort order. If the query is fundamentally an aggregation or join over large data, I would build a read model, materialized view, or OLAP pipeline instead of forcing the OLTP database to do it repeatedly.

7. Networking Architecture Playbook

Question

系统设计里怎么讲 load balancer、gateway、service discovery、timeouts、retries、circuit breaker、regional routing？

Request path

Client
  -> DNS / Global Load Balancer
  -> CDN / Edge
  -> API Gateway
  -> Service Load Balancer
  -> Backend Service
  -> Database / Cache / Queue

Timeouts

每一层都要有 timeout budget：

client: 2000 ms
gateway: 1500 ms
service A: 500 ms
service B: 500 ms
buffer: 500 ms

没有 timeout 的 retry 会放大故障。

Retry rules

  • Retry only idempotent calls。
  • Use exponential backoff + jitter。
  • Respect Retry-After。
  • Set max attempts。
  • Do not retry overload blindly。

Circuit breaker

当下游错误率/timeout 过高：

  • open circuit。
  • fail fast。
  • fallback。
  • half-open probe。

Interview answer

I would design the network path with explicit timeout budgets, idempotent retries, circuit breakers, and observability. Global load balancing routes users to healthy regions; API gateway handles auth/rate limits; service discovery and load balancing route internal calls. Retries must use backoff and only be used when the operation is idempotent or protected by an idempotency key.

8. Job Scheduling Scale and Reliability

Question

Job scheduler 已经有 delayed jobs，但如何支持大规模、可靠、可恢复、可观测？

Architecture

Job API
  -> Job Store
  -> Scheduler Shards
  -> Ready Queue
  -> Worker Pool
  -> Lease / Heartbeat
  -> Retry / DLQ

Sharding

Scheduler 可以按 job_id 或 tenant_id shard：

shard = hash(job_id) % N

每个 scheduler shard 扫描自己负责的 due jobs，避免全局锁。

Lease

Worker 领取 job：

UPDATE job
SET status = 'RUNNING',
    lease_until = now() + interval '60 seconds',
    worker_id = ?
WHERE job_id = ?
  AND status = 'READY'

Worker crash 后 lease 到期，job 回到 READY。

Retry

  • exponential backoff。
  • max attempts。
  • dead-letter queue。
  • poison job detection。
  • idempotent handler。

Interview answer

I would scale the scheduler by sharding the due-job scan and separating scheduling from execution. Workers claim jobs with leases so crashes do not lose work. Retries use exponential backoff and eventually move poison jobs to a dead-letter queue. Job handlers must be idempotent because a job can run more than once after lease expiry.

9. Scaling Reads Playbook

Question

读流量上来后，除了“加 cache”，还有哪些系统化手段？

Layers

Browser / client cache
CDN
API cache
Redis / Memcached
Read replica
Search index
Materialized view
OLAP store

Decision

  • Static or media：CDN。
  • Hot object：cache + request coalescing。
  • Read-heavy relational：read replicas。
  • Query by keyword：search index。
  • Expensive join：materialized view。
  • Aggregation dashboard：OLAP。

Cache correctness

Cache aside:

read cache
miss -> read DB -> set cache
write DB -> delete cache

Add:

  • TTL jitter。
  • stale-while-revalidate。
  • negative caching。
  • singleflight。

Interview answer

I would first classify the read bottleneck: hot object, expensive query, geographic latency, or aggregation. Then I would choose the right layer: CDN for static content, Redis for hot objects, replicas for read QPS, search index for keyword queries, materialized views for joins, and OLAP for analytics. Cache correctness needs invalidation, TTL jitter, and stampede protection.

10. AI-driven Realtime Recommendations

Question

如何把 recommendation 做成 realtime personalization？用户刚点击/观看/购买后，推荐马上变。

Architecture

User Event
  -> Kafka
  -> Realtime Feature Processor
  -> Online Feature Store
  -> Candidate Refresh
  -> Ranking Service
  -> Recommendation API

Feature design

Long-term:

  • user embedding。
  • category affinity。
  • historical conversion。

Short-term:

  • current session clicks。
  • last N watched items。
  • recent search query。
  • negative feedback。

Realtime recommender 要把 short-term intent 放大，但不能完全覆盖 long-term preference。

Serving path

  1. Fetch user long-term features。
  2. Fetch session/realtime features。
  3. Generate candidates from multiple sources。
  4. Rank with context features。
  5. Re-rank for diversity/safety/business rules。

Failure mode

Realtime feature store fail：

  • fallback to batch features。
  • fallback to popular/trending。
  • cache last recommendations。

Interview answer

I would combine batch user profiles with realtime session features. Events stream into a feature processor and online feature store, so recent user actions can affect candidate generation and ranking within seconds. The system still needs fallback to batch features or trending items if realtime features are unavailable, and it should monitor feature freshness and missing feature rate.
