9. Kafka / Queue / Stream

Kafka 是什么

Kafka 不是纯内存队列，而是基于磁盘的分布式 append-only commit log。

Producer
  -> Kafka Broker
  -> append to disk log
  -> Consumer reads by offset

Kafka 快的原因：

  • 顺序写磁盘 append-only。
  • OS page cache 缓存热数据。
  • zero-copy 减少数据拷贝。
  • batch 写入和 batch 读取。

Kafka 用来解决什么

  • 解耦：上游不用直接调用所有下游。
  • 削峰填谷：突发流量先进 Kafka。
  • 可靠事件日志：consumer 失败后从 offset 继续。
  • 异步处理：notification、search indexing、analytics。
  • CDC：DB change log 同步到 cache、ES、warehouse。

Kafka 和 Queue 的区别

Queue 更像任务队列，消息被消费后通常删除或不可见。Kafka 是 event log，消息保留一段时间，consumer 通过 offset 记录消费位置，可以 replay。

Kafka 核心概念

Producer -> Topic -> Partition -> Broker -> Consumer Group -> Consumer
  • Partition 是扩展吞吐的核心。
  • Kafka 只保证同一个 partition 内有序，不保证整个 topic 全局有序。
  • 如果 order events 需要有序，partition key 应该用 order_id。
  • 同一个 consumer group 内，一个 partition 同一时间只能被一个 consumer 消费。
  • Consumer 数量的有效上限是 partition 数。

Consumer 处理顺序

如果 Kafka 用来发 notification：

  1. Consume Kafka message。
  2. Call provider。
  3. 把结果写 DB：DELIVERED / FAILED / RETRYING。
  4. Commit Kafka offset。

不要先 commit offset 再写 DB。否则 provider 成功但 worker crash 后，系统不知道发送结果。

如何保证消息不丢

  • Producer 开启 ack / retry。
  • Kafka replication。
  • Consumer 先持久化处理结果，再 commit offset。
  • 对 DB -> Kafka 的可靠发布，用 outbox pattern。

如何处理重复消息

Kafka 常见语义是 at-least-once，所以重复消息很正常。

解决：

  • 每条消息带 event_id。
  • Consumer 处理前检查是否已处理。
  • DB 加 unique constraint：event_id 或 order_id + event_type。
  • 业务逻辑必须 idempotent。

如何处理消费慢

  • 增加 partition 数。
  • 增加 consumer 数。
  • 优化单条消息处理逻辑。
  • Batch consume / batch write。
  • 下游 DB 压力大时加限流、缓冲、降级。
  • 监控 consumer lag。

核心指标：

consumer lag = latest offset - committed offset

如果 lag 持续增长，说明消费速度跟不上生产速度。

Stream vs Queue

Stream 是事件日志，能保留、重放、多 consumer group，适合 realtime analytics、event sourcing、pub/sub。Queue 更像任务分发，适合每个 task 被一个 worker 消费。

Backpressure 怎么设计

Backpressure 的意思是：下游处理不过来时，上游必须感知并放慢速度，否则队列、内存、连接都会被打爆。

常见做法：

  1. Bounded queue
  • 队列必须有上限。
  • 超过上限后 reject、drop low-priority、或者返回 retry-after。
  1. Consumer lag based throttling
  • 如果 Kafka consumer lag 持续增长，说明下游处理不过来。
  • 上游 producer 降速，或者暂停非核心事件。
  1. Per-tenant quota
  • 防止一个 tenant 把 shared queue 塞满。
  1. Priority queue
  • 支付、订单、告警优先。
  • analytics、email digest、batch job 可以延后。
  1. Circuit breaker
  • 下游不健康时，不继续同步调用。
  • 请求进入 queue 或直接 fail fast。

面试回答模板：

I would make queues bounded and use consumer lag as a feedback signal. If lag grows beyond a threshold, the producer should throttle or shed low-priority traffic. Without backpressure, the system only moves the failure from one service to the queue or database.

Retry / DLQ / Poison Message

Retry 不是无限重试。无限重试会放大故障。

标准策略：

  • Retry with exponential backoff。
  • 加 jitter，避免所有请求同时重试。
  • 最大重试次数。
  • 超过次数进入 DLQ。
  • DLQ 需要 dashboard、alert、replay tool。

Poison message 是指某条消息永远处理失败，例如 payload 格式坏了或业务状态非法。必须识别并移到 DLQ，否则会卡住 consumer。

面试回答模板：

I would use bounded retries with exponential backoff and jitter. After max retries, the message goes to DLQ with enough metadata for debugging and replay. This prevents poison messages from blocking the whole consumer group.

10. Transactional Outbox / Dual Write

问题

如果系统先写 DB，再 publish Kafka，中间 crash，会出现：

DB 已经写入成功
Kafka 没有消息
下游永远不知道这次变更

Outbox pattern

在同一个 DB transaction 中同时写业务数据和 outbox event：

BEGIN;

UPDATE booking
SET status = 'CANCELLED'
WHERE booking_id = 123;

INSERT INTO outbox(event_type, payload, status)
VALUES ('CancellationAvailableEvent', '{"booking_id":123}', 'PENDING');

COMMIT;

之后由 relay / CDC publisher 读取 outbox，发布到 Kafka，成功后标记 sent。

CDC 发布方式

DB WAL / binlog
  -> Debezium / Canal
  -> Kafka
  -> Consumers

优点：延迟低，不需要业务服务轮询 DB。缺点：引入额外基础设施。

Dual write 迁移原则

不要裸 dual write。更安全的方式是：

  • Single source of truth + outbox/event log。
  • 下游写入必须 idempotent。
  • 失败进入 retry / DLQ。
  • 定期 reconciliation。
  • 新系统先 shadow write / shadow read compare。
  • 用 percentage / user_id / region 灰度切流量。
  • 保留 kill switch。
  • Schema 要 backward-compatible。

Saga Pattern

Saga 用来处理跨多个服务的 long-running transaction。它不用一个大 distributed transaction 锁住所有资源，而是把流程拆成多个本地 transaction，每一步都有 compensating action。

例子：下单流程

Create Order
  -> Reserve Inventory
  -> Authorize Payment
  -> Create Shipment
  -> Confirm Order

如果 Authorize Payment 失败，就执行补偿：

Release Inventory
Cancel Order

两种 Saga：

  1. Orchestration
  • 有一个 central orchestrator。
  • 它决定下一步调用哪个 service。
  • 好处是流程清晰、易 debug。
  • 缺点是 orchestrator 变成复杂中心。
  1. Choreography
  • 每个 service 通过 events 驱动下一步。
  • 好处是解耦。
  • 缺点是流程分散，debug 更难。

面试回答模板：

For cross-service workflows, I would avoid distributed transactions unless absolutely required. I would use Saga: each service commits a local transaction and emits an event. If a later step fails, we trigger compensating actions. For complex payment or booking flows, I prefer orchestration because it is easier to reason about and debug.

Reconciliation / 对账

只靠 online transaction 不够。支付、库存、订单系统都需要 reconciliation。

为什么：

  • Webhook 可能延迟或重复。
  • Provider 状态和本地状态可能不一致。
  • Kafka / worker 可能失败后进入 DLQ。
  • 人工退款、chargeback、取消订单可能绕过主流程。

常见设计：

Internal transaction log
External provider report
Immutable audit log in S3
Reconciliation job
Mismatch table
Auto repair or manual review

面试回答模板：

For financial correctness, I would not rely only on the online request path. I would keep an immutable event/audit log and run reconciliation jobs against the payment provider. Any mismatch goes to an exception table for auto-retry or manual review.

11. Stateless Server / Multi-region

Stateless server

API server 不依赖本机内存状态处理请求。用户第一次请求到 Server 1，第二次到 Server 3，也应该都能处理。

Client
  -> Load Balancer
  -> API Server 1 / 2 / 3
  -> Shared DB / Cache / Session Store

为什么重要

  • 可以随意水平扩容。
  • Load Balancer 不需要 sticky session。
  • 单台 server 挂了不会丢用户状态。

Multi-region 用户数据

常见方案：每个 user 有 home region。写入落在 home region，其他 region 有 async replica，用于就近读、灾备或 failover。

全球共享资源

如果是只读内容，可以每个 DC 都有 replica，并使用 CDN。

如果是全球用户都要写同一个有限资源，比如 inventory / ticket / booking，需要更谨慎：

  1. Single writer region：所有写入集中到一个 DC，强一致但远端 latency 高。
  2. Regional allocation：提前把库存分配到不同 region。
  3. Kafka single partition：同一个 resource 的请求进同一个 partition，天然有序。
  4. Global transaction DB：Spanner / CockroachDB，强一致但 latency 和成本高。

12. Atomicity / Concurrency Control

Atomic 是什么

Atomic = 原子性。一个操作要么完整成功，要么完全不发生，中间不会被别人打断，也不会只执行一半。

扣库存示例

不要先读再写：

if stock > 0:
    stock = stock - 1

更好的方式是让 DB 原子完成：

UPDATE inventory
SET stock = stock - 1
WHERE product_id = 123
  AND stock > 0;

如果 update 1 row，说明扣减成功。如果 update 0 row，说明库存没了。

Optimistic concurrency

适合读多写少、冲突不频繁的场景。每条记录带 version：

UPDATE jobs
SET cron = 'every 10 min', version = version + 1
WHERE job_id = 123
  AND version = 7;

如果 version 已经变了，更新失败，返回 409 Conflict。

写多冲突多怎么办

  1. Pessimistic locking
SELECT *
FROM inventory
WHERE product_id = 123
FOR UPDATE;

适合库存、账户余额、订单状态流转。缺点是吞吐下降。

  1. Atomic update

用一条 SQL 完成条件检查和更新。

  1. Single writer / queue
requests
  -> Kafka partition by product_id
  -> single consumer
  -> update stock
  1. Reduce contention

把热点拆成多个 bucket。例如库存 10,000 个，不要所有请求更新同一行，可以拆成多个 inventory bucket。

  1. Serializable transaction

金融账本、结算等严格正确场景可以使用 transaction + serializable isolation，但成本更高。

13. Cache / TTL / Dirty Cache / Stampede

TTL 如何实现

常见两种机制：

  1. Lazy delete：读取时检查 expire_at，如果已过期就删除。
  2. Periodic cleanup：后台线程定期扫描并删除过期数据。

Cache Aside

读路径：

read cache
if hit: return
if miss: read DB -> set cache with TTL -> return

写路径推荐：

update DB
delete cache

不要直接 update cache，因为并发写容易乱序导致 dirty cache：

T1: DB = A
T2: DB = B
T2: cache = B
T1: cache = A

最后 DB 是 B，但 cache 是 A。

Cache stampede / invalidation storm

热门抢票系统中，如果每次 seat 状态变化都 invalidate cache，缓存和 DB 会被打爆。

更好的设计：

  1. Static data 和 dynamic data 分离。
  • Static：演唱会名字、时间、海报，长 TTL。
  • Dynamic：座位状态、剩余票数，单独处理。
  1. 放弃逐条实时 invalidation。
  • Booking service 把 seat change 写 MQ。
  • Background aggregator 每 1 到 3 秒批量更新 Redis。
  1. 接受读路径 eventual consistency。
  • 用户可能看到旧座位状态。
  • 但写路径用 Redis SET NX 或 DB atomic update 保证不会超卖。

14. Exactly-once Effect / Idempotency

不要轻易说 exactly-once delivery

分布式系统中，network timeout、retry、crash、ack 丢失都会导致重复。

更准确的目标是 exactly-once effect：

请求或消息可以重复，但业务结果只能生效一次。

API 幂等

客户端带 idempotency key：

POST /payments
Idempotency-Key: abc123

服务端保存：

idempotency_key -> request_hash, status, response

同一个 key 再来时直接返回上次结果。如果 key 相同但 request body 不同，应该 reject。

DB 幂等

使用 unique constraint：

UNIQUE(idempotency_key)
UNIQUE(order_id, operation_type)

消息幂等

每条消息带 event_id。Consumer 处理前把 event_id 插入 processed_events 表，表上有 unique index。业务更新和 processed event 写入要在同一个 transaction。

状态机条件更新

例如订单只能：

PENDING -> PAID

用 conditional update：

UPDATE orders
SET status = 'PAID'
WHERE order_id = ?
  AND status = 'PENDING';

第二次执行时不会重复扣款。

15. CAP / Consistency

CAP 说的是：在分布式系统遇到 network partition 时，Consistency、Availability、Partition tolerance 不能同时完全满足。

三个概念

  • Consistency：所有节点读到的数据像来自同一个最新副本。
  • Availability：每个请求都能收到非错误响应，即使结果可能不是最新。
  • Partition tolerance：节点之间网络断开或消息丢失时，系统仍能运行。

现实中 P 基本必须接受，所以真正取舍是 partition 发生时选 CP 还是 AP。

CP

优先 consistency。网络分区时可能拒绝部分请求。

适合：

  • 金融转账
  • 库存扣减
  • 预订有限资源

AP

优先 availability。网络分区时继续服务，但可能返回旧数据。

适合：

  • 社交 feed
  • 点赞数
  • 浏览量
  • 缓存

面试回答模板

For money, inventory, and booking limited resources, I would favor consistency even if it reduces availability. For feeds, likes, and cached views, eventual consistency is usually acceptable because user experience benefits more from availability and low latency.

16. Realtime Communication

Long Polling / SSE / WebSocket

方式通信方向怎么工作适合场景
Long Pollingserver -> clientClient 发请求，server 等到有消息才返回，返回后 client 再发下一个请求低频通知、老系统兼容
SSEserver -> client 单向Client 建一个 HTTP 连接，server 持续推送通知、状态更新、AI streaming
WebSocket双向建立长连接，双方都能随时发消息聊天、游戏、协同编辑

面试回答模板

If the server only needs to push updates, I would use SSE. If both client and server need bidirectional realtime communication, I would use WebSocket. Long polling is mostly a fallback for compatibility.
