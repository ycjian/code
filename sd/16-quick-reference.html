33. 面试中最常用的句子

数据库选择

I would choose Postgres here because the core requirement is transactional correctness. We need ACID semantics and constraints more than unbounded horizontal write scaling.
I would choose DynamoDB here because the access pattern is key-value like, QPS is high, and we do not need joins or complex ad-hoc queries.

一致性选择

For money, inventory, and reservations, I would prioritize consistency. For feeds, counts, and search indexes, eventual consistency is acceptable.

Kafka

Kafka is not just a queue; it is a durable event log. I would use it to decouple services, buffer write spikes, and let multiple downstream consumers process the same event stream independently.

Outbox

To avoid the DB-write-success but Kafka-publish-fail gap, I would use the transactional outbox pattern. The business update and outbox event are committed in the same DB transaction.

Idempotency

I would not rely on exactly-once delivery. I would design for at-least-once delivery with idempotent processing, so duplicate requests or messages do not create duplicate business effects.

Cache

The DB is the source of truth; cache is derived data. For cache-aside, I would update the DB first, then delete the cache, and let the next read repopulate it.

Multi-region

For user-owned data, I would use home region writes with async replicas. For globally shared scarce resources, I would avoid multi-writer unless using a global transaction system, because correctness matters more than local write latency.

Rate limiter

I would use token bucket for API rate limiting because it supports steady rate control while allowing a bounded burst. In a distributed setup, I would store counters in Redis with TTL, and add a local limiter before Redis to reduce hot-key pressure.

Backpressure

I would make queues bounded and use lag, latency, and resource utilization as backpressure signals. When downstream systems fall behind, producers should throttle, shed low-priority traffic, or return retry-after instead of allowing unbounded queue growth.

Saga

For cross-service workflows, I would use Saga rather than a global distributed transaction. Each service commits a local transaction and emits an event; if a later step fails, we run compensating actions. For payment or booking flows, orchestration is easier to debug than pure choreography.

Notification

I would make notification delivery asynchronous. The request path writes a durable notification record and outbox event; workers send through provider-specific pools, persist delivery status before committing offsets, and use idempotency keys to avoid duplicate sends.

Feed

I would use hybrid fanout. Normal users use fanout-on-write for fast feed reads, while celebrities are merged at read time to avoid massive write amplification. Feed inboxes store post IDs, and the read path hydrates details from cache or post service.

Search

I would keep the primary database as source of truth and build Elasticsearch as a derived index through CDC or outbox. Search can tolerate slight lag, but deletes and permission changes need careful handling to avoid leaking stale results.

File upload

I would not proxy large files through app servers. The API returns a pre-signed object-store URL; the client uploads directly; storage events trigger async validation, transcoding, thumbnail generation, metadata update, and CDN distribution.

Model rollout

I would treat model rollout as a production deployment. New model versions go through shadow traffic, then canary traffic, with monitoring for latency, OOM, error rate, cost, and quality. The gateway must support quick rollback to the previous stable version.
