0. 面试沟通原则

优秀的系统设计候选人不只是知道很多概念，而是能快速抓住问题核心，用简洁语言说明取舍。

不要过度解释

如果是入门级概念，除非面试官主动问，否则不要花太多时间展开。例如负载均衡器是什么、HTTP 是什么、Redis 是什么，这些可以点到为止。

要做决定，不要只列选项

面试官想看到你如何做 trade-off，而不是只听你列出 3 个方案。

好的表达：

我这里选择 Postgres，因为需要 transaction、durability 和跨表一致性。当前规模下它不会成为瓶颈；如果写入规模继续增长，可以再讨论 sharding 或 async pipeline。

坏的表达：

可以用 Postgres，也可以用 DynamoDB，也可以用 Cassandra，也可以用 Kafka。

推荐回答结构

  1. 先明确 core requirement。
  2. 给出一个默认方案。
  3. 说明为什么选它。
  4. 主动标记 trade-off。
  5. 如果有风险，再说后续如何扩展。

1. 全球聊天系统：类似 WhatsApp

核心问题

全球用户分布在多个 data centers。系统既要低延迟投递消息，又要保证同一个 chat 内的 message ordering。

高层架构

Client
  -> Global Load Balancer
  -> nearest Data Center
  -> Message Server
  -> Message DB / Chat Primary Shard
  -> Cross-DC Forwarding / Pub-Sub
  -> recipient Message Server

关键设计

  • Global Load Balancer 把用户路由到最近的 DC。
  • 每个 DC 内有多个 Message Server。
  • 用 user_id -> message_server registry 或 consistent hashing，把用户连接固定到某个 server。
  • Message Server 维护该 user/device 的 WebSocket connection。
  • 每个 chat 按 chat_id sharding，落到某个 primary shard。
  • 新消息先写入 chat 的 primary shard，再推送给其他 participant 所在的 Message Server。

两条 flow 要分清楚

  1. DB replication flow：message 从 primary DB 同步到 replica。
  2. Delivery flow：message 直接 forward 到 recipient 所在的 Message Server。

这两条 flow 是独立的。为了低延迟，不能等 DB 跨 DC replication 完成后才投递。

为什么需要 single writer / primary shard

如果同一个 chat 可以在多个 DC 同时写，很难保证 message ordering。更稳妥的设计是让每个 chat 有一个 primary shard，所有写入都经过它。

面试回答模板

For global chat, I would separate persistence from delivery. Each chat has a primary shard to preserve ordering. The sender's Message Server writes the message to the primary shard, then forwards it to recipients' Message Servers through a global user-location registry. DB replication is for durability and recovery, while cross-DC forwarding is for low-latency delivery.

2. Job Scheduler / Delayed Job

标准方案

使用 DynamoDB + SQS Delay Queue 的 two-phase architecture。

数据模型

task_id
execute_at
status: PENDING / RUNNING / DONE / FAILED
retry_count
next_execute_at
payload
lease_until

两阶段执行

  1. Persistent storage
  • 所有 task 先写入 DynamoDB。
  • 远期任务只存在 DynamoDB，不直接进入队列。
  1. Scheduler / Watcher
  • Scheduler 每隔一小段时间扫描下一时间窗口，例如未来 2 分钟内到期的任务。
  • 把即将到期的任务投递到 SQS，并设置 Delivery Delay。
  1. Near-term direct enqueue
  • 如果任务本来就在未来 2 分钟内执行，可以写 DynamoDB 的同时直接放入 SQS。

为什么不用 Kafka 做精确定时

Kafka 是 append-only log，只能追加在 tail，不能高效“插队”。如果 task creation time 和 schedule time 不一致，Kafka 不适合直接按任意 execute_at 做精确定时。

SQS 的价值

  • SQS Delay Queue 可以让消息在指定 delay 后才可见。
  • SQS visibility timeout 可以防止多个 worker 同时处理同一条消息。
  • 如果 worker crash，没有 delete message，visibility timeout 后消息会重新可见。
  • SQS 通常是 at-least-once，所以 worker 必须幂等。

Worker flow

Worker receives message
SQS hides message for visibility timeout
Worker processes task
If success: DeleteMessage
If crash: message becomes visible again
Another worker retries

DynamoDB conditional write 抢任务

多个 worker 抢同一个 task 时，不需要显式 distributed lock，可以用 conditional write：

UPDATE task
SET status = 'RUNNING', lease_until = now + 30s
WHERE task_id = ?
  AND status = 'PENDING'

只有一个 worker 能成功把 PENDING -> RUNNING。如果 worker 超时没完成，其他 worker 可以在 lease_until < now 后重新抢。

面试回答模板

I would store every scheduled job durably in DynamoDB, then use a watcher to enqueue near-term jobs into SQS Delay Queue. Workers process SQS messages with visibility timeout. To avoid duplicate execution, workers claim jobs using DynamoDB conditional writes, moving status from PENDING to RUNNING with a lease. Since SQS is at-least-once, job execution must be idempotent.

3. DynamoDB 适合什么场景

一句话判断

如果 access pattern 固定、主要按 key 查询或更新、QPS 高、不需要复杂 join，DynamoDB 是自然选择。

适合的场景

  • Scheduler / Delayed Job
  • Notification Job Table
  • Retry Task Table
  • Idempotency Key Store
  • Rate Limiter Counter
  • Short URL Metadata
  • User Session Store
  • Shopping Cart
  • Order / Payment 状态表
  • Workflow State Table
  • Feature Flag / Config Store
  • IoT Device Latest State

为什么适合 Scheduler

  • 数据是大量小记录。
  • 查询模式固定：找出 execute_at <= now 的任务。
  • 支持 conditional write，适合 worker 抢任务。
  • Managed service，高可用、自动扩容，不容易打爆主业务 DB。

避免全表扫描

不要让 worker 扫全表。常见设计：

partition_key = shard_id or time_bucket
sort_key = execute_at

worker 只扫描自己负责 shard / time bucket 中已经到期的任务。

4. Lock / Mutex / Conditional Write

区别

类型控制范围保护什么
Mutex单进程 / 单机器内存变量
DB Lock多 server 共享数据库记录
Redis / ZooKeeper Distributed Lock多 server 共享跨机器资源
Conditional Write多 server 共享状态转换

Mutex

Mutex is an in-process lock. It protects shared memory within one process. 多台 server 不共享同一个 mutex，所以分布式系统里通常需要 DB lock、conditional write 或 distributed lock。

Conditional write 更适合任务抢占

在 Scheduler 里，任务本身就有状态机：

PENDING -> RUNNING -> DONE
PENDING -> RUNNING -> FAILED -> PENDING

用 conditional update 抢任务通常比显式 distributed lock 更简单。

Distributed Lock 的使用场景

适合多个服务短时间独占同一个稀缺资源：

  • 抢票 seat hold
  • 库存 reservation
  • ride-sharing driver matching
  • distributed cron
  • auction bid

Distributed Lock 注意点

  • 必须有 TTL，防止 holder crash 后锁永远不释放。
  • lock granularity 要小，能锁一张票就不要锁整个 event。
  • 要处理 retry、deadlock、lock expiry。
  • Redis Redlock 可以提，但不要说它绝对安全。

5. Replica Lag / Replication

如果 replica lag 太大，副本恢复后不能立刻接读流量，也不能立刻 promoted to primary。它必须先 catch up。

常见做法

  • Primary 给每次写入一个递增的 log offset 或 sequence number。
  • Replica 记录自己同步到哪里。
  • Replica 恢复后从 primary 或 durable replication log 拉取 missed writes。
  • 追平后才能重新加入 read traffic 或被提升为 primary。
  • 如果落后太多，replication log 已经过期，就先做 snapshot restore，再继续增量追平。

面试回答模板

We use async replication for low write latency, but replicas must track log offsets. After recovery, a replica first replays missed writes from the replication log. Only after it catches up should it serve reads or be promoted. If the lag is beyond log retention, we restore from snapshot and then apply incremental logs.

6. Index / Search / Range Query

Index 是什么

Index 是存储系统里的目录。它把某个字段或 key 映射到数据位置，让查询不用 full table scan。

常见索引

  • Postgres / MySQL: B+Tree index
  • DynamoDB: primary key / GSI
  • Elasticsearch: inverted index
  • RocksDB / LevelDB: sparse index, Bloom filter
  • PostGIS: geospatial index

Trade-off

  • 读更快。
  • 写更慢。
  • 占更多空间。
  • 维护更复杂。

一句话：index 是用空间和写入成本换查询速度。

SQL range query

例如查询 200 到 500 美元的票、某城市的演唱会、某日期范围内的酒店。Postgres 是 source of truth，可以通过 B+Tree / composite index 支持常见 range query：

CREATE INDEX idx_event_city_date_price
ON events(city, event_date, price);

Elasticsearch 什么时候用

如果需要全文搜索、多字段搜索、复杂过滤、相关性排序，可以把 Postgres 的变更同步到 Elasticsearch。

推荐同步方式：

Postgres WAL / binlog
  -> Debezium / Canal
  -> Kafka
  -> Elasticsearch

注意：Elasticsearch 是 derived index，允许 eventual consistency。Postgres 仍然是 source of truth。

7. Sharding / Consistent Hashing

Sharding key 怎么选

好的 shard key 应该：

  • 高基数 high cardinality。
  • 分布均匀，避免 hot shard。
  • 符合主要查询路径。
  • 方便未来扩容。

常见选择：user_id、tenant_id、chat_id、order_id。

Hash-based sharding

shard = hash(key) % N

优点是分布均匀。缺点是节点数 N 变化时，大量 key 需要重新映射。

Range-based sharding

适合自然按范围查询的场景，例如时间范围、tenant range。风险是热点明显，比如最新时间段可能写入特别多。

Consistent Hashing

Consistent Hashing 用 hash ring 把 key 分配到节点。节点增删时，只需要迁移一部分 key。

关键点：

  • key 和 server 都 hash 到同一个环上。
  • key 顺时针找到第一个 server。
  • 新增节点只接管部分 key。
  • 删除节点时，它负责的 key 迁移到下一个节点。
  • 使用 virtual nodes 让分布更均匀。

面试提醒

不要过早 sharding。先估算容量。一个调优好的单库加 read replicas 能撑过很多场景。只有数据量或写入量证明需要分片时再引入。

8. High Availability / Scaling

High Availability 的核心

不要让 single point of failure 打挂整个系统。

常见手段：

  1. Service / DB / cache 多副本。
  2. Multi-AZ / multi-region deployment。
  3. Load balancer + health check。
  4. Primary-replica failover。
  5. Timeout / retry with exponential backoff / circuit breaker。
  6. Queue / Kafka 做缓冲。
  7. Graceful degradation，让非核心功能失败时核心功能还能用。

Read-heavy 系统怎么优化

  1. Cache：Redis / Memcached 缓存热点数据。
  2. Read replica：读走 replica，写走 primary。
  3. CDN：静态资源、图片、视频、公开内容走边缘节点。
  4. Index：避免 full table scan。
  5. Pre-computation：提前计算排行榜、推荐、聚合结果。
  6. Sharding：数据量太大时分散到多个节点。
  7. Pagination / cursor / throttling：避免一次读取过多数据。
  8. Batch read：业务允许时减少 I/O round trips。

Write-heavy 系统怎么优化

  1. 减少同步索引，index 太多会拖慢写入。
  2. 用 Kafka / Pulsar / queue 先接住写流量。
  3. Batch insert，减少 round trip 和 I/O。
  4. 顺序写 / append-only log。
  5. 按 user_id / tenant_id / entity_id sharding。
  6. Search index、analytics、notification 异步处理。
  7. 能接受 eventual consistency 的路径不要强同步。

一句话：

Write-heavy 优化就是缩短 synchronous write path，把非核心工作异步化，用 log / queue / batch / sharding 分散和缓冲写压力。

High connection 怎么优化

使用 connection proxy / connection pool，把大量 client connection 聚合成较少的 DB connection。

例子：

  • Client 连接 proxy。
  • Proxy 维护少量到 DB 的 connection。
  • Non-blocking Redis commands 可以共享 connection。
  • Blocking commands 如 BLPOP 单独使用 connection。

Capacity Estimation 怎么做

系统设计面试里不要一上来画组件。先用粗略数字判断瓶颈在哪里。

常见估算顺序：

  1. DAU / MAU。
  2. QPS：平均 QPS 和 peak QPS。
  3. Read/write ratio。
  4. Payload size。
  5. Storage growth per day。
  6. Bandwidth。
  7. Hot key / hot partition 风险。
  8. Latency SLA。

示例：

10M DAU
每人每天 20 requests
daily requests = 200M
avg QPS = 200M / 86400 ~= 2300 QPS
peak QPS ~= avg * 5 to 10 = 12k ~ 23k QPS

面试里你不需要算得特别精确，重点是通过估算指导设计：

  • 如果 peak QPS 只有几千，先别急着 sharding。
  • 如果 payload 很大，bandwidth / object storage / CDN 可能更关键。
  • 如果 write QPS 很高，queue、batch、partition key 更关键。
  • 如果 read QPS 很高，cache、CDN、read replica 更关键。

API Gateway / Rate Limiter

API Gateway 常见职责：

  • Authentication / authorization。
  • Rate limiting。
  • Request validation。
  • Routing。
  • TLS termination。
  • Logging / tracing。
  • Canary / version routing。

Rate limiter 常见算法：

算法思路适合
Fixed window每个时间窗口计数简单，但边界会突刺
Sliding window log记录每次请求时间精准，但存储成本高
Sliding window counter当前窗口 + 上一窗口加权准确度和成本折中
Token bucket按速率补 token，允许短突发API 限流最常见
Leaky bucket固定速率流出平滑流量

Token bucket 解释：

bucket capacity = burst size
refill rate = allowed requests per second
each request consumes 1 token
if no token -> reject or queue

分布式 rate limiter：

  • 单机 limiter 只能保护单台 server。
  • 多 API server 需要共享计数，常用 Redis。
  • Redis key 可以是 rate:{user_id}:{window}。
  • 高 QPS 下可以做 local pre-limit + global Redis limit，减少 Redis 压力。

面试回答模板：

I would use token bucket because it supports both steady-state rate control and limited burst. For distributed API servers, I would store counters in Redis with TTL. For very high QPS, I would add a local limiter first and use Redis only for global enforcement.

Load Shedding / Backpressure

高并发系统不能让所有请求都进入核心链路。系统快崩时，必须主动拒绝或降级。

常见信号：

  • Queue length 持续增长。
  • P99 latency 超 SLA。
  • CPU / memory / connection pool 接近上限。
  • DB connection exhausted。
  • Kafka consumer lag 增长。
  • GPU KV cache / memory pool 接近上限。

常见动作：

  • Reject low-priority requests。
  • Return 429 Too Many Requests 或 503 Retry-After。
  • 限制 expensive query。
  • 降级非核心功能。
  • 暂停 batch / offline traffic。
  • 缩短 timeout，避免线程被慢依赖占满。

面试回答模板：

I would rather shed load than let the whole system collapse. When queue length, latency, or resource utilization crosses thresholds, I would reject or degrade low-priority traffic and return retry-after. This protects core traffic and prevents cascading failure.
