更完整的白板架构：Video Generation Serving

如果题目偏 Vision / Video generation，可以把架构画得比普通文本 LLM 更具体：

Client
  -> API Gateway
  -> Request Validator
       - resolution / frames / steps / model / LoRA / seed
  -> Cost Estimator
       - memory estimate
       - runtime estimate
       - quota check
  -> Router
       - choose model replica / GPU pool / priority queue
  -> Scheduler
       - shape bucket
       - micro-batch builder
       - prefetch planner
  -> Worker Node
       - Input Loader
       - Text/Image/Video Encoder
       - Denoising / Transformer Core
       - VAE Decoder / Postprocess
       - Output Encoder / Upload
  -> Stream progress / return artifact URL

为什么要有 Cost Estimator

Video generation 的成本差异太大。同一个模型下，下面这些参数都会显著改变 memory 和 latency：

  • num_frames
  • height / width
  • num_sampling_steps
  • guidance_scale / classifier-free guidance
  • batch size
  • reference image / control video / mask
  • LoRA adapter 数量
  • output format and encoding

Cost Estimator 要在 request 进入 GPU 前给出估算：

estimated_gpu_memory
estimated_runtime_ms
estimated_output_size
priority_class
can_run_now / queue / degrade / reject

这一步是防止 OOM、控制多租户公平性、保证 SLA 的核心。

Video generation memory 粗略模型

不要只说“显存不够就减 batch size”。可以这样拆：

GPU memory =
  model_weights
  + text_encoder / image_encoder weights
  + activations
  + attention workspace
  + latent video tensor
  + KV / feature cache
  + communication buffers
  + CUDA graph / allocator reserved memory
  + temporary postprocess buffers

其中 latent video tensor 大概跟下面因素成正比：

batch_size
* latent_channels
* num_frames
* latent_height
* latent_width
* bytes_per_element

如果 attention 在时空维度上做全局 attention，attention cost 可能接近：

O((frames * height * width)^2)

实际模型通常会用 window attention、factorized temporal/spatial attention、sparse attention 或 latent-space attention 来控制成本。

Diffusion / DiT 推理链路

很多 image/video generation 模型不是一次 forward 就结束，而是多步 denoising：

prompt / condition
  -> text encoder
  -> initial noise / latent
  -> for timestep in sampling_steps:
       denoiser / DiT / U-Net forward
       scheduler update latent
  -> VAE decode
  -> video encode / upload

所以 latency 大概是：

T_total ~= T_condition_encoder
          + sampling_steps * T_denoiser_step
          + T_vae_decode
          + T_encode_upload

这就是为什么 sampling_steps 是非常关键的 admission control 参数。

Classifier-Free Guidance 的隐藏成本

如果使用 classifier-free guidance，常见做法是同时跑 conditional 和 unconditional 分支：

pred = uncond + guidance_scale * (cond - uncond)

这可能让 denoiser forward 的 effective batch 近似翻倍。面试里可以主动提：

Guidance quality is not free. It can double the denoising compute or memory depending on implementation, so I would include guidance mode in the cost estimator and batching policy.

Shape Bucketing 为什么重要

Video requests 的 shape 很多：

480p / 720p / 1080p
16 / 32 / 64 frames
20 / 30 / 50 sampling steps
different aspect ratios

如果每个 request 都是动态 shape，会导致：

  • kernel selection 不稳定。
  • CUDA Graph 难复用。
  • memory workspace 波动。
  • batch packing 困难。
  • fragmentation 更严重。

解决：

  • 把请求归到固定 buckets，比如 (resolution, frames, steps, model_variant)。
  • 对接近的 shape 做 padding 到 bucket。
  • 每个 bucket 预热 engine / CUDA graph / memory pool。
  • Queue 可以按 bucket 组织，提升 batch efficiency。

Trade-off：

  • bucket 太少：padding 浪费多。
  • bucket 太多：每个 bucket 流量不足，batch 很难凑满。

Scheduler Policy：不要只按 FIFO

高分回答可以说 scheduler 有多个队列：

interactive_queue
batch_queue
premium_tenant_queue
long_video_queue
retry_queue

每轮调度考虑：

  • GPU memory budget。
  • 当前 bucket 是否能凑 batch。
  • 请求 deadline / SLA。
  • tenant quota。
  • estimated runtime。
  • 是否会造成 head-of-line blocking。
  • 是否需要 prefetch input frames。

Head-of-line blocking

如果 FIFO 里第一个请求是 1080p 128 frames，后面很多 480p 16 frames 都会被堵住。解决：

  • 按 shape bucket 分队列。
  • 长任务进入 async / batch queue。
  • interactive 小任务优先。
  • 对长任务做 chunking。
  • 设置 max queue wait time，超过就降级或转异步。

Micro-batching

Video generation 的 micro-batching 要比文本更小心：

  • batch 大：吞吐好，但 peak memory 高，单请求 latency 变差。
  • batch 小：latency 好，但 GPU utilization 差。
  • 不同 frame count / resolution 混 batch，会造成 padding waste。

好的说法：

I would use shape-aware micro-batching. Requests with the same model, resolution bucket, frame bucket, and step count are batched together. For interactive traffic, I cap max batch wait time. For offline traffic, I allow longer wait to improve throughput.

Preprocessing 和 GPU Compute 的流水线

不要让 GPU 等 CPU。Worker 内可以分 stage：

Stage 1: async read / download
Stage 2: decode / resize / normalize
Stage 3: H2D copy into staging buffer
Stage 4: GPU inference
Stage 5: D2H / encode / upload

使用 double buffering：

GPU runs batch N
CPU prepares batch N+1
H2D copies batch N+1 on another stream

目标是 overlap：

  • CPU decode with GPU compute。
  • H2D copy with previous GPU compute。
  • output upload with next request compute。

CPU/GPU 分工

可以按成本选择：

工作CPU 做GPU 做
Video decode简单部署，便宜高吞吐，减少 CPU bottleneck
Resize / crop灵活大 batch 时更快
Normalize / layout transformCPU 可做GPU 上可 fuse 到 input kernel
VAE decode通常 GPUCPU 太慢
Video encodeCPU 常见GPU encode 可降低 latency

面试里不要绝对化。更好的回答是 profile 后决定，把最慢 stage 移到更合适的硬件。

Memory Pool / Allocator 设计

Video inference 中 frequent alloc/free 会导致 fragmentation 和 allocator overhead。可以设计：

  • per-bucket preallocated memory pool。
  • fixed-size block allocator。
  • separate pools for activations / KV cache / temporary workspace。
  • warmup 后稳定最大 workspace。
  • request finish 后明确 release references。

为什么 separate pools：

  • KV cache 生命周期长。
  • activation / workspace 生命周期短。
  • output buffer 可能很大但只在尾部使用。
  • 混在一起更容易碎片化。

CUDA Graph 什么时候有用

CUDA Graph 可以减少 kernel launch overhead，但它偏好固定 shape。

适合：

  • 固定 bucket shape。
  • 稳定 batch size 或有限 batch size set。
  • decode / repeated denoising step。

不适合：

  • request shape 完全动态。
  • control flow 很复杂。
  • 每轮 tensor shape 都变化。

所以 CUDA Graph 和 shape bucketing 是一对组合拳。

Quantization 怎么讲

Quantization 可以减少 weight memory 和提高吞吐，但要分清对象：

  • Weight-only INT8 / INT4：主要减少 weights memory。
  • FP8：可能提高 GEMM throughput 并减少 activation / weight memory。
  • KV cache quantization：减少 cache memory，但要关注质量和 kernel support。
  • VAE / decoder 量化：可能影响视觉质量，需要 A/B eval。

回答不要只说“用 INT8”。要说：

I would quantize the parts that are memory or compute bottlenecks, then validate visual quality metrics and human evaluation. For generation models, small numerical changes can create visible artifacts, so quantization needs per-module validation.

LoRA / 多模型 Serving

如果线上有多个 LoRA adapter 或 model variants：

  • base model weights 常驻 GPU。
  • adapter weights 可按热度缓存。
  • request 带 adapter_id。
  • scheduler 尽量把同 adapter 的请求 batch 在一起。
  • 冷 adapter 需要 load，会增加 latency。

风险：

  • adapter 频繁切换导致 cache miss。
  • 多租户 adapter 占显存。
  • 不同 adapter 可能不能高效 batch。

Multi-GPU 切分策略怎么选

可以这样说：

  1. 模型单卡放得下，优先 data parallel replicas。
  • 简单，通信少，吞吐随 replicas 扩展。
  1. 模型单卡放不下，用 tensor parallel / pipeline parallel。
  • TP 降低单卡 weight memory，但每层引入 collective communication。
  • PP 降低每卡层数，但 batch 小时有 pipeline bubble。
  1. Video 很长或 attention 很重时，考虑 sequence / frame parallel。
  • 但要看 attention dependency，可能需要跨卡 exchange states。
  1. 结合硬件拓扑。
  • 单节点 NVLink / NVSwitch 内做 TP。
  • 跨节点尽量减少 latency-sensitive collective。

8-GPU Node 白板例子

Node: 8 x H100

Option A: 8 data-parallel replicas
  - each GPU has full model
  - best if model fits one GPU
  - minimal communication

Option B: 2 replicas x 4-way TP
  - each request uses 4 GPUs
  - model weights sharded
  - good for larger model
  - NCCL All-Reduce per layer

Option C: 1 replica x 8-way TP
  - largest model / highest per-request throughput
  - strongest communication pressure
  - lower concurrency

Option D: PP + TP hybrid
  - layers split into pipeline stages
  - each stage internally tensor-parallel
  - useful for very large models

面试里可以说你会 benchmark A/B/C/D，而不是凭感觉选。

Profiling Playbook

第一步不要改代码，先把时间分解出来：

nsight / profiler timeline:
  CPU data loading
  CPU preprocessing
  H2D copy
  GPU kernels
  NCCL collectives
  D2H copy
  video encode / upload

看几个问题：

  • GPU 有没有空洞？如果有，谁让它等？
  • NCCL kernel 是否和 compute overlap？
  • All-Reduce 占每步多少比例？
  • H2D copy 是否阻塞 default stream？
  • 是否有大量小 kernel launch？
  • 是否有某个 dynamic shape 触发超大 workspace？
  • batch 内 padding waste 多不多？

Nsight / PyTorch Profiler 里重点看什么

  • SM utilization。
  • Memory bandwidth utilization。
  • Tensor Core utilization。
  • Kernel launch gaps。
  • CUDA memcpy H2D / D2H。
  • NCCL AllReduce / AllGather 时间。
  • CPU thread 是否在 data loader / decode 上打满。
  • GPU memory allocated vs reserved。
  • Peak memory by stage。

OOM Case Studies

Case 1: 偶发 OOM，只在某些请求出现

可能原因：

  • 某些 request resolution / frames 特别大。
  • dynamic shape 触发更大的 cuDNN / attention workspace。
  • 某个 bucket 没有被 warmup。

解决：

  • admission control 加 shape limit。
  • shape bucketing。
  • warmup 每个 bucket。
  • 记录 OOM request 的 shape 和 stage。

Case 2: 跑一段时间后 OOM

可能原因：

  • tensor reference leak。
  • cache 没释放。
  • output buffer / logging 保存了 GPU tensor。
  • allocator reserved memory 持续增长。

解决：

  • request 完成后检查 live tensor。
  • 监控 per-request allocated delta。
  • 确保 cache ref_count 归零。
  • 避免把 GPU tensor 放入 Python list / closure / metrics。

Case 3: 总显存够，但仍然 OOM

可能原因：

  • fragmentation。
  • 需要连续大 block。
  • temporary workspace 瞬时过大。

解决：

  • memory pool。
  • block allocator。
  • shape bucket。
  • 降低最大 workspace。
  • 使用 memory-efficient attention。

Case 4: Multi-GPU 后 latency 反而变差

可能原因：

  • TP degree 太高。
  • All-Reduce 通信超过节省的 compute。
  • GPU 拓扑不合理。
  • batch 太小，通信无法摊薄。

解决：

  • 降低 TP degree。
  • 同 TP group 放 NVLink 内。
  • overlap comm/compute。
  • 增大 micro-batch 或改为 data parallel replicas。

Graceful Degradation Policy

可以把降级策略按用户体验分层：

压力等级系统动作
轻微压力增加 queue wait，优先 batch 同 bucket 请求
中等压力降低 offline traffic batch priority，限制 max frames / steps
高压力preempt low-priority jobs，切小模型或低分辨率
极端压力reject 新长任务，返回 retry-after，保护 GPU node 不 OOM

关键原则：

Protect the node first. A failed request is better than crashing the entire GPU worker and losing all in-flight requests.

面试中可以主动说的 Production Guardrails

  • Per-request max resolution / frames / steps。
  • Per-tenant GPU memory quota。
  • Queue timeout。
  • OOM circuit breaker。
  • GPU worker health check。
  • Automatic draining of unhealthy worker。
  • Canary new model / new kernel。
  • Rollback path。
  • Load shedding。
  • Artifact cleanup job。

Model Serving Reliability

AI inference 面试里，面试官经常会问：模型服务怎么上线、回滚、监控？

核心设计：

Model Registry
  -> model artifact + version + config + eval metrics
Deployment Controller
  -> canary / blue-green / shadow
Inference Gateway
  -> route by model version / tenant / experiment
Metrics
  -> latency / error / quality / cost
Rollback
  -> fast switch to previous stable version

上线策略：

  1. Shadow traffic
  • 新模型接收复制流量，但不影响用户结果。
  • 比较 latency、error rate、output quality。
  1. Canary
  • 先放 1% 流量。
  • 监控 P50/P95/P99 latency、OOM、error、quality metrics。
  • 逐步扩大到 5%、25%、50%、100%。
  1. Blue-green
  • 新旧环境并存。
  • 通过 routing switch 切换。
  • 回滚快，但成本更高。

必须监控：

  • Request QPS。
  • TTFT / inter-token latency / end-to-end latency。
  • GPU utilization。
  • GPU memory / KV cache free blocks。
  • OOM / preemption / swap count。
  • Error rate。
  • Output quality proxy metrics。
  • Cost per request。

面试回答模板：

I would treat model rollout like a production deployment, not a notebook update. Every model version is registered with artifact, config, and evaluation metrics. New versions first receive shadow traffic, then canary traffic. The gateway can route by model version, tenant, or experiment. If latency, OOM, error rate, or quality metrics regress, we roll back quickly to the previous stable version.

Model Cache / Cold Start

大模型 serving 的 cold start 很贵：

  • Load weights from storage。
  • Initialize CUDA kernels。
  • Warm up memory pool。
  • Build CUDA Graph。
  • Load LoRA adapters。

优化：

  • Hot models 常驻 GPU。
  • Warm pool：提前启动 workers。
  • Lazy load 冷门 model，但返回 async job 或较长 SLA。
  • Adapter cache 按 LRU / LFU 管理。
  • 预热常见 input shape buckets。

面试回答模板：

I would keep hot models resident on GPU and maintain a warm worker pool. For cold models or rare LoRA adapters, I would either lazy-load with a longer SLA or route to an async queue. I would also warm up common shape buckets so the first real user request does not pay kernel and memory initialization cost.

一段强回答

For a video generation inference pipeline, I would treat performance as an end-to-end systems problem, not only a model-forward problem. I would first build a cost estimator based on resolution, frame count, sampling steps, precision, and guidance mode. Then I would route requests into shape-aware queues and use micro-batching per bucket. On the worker, I would pipeline frame loading, preprocessing, H2D copy, GPU inference, and output encoding so the GPU is not waiting for CPU or storage. For multi-GPU execution, I would profile NCCL collectives and choose data parallel, tensor parallel, or pipeline parallel based on model size and hardware topology. For memory, I would use admission control, memory pools, bucketed shapes, and graceful degradation so a single long or high-resolution request cannot OOM the node.

面试回答模板

I would design the service around two scarce resources: GPU compute and KV cache memory. Continuous batching keeps GPU compute busy, but the real memory challenge is KV cache fragmentation. So I would use a paged KV cache manager: split KV cache into fixed-size blocks, maintain a per-sequence block table, and allow physical blocks to be non-contiguous, similar to virtual memory. This lets us admit dynamic-length requests without requiring large contiguous memory.
For multi-GPU execution, if the model is tensor-parallel, each layer requires collective communication such as All-Reduce or All-Gather. Decode is especially sensitive because this happens every generated token. I would optimize by keeping TP groups within fast interconnect topology, overlapping communication with computation using async streams, using fused kernels, and tuning TP degree based on profiling.
For a sudden long prompt, I would handle it before OOM through admission control. If accepted, I would use chunked prefill. Under memory pressure, I would preempt lower-priority sequences and choose between CPU swap and recomputation based on latency tolerance. For interactive requests I prefer rejecting or reducing max tokens over swapping; for batch jobs swapping may be acceptable.
