17. Ticketmaster / Seat Reservation

查询 API

GET /events/{eventId}

返回 event、venue、artist、seat map / ticket info。

GET /events/search?keyword={keyword}&start={start_date}&end={end_date}&pageSize={page_size}&page={page}

返回 event list。

订票 API

POST /bookings/{eventId}

Request:

{
  "ticketIds": ["seat-1", "seat-2"]
}

Response:

{
  "bookingId": "booking_123",
  "paymentIntent": "pi_123"
}

后端先创建 payment intent，前端再用 payment provider SDK / hosted fields 完成支付。不要自己保存原始卡号。

Seat hold

使用 Redis SET NX EX 做短时间 reservation：

SET seat:123 user_123 EX 600 NX
  • NX 保证只有第一个人能 hold 成功。
  • EX 600 表示 10 分钟后自动释放。
  • 支付成功后，真正写入 Postgres order / booking。

多座位原子 hold

如果用户一次买多个座位，不能用普通 for-loop，因为可能部分成功、部分失败。

使用 Redis Lua script：

  1. 预检所有 seat_id 是否已存在。
  2. 如果任意一个已存在，返回失败。
  3. 如果全部可用，一次性为所有 seat 写入 hold key。

Redis 执行 Lua script 时是原子的，脚本执行期间不会插入其他命令。

搜索与座位状态

  • Search listing 可以 eventual consistency，用 Elasticsearch / cache。
  • Booking / reservation 必须强一致，使用 unique key、Redis atomic operation 或 DB transaction。

18. Airbnb Reservation

最简单的数据模型

一个 listing 的一天一行：

ReservationNight(listing_id, date, reservation_id, state)
UNIQUE(listing_id, date)

这样同一个 listing 同一天只能被一个 reservation 占用。

Booking flow

  1. Search 走 eventually consistent index。
  2. Reserve / hold 使用 transaction 或 unique constraint。
  3. Payment 使用 reservation_id 或 idempotency_key 保证幂等。
  4. Confirm reservation 后写 outbox event。

Reservation confirmed 的 outbox

BEGIN;

UPDATE reservation
SET status = 'CONFIRMED'
WHERE reservation_id = ?;

UPDATE reservation_night
SET state = 'BOOKED'
WHERE reservation_id = ?;

INSERT INTO outbox(event_type, aggregate_id, payload, status)
VALUES ('ReservationConfirmed', ?, ?, 'PENDING');

COMMIT;

如果 service crash，outbox event 仍然存在，后续 worker 可以继续发布 notification、email、analytics、search index update。

Cancellation -> Waitlist

不要在 Booking Service cancel 成功后直接同步 call Waitlist Service。更可靠的做法：

Booking Service updates booking / inventory transactionally
Booking Service writes CancellationAvailableEvent to outbox
Outbox publishes to Kafka
Waitlist Matcher consumes event

关键点：cancellation event 不能丢。

19. Payment System

Non-functional requirements

  • Security。
  • Transaction safety and financial integrity。
  • Strong durability，不能丢交易。
  • No double charge。
  • High consistency。
  • 可扩展到高 TPS，例如 10k TPS。
  • Auditability / reconciliation。

Payment API

Create payment intent:

POST /payment-intents
{
  "amountInCents": 2499,
  "currency": "usd",
  "description": "Order #1234"
}

Process payment:

POST /payment-intents/{paymentIntentId}/transactions

实际生产中，前端通常使用 provider SDK / hosted fields 收集卡信息。Merchant backend 不保存原始卡号，只保存 token / paymentMethodId。

Check status:

GET /payment-intents/{paymentIntentId}

也可以通过 webhook 接收 provider 的异步状态更新。

Card security

更安全的表达：

The browser uses the payment provider's official SDK or hosted fields. Card details are encrypted or tokenized by the provider before reaching our backend. Our backend stores only tokenized payment method IDs, not raw card numbers. Provider-side private keys are protected by HSM.

Merchant request signing

为了确认是真实 merchant 在请求付款，使用 API key + request signing。

Merchant 拿到：

  • Public API key：标识 merchant。
  • Secret key：生成 HMAC signature，不能泄露。

每次请求签名：

signature = HMAC(secret, method + path + body + timestamp + nonce)

服务端校验：

  1. 根据 API key 找到 merchant。
  2. 用保存的 secret key 重新计算 HMAC。
  3. 比较 signature。
  4. 检查 timestamp 是否在允许窗口内。
  5. 检查 nonce 是否用过，防 replay attack。

不需要 unhash。HMAC 的验证方式是服务端用同样输入再算一遍，然后比较结果。

Payment audit

交易状态会不断更新，只看主 DB 可能只看到最新值。为了 audit：

DB transaction log / WAL
  -> Kafka
  -> S3 / data lake immutable log
  -> reconciliation with external provider

Kafka partition key 建议用 payment_id，避免用 merchant_id 或 customer_id 造成 hot partition。

20. Webhook

Webhook 是什么

Webhook 是事件驱动的 HTTP callback。别人系统发生事件后，主动 call 你的 API 通知你。

传统 API polling：

你一直问：好了没？

Webhook：

你告诉对方：好了就 call 这个 URL。

支付为什么需要 webhook

支付是异步过程。Provider 可能需要银行清算、风控、3D Secure。你的 server 不应该一直等待，也不应该每秒轮询。

标准流程：

  1. 用户在前端发起支付。
  2. Provider 处理支付。
  3. Provider 主动 POST 到你的 webhook endpoint。
  4. 你的系统验证签名。
  5. 幂等更新订单状态。

Webhook 三个高频追问

1. 如何防止假通知

使用 signature verification。Provider 在 header 中带签名，你用 webhook secret 重新计算并比较。

2. 通知丢了或重复怎么办

  • Provider 没收到 200 OK 会 retry。
  • 你的 webhook handler 必须 idempotent。
  • 处理前检查 event_id 或 payment_id 是否处理过。
  • 如果已处理，直接返回 200。

3. 乱序到达怎么办

使用 state machine control、timestamp、version 或 conditional update，防止旧事件覆盖新状态。

例如：

UPDATE payment
SET status = 'SUCCEEDED'
WHERE payment_id = ?
  AND status = 'PENDING';

21. Dependency Failure / Provider Isolation

下游 dependency 有问题怎么办

  1. Timeout。
  2. Exponential backoff retry。
  3. Failover to backup service。
  4. Circuit breaker：下游明显不健康时停止调用。
  5. Queue buffering：消息留在队列中，等下游恢复。
  6. Monitoring / alerting。
  7. DLQ：超过最大重试次数后进入 Dead Letter Queue。

Provider-specific concurrency isolation

例如 notification system 同时接 Twilio、SendGrid、Firebase。Twilio 变慢时，不能耗尽所有 worker。

做法：

  • 为每个 provider 建 dedicated worker pool / semaphore。
  • Twilio 最多占用自己的并发额度。
  • SendGrid / Firebase 不受影响。
  • 这个限制要应用到所有 Twilio traffic，包括 critical alerts 和 marketing messages。
  • 达到并发限制时 fail fast，放回 retry queue 或 DLQ，不要阻塞 worker。

Notification System

高频题：设计 push / email / SMS notification system。

核心 requirements：

  • 支持多 channel：push、email、SMS。
  • 支持 priority：critical alert、transactional、marketing。
  • 可靠投递，不能丢关键通知。
  • 幂等，不能重复发。
  • Provider failure isolation。
  • 用户 preference / unsubscribe。
  • Rate limit，防止 spam。

高层架构：

Producer services
  -> Notification API
  -> Notification DB(status=PENDING)
  -> Outbox / Kafka
  -> Channel workers
  -> Provider adapters
  -> Delivery status table
  -> Webhook from providers

关键设计：

  • API 层先写 notification record 和 outbox event。
  • Kafka 按 notification_id 或 user_id partition。
  • Worker 发送前检查 sent-state idempotency key。
  • Provider 返回成功后写 DELIVERED。
  • 失败后 retry with backoff，超过次数进 DLQ。
  • Twilio / SendGrid / Firebase 各自独立 worker pool。
  • Provider webhook 更新最终状态。

面试回答模板：

I would make notification delivery asynchronous. The request path only writes a durable notification record and an outbox event. Workers consume Kafka, send through provider-specific adapters, persist delivery status before committing offset, and use idempotency keys to avoid duplicate sends. Each provider has an isolated worker pool so a slow SMS provider cannot block email or push.

News Feed / Timeline

高频题：设计 Twitter / Instagram feed。

核心问题：

  • Fanout on write 还是 fanout on read。
  • Celebrity user 热点。
  • Feed freshness。
  • Ranking。
  • Cache。

Fanout on write：

User posts
  -> write post
  -> fanout to followers' feed inbox

优点：

  • 读 feed 很快。
  • 适合普通用户。

缺点：

  • celebrity 有几千万 followers，写入爆炸。

Fanout on read：

User opens feed
  -> fetch recent posts from followed users
  -> merge/rank

优点：

  • 发帖轻。
  • 适合 celebrity。

缺点：

  • 读 feed 慢，merge 成本高。

混合方案：

  • 普通用户 fanout on write。
  • Celebrity 不 fanout，读 feed 时单独拉取并 merge。
  • Feed inbox 存 post_id，不存完整 post。
  • Ranking service 根据 recency、engagement、relationship score 排序。

面试回答模板：

I would use a hybrid fanout model. For normal users, fanout-on-write gives fast feed reads. For celebrities, I would avoid pushing to every follower and instead merge their recent posts at read time. The feed inbox stores post IDs, and the read path hydrates post details from cache or post service.

Search / Autocomplete

搜索系统常见 requirements：

  • Full-text search。
  • Prefix autocomplete。
  • Typo tolerance。
  • Filtering / sorting。
  • Near real-time index update。
  • 高 QPS、低 latency。

高层架构：

Write path:
  DB source of truth
  -> CDC / outbox
  -> Kafka
  -> Indexer
  -> Elasticsearch / OpenSearch

Read path:
  API
  -> Search service
  -> Search index
  -> hydrate details from DB/cache if needed

Autocomplete 设计：

  • Trie 适合内存小规模 prefix。
  • Elasticsearch completion suggester / edge n-gram 适合生产搜索。
  • 热门 query 可以 cache。
  • 搜索结果允许 eventual consistency。

注意：

  • Search index 不是 source of truth。
  • DB update 到 search index 会有 lag。
  • 删除和权限变化要小心，避免搜索泄漏。

面试回答模板：

I would keep the primary database as source of truth and build Elasticsearch as a derived index through CDC or outbox. Search reads from the index for low latency, then hydrates details from cache or DB. I would accept slight index lag for search, but handle deletes and permission changes carefully.

File Upload / Media Processing

高频题：设计图片 / 视频上传系统。

核心要求：

  • 大文件上传。
  • 断点续传。
  • 病毒扫描 / 内容审核。
  • 转码 / thumbnail。
  • CDN 分发。
  • 元数据管理。

推荐流程：

Client asks API for upload URL
API returns pre-signed URL
Client uploads directly to object storage
Storage event -> Kafka / queue
Media worker processes file
  -> validate
  -> transcode
  -> thumbnail
  -> metadata update
  -> CDN available

为什么 client 直接传 object storage：

  • 避免大文件经过 API server。
  • API server 不被 bandwidth 打爆。
  • Object storage 更适合大文件和 multipart upload。

状态机：

INITIATED -> UPLOADING -> UPLOADED -> PROCESSING -> READY
                                  -> FAILED

面试回答模板：

I would not proxy large files through the application server. The API returns a pre-signed upload URL, and the client uploads directly to object storage. A storage event triggers an async media pipeline for validation, transcoding, thumbnails, and metadata update. The final artifact is served through CDN.
