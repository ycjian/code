Vision / Video Generation Inference 重点

如果岗位是基础大模型 Vision / Video generation 的 MLE，面试重点会比普通 LLM serving 更贴近底层 infra。对方想确认你不是只会调 API，而是真的理解 GPU pipeline、memory layout、multi-GPU communication 和端到端吞吐瓶颈。

这类岗位日常在优化什么

  1. Multi-GPU inference acceleration
  • 模型太大或视频生成计算太重，需要跨多 GPU 执行。
  • 重点是 Tensor Parallelism、Pipeline Parallelism、sequence / frame parallelism、NCCL communication。
  1. Frame loading / preprocessing
  • 视频模型经常不是 GPU compute 一项瓶颈。
  • frame decode、resize、crop、normalize、batch packing、host-to-device copy 都可能拖慢 pipeline。
  1. GPU memory efficiency
  • Video generation 会同时吃 activation、attention memory、latent tensors、KV cache 或 feature cache。
  • 分辨率、帧数、batch size、sampling steps 都会线性或更糟地推高 memory。
  1. End-to-end latency / throughput
  • 不是只看 model forward。
  • 要看 request queueing、CPU preprocessing、GPU compute、GPU communication、postprocessing、streaming / storage output。

Video generation 为什么更难

文本 LLM 的 token sequence 已经很长，但 video generation 还有几个额外维度：

batch_size
num_frames
height
width
channels / latent_channels
num_sampling_steps
attention_heads

所以 memory 和 compute 通常跟这些因素一起放大。比如扩散模型或 video transformer 里，帧数翻倍不只是输出大一倍，还会增加 attention / temporal module / latent buffer 的压力。

Frame Loading Pipeline

高吞吐视频推理常见 pipeline：

Storage / Object Store
  -> video read
  -> decode frames
  -> resize / crop / normalize
  -> pack tensor batch
  -> pinned CPU memory
  -> async H2D copy
  -> GPU inference
  -> postprocess / encode / upload

Frame loading 的常见瓶颈

  • Video decode 在 CPU 上太慢。
  • 小文件 / remote storage 读取 latency 高。
  • Resize / crop / normalize 没有 batch 化。
  • CPU memory 到 GPU memory copy 没有用 pinned memory。
  • H2D copy 和 GPU compute 没有 overlap。
  • Data loader worker 数不够，GPU 等数据。
  • Batch 内视频长短不一致，padding 太多。

Frame loading 优化话术

I would profile the input pipeline separately from model forward. For video generation, GPU underutilization often comes from CPU decode, preprocessing, or H2D transfer. I would use parallel dataloader workers, pinned memory, async copy, prefetching, and batch-level preprocessing. If decode is the bottleneck, I would consider GPU-accelerated decode or caching decoded frames / latent features depending on storage cost and reuse pattern.

Multi-GPU 通信瓶颈怎么深挖

面试官问 multi-GPU bottleneck，不要只说“用 NCCL”。要讲清楚是哪种 parallelism 引入哪种通信。

场景通信类型瓶颈
Tensor ParallelismAll-Reduce / All-Gather / Reduce-Scatter每层都通信，decode step latency 敏感
Pipeline Parallelismactivation send/recvmicro-batch 太小时 pipeline bubble 大
Data Parallel replicasrequest routing 较简单模型必须单卡放得下
Frame / sequence parallelexchange partial attention statesattention pattern 和 frame dependency 决定通信量
Distributed output storageupload generated frames/videopostprocess 可能拖慢 end-to-end latency

Multi-GPU 优化回答

  1. 先 profile
  • 分开测 compute time、NCCL time、H2D/D2H copy、CPU preprocessing。
  • 用 Nsight Systems / PyTorch profiler / NCCL logs 看 kernel timeline。
  1. 减少通信
  • 合理选择 TP degree，不是越多越好。
  • 能在单 NVLink island 内完成就不要跨慢链路。
  • 使用 fused kernels，减少中间 tensor materialization。
  1. 隐藏通信
  • async collectives。
  • overlap computation and communication。
  • 多 CUDA streams。
  1. 拓扑感知
  • TP group 放在 NVLink / NVSwitch 连接更紧密的 GPU 上。
  • 避免跨 PCIe root complex。
  • 跨节点时考虑 InfiniBand / RDMA 成本。
  1. 调 batch / micro-batch
  • batch 太小，communication overhead 占比高。
  • batch 太大，显存爆或 latency 太高。
  • 找 throughput 和 latency 的 sweet spot。

显存分配策略

Vision / Video inference 里，显存通常被这些东西吃掉：

  • Model weights。
  • Activations / intermediate tensors。
  • Attention workspace。
  • KV cache / feature cache。
  • Latent tensors。
  • CUDA graph memory pool。
  • Temporary buffers from cuDNN / custom kernels。
  • Fragmentation。

OOM 排查顺序

遇到 OOM，不要只说“减 batch size”。更 senior 的排查顺序：

  1. 复现 OOM
  • 固定 model、resolution、num_frames、batch、sampling steps、precision。
  • 区分是 deterministic OOM 还是偶发 OOM。
  1. 看 memory curve
  • 记录 peak allocated、reserved、fragmentation。
  • 看 OOM 出现在 prefill、attention、decode、postprocess 还是 copy 阶段。
  1. 区分 memory 类型
  • weights 固定占用。
  • activations 随 batch / resolution / frames 增长。
  • KV / feature cache 随 sequence / frames / output length 增长。
  • temporary workspace 可能由某些 kernel 突然申请。
  1. 看 fragmentation
  • 总 free memory 看似足够，但没有连续 block。
  • 需要 memory pool、block allocator、预分配、固定 shape bucket。
  1. 看是否有 leak
  • request 完成后 cache / tensor reference 没释放。
  • Python object 持有 GPU tensor。
  • stream / callback / logging 保存了 tensor。

OOM 解决手段

按优先级可以这样答：

  1. Admission control
  • 在进入 GPU 前按 resolution、frames、batch、max tokens / steps 估算 memory。
  • 超过 budget 就 reject、queue 或降级。
  1. Shape bucketing
  • 把请求按 resolution、frame count、sequence length 分 bucket。
  • 减少动态 shape 导致的 workspace 波动和 fragmentation。
  1. Mixed precision / quantization
  • FP16 / BF16 / FP8 / INT8。
  • 注意质量回归和 kernel 支持。
  1. Memory-efficient attention
  • FlashAttention / xFormers / tiled attention。
  • 降低 attention intermediate memory。
  1. Chunking / tiling
  • 长视频按 frame chunks 处理。
  • 高分辨率按 spatial tiles 处理。
  • 代价是边界一致性和额外 stitching。
  1. Offloading / swapping
  • 不活跃 cache offload 到 CPU memory。
  • 代价是 PCIe / NVLink copy latency。
  1. Recomputation
  • 用 compute 换 memory。
  • 适合 memory 紧但 compute 还有余量的场景。
  1. Graceful degradation
  • 降低 resolution。
  • 降低 num_frames。
  • 降低 sampling steps。
  • 降低 batch size。
  • 切小模型。
  • 返回 retry-after 或 async job id。

OOM Follow-up 答案模板

I would first prevent OOM through admission control rather than reacting after CUDA OOM. For video generation, I estimate memory from resolution, frame count, batch size, sampling steps, and model precision. If the request exceeds budget, I either queue it, route to a larger GPU, reduce generation parameters, or reject it. If OOM happens only under fragmentation, I would use shape bucketing and a preallocated memory pool. If it is true peak memory, I would use mixed precision, memory-efficient attention, chunked frame processing, offloading, or recomputation depending on the latency and quality requirements.

性能优化要怎么讲

不要只说“提高 GPU utilization”。要把端到端链路拆开：

T_total =
  T_queue
  + T_load
  + T_decode_frames
  + T_preprocess
  + T_H2D
  + T_model_compute
  + T_NCCL_comm
  + T_postprocess
  + T_upload

然后说你会 profile 哪一段最大，再针对最大段优化。

好的高分表达

In this kind of inference pipeline, I would not assume the model forward is the only bottleneck. I would break down latency into frame loading, decode, preprocessing, H2D transfer, GPU compute, NCCL communication, and postprocessing. For Multi-GPU models, I would pay special attention to All-Reduce latency and topology placement. For memory, I would track not only allocated memory but also reserved memory, fragmentation, cache growth, and temporary workspace spikes. The goal is to maximize GPU occupancy without letting long or high-resolution requests destabilize the node.

面试官真正想确认什么

  • 你是否知道 GPU memory 是硬约束，不是普通服务多加机器就能解决。
  • 你是否理解 pre-processing / loading 也可能让 GPU 空转。
  • 你是否知道 multi-GPU 通信可能吞掉模型切分带来的收益。
  • 你是否会用 profiler 定位问题，而不是凭感觉调参数。
  • 你是否能在 OOM 时做系统性排查：peak memory、fragmentation、leak、workspace、input shape。
  • 你是否能给出 engineering trade-off：latency、throughput、quality、cost、stability。
