1. Messaging App / WhatsApp

Question

设计 WhatsApp / Messenger 类 messaging app。支持 1:1 chat、group chat、online/offline delivery、read receipt、push notification、multi-device、message ordering。

Approach

Messaging 的核心不是简单 WebSocket，而是：

  • connection management。
  • durable message store。
  • per-conversation ordering。
  • offline delivery。
  • multi-device sync。

Architecture

Client
  -> WebSocket Gateway
  -> Message Service
  -> Conversation Service
  -> Message Store
  -> Delivery Queue
  -> Push Notification Service
  -> Presence Service

Data model

conversation(conversation_id, type, created_at)
conversation_member(conversation_id, user_id, role, joined_at)
message(conversation_id, message_seq, message_id, sender_id, body_ref, created_at)
delivery_state(message_id, user_id, device_id, delivered_at, read_at)

Use conversation_id + message_seq for ordering inside a conversation. Global ordering across all chats is unnecessary.

Send flow

  1. Client sends message with client_msg_id。
  2. Gateway forwards to Message Service。
  3. Message Service assigns sequence number。
  4. Persist message。
  5. Enqueue delivery to recipients/devices。
  6. Online devices receive via WebSocket。
  7. Offline users receive push notification and later sync missed messages。

Delivery semantics

Exactly-once delivery is unrealistic. Aim for exactly-once effect:

  • client_msg_id for dedup。
  • server message_id。
  • idempotent delivery ack。
  • client can ignore duplicate message_id。

Interview answer

I would design messaging around durable per-conversation message logs and realtime delivery gateways. WebSocket handles online delivery, but the source of truth is the message store ordered by conversation sequence. Offline users sync missed messages from the store and may receive push notifications. Duplicate sends are handled with client message ids and idempotent writes.

2. Pastebin / Paste Service

Question

设计 Pastebin。用户提交一段文本，系统返回短链接。支持 public/private paste、TTL、large paste、abuse detection、read-heavy traffic。

Difference from URL shortener

URL shortener maps short key -> long URL。Pastebin stores content itself：

short_key -> paste metadata -> blob/text content

核心瓶颈从 redirect latency 变成 content storage、read caching、abuse scanning。

Architecture

Create Paste API
  -> Key Generator
  -> Metadata DB
  -> Text/Object Store
  -> Abuse Scanner
  -> CDN / Cache
  -> Read API

Data model

paste(paste_id, short_key, owner_id, visibility, expires_at, content_ref, status)
paste_content(content_ref, storage_type, size, checksum)

Small paste 可以直接存在 DB text column；large paste 放 object storage。

Read path

  1. Lookup short_key。
  2. Check status / visibility / expiration。
  3. Fetch content。
  4. Cache hot paste。

TTL and deletion

Expired paste：

  • read path rejects after expires_at。
  • background cleanup deletes metadata/content later。
  • object storage lifecycle policy can clean large blobs。

Interview answer

Pastebin is similar to URL shortener in key generation but different in storage because the system owns the content. I would store paste metadata in a database and large content in object storage. Reads are cacheable by short key, while expiration is enforced on the read path and cleaned asynchronously. Abuse scanning can run synchronously for obvious cases and asynchronously for deeper checks.

3. CAP Theorem Interview Framing

Question

面试官问 CAP theorem，应该怎么回答而不是背定义？

Correct framing

CAP 不是说系统只能从 C/A/P 三选二。更准确：

When a network partition happens, a distributed system must choose between consistency and availability for the affected operation.

Partition tolerance 不是可选项。真实分布式系统必须假设网络会失败。

CP vs AP examples

CP：

  • payment。
  • inventory reservation。
  • seat booking。
  • leader election。

Partition 时宁愿 reject / timeout，也不要产生错误状态。

AP：

  • likes count。
  • feed freshness。
  • analytics。
  • presence。

Partition 时可以返回 stale/partial data，之后修复。

PACELC extension

CAP 只看 partition。PACELC 更贴近日常：

if Partition: choose Availability or Consistency
Else: choose Latency or Consistency

很多系统平时就在 latency vs consistency 之间 tradeoff。

Interview answer

I would not treat CAP as a database-labeling exercise. For each operation, I identify the business invariant. If the operation protects money, inventory, or reservations, I choose consistency and may reject requests during a partition. For feeds, counters, and analytics, I can choose availability and serve stale data. The important part is explaining the tradeoff per operation, not calling the whole system CP or AP.

4. ML System Design Blueprint

Question

ML system design 面试的 blueprint 是什么？怎么避免一上来就讲模型？

Blueprint

Product objective
  -> Prediction target
  -> Data collection
  -> Label definition
  -> Feature pipeline
  -> Training
  -> Offline evaluation
  -> Online serving
  -> A/B test
  -> Monitoring
  -> Feedback loop

Key idea

模型不是系统的起点，目标和 label 才是。比如 recommendation：

  • Product objective：increase long-term engagement。
  • Prediction target：probability of meaningful watch / click / conversion。
  • Label：watch time, completion, hide/report, conversion。

Serving split

常见 two-stage：

candidate generation -> ranking -> re-ranking

Candidate generation 追求 recall，ranking 追求 precision，re-ranking 加 diversity/safety/business constraints。

Interview answer

I would start ML system design from the product objective and prediction target, then work backward to labels, data, features, training, serving, evaluation, and monitoring. The online serving path must meet latency and reliability requirements, while the offline path builds datasets and retrains models. I would validate with both offline metrics and online A/B tests because model metrics alone can be misleading.

5. Behavioral Interview Strategy for System Design Candidates

Question

系统设计/infra 候选人在 behavioral 面试里怎么讲项目，才能体现 seniority？

Story structure

Use STAR, but make it technical：

Situation: system was failing / too slow / too costly
Task: my ownership
Action: diagnosis, design, rollout
Result: measurable impact

Strong signals

  • You found the real bottleneck with metrics。
  • You made tradeoffs explicit。
  • You shipped incrementally。
  • You protected rollback path。
  • You aligned stakeholders。
  • You measured impact。

Example shape

Before: P99 latency 2.5s, queue lag 20 min
Diagnosis: fanout workers blocked on DB writes
Change: batch writes, shard queue, idempotent retry
Rollout: shadow, canary, dashboard, rollback
After: P99 600ms, lag < 1 min

Interview answer

I would tell project stories around diagnosis and tradeoff, not just implementation. I first show the business or reliability problem, then the metrics that proved the bottleneck, the design options I considered, how I rolled out safely, and the measurable result. Seniority comes from making the system better without creating uncontrolled risk.

6. Manager Interview / Sustainable Change

Question

如果面试官问“你如何推动一个跨团队 infra 改造？”应该怎么回答？

Approach

大型系统改造不只是技术方案，还包括 adoption：

  1. Define the pain with data。
  2. Find a small high-impact slice。
  3. Build migration path。
  4. Add observability。
  5. Create rollback plan。
  6. Document and teach。
  7. Measure adoption。

Example

迁移 payment webhook processing：

  • Problem：duplicates and missed retries caused manual repair。
  • First slice：one provider + one event type。
  • Change：idempotency table + outbox + retry queue。
  • Rollout：dual write + shadow compare。
  • Result：reduced duplicate effects and manual tickets。

Interview answer

For sustainable change, I would avoid a big-bang rewrite. I would quantify the problem, choose a narrow slice, build a migration path with observability and rollback, and prove impact before expanding. Cross-team adoption requires clear contracts, documentation, and dashboards so other teams trust the new path.

7. Engineering Mastery / Yelp Follow-up

Question

Yelp/local review system 已经会设计，staff-level follow-up 会问什么？

Deeper angles

  1. Geo ranking
  • combine distance, rating, review quality, open hours, personalization。
  1. Review trust
  • spam detection。
  • reviewer reputation。
  • duplicate business detection。
  1. Search quality
  • query understanding。
  • category synonyms。
  • location intent。
  1. Business owner updates
  • hours/menu changes need freshness。
  • moderation for malicious edits。
  1. Data correction
  • duplicate business merge。
  • moved/closed business。

Interview answer

I would push Yelp beyond a simple geo-search problem. The source of truth includes business profiles, reviews, photos, and user actions, but ranking depends on distance, relevance, rating, freshness, trust, and personalization. Reviews need spam detection and reputation signals, while business metadata updates require moderation and freshness guarantees.

8. How to Use These Strategy Pages

In the interview

Use these pages as follow-up modules：

  • Messaging when the problem has bidirectional realtime communication。
  • Pastebin when short key maps to stored content。
  • CAP when discussing consistency under failure。
  • ML blueprint before diving into model choice。
  • Behavioral strategy when asked project ownership。
  • Manager strategy when asked cross-team change。
  • Yelp mastery when asked how to go from mid-level to staff-level answer。

Closing template

I would first protect the core invariant, then design the source of truth around the main write path. For read performance, I would add derived views such as cache, index, timeline, or materialized table. For reliability, I would make retries idempotent, expose metrics, and design a repair/rebuild path. For interview communication, I would make tradeoffs explicit and tie them back to the product requirement.
